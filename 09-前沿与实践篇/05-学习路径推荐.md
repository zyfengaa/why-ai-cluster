
**实验 2：小模型分布式训练**
```python
# 从 0 手写一个数据并行训练循环
# 不要用 DistributedDataParallel 封装
# 手动做 All-Reduce 梯度同步
# 理解"计算 → 通信 → 更新"的完整流程
```

**实验 3：FSDP2 分片策略对比**

注意 API 区分：`NO_SHARD / SHARD_GRAD_OP / FULL_SHARD / HYBRID_SHARD` 是 **FSDP1**（`FullyShardedDataParallel`）的 `ShardingStrategy` 枚举；**FSDP2** 的 API 是 `fully_shard()` + `reshard_after_forward` 参数。不要混用。

```python
# FSDP2 的对比实验：reshard_after_forward 的三种设置
from torch.distributed.fsdp import fully_shard

# 方案 A：reshard_after_forward=True（默认）
#   前向后立刻释放分片，显存最省，反向时需要 all-gather
model = fully_shard(model, reshard_after_forward=True)

# 方案 B：reshard_after_forward=False
#   前向后保留分片在显存里，反向省一次 all-gather，显存占用更高
model = fully_shard(model, reshard_after_forward=False)

# 方案 C：对最后一层不重分片（官方推荐技巧）
#   反向开始时马上要用最后几层，不释放它们可省一次通信
#   前面的层用 True，最后一层用 False
```

记录每种设置的：显存峰值、吞吐、通信耗时（可用实验 6 的 profiling 验证）。

**实验 4：NCCL 调优实验**

先说一个"不要做"：**不要去调 `NCCL_NTHREADS`** 这类内部线程参数——NCCL 默认的 auto 逻辑在绝大多数场景下比你手动猜得好，调内部参数通常只是制造问题。

该调的是这些：

```bash
# 1. 算法与协议（最值得试的两个变量）
NCCL_ALGO=Ring all_reduce_perf -b 128M -e 1G -f 2 -g 8
NCCL_ALGO=Tree all_reduce_perf -b 128M -e 1G -f 2 -g 8
NCCL_PROTO=Simple all_reduce_perf -b 128M -e 1G -f 2 -g 8
NCCL_PROTO=LL128  all_reduce_perf -b 128M -e 1G -f 2 -g 8
# 对比 busbw，理解不同消息大小下最优解不同

# 2. 跨机场景：确认拓扑被正确识别
NCCL_DEBUG=INFO mpirun -np 16 -H node1:8,node2:8 ./build/all_reduce_perf -b 128M -f 2 -g 8
# INFO 日志里看：检测到的网卡、NVLink 拓扑、选择的 NET/IB 还是 NET/Socket

# 3. IB 质量与流量分类（有权限的网络配置时）
# PFC/ECN、IB TC/SL 配置影响无损网络表现——
# 这属于网络侧调优，见第 03 网络篇，先测基线再改
```

**实验 6：Profiling 分析**
```bash
# 用 Nsight Systems 分析你的训练
nsys profile -o profile_output -t cuda,nvtx,nccl python train.py
# 建议加 --capture-range，只在目标区间采集，
# 避免把启动/数据加载阶段也算进去：
nsys profile --capture-range=cudaProfilerApi \
  -o profile_output -t cuda,nvtx,nccl python train.py
# （配合代码里的 torch.cuda.cudart().cudaProfilerStart/Stop）

# 分析顺序：先看时间线，再下钻
# 1. 整体时间线：计算段 vs 通信段 vs 空泡，比例是多少
# 2. 找到最宽的通信段，看它对应哪个 NCCL kernel
# 3. 有需要再下钻到单个 kernel 的细节
# 不要一上来就看单 kernel——先确认问题出在哪一段
```

## 三条延伸路径（补全本教程没展开的主题）

本教程聚焦训练集群的"为什么"，以下三个主题值得作为延伸学习：

### 路径 A：推理集群

```
为什么重要：2026 年算力大头在推理，架构和训练集群很不一样。

学习顺序：
  1. 基础指标：TTFT / TPOT / 好吞吐的定义
     （本教程第 09 篇 01 有最小公式集）
  2. prefill 与 decode 的负载差异 → 分离式架构（disaggregated serving）
  3. KV Cache 管理：PagedAttention、KV 分层（HBM → DRAM → SSD）
  4. 上手：vLLM / SGLang 跑一个 8B 模型，
     用 benchmark 工具观察 batch size 与 TTFT/TPOT 的取舍
  5. 进阶：投机解码、连续批处理、模型多实例编排

对应实践：实验 6 的 profiling 方法在推理服务上同样适用
```

### 路径 B：TCO、供电与碳排

```
为什么重要：集群预算的最终决定者，也是"选址—供电—冷却"链条的起点。

学习顺序：
  1. 成本结构：CapEx（GPU/网络/土建）vs OpEx（电费/折旧/运维）
  2. 电力链路：电网 → 变电站 → UPS → 机柜，
     每一级的损耗与 PUE 的关系
  3. 冷却经济学：PUE / WUE / 余热回收（对应第 09 篇 02）
  4. 碳排核算：电力来源（PPA 绿电 vs 电网均值）、
     制造碳排放 vs 运行碳排放
  5. 上手：用第 09 篇 01 的脚本估你自己配置的
     电费与碳排，做一个 3 年 TCO 对比表
     （自建 vs 云，不同 GPU 代际）
```

### 路径 C：故障定位

```
为什么重要：Llama 3 训练 54 天 419 次中断、78% 是硬件故障——
大集群的日常不是"跑训练"，而是"修集群"。

学习顺序：
  1. 建立基线：nvidia-smi topo -m、all_reduce_perf、ib_write_bw
     的健康值存档（对应第 09 篇 04）
  2. 分层定位法：应用 → 框架 → NCCL → 驱动 → 硬件/网络
  3. 工具链：dmesg（Xid 错误码）、NCCL_DEBUG、nsys 时间线、
     DCGM 诊断（dcgmi diag）
  4. 故障注入演练：拔线、kill rank、限卡——
     故障发生时你才不会手忙脚乱
  5. 进阶：checkpoint 恢复演练、慢节点自动隔离、
     读 Guard 论文（见必读列表）
```
