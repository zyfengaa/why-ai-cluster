# Q: Meta / Google / Microsoft 的超大集群长什么样？

## 为什么会有这个问题

之前的教程讲的是"通用 AI 集群"——任何一个团队都能搭建的那种。但当你听到：

- xAI 在 2024 年用约 122 天建成约 100K H100 的 Colossus，之后扩到约 200K
- Meta 在规划 1 GW 级的 Prometheus 集群
- OpenAI、SoftBank、Oracle、MGX 宣布 Stargate 项目：4 年 **$5,000 亿**、目标 2029 年 10 GW

你会好奇：**这些超大规模集群到底是怎么设计的？和普通集群有什么本质不同？**

## 解决什么问题

超大 AI 集群的核心挑战不是"装更多 GPU"——而是 **把这么多 GPU 高效地连起来一起工作，并且喂得饱、散得了热**。

### 主流架构对比（以各方官方公开口径为准）

| 维度 | Meta | xAI Colossus | Google TPU | Stargate（OpenAI+Oracle 等） |
|------|------|--------------|------------|------------------------------|
| **芯片** | H100/H200（自研 MTIA 做推荐推理） | H100，后加入 H200 | TPU v7 Ironwood | 公告未锁定具体型号（GB200/GB300 级别为主流猜测） |
| **互联** | Llama 3 用了两套集群：一套 RoCEv2 以太网、一套 InfiniBand NDR | Spectrum-X 以太网，三层网络 | ICI + 3D Torus | 官方公告未披露网络细节 |
| **规模** | 两套 **24,576 GPU** 集群（Llama 3 训练）；Prometheus 为 1 GW 级**规划** | 2024 年约 100K H100 → 后扩至约 200K H100/H200 | 9,216 芯片/Pod；全公司**百万级 TPU 部署（官方口径）** | 4 年 $500B，首期 $100B，2029 年目标 **10 GW** |
| **冷却** | DLC 液冷（新园区） | DLC 液冷 + 蒸发冷却 | DLC | Microsoft 的 Fairwater 园区采用闭环 DLC |

> 注意最后一列：**Stargate 不是 Microsoft 的项目**。Stargate 由 OpenAI、SoftBank、Oracle 和 MGX 共同投资，Microsoft 只是"技术伙伴"。Microsoft 自己的旗舰数据中心园区叫 **Fairwater**（GB200 NVL72 级别、闭环 DLC），两者不要混为一谈。

### Meta：Llama 3 训练集群 + Prometheus 规划

**官方口径的关键事实**（来自 Meta 工程博客与 Llama 3 论文）：

```
Llama 3 的训练基础设施：
  - 不是"一个 49,152 卡集群"，而是两套 24,576 GPU 集群
    · 一套 RoCEv2 以太网（Summa 交换机架构）
    · 一套 InfiniBand NDR 400
  - 两套集群分开训练 8B 和 70B，故障域互不传染
  - 405B 在 16,384 GPU 上训练
  - 54 天预训练期间 419 次意外中断，约 78% 是硬件故障
    （GPU 占大头——这也是第 08 篇"慢节点"的出处）

Prometheus：
  - 1 GW 级规划，选址俄亥俄州
  - 是"规划中"，不是已建成的 1 GW
  - Meta 同时规划了 Hyperion 等园区
```

### xAI：Colossus（约 100K → 200K）

**架构特点**（以 xAI 官方博客与公开报道为准）：

```
建造节奏：
  - 2024 年：约 122 天建成约 100K H100
  - 之后扩建至约 200K H100/H200

计算单元：
  - 8 卡 H100 服务器（8×700W = 5.6 kW 仅 GPU）
  - 8 台服务器/机架 = 64 GPU/机架

网络设计：
  - 后端网络是 NVIDIA Spectrum-X 以太网（不是 InfiniBand）
  - 三层网络结构
  - 每台服务器 8×BlueField-3 + 1×ConnectX-7
    = 9×400G = 3.6 Tb/s/服务器

供电：
  - 早期约 150 MW；扩产至 200K 后公开报道口径约 300 MW
    （两个数字是不同阶段的口径，不要混用）
  - 现场部署了大量移动燃气发电机作为过渡电源

散热：
  - DLC 液冷 + 蒸发冷却塔
```

### Google：TPU v7 Ironwood

**架构特点**（Google Cloud 官方博客口径）：

```
TPU v7 Ironwood 规格：
  - 192 GB HBM3E / 芯片，7.37 TB/s 带宽
  - 9,216 芯片组成一个 Pod

互联：
  - ICI（Inter-Chip Interconnect）
  - 3D Torus 拓扑（非 Fat-Tree）
  - Pod 内还有 OCS 光交换机参与链路重构（Google 可核验的 OCS 案例）

软件栈：
  - JAX / MaxText / PyTorch/XLA

部署规模：
  - Google 官方口径是"百万级 TPU 在部署"
    （不要引用"160 万+ TPU v6"这类未经核实的精确数）
  - 只通过 Google Cloud 提供，不对外出售芯片
```

### Stargate / Fairwater：两件不同的事

```
Stargate（OpenAI + SoftBank + Oracle + MGX）：
  - 4 年 $500B，首期 $100B
  - 目标 2029 年 10 GW
  - Microsoft 是技术伙伴，不是项目主体
  - 具体芯片/网络选型以官方后续公告为准

Microsoft Fairwater（独立的微软园区）：
  - GB200/GB300 NVL72 级别整机柜
  - 闭环 DLC 液冷（冷却液是水-乙二醇，不是"导电水"）
  - 单 GPU（GB300）TDP 1,400W，NVL72 整柜约 132 kW
  - 这是"必须 DLC"的典型场景——但注意：
    8 卡 DGX B300 整机约 14-15 kW，是可以风冷的
```

## 超大集群的另一半：推理集群与 TCO

前面都在讲训练集群，但 2026 年超大规模集群的**算力大头已经转向推理**。两个经常被忽略的主题：

### 推理集群和训练集群的架构差异

```
训练：目标是吞吐（token/s），All-Reduce 通信是主要瓶颈之一
      → 需要 NVLink/IB 全互联的大 Pod

推理：目标是 TTFT 和 TPOT
      · TTFT（Time To First Token）：首 token 延迟，由 prefill 决定
      · TPOT（Time Per Output Token）：每个输出 token 的延迟，由 decode 决定
      · prefill 是计算密集（吃 FLOPs），decode 是访存密集（吃 HBM 带宽）
      → 两阶段特征完全不同，现代推理集群把它们拆开调度
        （ disaggregated prefill/decode ）

KV Cache 是推理集群的"第二显存"：
  以 Llama 3 70B（80 层、8 个 KV head、head_dim=128）、
  128K 上下文、FP16、batch=1 为例：

  KV ≈ 2 × 80 × 8 × 128 × 131,072 × 2 bytes ≈ 40 GiB

  · 公式：2 × layers × kv_heads × head_dim × seq × batch × bytes
  · batch=8 时就是 320 GiB——远超任何单卡显存
  · 所以生产推理集群都有 KV Cache 分层：HBM（热）→ 主机 DRAM（温）→ SSD（冷）
```

### TCO、供电与碳排

```
超大规模集群的成本结构（定性，精确值随电价/折旧变化）：
  - 一次性：GPU 服务器（占大头）、网络、土建、变电站
  - 持续：电费、运维、GPU 折旧（4-5 年）、网络折旧
  - 每 MW IT 负载 ≈ 数十台 8 卡服务器，对应每年数百万美元级电费
  - 碳排：看电力来源（PPA 绿电 vs 电网）+ PUE
  - 10 GW 不是"一个电站"——是一整个区域的电网规划，
    这就是为什么 Stargate/Prometheus 的选址首先看供电，其次才是网络
```

## 超大集群的共性特征

| 特征 | 原因 | 实现 |
|------|------|------|
| **网络先于芯片** | 跨机通信是第一瓶颈 | Fat-Tree / Spectrum-X 以太网 / 3D Torus，收敛比是设计起点 |
| **液冷向 DLC 收敛** | 功率密度：NVL72 约 132 kW/柜 | 冷板 DLC（水-乙二醇），浸没式仍是小众 |
| **同构硬件** | 简化运维和容错 | 一批次采购同一型号 |
| **故障率高到影响设计** | 54 天 419 次中断（Meta 公开数据） | checkpoint、慢节点检测、自动排障 |
| **供电决定选址** | 电网容量不够 | 靠近电厂、自建变电站、绿电 PPA |
| **训练与推理分离** | 两者负载特征完全不同 | prefill/decode 分离、KV 分层存储 |

## 🛠 实操指南

### 📋 决策指南：你的集群需要向谁看齐？

```
你的预算和规模？
├─ < 100 万（个人/小团队）→
│   └─ 云 GPU 实例就够了，别想建集群
│
├─ 100 万-1,000 万 →
│   └─ 1-2 台 8 卡服务器
│       └─ 重点：NVLink 拓扑 + 风冷就够（8×B300 约 14-15 kW 仍可风冷）
│
├─ 1,000 万-1 亿 →
│   └─ 64-512 GPU 的中型集群
│       └─ 重点：网络收敛比 + bisection bandwidth + 开始考虑 DLC
│
└─ > 1 亿 →
    └─ 大规模自建集群
        └─ 重点：供电选址 > 网络拓扑 > 液冷 > GPU 选型（按这个顺序）
```

### 🔧 自己动手验：估算对分带宽与 PUE

```bash
#!/usr/bin/env bash
# 1. Bisection bandwidth 估算
# 口径说明：gpu_bw 指"每 GPU 分摊到的网络带宽"，不是 HBM 带宽。
# IB NDR 400 Gb/s 端口 = 50 GB/s 单向；
# 8 卡服务器插 8×400G 网卡 → 每 GPU 摊到 50 GB/s（不是 400 GB/s）。

n_gpus=128        # 集群规模
gpu_bw=50         # 每 GPU 网络带宽（GB/s，单向）= 400 Gb/s / 8

total_bw=$((n_gpus * gpu_bw))         # 聚合网络带宽（GB/s）
ideal_bisection=$((total_bw / 2))     # 1:1 非阻塞时的对分带宽

awk -v t="$total_bw" -v b="$ideal_bisection" 'BEGIN {
  printf "128 卡集群（每卡 50 GB/s 网络带宽）\n"
  printf "聚合网络带宽: %.1f TB/s\n", t/1000
  printf "理想对分带宽: %.1f TB/s\n", b/1000
}'

# 实际网络：1:1 非阻塞叶脊时，对分带宽等于理想值；
# 若上行链路有收敛（如 2:1），实际值减半
servers=$((n_gpus / 8))               # 8 卡服务器台数
oversub=1                             # 收敛比（1 = 无收敛；2 = 2:1）
actual_bisection=$((servers * 8 * gpu_bw / 2 / oversub))

awk -v a="$actual_bisection" -v b="$ideal_bisection" 'BEGIN {
  printf "实际对分带宽: %.1f TB/s（理想 %.1f TB/s）\n", a/1000, b/1000
  if (a < b) print "⚠️  网络有收敛，All-Reduce 跨机段将受网络限制"
  else       print "✅ 1:1 非阻塞"
}'

# 2. PUE 检查：PUE = 总用电 / IT 设备用电
total_power=1500    # 总用电 kW
it_power=1389       # IT 设备用电 kW
awk -v t="$total_power" -v i="$it_power" 'BEGIN {
  pue = t / i
  printf "PUE = %.2f（%s）\n", pue, (pue > 1.3 ? "偏高，先查冷却与配电链路" : "合格")
}'
```

这段脚本可以直接复制到 Linux 终端运行（macOS 也可以）。

### ⚠️ 常见误区

- **误区**："超大集群就是堆 GPU"
  - **实际**：**供电和网络的优先级高于 GPU 选型**。10 GW 级项目首先要解决的是"电从哪来"，然后是"GPU 之间怎么通信"，最后才轮到"买什么型号"。

- **误区**："Stargate 是微软建的"
  - **实际**：Stargate 是 OpenAI + SoftBank + Oracle + MGX 的项目，Microsoft 是技术伙伴。微软自家的旗舰园区是 Fairwater。两件事经常被混为一谈。

- **误区**："液冷是从超大集群才开始的"
  - **实际**：要看密度而不是规模。**NVL72 整柜约 132 kW 必须 DLC**，但 8 卡 DGX B300 整机约 14-15 kW 仍然可以风冷。小集群未必需要液冷。

- **误区**："Google 有 160 万块 TPU v6"
  - **实际**：Google 官方口径是"百万级 TPU 部署"，精确数字从未公布。引用精确数之前先找官方出处。

### 📊 底线数字速查

| 指标 | 个人集群 | 中型集群 | 超大规模集群 |
|------|---------|---------|------------|
| GPU 数量 | 1-8 | 64-512 | > 10,000 |
| 总功耗 | < 10 kW | 200-1,000 kW | > 150 MW（xAI 早期口径） |
| PUE | > 1.5 | 1.2-1.4 | 1.1-1.2 |
| 冷却方式 | 风冷 | 风冷 / DLC 过渡 | NVL72 级必须 DLC（约 132 kW/柜） |
| 网络 | PCIe/NVLink | IB/RoCE | Spectrum-X 以太网 / IB NDR / ICI |
| 每卡网络带宽 | — | 50 GB/s（IB NDR 400 单向） | 同左，靠全网规模取胜 |

### 💡 一句话记住

> **"超大规模集群不是放大版的个人集群。它们最本质的区别是：普通集群的瓶颈是 GPU 算力，超大集群的瓶颈是供电、网络拓扑和故障率。设计顺序是先问'电从哪来'，再问'卡怎么连'，最后才问'买什么卡'。"**

## 对后续的铺垫

超大集群的供电和散热需求，直接把液冷推到了主流位置。

在 GB300（1,400W/卡）、Rubin（约 1,800W/卡）的功率密度下，NVL72 级别的整柜**必须**用 DLC 液冷——但 8 卡风冷服务器依然活着。液冷到底会成为标配吗？
