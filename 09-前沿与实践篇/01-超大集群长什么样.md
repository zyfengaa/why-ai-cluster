# Q: Meta / Google / Microsoft 的超大集群长什么样？

## 为什么会有这个问题

之前的教程讲的是"通用 AI 集群"——任何一个团队都能搭建的那种。但当你听到：

- xAI 用 122 天建成 100K H100 的 Colossus 集群（2024-07-22 上线），再用约 92 天扩产到 200K（H100 + H200 混装）
- Meta 在规划 1 GW 的 Prometheus 集群，以及 5 GW 的 Hyperion 集群
- OpenAI + Oracle + SoftBank + MGX 的 Stargate 计划：初期 $1,000 亿、四年内最多 $5,000 亿（Microsoft 只是技术合作伙伴，微软自建的旗舰是威斯康星的 Fairwater）

你会好奇：**这些超大规模集群到底是怎么设计的？和普通集群有什么本质不同？**

## 解决什么问题

超大 AI 集群的核心挑战不是"装更多 GPU"——而是 **把这么多 GPU 高效地连起来一起工作**。

### 主流架构对比（2026）

| 维度 | Meta Prometheus | xAI Colossus | Google TPU Pod | Microsoft（Fairwater / Stargate）| Amazon Project Rainier |
|------|----------------|--------------|----------------|-------------------|------------------------|
| **GPU/芯片** | GB200/GB300（自研 MTIA 用于推荐/推理）| H100 + H200（200K+）| TPU v7 Ironwood | B200/B300 | Trainium2（约 50 万颗）|
| **互联** | RoCE（Arista 7800）/ InfiniBand Quantum2 | NVIDIA Spectrum-X 800G 以太网 | ICI 3D Torus | InfiniBand ×2 | NeuronLink + EFA（以太网 RDMA）|
| **网络拓扑** | 3 层 Fat-Tree | 3 层 rail-optimized Clos | 3D Torus | Dual-rail InfiniBand | Clos（EFA 以太网）|
| **规模** | Prometheus 1 GW + Hyperion 5 GW（规划）| 200K+ GPU（2025 已达）| 9,216 TPU/pod | Fairwater（威斯康星）+ Stargate 30 GW 规划 | 约 50 万 Trainium2（2025-10 激活）|

### Meta：Prometheus + Grand Teton

**架构特点**：

```
Meta 的两条腿走路战略：

腿 1：NVIDIA GPU 集群（训练旗舰模型）
  - Grand Teton 平台：裸金属上跑 Kubernetes
  - 两个 24,576 GPU 集群：一个用 RoCE（Arista 7800），一个用 InfiniBand Quantum2
  - Llama 3 实际是在 RoCE 集群上训练的
  - 3 层 Fat-Tree 拓扑

腿 2：自研 MTIA（推荐/推理）
  - RISC-V 架构的矩阵计算网格
  - 专注 TOPS/watt（不是峰值 FLOPS）
  - Meta 公开口径：MTIA 500 的推理 perf/W 约为 H100 的 3 倍；3nm 工艺下每操作功耗较上代降约 50%

Prometheus 集群：
  - 选址：俄亥俄州
  - 规划功率：1 GW（足够 60 万户家庭用电）
  - 自建燃气轮机供电（behind-the-meter 天然气，孤岛运行）
  - DLC 液冷全覆盖

Hyperion 集群：
  - 选址：路易斯安那州
  - 规划功率：5 GW（Meta 目前最大的规划）
```

### xAI：Colossus（100K → 200K）

**架构特点**：

```
建造奇迹：
  - 从动工到 100K → 122 天（2024-07-22 上线）
  - 100K → 200K 扩产 → 再 92 天（2025）
  - 200K 是 H100（约 150K）+ H200（约 50K）混装，不是"200K H100"
  - 分为 4 个 hall、每个约 25,000 GPU（未必作为统一系统运行）

网络设计：
  - NVIDIA Spectrum-X 800G 以太网（400G backend + BlueField-3 SuperNIC）
  - 三层、rail-optimized 的树形（Clos）拓扑
  - 每个 ToR（SN5600）交换机连接 64 个 GPU，ToR 单独成架（rail-optimized 的体现）
  - 没有"oversubscription"——全网非阻塞

供电：
  - 站点功耗约 250 MW（初期 ~150 MW）
  - 35 台燃气轮机（合计 ~420 MW）做冗余
  - 208 个 Tesla Megapack 做储能/峰值缓冲

散热：
  - DLC 液冷 + 蒸发冷却塔
  - 每 GPU 功耗 700W（H100）× 200K = 140 MW 总热负荷
```

### Google：TPU Pod（Ironwood）

**架构特点**：

```
TPU v7 Ironwood 规格：
  - 3nm TSMC 工艺
  - 192 GB HBM3E，7.37 TB/s 带宽
  - 单芯片 ~4.6 PFLOPS（FP8）
  - 9,216 芯片组成一个 Pod

互联：
  - ICI（Inter-Chip Interconnect）：9.6 Tb/s
  - 3D Torus 拓扑（非 Fat-Tree）
  - 每个 TPU 直接连接 6 个邻居（3D 网格的 6 个方向）
  - 自定义光学交换机

软件栈：
  - JAX / MaxText / PyTorch-XLA
  - SparseCore：加速 MoE 和 embeddings
  - Jetstream：推理引擎

部署：
  - 2026 年 TPU v6（Trillium）+ v7（Ironwood）合计数十万颗量级在生产
  - Ironwood 正在部署替换
  - 只通过 GCP 提供服务
```

### OpenAI Stargate 与 Microsoft Fairwater

**架构特点**：

```
规模：
  - 总预算：初期 $1,000 亿、四年内最多 $5,000 亿（OpenAI + Oracle + SoftBank + MGX 合资）
  - 规划功率：30 GW / 约 $1.4 万亿（Altman 2025-10 口径）
  - 目标是支撑 AGI 级别的训练需求
  - 微软自建的旗舰是 Fairwater（威斯康星），Stargate 里微软只是技术合作伙伴

芯片策略：
  - GPU（B200/B300）：旗舰训练
  - Maia 200：Azure Copilot 推理（内部专用）
  - 自定义 Microscaling（MX）格式降低推理功耗

网络：
  - Dual-rail InfiniBand（两套独立的 IB 网络）
  - Fairwater 园区内部布线约 18 万公里（"绕地球 4.5 圈"），不是跨全球的专用网络

冷却：
  - Fairwater 园区：闭环 DLC 液冷
  - 零运营水消耗
  - 余热回收为区域供暖

重要区别：Maia 200 对客户不可用
  - 外部用户只能通过 Azure API 间接访问
  - 直接可租用的还是 NVIDIA GPU
```

## 超大集群的共性特征

| 特征 | 原因 | 实现 |
|------|------|------|
| **非阻塞网络** | 避免跨机通信瓶颈 | Fat-Tree 或 3D Torus，无 oversubscription |
| **液冷全覆盖** | 50kW+/rack 的功率密度 | DLC + 蒸发冷却/热回收 |
| **同构硬件** | 简化运维和容错 | 一批次采购同一型号 GPU |
| **自研定制** | 降本增效 | 芯片/网络/软件三层定制 |
| **专用供电** | 电网容量不够 | 自建电站/燃气轮机（behind-the-meter）|
| **拓扑优先** | 通信模式决定性能 | 网络拓扑设计先于 GPU 选型 |

## 🛠 实操指南

### 📋 决策指南：你的集群需要向谁看齐？

```
你的预算和规模？
├─ < 100 万（个人/小团队）→
│   └─ 云 GPU 实例就够了，别想建集群
│
├─ 100 万-1,000 万 →
│   └─ 4-16 台服务器小集群
│       ├─ 参考 Meta 的"设计哲学"（不是规模）
│       └─ 重点：NVLink 拓扑 + NDR IB 网络
│
├─ 1,000 万-1 亿 →
│   └─ 64-512 GPU 的中型集群
│       ├─ 参考 xAI 的"网络不收敛"理念
│       └─ 重点：保证 bisection bandwidth
│
└─ > 1 亿 →
    └─ 大规模自建集群
        ├─ 参考 Google/Meta 的"芯片定制"
        ├─ 参考 Microsoft 的"双轨网络"
        └─ 重点：供电和液冷
```

### 🔧 自己动手验：检查你对标设计的合理性

```bash
# 1. 计算你的 bisection bandwidth 需求
# bisection bandwidth = 每秒能在两半集群之间传输的数据量
# 理想情况下 = N_gpu × GPU_bandwidth / 2

n_gpus=128  # 你的集群规模
gpu_bw=400  # H100 IB 带宽 GB/s
total_bw=n_gpus * gpu_bw
ideal_bisection=total_bw / 2

echo "128 卡集群的 Bisection Bandwidth 需求:"
echo "理想值: $ideal_bisection GB/s ($(echo $ideal_bisection/1000 | bc) TB/s)"

# 检查你的实际网络
actual_top_of_rack=8  # 每机架 IB 上行带宽(TB/s)
n_racks=16            # 机架数
actual_bisection=actual_top_of_rack * n_racks / 2
echo "实际值: $actual_bisection TB/s"

ratio=$(echo "scale=2; $actual_bisection / ($ideal_bisection/1000)" | bc)
echo "网络收敛比: $ratio (应 > 1)"

if (( $(echo "$ratio < 1" | bc -l) )); then
    echo "⚠️ 网络收敛不足，All-Reduce 将受网络限制"
else
    echo "✅ 网络非阻塞"
fi

# 2. 检查 PUE（Power Usage Effectiveness）
# 从数据中心监控获取
total_power=1500    # 总用电 kW
it_power=1389       # IT 设备用电 kW
pue=$(echo "scale=2; $total_power / $it_power" | bc)
echo "PUE: $pue"
if (( $(echo "$pue > 1.3" | bc -l) )); then
    echo "⚠️ PUE 偏高，考虑优化冷却"
else
    echo "✅ PUE 优秀"
fi
```

### ⚠️ 常见误区

- **误区**："超大集群就是堆 GPU"
  - **实际**：**200K GPU 的瓶颈不在 GPU 本身，在网络、供电和故障率**。Meta 的 Llama 3 训练报告记录了 **419 次非计划中断**；Guard 论文（部署在数万 GPU 规模的前沿模型预训练上）报告，慢节点导致的故障间隔（MTTF）基线只有 **6.6 小时**，用 Guard 检测后提升到 **16.7 小时**，单步时间从 **17s 降到 10s**。**网络拓扑决策在 GPU 选型之前，而"断了多快能恢复"决定了有效算力。**

- **误区**："开源方案比自研芯片差"
  - **实际**：对超大规模场景，自研芯片在**能效比**（TOPS/watt）上有 2-3 倍优势（厂商口径）。Google 的 SparseCore 专门加速 MoE 和 embeddings。但**这种优势只在超大规模（> 10 万芯片）时才能体现**。

- **误区**："Maia 200 是 NVIDIA GPU 的替代品"
  - **实际**：Maia 200 **只做推理**，不做训练，且只对 Azure API 内部使用。对外部客户来说，**Maia 不存在**。不要被"自研芯片取代 NVIDIA"的标题误导。

### 📊 底线数字速查

| 指标 | 个人集群 | 中型集群 | 超大规模集群 |
|------|---------|---------|------------|
| GPU 数量 | 1-8 | 64-512 | > 10,000 |
| 总功耗 | < 10 kW | 200-1,000 kW | > 100 MW |
| PUE | > 1.5 | 1.2-1.4 | < 1.1 |
| 冷却方式 | 风冷 | DLC 液冷 | DLC + 蒸发/热回收 |
| 网络 | PCIe/NVLink | NDR IB | 双轨/3D Torus |
| 网络收敛比 | — | 1:4 ~ 1:2 | 1:1（非阻塞）|
| 团队规模 | 1-2 人 | 10-30 人 | 100+ 人 |

### 💡 一句话记住

> **"超大规模集群不是放大版的个人集群。它们最本质的区别是：普通集群的瓶颈是 GPU 算力，超大集群的瓶颈是网络拓扑和供电。xAI 的 200K GPU 集群的设计起点不是'买什么 GPU'，而是'怎么给 200K GPU 供电和散热'。"**
