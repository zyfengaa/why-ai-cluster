# Q: 推理集群和训练集群有什么本质不同？

## 为什么会有这个问题

2026 年，集群里的算力大头已经转向推理。但很多团队把训练集群的经验直接套到推理上，结果发现：

- 同样的 GPU 数，训练能跑到 40% MFU，推理吞吐却上不去；
- 加卡之后吞吐不涨，延迟反而更抖；
- 长上下文请求一多，显存瞬间被 KV Cache 吃光；
- prefill 和 decode 混跑，互相拖慢，怎么调都不对。

**训练和推理的瓶颈不在同一个地方。** 训练是"算得多、通信多"，推理是"算得少、搬得多"——它们的并行、调度、容量规划都要分开设计。

## 解决什么问题：推理的两段式负载

```
请求 → [Prefill] → 首 token（TTFT）→ [Decode] → 后续 token（TPOT）→ 完成

Prefill：一次性处理整个 prompt
  · 计算密集（吃 FLOPs），矩阵乘为主
  · 决定 TTFT（Time To First Token）

Decode：每次生成一个 token
  · 访存密集（吃 HBM 带宽），每步都要读全部权重和 KV Cache
  · 决定 TPOT（Time Per Output Token）
```

**这两个阶段的硬件特征完全不同**，所以现代推理集群的核心设计是：**把 prefill 和 decode 拆开（PD 分离），分别扩缩容。**

### 先算账：KV Cache 和 decode 带宽

以 Llama 3 70B（80 层、8 个 KV head、head_dim=128）、FP16 为例：

```
每 token 的 KV Cache = 2 × L × kv_heads × head_dim × bytes
                     = 2 × 80 × 8 × 128 × 2
                     = 327,680 B ≈ 320 KiB/token

8K 上下文、batch=1：320 KiB × 8,192 ≈ 2.5 GiB
128K 上下文、batch=1：≈ 40 GiB（与 09-01 的算例一致）
```

**decode 的每步耗时由"读多少字节"决定**，不是由 FLOPs 决定：

```
TP=8 时，每张卡：
  权重读入 = 140 GB ÷ 8 = 17.5 GB / step
  KV 读入  = batch × 上下文长度 × 40 KiB / step（8 个 KV head 被 TP 切成 1 个/卡）

H100 HBM 3.35 TB/s：
  只读权重：17.5 / 3350 ≈ 5.2 ms/step
  batch=32、8K：KV ≈ 10.7 GB → 3.2 ms，未超过权重读
  batch=128、8K：KV ≈ 42.9 GB → 12.8 ms，开始主导
```

这解释了一个反直觉现象：**decode 阶段加 batch 能提吞吐，但到一定程度后吞吐会 plateau**——因为每步时间从"权重读"切换到了"KV 读"，后者随 batch 和上下文线性增长。

### 并行方式：TP 为主，EP 给 MoE

| 模型 | 推理并行 | 说明 |
|---|---|---|
| 稠密 70B | **TP=8**（单机 NVLink） | 权重按 TP 切；没有梯度同步，不需要 DP |
| MoE 大模型 | **TP + EP** | attention 复制/TP，专家按 EP 分布；与训练的 5D 不同，推理没有优化器状态 |
| 超长上下文 | TP + CP（可选） | 序列切分，KV 环传；代价是通信 |
| 多机推理 | TP 跨节点（不推荐）或 **LWS 多实例** | 跨机 TP 每层通信会走 IB，通常用多实例 + 路由替代 |

**推理不需要 PP**：PP 是为了摊平训练状态和气泡，推理没有梯度，PP 只会增加流水线延迟。**推理也不需要数据并行的梯度同步**，它的"DP"是多个独立副本 + 请求级负载均衡。

### PD 分离：为什么要拆，什么时候不该拆

```
PD 混跑：
  prefill 的长请求占住 GPU → decode 请求排队 → TPOT 抖动
  两类负载互相干扰，扩缩容只能整池扩

PD 分离：
  Prefill Pool：计算密集，按 TTFT SLO 扩容
  Decode Pool：访存密集，按 TPOT SLO 扩容
  中间通过 KV Cache 传输连接
```

**代价**是 KV Cache 要在两个池之间搬：

```
8K prompt 的 KV ≈ 2.5 GiB
IB NDR 单端口 50 GB/s → 约 50 ms
NVLink 900 GB/s → 约 2.8 ms
```

所以 PD 分离适合"prefill 和 decode 负载比例差异大、且池间有高速互联"的场景；如果 prompt 很短、或者网络只是普通以太网，KV 传输的代价可能吃掉收益。**PD 分离不是默认正确，是一个需要算账的架构选择。**

### 路由：把请求送到"已经有它的 KV"的实例

推理集群的调度不是"找一张空闲卡"，而是"找最合适的实例"：

| 策略 | 依据 | 适用 |
|---|---|---|
| Least-loaded | 当前请求数/队列深度 | 通用 |
| **Prefix-aware** | 相同前缀命中已有 KV Cache | 多轮对话、RAG、固定系统提示词 |
| **KV-aware** | 目标实例的 KV 占用与命中率 | 大规模、多租户 |
| Session affinity | 同一会话粘到同一实例 | 长对话 |

Kubernetes 侧的代表方案是 **Gateway API Inference Extension**（`InferencePool` / `InferenceModel`）和 llm-d；它们在网关层做推理感知路由，而不是让 kube-scheduler 去猜。

## 🛠 实操指南

### 📋 决策指南：你的推理集群怎么配？

```
你的请求形态？
├─ 短 prompt、低延迟 →
│   └─ 单池（prefill/decode 混跑）+ TP=8 + continuous batching
│
├─ 长 prompt（> 8K）、TTFT 敏感 →
│   ├─ 先试 chunked prefill（不拆池，降低 decode 抖动）
│   └─ 仍不够 → PD 分离，池间用 NVLink/IB
│
├─ 多轮对话 / RAG / 固定前缀 →
│   └─ prefix cache + 前缀感知路由
│
└─ MoE 大模型 →
    └─ TP（attention）+ EP（专家）；decode 阶段优先保 HBM 带宽
```

### 🔧 自己动手验：推理容量算例

一个 8×H100 跑 Llama 3 70B、TP=8、8K 上下文的粗略容量：

```python
# 每卡显存预算
vram_gb = 80
weights_per_gpu = 140 / 8          # 17.5 GB
workspace = 5                      # 激活、CUDA 上下文、碎片
kv_budget = vram_gb - weights_per_gpu - workspace   # ≈ 57.5 GB

# 单序列 KV（每卡，8K 上下文）：40 KiB/token = 40,960 B
kv_per_seq_gb = 8192 * 40_960 / 1e9       # ≈ 0.3355 GB
max_batch = int(kv_budget / kv_per_seq_gb)   # ≈ 171

print(f"每卡可容纳约 {max_batch} 条 8K 序列")

# decode 单步时间（只算权重读 + KV 读，取较大者）
hbm_tb_s = 3.35
def step_ms(batch, ctx=8192):
    kv_read_gb = batch * ctx * 40_960 / 1e9
    return max(weights_per_gpu, kv_read_gb) / hbm_tb_s * 1000

for b in (8, 32, 64, 128):
    t = step_ms(b)
    print(f"batch={b:3d}: step ≈ {t:5.1f} ms, 吞吐 ≈ {b/t*1000:6.0f} tokens/s")
# batch=8   → step 5.2 ms, ~1,530 tok/s
# batch=32  → step 5.2 ms, ~6,130 tok/s
# batch=64  → step 6.4 ms, ~10,000 tok/s
# batch=128 → step 12.8 ms, ~10,000 tok/s（进入 KV 带宽主导，吞吐 plateau）
```

**结论**：decode 的吞吐不是"batch 越大越好"，而是由 `max(权重读, KV 读)` 决定；超过临界 batch 后继续加 batch 只会增加延迟，不增吞吐。

### ⚠️ 常见误区

- **误区**："推理就是训练完加个 server"
  - **实际**：推理是访存密集型（decode 每步读全部权重 + KV），训练是计算密集型；并行、批处理、调度、指标全都不同。

- **误区**："PD 分离一定更好"
  - **实际**：PD 分离引入 KV Cache 跨池传输。短 prompt 或低速网络下，传输代价可能大于收益。先试 chunked prefill，再考虑拆池。

- **误区**："batch 越大吞吐越高"
  - **实际**：decode 的每步时间由权重读和 KV 读的较大者决定。超过临界 batch 后，KV 读主导，吞吐 plateau，TTFT/TPOT 反而变差。

- **误区**："KV Cache 只是显存问题"
  - **实际**：它同时是**带宽**问题——decode 每步都要把 KV 从 HBM 读一遍。上下文越长、batch 越大，带宽压力越先撞墙。

- **误区**："推理不需要监控 MFU 之外的东西"
  - **实际**：推理的核心指标是 TTFT、TPOT、队列深度、KV 命中率。MFU 对 decode 几乎没有解释力。

## 💡 一句话记住

> **"训练算得多，推理搬得多：prefill 吃 FLOPs 决定 TTFT，decode 吃 HBM 带宽决定 TPOT。推理用 TP（MoE 加 EP），不用 PP；KV Cache 既是显存账也是带宽账；PD 分离是算过账才做的选择，不是默认架构。"**
