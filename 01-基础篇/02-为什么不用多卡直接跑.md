# Q: 为什么不能直接把多张 GPU 拼在一起用？

## 为什么会有这个问题

上篇讲到单卡不够。"那就加卡呗"——听起来很简单。假设你把模型复制到 8 张 GPU 上，每张处理不同的数据：

```
GPU 0: batch 0-31    → 计算结果   loss_0, grad_0
GPU 1: batch 32-63   → 计算结果   loss_1, grad_1
GPU 2: batch 64-95   → 计算结果   loss_2, grad_2
...                   → ...
GPU 7: batch 224-255 → 计算结果   loss_7, grad_7
```

现在问题来了：**每张卡算出来的梯度不一样**（因为数据不同），那模型参数以谁的为准？

## 解决什么问题

答案是 **梯度同步（Gradient Synchronization）**。每张卡算完自己的梯度后，必须和其他卡交换梯度，然后取**平均**，再用平均后的梯度去更新每张卡的参数。

这样所有卡的模型参数始终保持一致。

### 通俗地理解

> 8 个人做同一套试卷的不同题目，每个人先独立做出自己的答案。然后大家互相交换答案，把同一道题的答案取平均。平均后再各自改正自己的答案。这样大家的最终答案就一致了。

这就是 **数据并行（Data Parallelism, DP）** 的核心思想。详见 [[05-并行策略篇/01-数据并行DP]]。

---

## 优缺点

### 优点
- 实现简单，框架原生支持
- 显存够放模型时，理论上可以线性扩展

### 缺点
- **每次迭代都要同步一次梯度**
- 同步需要通信，通信需要时间
- GPU 越多，通信开销越大

这就是致命问题——**通信成了瓶颈**。

---

## 具体有多慢？

来看实际的例子。一张 H100 上做一次前向+反向传播可能需要 **0.1 秒**。但把 128 张 H100 的梯度做一次 All-Reduce 同步，取决于网络：

| 同步方式 | 同步时间 | 对训练速度的影响 |
|---------|---------|----------------|
| 单机 8×H100 NVLink | ~2 ms | 可忽略（~2%） |
| 8 机 64×H100 IB | ~15 ms | 明显（~13%） |
| 32 机 256×H100 以太网 | ~50 ms+ | 严重瓶颈（损失 33%+） |

**越大的集群，通信占比越高**。这就像 256 个人在一张大桌子上同时交换答案——传递的时间超过了做题的时间。

## 🛠 实操指南

### 📋 决策指南：你的多卡方案通信开销多大？

**通信占比 = 同步时间 ÷ （计算时间 + 同步时间）**

```
例子：单次迭代 100 ms，All-Reduce 15 ms
通信占比 = 15 ÷ (100 + 15) = 13%
```

**2026 年典型场景的通信占比参考：**

| 场景 | 计算/迭代 | 同步方式 | All-Reduce 时间 | 通信占比 | 可接受？ |
|------|----------|---------|----------------|---------|---------|
| 单机 8×H200，NVLink 内 | 200 ms | NVLink 4.0 | ~2 ms | ~1% | ✅ 优秀 |
| 4 机 32×H200，IB NDR | 500 ms | NCCL Ring | ~15 ms | ~3% | ✅ 良好 |
| 16 机 128×H200，RoCEv2 | 500 ms | NCCL Tree | ~40 ms | ~7% | ⚠️ 注意 |
| 64 机 512×H100，RoCEv2 未调优 | 500 ms | NCCL 默认 | ~150 ms | ~23% | ❌ 严重瓶颈 |
| 128 机 1024×H100，IB 调优 | 300 ms | NCCL + SHARP | ~50 ms | ~14% | ⚠️ 需优化 |

**通信占比 > 10% 时，必须进行 NCCL 调优。**

### 🔧 自己动手验：测你的多卡通信效率

```bash
# 1. 安装 nccl-tests
git clone https://github.com/NVIDIA/nccl-tests
cd nccl-tests && make

# 2. 测单机内 All-Reduce 带宽（看 NVLink 是否正常）
# 8 卡 H100/H200 预期 > 400 GB/s
mpirun -np 8 ./build/all_reduce_perf -b 128M -e 128M -f 2

# 3. 测跨机 All-Reduce 带宽（看网络是否正常）
# 2 节点，每节点 8 卡，预期 > 35 GB/s（RoCE）或 > 80 GB/s（IB NDR）
mpirun -np 16 --hostfile hosts.txt \
  ./build/all_reduce_perf -b 128M -e 128M -f 2

# 4. 关键检查：随着 GPU 数增加，带宽是否线性扩展？
# 如果从 16 GPU 加到 32 GPU 时带宽不增加 → 网络拓扑有瓶颈

# 5. 在你的训练脚本中埋点测实际通信开销
torch.cuda.synchronize()
t0 = time.time()
optimizer.step()  # 这里包含了 all-reduce
torch.cuda.synchronize()
sync_time = time.time() - t0
step_time = time.time() - step_start
print(f"通信占比: {sync_time/step_time*100:.1f}%")
# 预期：< 10%。如果 > 20% → 必须优化
```

### ⚠️ 常见误区

- **误区**："多卡训练就是把 batch size 拆开，各跑各的"
  - **实际**：每张卡算完自己的梯度后必须做 **All-Reduce 同步**——所有卡等最慢的那张算完，然后交换梯度取平均。这个同步过程是**集体通信**，不是异步的。一张卡慢，所有卡等你。

- **误区**："我用的是 NVLink，没有通信瓶颈"
  - **实际**：NVLink 只在**单机内**（8 卡）能达到 400-450 GB/s。一旦跨机（>8 卡），通信就要走 InfiniBand 或 RoCE，带宽从 450 GB/s 掉到 35-100 GB/s，**差了 5-12 倍**。跨机通信才是真正的瓶颈。

- **误区**："通信时间是固定的，卡越多反而越快"
  - **实际**：All-Reduce 的时间随 GPU 数量**对数增长**（Ring 算法），不是常数。128 卡比 8 卡的通信时间大约多 3-5 倍。而且 NCCL 默认配置经常不是最优的——2025 年 IPDPSW 论文显示，调优 NCCL 参数可带来 **112 倍 All-Reduce 带宽提升**（在 Leonardo 超算上）。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 通信占比（单机 8 卡） | < 3% | 3-5% | > 5% |
| 通信占比（跨机 32+ 卡） | < 10% | 10-20% | > 20% |
| 单机 NVLink All-Reduce 带宽 | > 400 GB/s | 200-400 GB/s | < 200 GB/s |
| 跨机 IB NDR All-Reduce 带宽 | > 80 GB/s | 40-80 GB/s | < 40 GB/s |

### 💡 一句话记住

> **"多卡训练不是加法，是木桶原理——通信就是那块最短的板。8 卡靠 NVLink 勉强够用，32 卡以上不调 NCCL，你的 GPU 一半时间在等数据而不是算数据。"**
