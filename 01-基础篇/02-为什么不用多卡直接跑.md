# Q: 为什么不能直接把多张 GPU 拼在一起用？

## 为什么会有这个问题

上篇讲到单卡不够。但"单卡不够"其实有**两层完全不同的问题**，先别急着混在一起：

1. **算得太慢**——模型放得下，但等不起（70B 在单卡上要几百年）
2. **根本放不下**——70B 仅权重就 140 GB，一张 80 GB 的 H100 装不下

最直觉的答案是"那就加卡，每张卡处理不同的数据"：

```
GPU 0: batch 0-31    → 计算结果   loss_0, grad_0
GPU 1: batch 32-63   → 计算结果   loss_1, grad_1
GPU 2: batch 64-95   → 计算结果   loss_2, grad_2
...                   → ...
GPU 7: batch 224-255 → 计算结果   loss_7, grad_7
```

现在问题来了：**每张卡算出来的梯度不一样**（因为数据不同），那模型参数以谁的为准？

## 解决什么问题

答案是 **梯度同步（Gradient Synchronization）**。每张卡算完自己的梯度后，必须和其他卡交换梯度，然后取**平均**，再用平均后的梯度去更新每张卡的参数。

这样所有卡的模型参数始终保持一致。

### 通俗地理解

> 8 个人做同一套试卷的不同题目，每个人先独立做出自己的答案。然后大家互相交换答案，把同一道题的答案取平均。平均后再各自改正自己的答案。这样大家的最终答案就一致了。

这就是 **数据并行（Data Parallelism, DP）** 的核心思想。详见 [[05-并行策略篇/01-数据并行DP]]。

### 先泼一盆冷水：DP 解决的是"慢"，不是"放不下"

注意上面方案的前提——**每张卡都要放下完整的模型**。数据并行是把整个模型复制到每一张卡上，各卡只是数据不同。所以：

- 7B 模型（全量训练约 112 GB 显存）→ 单卡放不下，8 张卡也一样放不下，因为每张卡都要一份完整副本
- 70B 模型仅权重 140 GB → 8 卡、800 卡都一样，**每张卡都要 140 GB**

**DP 提高的是吞吐量，不是显存容量。**"单卡放不下"这个问题要靠 TP/PP 等模型并行或 ZeRO-3/FSDP 分片解决——注意 ZeRO-3 和 FSDP 本质上是 DP 家族的分片实现：并行方式还是"各算各的数据"，只是把模型切开放。纯 DDP 对 70B+ 是失效的，但"DP + ZeRO-3/FSDP"仍然是主流路线。

---

## 优缺点

### 优点
- 实现简单，框架原生支持（PyTorch DDP 几行代码就能用）
- 模型放得下时，吞吐接近线性扩展
- 配上 ZeRO-3/FSDP 分片后，能覆盖从 8B 到千亿级的绝大多数场景

### 缺点
- **每次迭代都要同步一次梯度**
- 同步需要通信，通信需要时间；同步时间取决于**模型大小、每卡带宽和每步计算量**——用"通信占比"判断，不要用"超过多少张卡"一刀切
- 纯 DDP 要求每张卡放下完整模型，大模型需要先加分片

通信什么时候成为瓶颈？看占比，别背"卡数阈值"。

---

## 具体有多慢？

以 Ring All-Reduce（DDP 的默认路径）为例。N 张卡组成一个环：

1. **reduce-scatter**：N−1 步，每步每卡收发 S/N 的数据，结束后每张卡持有 1/N 份"已求和"的梯度
2. **all-gather**：再 N−1 步，把这 1/N 份拼回完整梯度

（不是"N−1 轮后广播"——那是老教材对朴素实现的描述，Ring All-Reduce 是两段各 N−1 步。）

由此得到两个关键结论：

- **每卡总通信量 = 2S(N−1)/N ≈ 2S**（S = 本卡梯度的字节数），**与 N 基本无关**。加卡摊薄不了单个梯度的同步成本。
- **总耗时 T ≈ 2S(N−1)/(N·B)**，B = 每卡有效带宽。步数 2(N−1) 随 N 线性增长，所以 **Ring 的时延是 O(N)**；Tree 算法时延是 O(log N)，但每卡流量更高。NCCL 默认算法是 auto，会按消息大小和拓扑自动选。

两种同步实现的通信账本对比（S = 每卡梯度字节数，BF16 下约为参数量 × 2）：

| 实现 | 每卡每步通信量 | 时延随 N |
|------|--------------|---------|
| Naive DP（参数服务器） | 2S（上传 S + 下载 S），但服务器侧要收发 2NS，成为单点瓶颈 | — |
| DDP（Ring All-Reduce） | 2S(N−1)/N ≈ 2S，**与 N 基本无关** | Ring **O(N)**；Tree O(log N) |

### 不同网络下的实测量级

按 nccl-tests 标准测试点 **128 MB 消息**、每卡 2S 流量计算：

| 场景 | 每卡有效带宽 | 128 MB All-Reduce 时延 | 占 200 ms 步时的比例 |
|------|------------|----------------------|---------------------|
| 单机 8×H200，NVLink 内 | >400 GB/s（busbw） | ~0.6–1 ms | ~0.3–0.5% |
| 跨机 IB NDR | 每卡 40–50 GB/s | ~5–7 ms | ~3% |
| 跨机 RoCEv2 | 每卡 25–35 GB/s | ~8–13 ms | ~5% |
| 512 卡大集群 | 取决于拓扑与调优 | ~15–25 ms | ~10% |

**越大的集群，通信占比越高**。这就像 512 个人在传递答案——传递的时间开始和做题的时间打平。

还有一个放大器别忘了：真实训练里 70B 模型每卡的梯度是 **140 GB**，不是 128 MB，同步时间要按 2S 等比放大 1000 倍以上。这就是为什么大集群必须做**通信-计算重叠**和 **ZeRO 分片**——让通信藏进计算里，并把每卡的同步量切小。

## 🛠 实操指南

### 📋 决策指南：你的多卡方案通信开销多大？

**通信占比 = 同步时间 ÷ （计算时间 + 同步时间）**

```
例子：单次迭代 200 ms，All-Reduce 6 ms
通信占比 = 6 ÷ (200 + 6) ≈ 3%
```

**判断标准用通信占比，不要用固定卡数**——同一个 DP degree，小模型可能毫无压力，大模型就撑不住了。

### 🔧 自己动手验：测你的多卡通信效率

```bash
# 1. 安装 nccl-tests
git clone https://github.com/NVIDIA/nccl-tests
cd nccl-tests && make

# 2. 测单机内 All-Reduce 带宽（看 NVLink 是否正常）
# 8 卡 H100/H200 预期 busbw > 400 GB/s
mpirun -np 8 ./build/all_reduce_perf -b 128M -e 128M -f 2

# 3. 测跨机 All-Reduce 带宽（看网络是否正常）
# 2 节点，每节点 8 卡；单端口 IB NDR 50 GB/s 的物理上限决定了
# 每卡 busbw 预期 > 40 GB/s（IB NDR）或 > 25 GB/s（RoCEv2）
mpirun -np 16 --hostfile hosts.txt \
  ./build/all_reduce_perf -b 128M -e 128M -f 2

# 4. 关键检查：随着 GPU 数增加，每卡带宽是否保持稳定？
# 如果从 16 GPU 加到 32 GPU 时每卡带宽明显下降 → 网络拓扑有瓶颈
# （每卡通信量基本不随 N 变，所以健康的集群带宽也应该基本不变）

# 5. 在你的训练脚本中埋点测实际通信开销
torch.cuda.synchronize()
t0 = time.time()
loss.backward()      # 这里包含了梯度 All-Reduce
torch.cuda.synchronize()
sync_time = time.time() - t0
step_time = time.time() - step_start
print(f"通信占比: {sync_time/step_time*100:.1f}%")
# 预期：< 10%。如果 > 20% → 先查拓扑与 NCCL 配置，再考虑通信重叠
```

### ⚠️ 常见误区

- **误区**："多卡训练就是把 batch size 拆开，各跑各的"
  - **实际**：每张卡算完自己的梯度后必须做 **All-Reduce 同步**——所有卡等最慢的那张算完，然后交换梯度取平均。这个同步过程是**集体通信**，不是异步的。一张卡慢，所有卡等你。

- **误区**："我用的是 NVLink，没有通信瓶颈"
  - **实际**：NVLink 只在**单机内**（8 卡）能把每卡 All-Reduce 带宽做到 400 GB/s 以上。一旦跨机（>8 卡），通信就要走 InfiniBand 或 RoCE，每卡有效带宽掉到 25–50 GB/s，**差约 8–16 倍**。跨机通信才是真正的瓶颈。

- **误区**："All-Reduce 时间随 GPU 数对数增长，卡越多摊得越薄"
  - **实际**：反了。每卡通信量 ≈ 2S，**与 N 基本无关**，加卡摊薄不了它；Ring 算法的**时延**随 N 线性增长（O(N)），Tree 算法才是 O(log N)——代价是每卡流量更高。带宽调优能让它涨得慢，但不会让它变成常数。

- **误区**："模型放不下就多加几张卡跑 DDP"
  - **实际**：DP 在每张卡上复制完整模型，加卡不解决显存问题。70B 的 140 GB 权重，8 张卡和 800 张卡都需要每张放下 140 GB。"放不下"要用 TP/PP 或 ZeRO-3/FSDP 分片解决——它们才是显存问题的答案。

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|

### 💡 一句话记住

> **"多卡训练不是加法，是木桶原理——通信就是那块最短的板。DP 能让你的卡一起算得快，但前提是每张卡都装得下模型；装不下的时候，你需要的是分片，不是更多的卡。"**
