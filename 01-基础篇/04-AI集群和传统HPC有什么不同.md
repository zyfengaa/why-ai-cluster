# Q: AI 集群和传统 HPC 集群有什么不同？

## 为什么会有这个问题

你可能听说过"超级计算机"这个概念——比如中国的"天河"、"神威·太湖之光"，或者 TOP500 榜单上的那些巨无霸。

AI 集群也属于"集群"的一种，但它的设计逻辑和传统 HPC 有本质不同。如果不理解这些差异，拿 HPC 的思路去做 AI 集群，会踩很多坑。

## 核心差异

### 先纠正一个常见混淆：HPC 也分两种

- **capacity（吞吐型）HPC**：大量**互相独立**的作业排队跑（渲染、基因组学、参数扫描），节点之间几乎不通信，慢一台机器只影响它自己那份作业。
- **capability（能力型）HPC**：**紧耦合**的单一巨型任务（气候模拟、CFD、分子动力学），成千上万个节点每个时间步都要交换边界数据，对低延迟互联的要求极端苛刻。

很多人印象里的"HPC = 各节点各跑各的"只说对了 capacity 型。拿 capability 型 HPC 和 AI 训练比，反而会发现它们惊人地相似——都怕慢节点、都吃低延迟网络。

| 维度 | capacity 型 HPC | capability 型 HPC | AI 训练集群 |
|------|----------------|-------------------|------------|
| **计算模式** | 大量独立作业 | 紧耦合仿真，节点高频互传边界数据 | 所有节点协同训练同一个模型 |
| **通信模式** | 点对点为主，量很小 | MPI 集合通信 + 点对点，量很大 | 集体通信（All-Reduce）占主导 |
| **同步频率** | 低（作业间几乎无同步） | 高（每个时间步同步） | 高（每次迭代同步一次） |
| **任务时长** | 分钟到小时 | 小时到天 | 天到周 |
| **容错方式** | Checkpoint + 重跑 | Checkpoint + 重跑 | Checkpoint + 重跑，弹性/抢占更普遍 |
| **调优目标** | 作业吞吐量 | 单应用扩展效率 | 集群有效吞吐量（MFU）最大化 |
| **负载均衡** | 作业独立，天然均衡 | 高度耦合，慢节点拖慢整体 | 高度耦合，慢节点拖慢整体 |
| **存储 IO** | 读多写少 | 读写都重 | 读写都很重（Checkpoint） |
| **适合调度器** | Slurm（确定性批处理） | Slurm | Slurm 或 K8s（取决于场景） |

### 为什么 AI 集群对网络要求更高？

这是最本质的区别。capacity 型 HPC 里节点各干各的，偶尔传点数据。但在 AI 训练中：

```
每次迭代：
  1. 所有 GPU 跑前向传播（计算）
  2. 所有 GPU 跑反向传播（计算）
  3. 所有 GPU 做 All-Reduce 同步梯度（通信）
  4. 所有 GPU 更新参数（计算）
  5. 回到 1
```

步骤 3 中，**所有 GPU 必须等最慢的那个完成**（同步训练的步时 T_step = max(T_i)）。这意味着：

- **capacity 型 HPC**：100 个节点里 1 个慢了，只影响它自己的作业，其余 99 个照跑
- **AI 集群**：1 个 GPU 慢了，**100% 的作业都被拖住**——影响范围是全部
- 但"影响 100%"不等于"损失 100%"：**吞吐损失取决于慢多少**。单卡慢 10%，整步大约也慢 10%（吞吐降约 9%），而不是全体报废。真正要防的是慢性掉队（straggler）长期存在——它持续吃掉同比例的集群算力。

所以 AI 集群对网络的**确定性、低延迟、无抖动**有极端要求（[[03-网络篇/03-为什么大集群IB有不可替代的优势]]）。capability 型 HPC 的需求其实很接近——这不是 AI 独有的苛刻，是"紧耦合"共有的苛刻。

### 容错：两边都 checkpoint，但敏感度不同

- 传统 HPC 和 AI 训练**都靠 checkpoint/重启容错**，没有谁"天生不用容错"。
- 区别在姿态：AI 生态更接受中断——抢占式调度、弹性训练（节点挂了缩容续跑）是常规操作；capability 型 HPC 追求长周期连续运行。
- 但万卡 AI 训练对**故障恢复时间**极其敏感：Llama 3 405B 在 16,384 张 GPU 上训练 54 天，发生了 **419 次意外中断**，约 78% 由硬件问题引起。每多花 10 分钟恢复，就白烧 10 分钟 × 16,384 张卡的机时。所以 AI 集群把"快速检测故障 + 快速回滚到最近 checkpoint"当成一等公民来设计。

## 一个类比

| 场景 | capacity 型 HPC | AI 训练集群 |
|------|----------------|------------|
| 比喻 | **100 个独立研究员** | **100 个人写同一篇论文** |
| 方式 | 每人写自己的章节 | 每人写一部分，每改一行就要同步所有人 |
| 同步成本 | 只有最终出版时要合稿 | 每改一行，群体等待最慢的人看完 |
| 结果 | 快慢互不影响 | 最慢的人决定整体速度 |

---

## 为什么这个差异越来越重要

过去很多企业搭建 AI 集群时会直接照搬 HPC 的经验（买 InfiniBand 交换机、用 Slurm、装 Lustre）。但 AI 训练的特殊性让几个投入的优先级完全不同了：

1. **网络不再是"能通就行"** — 通信延迟和去中心化路由设计会直接影响 MFU
2. **调度不是"能跑就行"** — Gang Scheduling 死锁可能让半数机器闲着
3. **存储不是"能存就行"** — Checkpoint I/O 成为千万级 GPU 小时开销的隐形杀手

## 🛠 实操指南

### 📋 决策指南：你的集群是按 HPC 还是 AI 思路设计？

**回答下面三个问题，判断你的集群设计思路是否正确：**

```
Q1：你的网络是按"点对点通信"还是"集体通信"设计的？

  capacity 型 HPC 思路：作业互相独立，网络过订阅（oversubscription）2:1 甚至 4:1 是常态
  capability 型 HPC / AI 思路：紧耦合同步是主角，网络必须不阻塞（non-blocking），过订阅 = 性能灾难
  → 如果用 4:1 过订阅网络跑 AI 训练，通信占比会显著上升，MFU 明显下降

Q2：你的存储是按"一次写入、多次读取"还是"频繁大文件读写"设计的？

  HPC 思路：高性能并行文件系统（Lustre/GPFS），临时 scratch 空间，任务结束清理
  AI 思路：同样需要并行文件系统，但 Checkpoint 频繁写入 + 数据集反复读取 + 元数据压力大
  → 用 NFS 当 AI 训练存储 = GPU 等数据

Q3：你如何处理慢节点？

  capacity 型 HPC 思路：作业独立，1 个慢节点只影响它自己的作业
  capability 型 HPC / AI 思路：同步耦合，1 个慢节点拖住所有人的步进
  → AI 集群必须有慢节点检测机制（如 Guard/Slurm 健康检查）
```

**如果你对以上三个问题的回答让 AI 思路占多数 → 你的集群设计方向正确。**

### 🔧 自己动手验：你的集群是 AI 型还是 HPC 型？

```bash
# 1. 检查网络拓扑是否"过订阅"（oversubscribed）
# 在 Fat-Tree 中，脊层带宽 < 叶层总带宽就是过订阅
# 用 nccl-tests 验证：

# 先测 2 节点
mpirun -np 16 --host node1,node2 \
  nccl-tests/build/all_reduce_perf -b 128M -e 128M -f 2
# 记录带宽 BW_2

# 再测 4 节点
mpirun -np 32 --host node1,node2,node3,node4 \
  nccl-tests/build/all_reduce_perf -b 128M -e 128M -f 2
# 记录带宽 BW_4

# 如果 BW_4 < BW_2 × 2（节点数翻倍带宽没翻倍）→ 网络过订阅了
# AI 训练要求：BW_N ≈ BW_2 × (N/2) × 0.85

# 2. 检查存储系统的元数据性能
time ls -l /shared/dataset/ | wc -l
# 10 万文件 → 预期 < 5 秒
# 如果 > 30 秒 → 存储系统不适合 AI（元数据瓶颈）

# 3. 检查调度器是否支持 Gang Scheduling
# Slurm 中查看是否配置了 gang scheduling：
scontrol show config | grep -i gang
# 如果输出为空 → 不支持，可能导致多机任务死锁
```

### ⚠️ 常见误区

- **误区**："TOP500 超算都能跑 AI，用 HPC 的设计思路肯定没错"
  - **实际**：TOP500 按 LINPACK（FP64）性能排名，**口径里根本不统计 AI 负载**——"新增算力有百分之多少给了 AI"这类说法在 TOP500 的方法论里不成立，别拿它当依据。但方向是真实的：公开报道的新建 AI 集群已到 10 万卡量级，投资规模远超绝大多数传统 HPC 项目；超算优化的 FP64 也和 AI 训练的 FP8/BF16 不是一回事。**HPC 的工程纪律（拓扑、调度、存储）值得继承，但投资优先级要按 AI 的通信模式重新排。**

- **误区**："存储够大就行了，速度慢一点没关系"
  - **实际**：capacity 型 HPC 的存储读写模式是"一次写入、多次读取、任务结束清理"。AI 训练每 30-45 分钟写一次数百 GB 的 Checkpoint + 持续读取 TB 级训练数据。按**容量规划口径**估算（每卡预留约 0.5 GB/s 读 + 0.25 GB/s 写，含预处理峰值与 Checkpoint，**不是平均净读取**），一个 10,000 GPU 集群需要约 5 TB/s 读、2.5 TB/s 写——这个量级只有并行文件系统能做到。

- **误区**："HPC 和 AI 集群用一样的 InfiniBand 网络，没区别"
  - **实际**：capacity 型 HPC 的作业之间没有通信，网络拥塞影响有限；但 AI 训练的 All-Reduce 是**所有 GPU 同时同步**，任何一条链路的抖动都会卡住全局（capability 型 HPC 在这点上同样敏感）。Meta 为 Llama 3 建了一套 RoCEv2 集群，与 InfiniBand 集群并行使用——其 Rail-Optimized 拓扑是专门为 All-Reduce 设计的，不是照搬通用 HPC 拓扑。

### 📊 底线数字速查

| 维度 | capacity 型 HPC | AI 训练集群 | 差异要点 |
|------|----------------|------------|---------|
| 精度需求 | FP64（双精度） | FP8/BF16（混合精度） | 算力密度差 8-16× |
| 网络过订阅比例 | 4:1 可接受 | **1:1（不阻塞）** | 网络成本差 4× |
| 每 GPU 存储吞吐 | ~0.1 GB/s | **~0.5 GB/s 读 + 0.25 GB/s 写**（容量规划口径，非平均净读取） | 5-7.5× |
| 慢节点影响 | 只影响它自己的作业 | **拖住 100% 的作业；吞吐损失 ≈ 慢多少**（慢 10% → 整步约慢 10%） | 同步耦合 |
| 通信模式 | 点对点为主 | **集体通信（All-Reduce）** | 网络需求本质不同 |
| 单任务典型时间 | 分钟~小时 | **天~周** | 10-100× |

### 💡 一句话记住

> **"吞吐型 HPC 是 100 个独立的科学家各算各的，AI 集群是 100 个人写同一篇论文——每改一行都要所有人同步，最慢的人决定整体速度。所以 AI 集群对网络和存储的要求，按紧耦合系统的标准来，而不是按批处理系统的标准来。"**
