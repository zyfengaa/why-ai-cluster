# Q: 混合精度训练（FP16/BF16/FP8）是怎么递进的？

## 为什么会有这个问题

训练大模型，精度和速度是一对天生的矛盾。FP32 最精确但显存消耗最大、计算最慢；FP16 快但动态范围不够；BF16 范围够了尾数精度又低……

业界花了多年时间，走了一条从"被迫降精度"到"主动降精度"的路。

## 解决什么问题

混合精度训练的核心目标：**在尽量不损失模型精度的前提下，用更低的数值精度加速计算、节省显存。** 注意：**不是把所有状态都降到同一精度**——权重/梯度用低精度存储和计算，而优化器状态（尤其 Adam 的 m/v）通常保持在 FP32。

### 精度格式的演化

```
FP32 → FP16 + Loss Scaling（2018）→ BF16（2020+）
→ FP8（2022 论文 / H100 硬件）→ MXFP8/NVFP4（Blackwell）
```

| 格式 | 位宽 | 指数位 | 尾数位 | 动态范围 | 硬件支持 |
|------|------|--------|--------|---------|---------|
| FP32 | 32 | 8 | 23 | 约 10⁻³⁸ ~ 10³⁸ | 所有 GPU |
| FP16 | 16 | 5 | 10 | 约 6×10⁻⁵ ~ 6.5×10⁴ | 所有 GPU |
| BF16 | 16 | **8** | 7 | **约 10⁻³⁸ ~ 10³⁸（与 FP32 同范围）** | A100+ |
| FP8 E4M3 | 8 | 4 | 3 | 最大值 448 | Ada/Hopper+ |
| FP8 E5M2 | 8 | 5 | 2 | 最大值 57,344 | Ada/Hopper+ |
| NVFP4 | 4 | 2（E2M1） | 1 | 最大值 6，靠微块缩放救精度 | Blackwell |

关键点：

- **BF16 与 FP32 的动态范围几乎相同**（指数位同为 8 位），差别在尾数：BF16 只有 7 位尾数，精度低。它不是"更小的 FP32 数值范围"，而是"同范围、低精度"。
- FP16 的 5 位指数范围只有约 10⁻⁵~10⁴，梯度一旦小于最小正规数就下溢为 0——这就是它需要 Loss Scaling 的原因。

**FP16 和 BF16 谁更好？** FP16 尾数更多（10 bit vs 7），精度更高；BF16 范围大（8 bit 指数）。对训练而言范围比精度重要——**BF16 不需要 Loss Scaling 就能覆盖梯度的动态范围**，这是它成为主流训练格式的原因。

### 显存账本：为什么"8 张 H100 装下 70B"是错的

混合精度训练的显存大头不是"算得多快"，而是**状态存了多少**。用 Adam 的标准混合精度配置：

```
70B 模型（Adam，BF16 混合精度）：
  BF16 权重          2 B/参数 = 140 GB
  BF16 梯度          2 B/参数 = 140 GB
  FP32 master 权重   4 B/参数 = 280 GB
  Adam m (FP32)      4 B/参数 = 280 GB
  Adam v (FP32)      4 B/参数 = 280 GB
  ─────────────────────────────────
  完整训练状态       16 B/参数 ≈ 1.12 TB
```

**8×H100 = 640 GB < 1.12 TB，放不下**——这还没算激活值。70B 训练需要 16–32 张 80 GB 卡，或者用 ZeRO/TP/PP 把 1.12 TB 分片到更多卡上（见本篇 01/02）。

注意这条账本**与"显存不够就换 FP16"无关**：FP16 和 BF16 都是 2 字节/元素，换了不省显存。省显存的路径是：分片（ZeRO/FSDP）、卸载（CPU/NVMe）、激活重计算，或改变优化器状态（如 8-bit Adam、Adafactor）——而不是把权重从 BF16 换成 FP16。

### 混合精度的真正含义

"混合"指的是**不同状态用不同精度**，而不是所有东西统一降位：

```
前向/反向 GEMM：BF16/FP8（快，Tensor Core）
权重存储：BF16 副本 + FP32 master（更新在 FP32 上做，避免低精度累加误差）
梯度：BF16（FP8 训练时部分在 FP8）
优化器状态：FP32（m/v 的累加对精度敏感，一般不降）
LayerNorm / Softmax / 损失：FP32 或 BF16（数值敏感操作）
```

## 混合精度训练的演进

### 第一阶段：FP16 + Loss Scaling（2018）

Micikevicius 等人 2018 年提出混合精度训练（Mixed Precision Training），核心做法：

```
1. 前向/反向用 FP16（快）
2. 主权重用 FP32 副本（精度不丢）
3. 损失缩放（Loss Scaling）：反向前把 loss 放大 2^K 倂，
   避免梯度在 FP16 下"消失"（小于最小正规数 6×10⁻⁵ 被舍入为 0）
4. 优化器更新在 FP32 上做
```

**痛点**：
- Loss Scaling 需要动态调整——太大了梯度上溢，太小了下溢
- FP16 的 5 位指数覆盖不了梯度的分布范围

### 第二阶段：BF16 成为默认（2020+）

A100 引入 BF16，**指数位与 FP32 相同（8 位）**：

```
BF16 的优势：
  - 不需要 Loss Scaling（动态范围与 FP32 一致）
  - 训练稳定，不用操心梯度上/下溢
  - 硬件 Tensor Core 速度与 FP16 一样快

BF16 的代价：
  - 尾数只有 7 bit（FP16 是 10 bit），有效数字约 2~3 位十进制
  - 但实验证明：对训练收敛影响很小
```

**现状**：BF16 是训练的"默认计算精度"，FP32 留给 master 权重、优化器状态和数值敏感操作。

### 第三阶段：FP8 训练（Hopper+）

H100 的 Transformer Engine 原生支持 FP8 计算：

**FP8 的两种格式**：
- **E4M3**（4 指数 + 3 尾数）：用于前向（权重和激活分布较稳定，要精度）
- **E5M2**（5 指数 + 2 尾数）：用于反向（梯度范围变化大，要动态范围）

**FP8 的缩放（scaling）体系**——这是 FP8 训练最容易混淆的部分，不同方案对应不同粒度：

- **per-tensor 延迟缩放（delayed scaling）**：每个张量一个缩放因子，用**上一步的历史 amax**（amax history，维护最近若干步的最大绝对值）推当前步的因子——因为当前步的 amax 在 GEMM 前还不知道
- **per-channel / per-block 当前缩放（current scaling）**：按通道或块粒度，在 GEMM 内实时计算 amax 并缩放，精度更好，但对 amax history 的依赖更小
- 缩放粒度越细（tensor → channel → block），精度越好，元数据开销也越大

**FP8 训练的实际做法**：
```python
# 只在 Linear 层的 GEMM 使用 FP8（经 Transformer Engine 自动替换/管理）
# LayerNorm、Dropout、Softmax、损失计算 → 保持 BF16/FP32
# 前向 E4M3、反向 E5M2（TE 的 hybrid 策略）
```

### 第四阶段：MXFP8 与 NVFP4（Blackwell）

Blackwell 引入两种微块（micro-block）格式：

**MXFP8（OCP MX 规范）**：
- 每 **32 个元素**共享一个缩放因子，缩放因子是 **E8M0**（2 的幂）
- 粒度比 per-tensor 细得多 → 精度明显改善

**NVFP4（4-bit 浮点，E2M1）**：
- 元素格式是 **E2M1（2 位指数、1 位尾数）**，动态范围极小
- 每 **16 个元素**一个微块，块缩放用 **E4M3**（比 MXFP4 的 E8M0 更高精度）
- 在此之上还有一层 **FP32 全局缩放**（per-tensor scale）
- Blackwell Tensor Core 原生执行 NVFP4 GEMM

**加速比的正确打开方式**：NVFP4/FP8 相对 BF16 的 **2×/4× 是矩阵乘（GEMM）吞吐的峰值倍数**，不是端到端训练加速。GEMM 只占整步时间的一部分，加上其他层仍是 BF16/FP32、通信和数据搬运不变，**端到端加速通常只有 1.1–1.3×**；NVIDIA 在特定的大规模预训练设置下报告过 NVFP4 约 1.6× 的吞吐提升——那是有完整配方（见下）支撑的最优值，不是随手可得。

```
NVFP4 训练的稳定性配方（来自 NVIDIA 公开博客，具体超参见原文）：
  1. 最后若干层保持高精度（BF16/FP8）——模型末端对量化最敏感，
     全 NVFP4 直接训练会发散
  2. 配合随机舍入（stochastic rounding）、Hadamard 变换等技巧
     防止小更新被量化抹掉
  3. 优化器超参需要针对性调整，不能直接套 BF16 的配方
```

## 🛠 实操指南

### 📋 决策指南：你该用哪种精度？

```
你的 GPU 型号？
├─ Blackwell（B200/B300）→
│   ├─ 追求极致吞吐 → NVFP4（按 NVIDIA 配方，末端层留高精度）
│   └─ 稳妥路线 → MXFP8
│
├─ Hopper（H100/H200）→
│   └─ FP8（E4M3 前向 / E5M2 反向），Transformer Engine 自动管理缩放
│       └─ 注意：只在 Linear 层 GEMM 用 FP8，其他层 BF16
│
└─ Ampere（A100）→
    └─ BF16（默认），不需要 Loss Scaling
         └─ 显存不够 → 上 ZeRO/FSDP 分片、CPU 卸载或激活重计算
            （换 FP16 没有用：它和 BF16 一样是 2 字节）
```

```python
# 正确的显存判断方式：状态按"角色"计价，不按"精度档位"一刀切
model_size = 70e9  # 参数量

bytes_per_param = {
    "BF16 权重": 2,
    "BF16 梯度": 2,
    "FP32 master": 4,
    "Adam m": 4,
    "Adam v": 4,
}
total = sum(bytes_per_param.values())  # 16 B/参数
state_gb = model_size * total / 1e9    # ≈ 1,120 GB（1.12 TB）

gpu_mem, n_gpus = 80, 8
print(f"70B 完整训练状态 ≈ {state_gb:.0f} GB")
print(f"8×{gpu_mem} GB = {n_gpus*gpu_mem} GB → {'放得下' if state_gb < n_gpus*gpu_mem else '放不下：需要 16-32 卡，或 ZeRO/TP/PP 分片'}")
```

```python
# 检查你的 GPU 是否支持 FP8
import torch
print("FP8 dtypes:", hasattr(torch, "float8_e4m3fn"))
print("Compute capability:", torch.cuda.get_device_capability())
# FP8 Tensor Core 需要算力 8.9（Ada）或 9.0（Hopper）及以上；
# NVFP4 需要 Blackwell（算力 10.0+）
```

```python
# 对比不同精度的 GEMM 速度（注意：测的是 GEMM，不是端到端训练）
import torch, time

for dtype in [torch.float32, torch.bfloat16]:
    x = torch.randn(4096, 4096, device="cuda", dtype=dtype)
    w = torch.randn(4096, 4096, device="cuda", dtype=dtype)
    for _ in range(20): torch.mm(x, w)          # 预热
    torch.cuda.synchronize()
    t0 = time.time()
    for _ in range(200): torch.mm(x, w)
    torch.cuda.synchronize()
    print(f"{dtype}: {200/(time.time()-t0):.0f} it/s")
```

### ⚠️ 常见误区

- **误区**："FP16 和 BF16 是一样的"
  - **实际**：两者都是 2 字节，但 FP16 是 5 位指数 + 10 位尾数，BF16 是 8 位指数 + 7 位尾数。BF16 范围与 FP32 相同、精度更低；FP16 范围只有 ~10⁻⁵~10⁴、精度更高。训练默认 BF16。

- **误区**："FP32/BF16 的动态范围是 10⁻⁸~10⁸"
  - **实际**：FP32 范围约 10⁻³⁸~10³⁸（8 位指数决定），BF16 指数位与 FP32 相同所以范围也一样——差别在 7 位尾数带来的低精度。

- **误区**："显存不够就把权重换成 FP16"
  - **实际**：FP16 和 BF16 同为 2 字节/元素，显存一个字节都不会省。省显存靠分片（ZeRO/FSDP）、卸载（CPU/NVMe）、激活重计算，或减小优化器状态——精度格式只影响"算得多快"和"计算时那些操作数占多少显存"，动不了 1.12 TB 训练状态的大头。

- **误区**："FP8 训练一定会损失精度 / FP8 可以随便用"
  - **实际**：FP8 只用于 Linear 层 GEMM、配好缩放策略（延迟缩放 + amax history，或当前缩放）后，端到端精度损失可以做到很小；但缩放策略配错（比如梯度 amax 突变时用滞后的 per-tensor 因子）会直接训崩。

- **误区**："NVFP4 有 4× 吞吐，端到端也快 4×"
  - **实际**：4× 是 GEMM 峰值。GEMM 之外的时间（其他精度的层、通信、数据搬运）不变，端到端通常 1.1–1.3×；NVIDIA 报告的 ~1.6× 是特定预训练设置 + 完整稳定性配方的结果。

- **误区**："NVFP4 就是 4-bit 量化，可以闭眼用"
  - **实际**：E2M1 只有 1 位尾数，必须靠 16 元素微块 + E4M3 块缩放 + FP32 全局缩放的三层缩放体系，以及末端层留高精度等配方，才能稳定训练。直接全模型 NVFP4 会发散。

### 📊 底线数字速查

| 精度格式 | GEMM 吞吐（vs BF16，峰值） | 端到端训练加速（典型） | 显存影响 | 硬件要求 |
|---------|-------------------|---------|---------|---------|
| FP16 | ~1× | ~1× | 2 B/元素，与 BF16 相同 | 所有 GPU |
| BF16 | baseline | baseline | baseline | A100+ |
| FP8 E4M3 | 2×（峰值） | 约 1.1–1.3× | 部分操作数减半 | Hopper+ |
| MXFP8 | ~2×（峰值） | 约 1.1–1.3× | 微块元数据略增 | B200+ |
| NVFP4 | 4×（峰值） | 约 1.2–1.6×（需完整配方） | 部分操作数 1/4 | Blackwell |

**一键决策**：A100 用 BF16；H100 用 FP8（Linear 层 GEMM，TE 管缩放）；Blackwell 求稳用 MXFP8、求极致吞吐用 NVFP4 + 官方配方。**无论哪档，显存不够时先想分片和卸载，不是换 FP16。**

> 并行口径备注（与第 03/05 篇一致）：总卡数 = 各并行维度相乘；5D 并行指 **TP + EP + CP + DP + PP**，例如 TP=8 × EP=8 × CP=16 × DP=4 = 4,096 卡（PP 再乘上去时注意总 world size 同步相乘）。

### 💡 一句话记住

> **"混合精度不是'所有状态降一位'：计算走 BF16/FP8/NVFP4，优化器状态和 master 权重留在 FP32。BF16 的指数位与 FP32 相同（范围 ~10⁻³⁸–10³⁸），只是尾数更短；FP8/NVFP4 的 2×/4× 是 GEMM 峰值，端到端通常只有 1.1–1.3×；而显存的大头是 16 B/参数的训练状态——70B 就是 1.12 TB，8×H100 装不下，省显存靠分片和卸载，不靠换 FP16。"**
