# Q: 网络拓扑怎么选？

## 为什么会有这个问题

光有 IB/RoCE 协议还不够——你怎么把这些链路"组织"成一个网络？**这就看拓扑了。**

你可以把网络拓扑理解为城市交通规划：
- **Fat-Tree（叶脊/Clos）** = 网格状道路，哪哪都能到，但路口多
- **Rail-optimized（轨道优化）** = 把"同排住户"先串起来，跨排再走上层路
- **Dragonfly+** = 高速环线，跨区快，但设计复杂
- **3D Torus** = 棋盘格，只连邻居，规律整齐

## 先建立两个概念：对分带宽与超订阅比

- **对分带宽（Bisection Bandwidth）**：把集群一刀切成两半时，穿过切口的带宽。它是"最坏情况下的群体通信能力"，是拓扑优劣的第一指标。
- **超订阅比（Oversubscription Ratio）**：下层上行带宽与下层下行带宽之比。1:1 = 无收敛（non-blocking，任何两卡通信都有满带宽）；2:1 = 跨层通信的可用带宽只有本层的一半。

**为什么超订阅比对 AI 训练特别致命**：All-Reduce 是**所有 GPU 同时同步数据**的集体通信，不是点对点随机流量。任何一层 2:1 的收敛，都意味着依赖跨层流量的 All-Reduce 阶段时间直接翻倍。NCCL 会感知拓扑、尽量把通信压缩在低层（如按 rail 分组），但收敛比是物理上限。

## 四种主流拓扑

### Fat-Tree（叶脊架构，Clos）

最常用的 AI 集群拓扑。

```
         ┌──────脊层交换机──────┐
         │ Spine 1  Spine 2  Spine 3│
         └──┬──┬──┬──┬──┬──┬──┘
            │  │  │  │  │  │
         ┌──┴──┴──┴──┴──┴──┴──┐
         │ Leaf 1  Leaf 2  Leaf 3│
         ├───┬───┬────┬───┬───┤
         │GPU│GPU│GPU │GPU│GPU│
         │机 │机 │机  │机 │机 │
         └───┴───┴────┴───┴───┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **最佳**（1:1 配置下任何切分都保证全带宽）|
| 扩展性 | 好（多加一层可扩容，Meta 用三层 Fat-Tree 扩到 24,576 卡）|
| 成本 | 高（需要大量上层交换机和光模块）|
| 维护 | 简单（所有路径等长，路由确定）|
| 适用 | 大多数自建 AI 集群的默认选择 |

**无阻塞（Non-blocking）**：如果每台 leaf 的上行带宽 = 下行带宽（超订阅比 1:1），网络就是无阻塞的——任何 GPU 之间通信都有满带宽。

### Rail-optimized（轨道优化）

Fat-Tree 的 AI 专用变体，几乎所有的 GPU 集群都在用它的思想：

```
8 卡服务器（H100/H200）里每张 GPU 配 1 块 400G 网卡。
"Rail 0" = 所有服务器的 GPU0 的网卡 → 接入交换机 A（或 A 组）
"Rail 1" = 所有服务器的 GPU1 的网卡 → 接入交换机 B
……

好处：
  - 同一 rail 上的卡（如所有服务器的 GPU0）一跳直达，
    最适合按卡分片的集合通信（NCCL 的 rail-aware 优化正建立在此之上）
  - 跨 rail 的通信走上层叶脊网络
```

### Dragonfly+

每组是一个"龙组"，组内全互联，组间通过少量链路互连。

```
  ┌─────────────────────────────┐
  │ Dragonfly Group 1           │
  │  ┌───┐ ┌───┐ ┌───┐         │
  │  │GPU│ │GPU│ │GPU│───互联线──│──→ Group 2
  │  └───┘ └───┘ └───┘         │
  └─────────────────────────────┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | 中等（跨组通信有竞争）|
| 扩展性 | 好（结构上可扩到数十万节点）|
| 成本 | 较低（比全带宽 Fat-Tree 省线缆和交换机）|
| 路由 | 复杂（依赖自适应路由避免拥塞）|
| 适用 | 大规模、有强路由软件能力的系统 |

**优点**：用更少的交换机连接更多的 GPU。
**缺点**：跨组通信的延迟和带宽不一致，需要智能路由算法。

> 澄清一个流传甚广的说法：**"Meta 和 Google 的万卡集群用了 Dragonfly+ 变体"是错的**——Meta Llama 3 用的是三层 Fat-Tree（T0–T1 收敛比 2:1、T1–T2 收敛比 7:1），Google TPU 用的是 3D Torus。

### 3D Torus

Google TPU 的招牌拓扑。

```
            ┌───────┐
            │ TPU   │────→ TPU (X方向)
            │       │
            │   │   │
            │   ↓   │
            │ TPU←──│────→ TPU (Y方向)
            └───────┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **受限**（取决于切分方向）|
| 扩展性 | Pod 内规模大（Google Ironwood 一个 Pod 9,216 芯片）|
| 成本 | 布线复杂度低（只连邻居），**但光互联/OCS 成本不可忽略** |
| 路由 | 确定性（已知的最短路径）|
| 适用 | Google TPU Pod 自有 |

> **两个常见误读要纠正**：
> 1. 3D Torus **不是"无限扩展"**——Google Ironwood 是"Pod 内 3D Torus（9,216 芯片）+ Pod 间靠 OCS 光交换/数据中心网络扩展"的架构，Pod 之间不是全互联。
> 2. 3D Torus **不是"零成本"**——它省的是布线复杂度（每芯片只连 X/Y/Z 方向的邻居），但 Google 方案里支撑它的 OCS 光交换层是一笔真实且不菲的投入。

## 现实中怎么设计？——1,000 卡拓扑账本

从需求正着算一遍（这是本书统一口径的账本）：

```
已知：
  - 1,000 张 H100 GPU
  - 每卡 1 × 400G（= 50 GB/s 单向）后端网络
  - Fat-Tree 拓扑，64 端口 400G 交换机（交换容量 64 × 400G = 25.6 Tb/s）

计算：
  1. 服务器数：1,000 ÷ 8 ≈ 125 台（8 卡/台）
  2. 每台服务器 8 × 400G = 3.2 Tb/s 接入带宽
     → 聚合接入带宽 = 125 × 3.2 = 400 Tb/s
  3. 每台 leaf 交换机 64 端口：32 个下联服务器（12.8 Tb/s）
     + 32 个上联（12.8 Tb/s）→ 超订阅比 1:1
  4. leaf 数量 = 1,000 个服务器端口 ÷ 32 ≈ 32 台
  5. 上联链路总数 = 32 leaf × 32 = 1,024 条
     spine 数量 = 1,024 ÷ 64 = 16 台（每台 spine 64 端口全部下联 leaf）
     每 leaf 连接全部 16 台 spine，每对之间 2×400G（或 1×800G）
  6. 对分带宽 ≈ 200 Tb/s（= 聚合接入带宽的一半，1:1 无收敛）
```

> **对照旧版的错误算法**："叶层 50 台、脊层 20,000 ÷ 25,600 ≈ 8 台"是把 Tb/s 当成了 Gb/s 又把交换容量当成了背板对分——量纲和算术都错。正确答案是 **32 台 leaf、16 台 spine**（1:1 无收敛）。

如果预算紧张，可以把上联砍半（每 leaf 16 条 400G 上联），得到 2:1 收敛——成本下降，但跨 spine 的集合通信时间约翻倍。这是拓扑设计里最常见的取舍。

## 2026 年的选型建议

| 集群规模 | 推荐拓扑 | 理由 |
|---------|---------|------|
| < 512 GPU | Fat-Tree（单脊层）+ rail-optimized | 简单，无阻塞，运维容易 |
| 512 - 4,096 GPU | Fat-Tree（多脊层）+ rail-optimized | 扩展性好，可分段建设 |
| 4,096 - 16,384 GPU | Fat-Tree（两到三层） | Meta 24,576 卡验证过；预算敏感时可局部收敛 |
| > 16,384 GPU | **仍然可选 Fat-Tree/三层 Clos**（收敛比换规模）；3D Torus（Google）；Dragonfly+（特定系统） | **"只能用 Dragonfly+"不成立**——Meta 用三层 Fat-Tree 建到 24,576 卡，xAI 用 Spectrum-X 以太网三层架构建到十万卡级 |

## 🛠 实操指南

### 📋 决策指南：你的网络拓扑该选哪种？

**回答这三个问题：**

```
Q1: 你的集群是单租户还是多租户？
  单租户（一个团队独占） → Fat-Tree 或（有路由软件能力时）Dragonfly+
  多租户（多个团队共享） → Fat-Tree（脊层做隔离更简单）

Q2: 你更关注成本还是确定性？
  成本优先 → 收敛比 2:1 的 Fat-Tree，或 Dragonfly+
  性能确定性优先 → 1:1 无收敛 Fat-Tree

Q3: 你打算扩展到多大？
  不超过 4,096 GPU → 两层 Fat-Tree 是最保险的选择
  更大规模 → 三层 Fat-Tree（有先例）或评估 Dragonfly+/专用架构
```

### 🔧 自己动手验：你的网络拓扑有什么问题？

```bash
# 1. 检查你的拓扑是否"无阻塞"
# 判断：每台 leaf 的上行端口带宽总和 ≥ 下行端口带宽总和（超订阅比 ≤ 1:1）

# 2. 检查实际 All-Reduce 带宽是否和理论一致
# 在 N 个节点上跑 nccl-tests，逐步增加节点数
# 如果每加一倍节点，busbw 明显下降 → 说明存在收敛（过订阅）

# 3. 用 NCCL 的拓扑感知验证
NCCL_DEBUG=INFO mpirun -np 64 all_reduce_perf -b 256M -e 256M 2>&1 | grep "Ring"
# 看 NCCL 是否选择了正确的 Ring 路径
```

### ⚠️ 常见误区

- **误区**："Fat-Tree 太浪费交换机端口了，Dragonfly+ 更高效"
  - **实际**：Fat-Tree 的"浪费"换来的是**运维确定性**——任何路径长度相等，故障排查简单。Dragonfly+ 省线缆，但要承担自适应路由的复杂度。**如果你的团队没有网络专家，Fat-Tree 更可靠。**
- **误区**："过订阅（Oversubscription）没关系，AI 训练不是所有 GPU 同时通信"
  - **实际**：All-Reduce 就是**所有 GPU 同时同步数据**——这是集体通信，不是点对点随机通信。2:1 的收敛会让依赖跨层流量的集合通信时间约翻倍；NCCL 的 rail-aware 优化只能缓解、不能消除物理上限。
- **误区**："我的拓扑以前跑 HPC 没问题，跑 AI 训练应该也行"
  - **实际**：HPC 任务通常是"各自算各自的，偶尔交换结果"。AI 训练是"每轮迭代所有人都要同步"。同样的拓扑、同样的带宽，AI 训练可能比 HPC 慢 2-3 倍。

### 📊 底线数字速查

| 拓扑类型 | 典型规模 | 对分带宽 | 线缆/交换成本 | 运维复杂度 |
|---------|----------------|---------|---------|-----------|
| 单脊层 Fat-Tree（+rail） | 256-512 GPU | 无收敛 | 中等 | **低** |
| 多层 Fat-Tree（+rail） | 数百至数万 GPU | 无收敛或按设计收敛 | 高 | 中等 |
| Dragonfly+ | 数万级 | 依赖路由（有跨组竞争） | 较低 | **高** |
| 3D Torus | Pod 内（Ironwood 9,216 芯片）| 方向相关 | 布线省、**光互联/OCS 不便宜** | 中等 |

### 💡 一句话记住

> **"Fat-Tree 是'每个十字路口都装红绿灯'——安全但贵；Dragonfly+ 是'快速环线配几个大转盘'——高效但容易迷路。先算清超订阅比，再谈省不省钱。"**
