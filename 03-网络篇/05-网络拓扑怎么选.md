# Q: 网络拓扑怎么选？

## 为什么会有这个问题

光有 IB/RoCE 协议还不够——你怎么把这些链路"组织"成一个网络？**这就看拓扑了。**

你可以把网络拓扑理解为城市交通规划：
- **Fat-Tree** = 网格状道路，哪哪都能到，但路口多
- **Dragonfly+** = 高速环线，跨区快，但设计复杂
- **3D Torus** = 棋盘格，规律整齐，扩展性有限

## 主流拓扑

### Fat-Tree（叶脊架构，Clos 的不阻塞特例）

最常用的 AI 集群拓扑。

```
         ┌──────脊层交换机──────┐
         │ Spine 1  Spine 2  Spine 3│
         └──┬──┬──┬──┬──┬──┬──┘
            │  │  │  │  │  │
         ┌──┴──┴──┴──┴──┴──┴──┐
         │ Leaf 1  Leaf 2  Leaf 3│
         ├───┬───┬────┬───┬───┤
         │ GPU│GPU│GPU │GPU│GPU│
         │ 机 │ 机 │ 机 │ 机 │ 机 │
         └───┴───┴────┴───┴───┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **最佳**（任何切分都保证全带宽）|
| 扩展性 | 好（加脊层可扩容）|
| 成本 | 高（需要大量脊层交换机）|
| 维护 | 简单（所有路径等长）|
| 适用 | **最主流的方案**（Meta、微软、阿里等大型训练集群普遍采用）|

**不阻塞拓扑（Non-blocking）**：严格定义是**任意一个下行端口与另一个下行端口之间都能线速通信**（等价于对分带宽 = 全带宽）。工程上的直观判据是：脊层的总带宽不低于叶层的总下行带宽。

### Dragonfly+

每组是一个"龙组"，组内全互联，组间通过少量链路互连。

```
  ┌─────────────────────────────┐
  │ Dragonfly Group 1           │
  │  ┌───┐ ┌───┐ ┌───┐         │
  │  │GPU│ │GPU│ │GPU│───互联线──│──→ Group 2
  │  └───┘ └───┘ └───┘         │
  └─────────────────────────────┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **中等**（跨组通信有竞争）|
| 扩展性 | **最好**（可以到百万节点）|
| 成本 | 较低（经验值：比同等规模 Fat-Tree 少约 40% 线缆）|
| 路由 | 复杂（需要自适应路由避免拥塞）|
| 适用 | **万卡以上、成本敏感的集群** |

**优点**：用更少的交换机连接更多的 GPU。
**缺点**：跨组通信的延迟和带宽不一致，需要智能路由算法。

需要说明的是，Meta 和 Google 的万卡集群**并不**采用 Dragonfly+：Meta 用的是两级 Clos + ATSW 第三级（见其 SIGCOMM'24 论文），Google 用的是 3D Torus + 光交换。

### 3D Torus

Google TPU 的招牌拓扑。

```
            ┌───────┐
            │ TPU   │────→ TPU (X方向)
            │       │
            │   │   │
            │   ↓   │
            │ TPU←──│────→ TPU (Y方向)
            └───────┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **受限**（取决于切分方向）|
| 扩展性 | 受维度与 Pod 规模限制（TPU v7 单 Pod 为 9,216 颗）|
| 成本 | 最低（只需要邻居链路）|
| 路由 | 确定性（已知的最短路径）|
| 适用 | **TPU Pod 自有** |

Google TPU v7（Ironwood）采用 **Twisted 3D Torus**，单个 Pod 可容纳 **9,216 颗芯片**；Pod 的最小单元是 **4×4×4 = 64 颗芯片**，并由 **48 台 OCS（光电路交换机）** 动态重构光路。

### Rail-Optimized（多轨）拓扑

前面几种是"教科书"拓扑。但在真实 AI 集群中——**NVIDIA DGX SuperPOD、Meta、xAI 等**——用得最多的其实是 **Rail-Optimized（多轨）** 拓扑。

思路很简单：把每台服务器里的 8 张 GPU 按序号"归轨"——第 1 张 GPU 接第 1 轨、第 2 张接第 2 轨……同一轨的 GPU 全部接到同一组交换机上。于是：

- 每张 GPU 只跨一层交换机，就能和所有其他服务器上"同轨"的 GPU 通信；
- 而 NCCL 的 Ring/Tree AllReduce 往往正是"跨节点、同 GPU 序号"之间的流量——与 rail 结构天然匹配，能把大部分跨机流量压进一层交换机内。

代价是：一旦通信模式不是"同轨对同轨"，就可能要绕行，所以 rail-optimized 通常配合自适应路由使用。

| 特点 | 说明 |
|------|------|
| 对分带宽 | 好（同轨流量一层可达）|
| 扩展性 | 好（按轨增加交换机即可）|
| 成本 | 中（比全 Fat-Tree 略省）|
| 路由 | 需要自适应路由应对跨轨流量 |
| 适用 | **DGX SuperPOD、Meta、xAI 等大型训练集群** |

## 2026 年的选型建议

| 集群规模 | 推荐拓扑 | 理由 |
|---------|---------|------|
| < 512 GPU | Fat-Tree（单脊层） | 简单，不阻塞，运维容易 |
| 512 - 4,096 GPU | Fat-Tree（多脊层） | 扩展性好，可分段建设 |
| 4,096 - 16,384 GPU | Fat-Tree 或 Dragonfly+ | 看预算，Fat-Tree 保险但贵 |
| > 16,384 GPU | Fat-Tree/Clos、Dragonfly+ 或 3D Torus | 视团队与预算：Meta、微软、阿里多用 Clos，Google 用 3D Torus |
| TPU Pod | 3D Torus | Google 固定方案 |

## 现实中怎么设计？

从需求倒推：

```
已知：
  - 1,000 张 H100 GPU
  - 每 GPU 需要 400 Gb/s 网络带宽
  - 采用 Fat-Tree 拓扑

计算（用 64 口交换机，每口 400G）：
  1. 服务器数：1,000 ÷ 8 = 125 台
  2. 每台 8 × 400G NIC = 3.2 Tb/s 上行 → 全集群下行带宽 = 125 × 3.2 = 400 Tb/s
  3. 叶层：64 口交换机一半做下行、一半做上行 → 每台 32 个 400G 下行口
          共需 1,000 个 400G 下行口 → 叶层交换机 = 1,000 ÷ 32 = 32 台
  4. 脊层上行口总量：32 台 × 32 个上行口 = 1,024 个 400G = 409.6 Tb/s（≥ 400 Tb/s，不阻塞）
  5. 脊层交换机数量：1,024 ÷ 64 = 16 台
```

## 🛠 实操指南

### 📋 决策指南：你的网络拓扑该选哪种？

**回答这三个问题：**

```
Q1: 你的集群是单租户还是多租户？
  单租户（一个团队独占） → Fat-Tree 或 Dragonfly+
  多租户（多个团队共享） → Fat-Tree（脊层做隔离更简单）

Q2: 你更关注成本还是确定性？
  成本优先 → Dragonfly+（省 40% 线缆）
  性能确定性优先 → Fat-Tree（不阻塞）

Q3: 你打算扩展到多大？
  不超过 4,096 GPU → Fat-Tree 是最保险的选择
  > 16,384 GPU → Fat-Tree/Clos、Dragonfly+ 或 3D Torus 都有成功案例，按团队能力与预算定
```

### 🔧 自己动手验：你的网络拓扑有什么问题？

```bash
# 1. 检查你的拓扑是否能达到"不阻塞"
# 以 Fat-Tree 为例：脊层端口数 × 每端口带宽 ≥ 叶层总上行带宽

# 2. 检查实际 All-Reduce 带宽是否和理论一致
# 在 N 个节点上跑 nccl-tests，逐步增加节点数
# 如果每加一倍节点，带宽减半 → 说明脊层带宽不足（过订阅）

# 3. 用 NCCL 的拓扑感知验证
NCCL_DEBUG=INFO mpirun -np 64 all_reduce_perf -b 256M -e 256M 2>&1 | grep "Ring"
# 看 NCCL 是否选择了正确的 Ring 路径
```

### ⚠️ 常见误区

- **误区**："Fat-Tree 太浪费交换机端口了，Dragonfly+ 更高效"
  - **实际**：Fat-Tree 的"浪费"换来的是**运维确定性**——任何路径长度相等，故障排查简单。Dragonfly+ 省了 40% 线缆，但要承担自适应路由的复杂度。**如果你的团队没有网络专家，Fat-Tree 比 Dragonfly+ 更可靠。**
- **误区**："过订阅（Oversubscription）没关系，AI 训练不是所有 GPU 同时通信"
  - **实际**：All-Reduce 就是**所有 GPU 同时同步数据**——这是集体通信，不是点对点随机通信。过订阅的拓扑在 All-Reduce 场景下会导致严重的性能下降。
- **误区**："我的拓扑以前跑 HPC 没问题，跑 AI 训练应该也行"
  - **实际**：HPC 任务通常是"各自算各自的，偶尔交换结果"。AI 训练是"每轮迭代所有人都要同步"。同样的拓扑、同样的带宽，AI 训练可能比 HPC 慢 2-3 倍。

### 📊 底线数字速查

| 拓扑类型 | 最大规模（推荐） | 对分带宽 | 线缆成本 | 运维复杂度 |
|---------|----------------|---------|---------|-----------|
| 单脊层 Fat-Tree | 256-512 GPU | 100% | 中等 | **低** |
| 多脊层 Fat-Tree | 512-4,096 GPU | 100%（可配置） | 高 | 中等 |
| Dragonfly+ | 4,096-100K+ GPU | 经验值 60-80% | **低**（经验值：省约 40%） | **高** |
| 3D Torus | 有限（9,216 TPU/Pod） | 方向相关 | **最低** | 中等 |
| Rail-Optimized | 一层可达同轨流量，按轨扩展 | 同轨 100% | 中 | 中等 |

### 💡 一句话记住

> **"Fat-Tree 是'每个十字路口都装红绿灯'——安全但贵；Dragonfly+ 是'快速环线配几个大转盘'——高效但容易迷路。没经验时选贵的那个最省钱。"**
