# Q: 网络拓扑怎么选？

## 为什么会有这个问题

光有 IB/RoCE 协议还不够——你怎么把这些链路"组织"成一个网络？**这就看拓扑了。**

你可以把网络拓扑理解为城市交通规划：
- **Fat-Tree** = 网格状道路，哪哪都能到，但路口多
- **Dragonfly+** = 高速环线，跨区快，但设计复杂
- **3D Torus** = 棋盘格，规律整齐，扩展性有限

## 三种主流拓扑

### Fat-Tree（叶脊架构，Clos）

最常用的 AI 集群拓扑。

```
         ┌──────脊层交换机──────┐
         │ Spine 1  Spine 2  Spine 3│
         └──┬──┬──┬──┬──┬──┬──┘
            │  │  │  │  │  │
         ┌──┴──┴──┴──┴──┴──┴──┐
         │ Leaf 1  Leaf 2  Leaf 3│
         ├───┬───┬────┬───┬───┤
         │ GPU│GPU│GPU │GPU│GPU│
         │ 机 │ 机 │ 机 │ 机 │ 机 │
         └───┴───┴────┴───┴───┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **最佳**（任何切分都保证全带宽）|
| 扩展性 | 好（加脊层可扩容）|
| 成本 | 高（需要大量脊层交换机）|
| 维护 | 简单（所有路径等长）|
| 适用 | **90% 的 AI 集群采用此方案** |

**不阻塞拓扑（Non-blocking）**：如果脊层交换机的总带宽 ≥ 叶层总带宽，网络就是"不阻塞"的——任何 GPU 之间通信都有满带宽。

### Dragonfly+

每组是一个"龙组"，组内全互联，组间通过少量链路互连。

```
  ┌─────────────────────────────┐
  │ Dragonfly Group 1           │
  │  ┌───┐ ┌───┐ ┌───┐         │
  │  │GPU│ │GPU│ │GPU│───互联线──│──→ Group 2
  │  └───┘ └───┘ └───┘         │
  └─────────────────────────────┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **中等**（跨组通信有竞争）|
| 扩展性 | **最好**（可以到百万节点）|
| 成本 | 低（比 Fat-Tree 少 40% 线缆）|
| 路由 | 复杂（需要自适应路由避免拥塞）|
| 适用 | **万卡以上、成本敏感的集群** |

**优点**：用更少的交换机连接更多的 GPU。
**缺点**：跨组通信的延迟和带宽不一致，需要智能路由算法。

Meta 和 Google 的万卡集群部分采用了 Dragonfly+ 变体。

### 3D Torus

Google TPU 的招牌拓扑。

```
            ┌───────┐
            │ TPU   │────→ TPU (X方向)
            │       │
            │   │   │
            │   ↓   │
            │ TPU←──│────→ TPU (Y方向)
            └───────┘
```

| 特点 | 说明 |
|------|------|
| 对分带宽 | **受限**（取决于切分方向）|
| 扩展性 | **好**（3 个方向无限扩展）|
| 成本 | 最低（只需要邻居链路）|
| 路由 | 确定性（已知的最短路径）|
| 适用 | **TPU Pod 自有** |

Google TPU v7（Ironwood）的 3D Torus 可以扩展到 **9,216 个 TPU 在一个 Pod 内全互联**。

## 2026 年的选型建议

| 集群规模 | 推荐拓扑 | 理由 |
|---------|---------|------|
| < 512 GPU | Fat-Tree（单脊层） | 简单，不阻塞，运维容易 |
| 512 - 4,096 GPU | Fat-Tree（多脊层） | 扩展性好，可分段建设 |
| 4,096 - 16,384 GPU | Fat-Tree 或 Dragonfly+ | 看预算，Fat-Tree 保险但贵 |
| > 16,384 GPU | Dragonfly+ 变体 | 只有这个选项性价比可行 |
| TPU Pod | 3D Torus | Google 固定方案 |

## 现实中怎么设计？

从需求倒推：

```
已知：
  - 1,000 张 H100 GPU
  - 每 GPU 需要 400 Gb/s 网络带宽
  - 采用 Fat-Tree 拓扑

计算：
  1. 服务器数：1,000 ÷ 8 = 125 台
  2. 每台 8 × 400G NIC = 3.2 Tb/s 上行
  3. 叶层交换机：125 × 3.2 Tb/s ÷ 64 × 400G = 需要 50 台 64 端口交换机
  4. 脊层交换机：50 × 400G = 20 Tb/s 脊层转发能力
  5. 脊层交换机数量：20,000 ÷ (64 × 400G) ≈ 8 台
```

## 🛠 实操指南

### 📋 决策指南：你的网络拓扑该选哪种？

**回答这三个问题：**

```
Q1: 你的集群是单租户还是多租户？
  单租户（一个团队独占） → Fat-Tree 或 Dragonfly+
  多租户（多个团队共享） → Fat-Tree（脊层做隔离更简单）

Q2: 你更关注成本还是确定性？
  成本优先 → Dragonfly+（省 40% 线缆）
  性能确定性优先 → Fat-Tree（不阻塞）

Q3: 你打算扩展到多大？
  不超过 4,096 GPU → Fat-Tree 是最保险的选择
  > 16,384 GPU → Dragonfly+ 几乎是唯一经济可行的方案
```

### 🔧 自己动手验：你的网络拓扑有什么问题？

```bash
# 1. 检查你的拓扑是否能达到"不阻塞"
# 以 Fat-Tree 为例：脊层端口数 × 每端口带宽 ≥ 叶层总上行带宽

# 2. 检查实际 All-Reduce 带宽是否和理论一致
# 在 N 个节点上跑 nccl-tests，逐步增加节点数
# 如果每加一倍节点，带宽减半 → 说明脊层带宽不足（过订阅）

# 3. 用 NCCL 的拓扑感知验证
NCCL_DEBUG=INFO mpirun -np 64 all_reduce_perf -b 256M -e 256M 2>&1 | grep "Ring"
# 看 NCCL 是否选择了正确的 Ring 路径
```

### ⚠️ 常见误区

- **误区**："Fat-Tree 太浪费交换机端口了，Dragonfly+ 更高效"
  - **实际**：Fat-Tree 的"浪费"换来的是**运维确定性**——任何路径长度相等，故障排查简单。Dragonfly+ 省了 40% 线缆，但要承担自适应路由的复杂度。**如果你的团队没有网络专家，Fat-Tree 比 Dragonfly+ 更可靠。**
- **误区**："过订阅（Oversubscription）没关系，AI 训练不是所有 GPU 同时通信"
  - **实际**：All-Reduce 就是**所有 GPU 同时同步数据**——这是集体通信，不是点对点随机通信。过订阅的拓扑在 All-Reduce 场景下会导致严重的性能下降。
- **误区**："我的拓扑以前跑 HPC 没问题，跑 AI 训练应该也行"
  - **实际**：HPC 任务通常是"各自算各自的，偶尔交换结果"。AI 训练是"每轮迭代所有人都要同步"。同样的拓扑、同样的带宽，AI 训练可能比 HPC 慢 2-3 倍。

### 📊 底线数字速查

| 拓扑类型 | 最大规模（推荐） | 对分带宽 | 线缆成本 | 运维复杂度 |
|---------|----------------|---------|---------|-----------|
| 单脊层 Fat-Tree | 256-512 GPU | 100% | 中等 | **低** |
| 多脊层 Fat-Tree | 512-4,096 GPU | 100%（可配置） | 高 | 中等 |
| Dragonfly+ | 4,096-100K+ GPU | 60-80% | **低**（省 40%） | **高** |
| 3D Torus | 有限（9,216 TPU） | 方向相关 | **最低** | 中等 |

### 💡 一句话记住

> **"Fat-Tree 是'每个十字路口都装红绿灯'——安全但贵；Dragonfly+ 是'快速环线配几个大转盘'——高效但容易迷路。没经验时选贵的那个最省钱。"**
