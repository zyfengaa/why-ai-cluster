# Q: InfiniBand 和 RoCEv2 到底有什么区别？

## 为什么会有这个问题

上篇讲到 RDMA（Remote Direct Memory Access，远程直接内存访问）是 AI 集群网络的基石。RDMA 允许一台机器直接读写另一台机器的内存（GPU 显存），完全绕过 CPU——这就避免了"CPU 做中转"的延迟。

RDMA 有两种技术路线：

| 方案 | 全称 | 底层硬件 | 一句话 |
|------|------|---------|--------|
| **InfiniBand** | 原生 RDMA 网络 | **专用**交换机和 HCA 卡 | 为 RDMA 而生，一切硬件都为这个目标设计 |
| **RoCEv2** | RDMA over Converged Ethernet | **标准以太网**交换机 + 网卡 | 在普通以太网上跑 RDMA（UDP 封装） |

这个区别听起来像"专用工具 vs 通用改造"，但实际上它们的差距比这个名字要深刻得多。

---

## 核心差异：信用流控 vs PFC

### InfiniBand：先确认，再发送（信用流控）

InfiniBand 的流控原理类似于**你在电话里订外卖**：

```
用户（发送方）→ 商家（接收方）：
  "喂，我现在有 4 份菜（数据包）要送，你那里能接多少？"

商家（接收方）→ 用户（发送方）：
  "我现在可以接 3 份，你送吧。"

用户 → 商家：送出 3 份
商家 → 用户：吃完 1 份，释放 1 个位置 → "现在还可以再接 1 份"
[循环，直到所有数据送完]
```

**关键**：发送方从不去做"我猜你能收到"的假设。**每一次发送都基于接收方明确确认的容量。** 这就叫"基于信用的链路级流控"（credit-based link-level flow control）。

结果是：InfiniBand 网络**天生是无损的**。数据包永远不会因为"接收端缓冲区满了"而被丢弃。

### RoCEv2：先发出去，堵了再刹车（PFC）

RoCEv2 没有链路级的信用机制。它就像**高速公路上的车流**：

```
正常情况：车流畅通

高峰期：某出口堵了
  出口 1 堵塞 → 车辆排到主路 → 影响出口 2 → 影响出口 3
  交警（PFC）发出 PAUSE 帧："入口暂停放行！"
  结果：所有入口都暂停了，包括不需要去出口 1 的车辆
  
PAUSE 帧传播效果：
  GPU 1 ──→ 交换机 A ──→ 交换机 B ──→ 交换机 C ──→ GPU 2
               ↓
          缓存满了
               ↓
         上游 PAUSE → 传播到 32 个端口
               ↓
         不相关的流量也一起减速
               ↓
         ┌─────────────────────────────────┐
         │      PFC 风暴！                  │
         │  不是只有堵了的那条路受影响       │
         │  整个集群的 RDMA 都可能降速       │
         └─────────────────────────────────┘
```

这个机制叫 **PFC（Priority Flow Control，优先级流控）**。它是 RoCEv2 实现"无损"的方式——不是预防丢包，而是**丢包前紧急叫停**。问题是，PFC 的"叫停"会级联扩散，影响范围可能远超拥堵点本身。

## 一个真实的 PFC 风暴案例

2024 年，国内某云计算公司为其内部大模型团队搭建了一个 2,048 卡 H100 集群，采用 RoCEv2 网络。

**症状**：训练程序每隔 2-3 天就会卡死一次。NCCL 日志显示：`NCCL WARN Net : Socket creation failed`，或者 `NCCL WARN Call to connect returned Connection timed out`。

**排查过程**：
1. 第一反应是检查 GPU —— 两张卡有问题，换掉，问题依旧
2. 检查光纤 —— 发现 3 根光纤的 RX 光功率偏低（-12 dBm，正常应 > -8 dBm），更换，问题依旧
3. 终于想起来看网络计数器

```
# 通过 ethtool 查看 PFC 计数器
ethtool -S eth0 | grep pause
     rx_pause: 4,287,613,941     ← 收到了 42 亿次 PAUSE 帧
     tx_pause: 3,196,542,178     ← 发出去 31 亿次 PAUSE 帧

# 对比正常值
# 正常运行的集群：rx_pause 和 tx_pause 应在百万级别以下
# 这个集群：几十亿次，说明整个网络处于持续的 PFC 风暴中
```

**根因**：存储流量和 GPU 训练流量被分配到了同一个 PFC 优先级队列，存储的突发写入（Checkpoint 触发时）占满了交换机缓存，导致所有 GPU 间的 RDMA 流量都被 PFC 暂停。

**修复**：将存储流量和 GPU 流量分到不同的 PFC 优先级队列，并调整 ECN 标记阈值。修复后 PFC 计数器从每小时数亿次降到百万次级别，训练不再卡死。

但这个故事反映了一个现实：**生产环境中 RoCE 网络的问题往往不是"某个参数错了"，而是"几个参数的组合效应恰好踩到了坑"。**

## 关键规格对比（带实际含义）

| 特性 | InfiniBand (NDR) | RoCEv2 | 实际影响 |
|------|-----------------|--------|---------|
| 交换机延迟 | **~260-300 ns**（直通式） | ~500-1000 ns（存储转发） | 单跳差 ~500ns，**10 跳差 5μs**，累积在万卡通信中不可忽略 |
| 端到端延迟 | **~0.9 μs** | ~1.5-3 μs（调优后） | All-Reduce 的 barrier 等待时间，直接影响 MFU |
| 丢包恢复 | 链路级信用流控，几乎不丢包 | 端到端重传，毫秒到秒级 | RoCE 一次丢包会拖慢整组等待重传的卡 |
| 拥塞控制 | 集中式子网管理器 + 转发自适应 | ECN + DCQCN，需调参 | 调优周期：IB 基本即插即用 vs RoCE 需要专门验证 |
| 多路径 | 支持自适应路由（自动均衡） | 标准 ECMP 按哈希选路；RoCEv2 协议本身**不禁止**自适应路由（NVIDIA Spectrum-X 就支持逐包自适应路由） | ECMP 哈希冲突 → 多条流挤到同一路径 → 局部拥塞 |
| 单个子网规模 | 16-bit LID，单子网单播约 **4.8 万端**上限；更大规模靠 subnet router 拆子网互联 | **没有协议层硬上限**，取决于路由/ARP/ECMP 设计，实践中可达数万节点（Meta 的 24,576 卡 RoCE 集群就是一套三层以太网） | 两边都要认真设计，别信"IB 无限"或"RoCE 只能 2,000 节点"的传说 |
| 成本 | 端到端专用硬件 | 复用以太网生态 | 不同规模/配置下差价差异很大，**没有"固定便宜 50-70%"的规律**，请按实际报价核算 |

## 性能差距：怎么测、心里有数

网上流传的"IB vs RoCE 吞吐对比表"大多无法溯源，建议**在自己的集群上实测**。方法是跑 nccl-tests，对比 busbw（每卡口径）：

| 配置 | 经验期望值（每卡 busbw） |
|------|------------------------|
| 单机 8×H100（NVLink 域） | > 400 GB/s |
| 2 节点 16×H100 + IB NDR400 | ~40-50 GB/s（受单端口 50 GB/s 单向限制） |
| 2 节点 16×H100 + RoCEv2 400G（调优后） | ~40-48 GB/s，约为 IB 的 85-95% |
| 2 节点 16×H100 + RoCEv2 400G（未调优） | 可能只有调优后的一半 |

**结论**：跨机 All-Reduce 的上限被 400G 单端口卡死（50 GB/s 单向），IB 和调优好的 RoCE 差距不大；**真正的差距在稳定性、运维成本和故障恢复**——这也是下一章的主题。

## 实际调优 RoCE 需要的步骤

一份通用的 RoCE 集群调优清单：

```
Week 1: 基础搭建
  - 交换机固件升级（1 天）
  - PFC 队列分配：GPU 流量 → 优先级 3，存储 → 优先级 4，管理 → 0
  - DCQCN 初始参数（标准定义）：
      α：收到 CN 通知后的降速比例因子，取值 0–1（先取小值如 0.2–0.4）
      g：速率恢复阶段的增速因子，典型 1/256–1/16
      RAI（Rate Adjustment Interval）：速率调整间隔，常见约 55 μs
  - MTU 设置为 9000（jumbo frames），否则吞吐损失明显

Week 2: 迭代调优
  - 跑 nccl-tests all_reduce_perf 观察 busbw（每卡口径）
  - 如果 busbw 低于期望值 20%+：
    调整 ECN 标记阈值（从较小的标记门限开始试）
    调整 DCQCN 的速率恢复参数
  - 在真实训练负载上跑 12h+：
    监控 PFC 计数器（ethtool -S）
    如果 rx_pause > 1M/小时，继续调
  
Week 3+: 稳定性验证
  - 引入存储流量，检查 PFC 风暴是否触发
  - 模拟链路故障，验证恢复时间
  - 持续监控，建立告警基线
```

一个经验丰富的网络工程师做完这一套大约需要 **2 周以上**。而 InfiniBand 集群上电后，网络工程师只需要验证子网管理器自动发现拓扑就完成了——**几个小时**。这就是"调优成本"的来源。

## 到底选哪个？

没有放之四海而皆准的答案，但有一个经过大量实践检验的决策框架：

```
你的集群规模：
  < 100 GPU   → RoCE 完全够用（生态开放，成本低）
  100-500 GPU → 两种都可行，看团队能力
  > 500 GPU   → 两种都有大规模先例，关键变量变成了"团队"
      （Meta 用 RoCE 跑了 24,576 卡；更多公司在大规模选 IB；
        xAI 用 Spectrum-X 以太网跑到了 10 万卡级别）
      
你的团队：
  有 3+ 资深网络工程师且熟悉 RDMA → RoCE 是合理选项
  没有 → IB 的"开箱即用"通常更省钱（省下的运维与中断损失 > 硬件差价）
```

## 🛠 实操指南

### 📋 决策指南：我怎么选 IB 还是 RoCE？

用这个简单的决策树：

```
你的团队有 3+ 名熟悉 RDMA 的网络工程师吗？
├─ 有 →
│  你能接受"持续调优 + 定期回归验证"吗？
│  ├─ 能 → 两种都可以，按成本和供应链选
│  └─ 不能 → 选 IB
└─ 没有 →
   你的集群 > 100 GPU 吗？
   ├─ 是 → 选 IB（你付不起 RoCE 的隐性成本）
   └─ 否 → RoCE 够用
```

### 🔧 自己动手验：你的 RoCE 集群健康吗？

```bash
# 1. 检查 PFC 风暴风险（所有 GPU 节点执行）
ethtool -S eth0 | grep -E "rx_pause|tx_pause"
# 期望：每小时增量 < 100 万次
# 如果 > 1,000 万次/小时 → PFC 风暴进行中

# 2. 检查 RDMA 流量是否真的在走
cat /sys/class/infiniband/*/ports/1/counters/port_rcv_data
# 这个计数器不动 → 你的 RDMA 链路可能没工作

# 3. 检查 NCCL 实际走的传输
NCCL_DEBUG=INFO mpirun -np 8 all_reduce_perf -b 256M -e 256M 2>&1 | grep "NCCL INFO"
# "via NET/IB" 或 "via NET/GDRDMA" = RDMA 生效
# "via NET/Socket" = NCCL 退回了 socket 传输（慢！）
```

> **注意区分**：`NET/Socket` 是 **NCCL 在 RDMA 不可用时的回退**——这是 NCCL 的行为，不是 RoCEv2 的。RoCEv2 本身是 UDP 封装的 RDMA 协议，**不存在"TCP 回退"这种机制**。

### ⚠️ 常见误区

- **误区**："RoCE 比 IB 便宜 X%，选 RoCE 肯定是省钱的"
  - **实际**：硬件报价通常 RoCE 低一些，但比例随规模、配置、供应商差异很大，没有"固定便宜 50-70%"的规律。运维成本 + 训练中断损失可能吃掉甚至反超硬件差价。**TCO 要按自己的报价和团队情况算，别套用别人的百分比。**
- **误区**："ECMP 哈希可以把流量均匀分配到所有路径"
  - **实际**：ECMP 按流的五元组哈希分配，多条并行 All-Reduce 流可能哈希到同一条链路，造成局部拥塞。缓解办法是自适应路由——IB 支持它，**RoCEv2 协议本身也不禁止它**（NVIDIA Spectrum-X 这类以太网方案就提供逐包自适应路由），只是传统 RoCEv2 交换机通常只做 ECMP。
- **误区**："我们的网络团队很厉害，RoCE 调优没问题"
  - **实际**：RoCE 调优不是"一次搞定"——每次换固件、换光模块、换交换机型号、增减节点，都要重新验证 PFC 行为。**IB 是"配好就不动"，RoCE 是"每次变更都要回归验证"。**

### 📊 底线数字速查

| 指标 | 正常 | 预警 | 故障 |
|------|------|------|------|
| PFC rx_pause 增量速率 | < 100 万/小时 | 100 万-1,000 万/小时 | > 1,000 万/小时 |
| NCCL busbw（2 节点 RoCE 400G，每卡口径） | > 40 GB/s | 30-40 GB/s | < 30 GB/s |
| NCCL busbw（2 节点 IB NDR400，每卡口径） | > 45 GB/s | 35-45 GB/s | < 35 GB/s |
| 光模块 RX 光功率 | > -8 dBm | -8 ~ -12 dBm | < -12 dBm |
| 交换机温度 | < 65°C | 65-75°C | > 75°C |
| 端到端节点间 RDMA 延迟 | < 2 μs | 2-5 μs | > 5 μs |

### 💡 一句话记住

> **"IB 是打专线电话（先确认再发），RoCE 是发快递（先发了再说）。快递便宜，但你要自己雇一队调度员；专线贵，但接线员是人家配好的。"**
