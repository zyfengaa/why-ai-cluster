# Q: 什么情况下大集群应该选 InfiniBand？

## 为什么会有这个问题

上篇对比了 IB 和 RoCE 的技术差异。按照直觉，RoCE 复用以太网生态、成本通常更低，似乎应该是更好的选择。但现实是——**Meta 用 RoCE 跑了 24,576 卡，xAI 用 Spectrum-X 以太网跑到了 10 万卡级，Google 用自家 ICI，AWS 用 EFA。IB 并不是大规模 AI 集群的唯一选择。**

那 IB 靠什么立足？**靠的是"确定性"：硬件无损、集中式路由管理、开箱即用。** 对于强通信、低延迟敏感、又没有庞大网络团队的场景，这种确定性值得付溢价。本章讲清楚：这份溢价到底买到了什么、什么情况下值得买。

---

## 三大现实问题：每一个都是钱的问题

### 问题 1：PFC 风暴的连锁灾难

之前我们已经讲过了 PFC 的原理。现在来看它在生产环境中的真实后果。

**国内某头部云厂商的 RoCE 集群事故报告（2024年）：**

```
集群规模：3,200 张 A100
网络拓扑：2 级 Clos，RoCEv2

现象：
  - 训练运行稳定时，PFC 暂停帧约 50 万次/小时（属于正常范围）
  - 一旦存储系统开始写 Checkpoint（每 45 分钟一次）：
    - 存储服务器涌出发送请求
    - 交换机缓存瞬间被填满
    - PFC PAUSE 帧爆发：从 50 万/小时飙升到 2 亿/小时
    - PFC 风暴扩散到整个 Pod（1,024 个端口）
    - 所有 GPU 间的 RDMA 通信暂停 3-8 秒
    - （NCCL watchdog 默认超时是 1,800 秒即 30 分钟，
      短时暂停不会触发崩溃——但累积效应严重）

后果：
  - 每次 Checkpoint 触发一次"微中断"：训练不崩溃，但 MFU 从 38% 跌到 12%
  - 持续时间：约 5-8 秒（直到存储写入完成）
  - 每 45 分钟一次，一天 32 次，每天损失 ~4 分钟的全集群算力
  - 3,200 卡 × $3.5/小时 × 4 分钟/天 × 30 天 = $22,400/月 直接损失
  - 还不算工程师排查问题的时间成本（3 人 × 2 周 = 6 人周）
```

**更糟糕的情况**：如果 PFC 风暴导致某张 GPU 的梯度同步超时，整个训练任务崩溃，需要从上一个 Checkpoint 恢复：

```
训练崩溃一次：
  1. 检测到 NCCL 超时 → 所有 GPU 停止
  2. 重新加载 Checkpoint（~3 分钟）
  3. 重新建立 NCCL 通信（~1 分钟）
  4. 跳过已经训练过的 batch（~2 分钟重新计算）
  总损失 = 6 分钟 × 3,200 GPU = 19,200 GPU 分钟 ≈ $1,120

每月 2-3 次崩溃 = $2,800-3,360
加上前面说的性能损失 $22,400/月
RoCE 的"隐形成本"：约 $25,000/月 只针对这个 3,200 卡集群
```

**这些费用并没有出现在采购合同里。**

### 问题 2：故障频率与故障恢复——数据说话

万卡级训练到底会遇到多少故障？Meta 的 Llama 3 论文给了目前最完整的一手数据（16,384 GPU 训练 405B）：

```
54 天训练周期内：419 次意外中断（约 7.8 次/天）
其中约 78% 归因于硬件问题
网络相关的中断约 0.65 次/天（54 天约 35 次）
```

这些"故障"包括：光模块退化、光纤折损、端口误码率升高、交换机温度过高导致的端口震荡…… 都不是"坏了"而是"偶尔抽风"。规模越大，"偶尔抽风"越是常态。

**问题是如何处理这些故障：**

```
InfiniBand 遇到链路故障：
  子网管理器检测到链路变化（毫秒级）
  → 自动重新计算路由表
  → 流量切换到备用路径
  → NCCL 继续跑，训练基本无感
  → 训练不中断  ← 关键

RoCEv2 遇到链路故障：
  依赖链路层/路由收敛 + 端到端 RDMA 重传（毫秒到秒级）
  → 注意：ECN 只做拥塞信号，不做链路故障检测；
    RoCEv2 也没有"TCP 回退"这回事（它不是 TCP）
  → 收敛期间流量黑洞或重传风暴 → NCCL 等待超时的概率更高
  → 训练崩溃的风险更高（取决于调优与监控水平）
```

Meta 自己在论文里给出的解法也印证了这一点：他们开发了定制的 NCCL 调优与故障快速定位工具，把每次中断的平均排查时间压缩下来——**这是只有顶级网络团队才养得起的"人力换确定性"**。

### 问题 3：排错难度与"黑盒"困境

一个典型的对比。某 AI 公司 2024 年采购了两套集群：

```
集群 A：512 卡 H100 + InfiniBand（NDR）
集群 B：512 卡 H100 + RoCE（华为 CloudEngine 等以太网方案）

对比项：
  A 的网络团队：1 人（兼职），主要负责交换机固件升级和光模块管理
  B 的网络团队：3 人（全职），每天处理 RDMA 性能相关工单

典型问题对比：
  A 的网络问题："交换机风扇报警"（换风扇，5 分钟）
  B 的网络问题：
    - "今天训练慢了 15%": 排查从 NCCL 参数 → 交换机 ECN 阈值 → 光模块功率 → 光纤损耗 → PFC 优先级配置
    - "某个节点的 All-Reduce 比其他节点慢 30%": 发现该节点的网卡固件版本和交换机不兼容
    - "存储 Checkpoint 时训练卡顿": 调整 PFC 队列映射（第二天又出别的问题）
```

公司最后得出的结论："买 IB 多花的钱，省下的运维成本在 6 个月内就回来了。"

## 国产路线：另一组选项

对中国客户来说，除了进口 IB 与标准 RoCE，还有国产路线：**华为 CloudEngine 数据中心以太网（RoCE）/ UnifiedBus 超节点互联**，以及部分厂商的 IB 类自研方案。

选国产方案时的原则不变：
- 要求厂商提供与你规模相近的**可验证实测数据**（busbw、故障率、恢复时间），而不是宣传数字；
- 注意 IB 类方案的单子网端点规模受 16-bit LID 约束（单子网约 4.8 万端），跨子网要靠 subnet router 或等效机制；
- 把调优人力和故障恢复时间计入 TCO，而不是只比硬件报价。

## 选型：算一笔总账（TCO）

以 **2,048 卡 H100 集群运行 3 年** 为场景。按 $3.5/GPU-hour 计算，整集群的分钟成本 = $3.5 × 2,048 ÷ 60 ≈ **$119.5/分钟**（不是「每 GPU 分钟」）。

| 成本项 | IB 方案 | RoCE 方案 |
|--------|--------|----------|
| 网络硬件（网卡+交换机+线缆） | $12.29M（$6,000/卡 × 2,048） | **$7.17M**（$3,500/卡 × 2,048） |
| 网络工程师（3 年） | **$0.75M**（1 人 × $250K） | $2.25M（3 人 × $250K） |
| 训练中断损失 | **≈$0.04M**（0.3 次/月 × 36 月 × 20 min） | ≈$0.17M（2 次/月 × 36 月 × 20 min） |
| **3 年 TCO** | **≈$13.1M** | **≈$9.6M** |

**一个反直觉的结论**：按这个（对 RoCE 相当宽松的）假设算，**RoCE 的 3 年 TCO 反而更低**——硬件差价（≈$5.1M）大于人力与中断的隐性成本（≈$2.4M）。网上流传的"RoCE 三年要花 $12.3M"之类的算法，很多来自错误的计算（比如把 $/h 乘以分钟数却忘了除以 60，或引入无来源的修正系数）。**你自己算 TCO 时，务必检查量纲：$/h × 分钟 ÷ 60 才是 $。**

那 IB 溢价 $3.5M 买到了什么？**确定性**：没有 PFC 风暴、集中式路由、免调优、故障自动绕行。如果你的训练任务中断一次损失千万级（比如临近收尾的 run）、或者你没有 3 个全职 RDMA 工程师，这个溢价是值的；反之，有强网络团队的公司用 RoCE 完全算得过账。

## 🛠 实操指南

### 📋 决策指南：你的公司该选 IB 还是 RoCE？

**做决策前先按上面的方法算你自己的 TCO 账：**

```python
# 一个透明的 TCO 计算模型（量纲已修正）
def tco_compare(gpu_count, years=3):
    # 每卡后端网络成本（网卡 + 交换机端口 + 线缆摊销）
    net_cost_ib   = gpu_count * 6000   # $/GPU
    net_cost_roce = gpu_count * 3500   # $/GPU

    # 网络工程师人力
    eng_cost_ib   = 1 * 250000 * years
    eng_cost_roce = 3 * 250000 * years

    # 训练中断：GPU 分钟成本 = $3.5/GPU-h ÷ 60
    gpu_min_cost = 3.5 * gpu_count / 60          # $/GPU 分钟
    outage_min_ib   = 0.3 * 12 * years * 20      # 中断次数/月 × 月数 × 恢复分钟
    outage_min_roce = 2.0 * 12 * years * 20
    outage_cost_ib   = outage_min_ib * gpu_min_cost
    outage_cost_roce = outage_min_roce * gpu_min_cost

    tco_ib   = net_cost_ib   + eng_cost_ib   + outage_cost_ib
    tco_roce = net_cost_roce + eng_cost_roce + outage_cost_roce
    return tco_ib, tco_roce

# 2,048 卡、3 年：
# IB   ≈ $13.1M（硬件 12.29 + 人力 0.75 + 中断 0.04）
# RoCE ≈ $9.6M （硬件 7.17 + 人力 2.25 + 中断 0.17）
```

**经验法则**：如果你没有现成的 RDMA 专家团队、且训练中断的业务代价高（大模型收尾阶段、对外 SLA），**500 GPU 以上直接选 IB**通常更稳妥；如果你有强网络团队并愿意持续投入，RoCE/Spectrum-X 类以太网的账也算得平。

### 🔧 自己动手验：你的集群会不会被 PFC 风暴拖垮？

```bash
# 第一步：在所有交换机的所有端口上读取 PFC 计数器
#（不同交换机命令不同，以下以 Mellanox / NVIDIA 交换机为例）
mlxreg -d /dev/mst/mt4123_pciconf0 --reg_name PPFC 0x0.0:1

# 第二步：如果 PFC 计数器在 1 小时内增长超过 100 万，做流量分离
# GPU 流量 → 优先级 3，存储流量 → 优先级 4
# 确保 NCCL 流量不在 PFC 队列里和存储抢缓存

# 第三步：建立告警
# 任何端口的 rx_pause 增长率 > 1M/小时 → 自动告警
# 连续 10 分钟 > 5M/小时 → PFC 风暴进行中，自动通知值班
```

### ⚠️ 常见误区

- **误区**："我们集群才 200 卡，用 RoCE 完全没问题"
  - **实际**：200 卡没问题，但你要问一个更重要的问题——**你明年会不会扩展到 500 卡、1,000 卡？** 如果会，现在定型时要考虑未来改造的代价。网络不像 GPU——不能按月扩容。
- **误区**："IB 太贵了，多花几百万不值"
  - **实际**：TCO 算下来 RoCE 往往更低，但 IB 溢价买到的是**确定性和免调优**。这不是"谁对谁错"，而是"你的团队和业务能不能消化 RoCE 的复杂度"。
- **误区**："头部互联网公司用 RoCE 跑通了，我们照抄就行"
  - **实际**：头部公司有数百人的自研网络团队和自研集合通信调优能力。你的团队有这个规模吗？**没有的话，把他们的结论当成"RoCE 可行"的证据，而不是"RoCE 省心"的证据。**

### 📊 底线数字速查

| 指标 | 安全 | 注意 | 危险 |
|------|------|------|------|
| PFC 风暴导致训练中断频率 | 0/月 | < 1/月 | ≥ 1/月 |
| IB 子网管理器路由切换延迟 | < 10ms | 10-50ms | > 50ms |
| 万卡集群意外中断频率（Meta 16K 实测口径） | — | 约 7.8 次/天（其中网络相关约 0.65 次/天） | 你的集群显著高于此值 |
| 单光纤链路日故障率 | < 0.1% | 0.1-1% | > 1% |

### 💡 一句话记住

> **"大集群选 IB，买的不是带宽，是确定性——免调优、集中管控、故障自动绕行。有强网络团队、能消化复杂度的公司可以省下这笔钱；没有的话，确定性就是最便宜的选项。"**
