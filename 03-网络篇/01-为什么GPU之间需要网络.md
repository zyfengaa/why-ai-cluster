# Q: 为什么 GPU 之间需要网络？

## 为什么会有这个问题

NVLink 很强，但 NVLink 线缆最长只能到 ~0.5 米（机箱内部）。当集群从 8 卡扩展到 64 卡、1,000 卡时，你**必须通过服务器间的网络来传输数据**。

这里有一个很多人都忽视的问题：**NVLink 虽然带宽高达 900 GB/s，但它只覆盖了你集群通信中大约 1/3 的流量。** 剩下的 2/3 通信量——跨机 All-Reduce、梯度同步、参数广播——全部要走网络。

### 规模的决定性

来看一个真实的集群架构。xAI 在 2025 年搭建的 Grok 4.0 训练集群——**20 万张 H100 GPU** — 它的网络设计是这样的：

```
每个计算节点：8 张 H100
每个机架：2 个计算节点（16 GPU）
每个 Pod：64 个机架（1,024 GPU）
总规模：约 200 个 Pod（200,000+ GPU）

每张 H100 配 9 张 ConnectX-8 400G 网卡
每台服务器：72 × 400G = 28.8 Tb/s 上行带宽
    
这只是一个例子。更常见的 1,000 卡集群会是这样：
```

| 集群规模 | GPU 数 | 服务器数（8卡/台） | 网络端口数 |
|---------|--------|-----------------|-----------|
| 小规模 | 8 | 1 | 仅 NVLink |
| 中等规模 | 64 | 8 | 64 × 400G |
| **典型大模型项目** | **1,024** | **128** | **1,024 × 400G** |
| Meta Llama 3 | 49,152 | 6,144 | 49,152 × 400G |
| xAI Grok 4.0 | 200,000+ | 25,000+ | 200,000+ × 400G |

**一个 1,024 卡的网络后端就需要超过 1,000 个 400G 端口**。每一个端口、每一根光模块、每一台交换机，都要精心选型。

## 跨机通信的核心场景

### 场景 1：All-Reduce（梯度同步）— 最高频、最敏感的通信

这是 AI 集群中最重要的通信模式。来看一个具体的时间线：

```
时间线（每次训练迭代，单位：毫秒）：

0 ms      50 ms     100 ms    150 ms    200 ms
├──────────┼──────────┼──────────┼──────────┤
███████████████████░░░░░░░░░░░░░░░░░░░░░░░░
│  前向传播（50ms）   │  反向传播（100ms）   │
                      └────────── All-Reduce 梯度同步（50ms）
```

每次迭代都要做一次 All-Reduce。以 Llama 3 70B 训练为例：
- 每张 GPU 每轮迭代产生 ~200 MB 的梯度数据
- 1,024 张卡的 All-Reduce：每轮传输总量 ~200 GB（聚合流量）
- 每秒约 1-3 次迭代 → 每秒 **200-600 GB 网络流量**

如果一次 All-Reduce 因为网络抖动从 50 ms 变成 150 ms，那 MFU 直接跌去 25%。

### 场景 2：Checkpoint 保存 — 低频但毁灭性的写风暴

训练一个 70B 模型（BF16），每 30-45 分钟保存一次 Checkpoint：

```
每次 Checkpoint：
  模型参数：140 GB（70B × 2 bytes）
  Optimizer 状态：280 GB（Adam 需要额外 2 倍）
  总写入量：420 GB 到存储

1,024 卡集群每 45 分钟写一次：
  一天 32 次 Checkpoint
  一天写入总量：13.4 TB
  每次 Checkpoint 写时间 = GPU 闲置时间
```

如果网络/存储带宽不够，每次 Checkpoint 需要 5 分钟 vs 30 秒，一天就多浪费 **2.4 小时**的万卡算力。按 H100 每小时 $3.5 算，一天烧掉 **$8,600**。

### 场景 3：数据加载 — 喂不饱的 GPU

训练时 CPU 负责读取训练数据、做预处理，然后送给 GPU。数据量看一个真实的吞吐需求：

```
1,024 张 H100 训练时，假设：
  - 每张卡 global batch size = 4
  - 序列长度 = 8,192 tokens
  - 每次迭代 = 4 × 8,192 × 2 bytes = 65,536 bytes 数据输入
  - 每秒 2 次迭代

每张 GPU 的数据消耗：131 KB/s —— 这很小，对吧？
但是：
  - 实际数据需要先加载、解压、tokenize、shuffle、batch
  - 原始数据集可能是 10-100 TB（预训练语料）
  - 数据预处理不仅需要带宽，还需要 CPU 算力
  - 训练过程中需要不断读取新数据

所以问题不在于"数据有多大"，而在于：
  存储系统能不能持续以 30+ GB/s 的吞吐输出数据？
```

## AI 训练对网络的极端要求

为什么普通数据中心网络不行？看一个真实对比：

| 要求 | 普通数据中心 | AI 训练集群 | 差距原因 |
|------|------------|------------|---------|
| 带宽 | 10-100 Gb/s 每服务器 | **400-1,600 Gb/s** | GPU 通信量是普通服务的百倍 |
| 延迟容忍 | 1-10 ms | **< 2 μs** | 每次迭代都在同步，延迟直接积少成多 |
| 丢包容忍 | 可重传（TCP 设计如此） | **零容忍** | 一个丢包拖住 1,024 张卡等重传 |
| 流量模式 | 随机、疏密不均 | **周期性 All-Reduce 风暴** | 所有节点同时发请求，同时静默 |
| 可靠性 | 99.9% 链路可用 | **99.9999%** | 0.1% 的故障在万卡上 = 10 张卡永远掉线 |

**一个真实的数字**：2024 年某公司训练 1,200 卡集群，因为 RoCE 网络 PFC 风暴，平均每 3 天训练崩溃一次。每次恢复耗时 30-90 分钟。一个月损失 **400+ GPU 年的算力** = 约 **$350 万浪费**。

## 真实案例：Meta 的 Llama 3 网络怎么搭

Meta 在 2024 年公开了 Llama 3 训练的网络架构。他们的 49,152 GPU H100 集群用了两层设计：

```
集群规模：49,152 H100（6,144 台服务器）
网络方案：混合 RoCE + InfiniBand
  - 计算内网：400G RoCE（2 级 Clos 拓扑）
  - 存储网络：400G RoCE（独立 VLAN）
  - 管理网络：100G 标准以太网

为什么 Meta 选 RoCE 而不是全 IB？
  - Meta 拥有全球最大的数据中心网络团队（数千人）
  - 他们有能力做深度网络调优
  - 成本和供应链考虑（IB 供应受限）

结果：
  - 训练期间达到了良好的 MFU（~38-43%）
  - 但网络团队花了数月时间调优 PFC 参数
  - 小故障（如光模块退化）导致多次训练中断
```

这个故事的关键教训：**只有 Meta、Google 这种级别的公司才能搞定万卡级 RoCE 网络。普通公司买 IB 反而是更省钱的选择。**

## 🛠 实操指南

### 📋 决策指南：你在什么规模需要开始操心网络？

| 你的集群规模 | 你应该关心的事 | 行动建议 |
|------------|--------------|---------|
| 1 台机器（8 GPU） | 几乎不需要操心网络 | 全在 NVLink 域内，Checkpoint 写本地盘 |
| 2-4 台（16-32 GPU） | 需要了解你的网络方案 | 确认网卡类型、交换机型号、链路带宽 |
| 16+ 台（128+ GPU） | **必须专业设计网络** | 找有经验的人做网络规划，不要自己搭 |
| 128+ 台（1,024+ GPU） | 网络决定训练成败 | IB 优先，或请专门的公司做 RoCE 调优 |

### 🔧 自己动手验：你的网络够不够快？

在你的集群上跑一下 NCCL 带宽测试：

```bash
# 单机内测（确认 NVLink 正常）
mpirun -np 8 all_reduce_perf -b 128M -e 256M -f 2

# 跨机测（确认网络正常，N 为总 GPU 数）
mpirun -np N --hostfile hosts all_reduce_perf -b 256M -e 512M -f 2
```

**期望结果速查**：

| 配置 | 期望 busbw | 如果更低说明 |
|------|-----------|------------|
| 8×H100 NVLink 单机 | 460-480 GB/s | GPU/NVLink 可能有问题 |
| 2 节点 H100 + IB NDR400 | 350-380 GB/s | 检查 GDR 是否启用 |
| 2 节点 H100 + RoCEv2 400G | 280-350 GB/s（调优后） | 需要开始调优 |
| 2 节点 H100 + 以太网 TCP | 25-100 GB/s | **严重问题，必须上 RDMA** |

> **注意**：`all_reduce_perf` 是 NCCL-tests 套件中的工具，你可以在 [GitHub - NVIDIA/nccl-tests](https://github.com/NVIDIA/nccl-tests) 找到源码，编译后在集群上运行。这是任何 AI 集群上线的**第一道测试**。

### ⚠️ 常见误区

- **误区**："我的网络是 400G，带宽肯定够"
  - **实际**："400G"是网卡单端口物理速率，实际有效带宽受限于协议、交换机背板、对分带宽、拥塞控制。未调优的 RoCE 可能只能用到 60% 的带宽。
- **误区**："网络延迟 1ms，这么小的影响可以忽略"
  - **实际**：AI 训练每次迭代同步一次，1ms 延迟 × 每秒 2 次迭代 × 训练 30 天 = **5,184 秒 = 1.44 小时的纯浪费等待时间**。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 网络对分带宽 / 总峰值算力 | > 1:1 | 0.5:1 - 1:1 | < 0.5:1 |
| NCCL All-Reduce 带宽利用率 | > 90% | 70-90% | < 70% |
| 跨机 All-Reduce 延迟抖动 | < 5% | 5-15% | > 15% |
| 网络故障导致训练中断频率 | 0/月 | < 1/月 | > 1/月 |

### 💡 一句话记住

> **"AI 集群的网络不是'能通就行'，它决定了你几千万买的 GPU 能用出几分力。"**

## 回到根本问题

网络不是什么"能用就行"的东西。在 AI 集群中，网络直接决定了：
- 你的 MFU 能跑多高（MFU 的损失 40% 来自通信）
- 你的训练能多稳定（网络抖动 = 训练中断的风险）
- 你的团队要多累（IB vs RoCE 运维工作量差 10 倍）

这引出了两个关键技术的选择：**InfiniBand vs RoCEv2**。
