# Q: UEC 1.0 是什么？它要革谁的命？

## 为什么会有这个问题

RoCEv2 的 PFC 风暴和运维难题是 Ethernet 阵营的心病。传统的以太网并不适合 GPU 通信，因为它是为"通用互联网"设计的——可以丢包重传，但对 GPU 来说丢一次包就是性能灾难。

但 **Ethernet 的生态太强大了**——全世界的数据中心网络基础设施都是以太网的。如果能解决 RoCE 的架构性问题，就能在保持价格优势的同时达到 IB 级的性能。

## 解决什么问题

**UEC（Ultra Ethernet Consortium，超级以太网联盟）** 是 2023 年在 **Linux Foundation** 成立的开放标准项目（AMD、Arista、Broadcom、Cisco、Eviden、HPE、Intel、Meta、Microsoft、Oracle 等发起）。**2025 年 6 月 11 日**，UEC 发布了 **1.0 规范**。

UEC 1.0 不是一个"补丁"，而是 **为 AI/HPC 重新设计以太网传输层**：新的 Ultra Ethernet Transport（UET），配合新的拥塞控制（UEC-CC，接收端驱动、基于 ECN），目标是替代 RoCEv2 时代"DCQCN + PFC"的拼凑方案，并扩展到百万端点规模。

### 关键机制：注意哪些是核心、哪些是可选

| 机制 | 解决什么问题 | 状态 |
|------|------------|---------|
| **Packet Spraying（包喷射）/ 熵路由** | ECMP 哈希冲突导致带宽不均 | UET 传输层的**核心设计**：逐包/按熵动态分散到多条路径，接近满链路利用率 |
| **UEC-CC（拥塞控制）** | PFC/DCQCN 的脆弱性 | 核心组成部分：接收端驱动、基于 ECN，目标是**摆脱对 PFC 的依赖** |
| **LLR（链路层重传）** | 丢包→端到端重传太慢 | **可选**能力：链路本地修复丢包，不必惊动发送端 |
| **CBFC（基于信用的流控）** | PFC 风暴的根源 | **可选**能力：类似 IB 的"先确认再发送"，但不是规范强制的核心 |

> 网上很多文章把"LLR + CBFC + 包喷射"并列为"三项强制核心改进"，这是误读——**规范里 LLR 和 CBFC 是可选能力**，包喷射/熵路由和 UEC-CC 才是 UEC 传输层的招牌。

### LLR 为什么有价值（在支持的硬件上）

```
传统 RoCE 丢包处理：
发送方 ──→ 交换机A ──→ 交换机B ──→ 接收方
          数据包丢了！
                                等待接收方发现丢包（RTT）
接收方 ←── 发送 NAK ────────────
发送方 ←── 重传丢失的数据包 ────
整个过程：毫秒到秒级

UEC LLR（可选启用）：
发送方 ──→ 交换机A ──→ 交换机B ──→ 接收方
          数据包丢了！
          交换机B：在链路本地修复（链路层重传）
          接收方：几乎无感知
整个过程：微秒级
```

### 和 RoCEv2 + DCQCN 的差别：到底换了什么

| 维度 | RoCEv2 + DCQCN | UEC 1.0 |
|------|----------------|---------|
| 拥塞信号 | ECN 标记，发送端降速（Kmin/Kmax/Pmax、g、RAI 等） | 接收端驱动的 UEC-CC + ECN |
| 丢包兜底 | 通常依赖 PFC，PFC 风暴是主要运维风险 | 目标摆脱 PFC；CBFC 为可选 |
| 路径利用 | ECMP 流级哈希，冲突时链路不均 | 包喷射/熵路由，逐包分散 |
| 乱序处理 | RoCE 对乱序敏感，重排代价高 | UET 传输层原生处理乱序 |
| 调参对象 | 一组明确的 DCQCN 参数 | 规范不规定同一组旋钮，参数由厂商 SDK 决定 |

**不要把 DCQCN 的参数照搬到 UEC**：两者把拥塞决策放在不同位置（发送端 vs 接收端），旋钮不是一一对应的。UEC 的调优更多取决于网卡/交换机厂商的实现与互操作测试。

### 迁移路径：现有 RoCE 集群怎么走

1. **先确认传输层支持**：交换芯片的 102.4 Tb/s 只是容量，不等于支持 UET；要查网卡/交换机 NOS 的 UEC 特性清单。
2. **升级软件栈**：UEC 需要新的驱动、SDK 与集合通信库配合；NCCL 对 UEC 的支持以你使用的版本为准。
3. **做多厂商互操作测试**：规范发布到"端到端可用"之间，互操作测试比参数表更有说服力。
4. **短期更现实**：RoCEv2 调优 + Spectrum-X 仍是主流；UEC 作为下一代选型的观察项，而不是现在重构网络的理由。

### 硬件支持（公开规格口径）

| 芯片 | 厂商 | 交换容量 | 备注 |
|------|------|---------|------|
| Tomahawk 6 | Broadcom | **102.4 Tb/s** | 面向 AI 的旗舰交换芯片之一 |
| Spectrum-6（SN6000 系列） | NVIDIA | **102.4 Tb/s，800G/端口** | Spectrum-X 平台成员 |
| 1.6T/端口、更高速率 | 各厂商 | — | **下一代**（如 Spectrum-7 / CX-9 级别），不是当前一代 |

> 注意：交换芯片具备高吞吐和某些硬件能力，不等于"端到端 UEC 认证可用"——UEC 1.0 的完整落地还需要网卡、SDK 和软件栈配合，互操作性测试在推进中。

## UEC 和 GSE：不是一回事

一个常见混淆：**UEC 不是"国产 GSE"，两者是独立并行的东西。**

- **UEC**：Linux Foundation 旗下的国际开放标准项目，2023 年成立，2025-06-11 发布 1.0 规范。**华为等中国厂商也是 UEC 成员**，中国并非"没有跟进"。
- **GSE（Global Scheduling Ethernet，全局调度以太网）**：**中国移动** 2023 年 5 月牵头提出的另一条并行路线，主要面向国内产业生态，思路是在交换机侧做增强以兼容存量网卡。

| 特性 | UEC | GSE |
|------|-----|-----|
| 主导方 | Linux Foundation 开放项目（全球厂商） | 中国移动牵头的国内路线 |
| 改造深度 | 传输层（UET）+ 拥塞控制整体重写 | 主要改交换机，网卡尽量兼容 |
| 兼容性 | 完整特性需要新硬件/新 SDK | 目标兼容现有标准 RoCEv2 网卡 |
| 包分散 | Packet Spraying（逐包/按熵） | 容器级/流级分散（避免乱序的折中） |
| 生态 | 全球互操作测试推进中 | 主要面向国内 |

GSE 的 **N2N（Network-to-Network）模式** 是一个务实的折中——用"只在交换机层面做创新"来保护现有的网卡投资。两条路线解决的是同一个问题（以太网上的大规模 AI 通信），但**不是同一个标准，也不互为代表**。

## UEC 的影响

### 对 InfiniBand
- UEC 会分走 IB 的部分市场，但不会立刻替代
- IB 生态成熟、运维简单，在"确定性"敏感的场景仍有明显优势
- UEC 硬件生态仍在早期，未来几年 IB 仍会是万卡级集群的主力选项之一

### 对 RoCEv2
- UEC 是 RoCEv2 的"接班人"方向，但 RoCEv2 不会被立即替代
- **存量硬件不要指望纯固件升级**：UEC 1.0 的部分能力（如部分拥塞控制特性）可以在现有以太网 ASIC 上以软件实现，但完整特性（UET 传输层、逐包喷射）需要新硬件与新 SDK 配合
- UEC 解决了 RoCEv2 最被诟病的问题，但运维复杂度不会自动消失

## 🛠 实操指南

### 📋 决策指南：我需要现在就关注 UEC 吗？

**当下的建议**：

| 你的状态 | 建议 |
|---------|------|
| 正在采购新网络 | 关注交换芯片与网卡厂商的 UEC 路线图（Tomahawk 6、Spectrum-6 等新一代芯片是基础），但**不必等 UEC 生态成熟才采购**——先按 IB/RoCE/Spectrum-X 落地，硬件选型上为 UEC 留出演进空间 |
| 已有 IB 网络 | **不动**。IB 生命周期还长，UEC 短期内不会替代 IB |
| 已有 RoCE 网络 | 继续深耕调优；把 UEC 当作 2-3 年后的升级路径评估，不要现在押注 |
| 预算有限的中小集群 | 现在的 RoCEv2 对你够用。UEC 首先解决的是"万卡以上"的问题 |

### 🔧 自己动手验：你的交换机"支持 UEC"吗？

目前 UEC 还没有统一的"UEC Ready"自检命令，判断方法是：

```
1. 查芯片厂商官方公告：交换芯片与网卡是否宣布支持 UEC 1.0
   （Broadcom Tomahawk 6、NVIDIA Spectrum-6 等新一代芯片是基础）
2. 查交换机 SDK / NOS 的 release note：是否包含 UEC 相关特性
   （逐包喷射/熵路由、UEC 拥塞控制等）
3. 查网卡（SuperNIC/DPU）是否提供 UEC 传输所需的 SDK 支持
4. 最可靠的证据是厂商间的互操作测试报告，而不是参数表
```

> **别把"芯片参数够高"当成"支持 UEC"**：102.4 Tb/s 的交换容量是硬件规格，UEC 是协议栈特性，两回事。

### ⚠️ 常见误区

- **误区**："UEC 1.0 发布了，RoCEv2 马上淘汰"
  - **实际**：UEC 1.0 只是规范的起点，端到端部署需要新硬件 + 新 SDK + 互操作性验证。RoCEv2 存量还会运行很多年。
- **误区**："现有硬件刷个固件就能支持 UEC"
  - **实际**：UEC 1.0 的部分能力可以在现有以太网 ASIC 上以软件实现，但**完整特性需要新一代硬件和新 SDK**。任何"纯固件升级即可全面支持 UEC"的承诺都不可信。
- **误区**："UEC 就是 IB 的以太网版"
  - **实际**：UEC 的可选 CBFC 确实借鉴了 IB 的信用思想，但 UEC 的包喷射/熵路由、接收端驱动的 UEC-CC 都是 IB 没有的新设计。**UEC 不是"IB 翻版"，而是"借鉴 IB 部分思想 + 以太网生态"的新协议栈。**
- **误区**："UEC 已经取代/必将全面取代 IB"
  - **实际**：定位不同——IB 是端到端专有方案（含网络、网卡、软件），UEC 是开放以太网标准。未来几年两者会并存，选型取决于运维能力、供应链和成本结构。
- **误区**："UEC 是国产方案 / 中国没有参与"
  - **实际**：UEC 是 Linux Foundation 项目，华为等中国厂商是成员；GSE 才是中国移动牵头的国内并行路线。两者并存，不是同一件事的两个名字。

### 📊 底线数字速查

| 技术 | 成熟度 | 何时要认真考虑 | 风险 |
|------|--------|---------------|------|
| RoCEv2 | 成熟，万卡级验证（Meta 24,576 卡） | 现在 | PFC 风暴、调优复杂 |
| UEC 1.0 | 规范已发布（2025-06-11），生态建设中 | 新一代硬件普及后 | 互操作性与产品成熟度待验证 |
| GSE | 国内并行路线，试点推进 | 国产化要求场景 | 生态局限在国内 |
| InfiniBand NDR | 成熟，万卡级验证 | 现在 | 供应商锁定，成本高 |

### 💡 一句话记住

> **"UEC 不是 RoCE 的补丁，是以太网为 AI 重写的一次传输层——但规范发布到主流部署，历史上从来都是以年计的。当下的选型仍然是 IB vs RoCE（/Spectrum-X），UEC 决定的是你今天买的硬件要不要为它留后路。"**
