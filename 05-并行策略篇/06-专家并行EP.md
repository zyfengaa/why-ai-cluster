# Q: MoE 模型为什么需要专家并行（EP）？

## 为什么会有这个问题

MoE（Mixture of Experts，混合专家模型）是 2025-2026 年大模型的核心架构趋势。它的核心思想：**不激活全部参数，而是根据输入只激活一部分"专家"**。

```
MoE 层结构：
输入 → Router（路由） → Expert 1（激活） → 输出
                      → Expert 2（激活） 
                      → Expert 3（未激活）
                      → Expert 4（未激活）
                      ...
                      → Expert N（未激活）

只有部分 expert 被激活，但所有 expert 都占用显存
```

**核心矛盾**：MoE 模型的总参数量巨大（DeepSeek-V2 有 236B 总参数），但每个 token 只激活一小部分（比如激活 6/160 个 expert）。**用常规的 TP/DP，每张 GPU 都要存储所有 expert 的参数，大量的参数被闲置。**

## 解决什么问题：专家并行（Expert Parallelism，EP）

EP 的核心思想：**把不同的 expert 放在不同的 GPU 上，每个 token 的路由决定它去哪些 GPU 上计算。**

```
EP 方式（EP=4，16 个 expert）：
GPU 0: Expert 0, 1, 2, 3
GPU 1: Expert 4, 5, 6, 7
GPU 2: Expert 8, 9, 10, 11
GPU 3: Expert 12, 13, 14, 15

输入 token 经过路由决定去 GPU 0 和 GPU 2
→ All-to-All dispatch：把 token 发送到目标 expert 所在的 GPU
→ 在目标 GPU 上计算 expert
→ All-to-All combine：把结果送回原 GPU
```

**关键差异**：TP/DP 是**等量切分**——每张 GPU 处理的数据量相同。EP 是**按需分配**——不同 GPU 处理不同数量的 token，取决于路由的分配。

### EP 与 DP 的关系（别把卡数乘错）

EP 不是与 DP 并列的"再乘一维"。在 Megatron 系实现中，**expert-parallel 组通常是从 DP 组的 rank 里组织出来的**：同一份数据并行的多个副本，把各自的 MoE 层改造成"每卡放不同专家"。所以：

```
总卡数仍然 = TP × PP × DP
MoE 时：DP 组的一部分组织能力被 EP 使用（EP ≤ DP×TP，视实现而定）
每张卡依然属于某个 DP 副本，只是它存的专家不同
```

### EP 的通信模式：All-to-All

EP 的通信模式和 TP/DP/PP 完全不同：
- **TP/DP**：All-Reduce（所有 GPU 参与，等量数据交换）
- **PP**：P2P（邻居之间传激活值）
- **EP**：**All-to-All**（每层两次：dispatch 发 token 去 expert 所在卡、combine 收结果）

All-to-All 的代价要点：
1. **每层两次**跨卡全交换，通信量正比于被路由的 token 量（≈ 激活的 token 数 × hidden 大小）；
2. **对网络极敏感**：跨机 All-to-All 受最慢链路拖累，所以 EP 常与"专家放在机内/机架内"的映射策略配合；
3. **负载不均会放大通信**：路由偏斜时，部分卡的 dispatch/combine 队列成为瓶颈。

### 负载不均衡、容量因子与专家复制

- **负载不均衡**：router 偏向某些 expert → 部分 GPU 过载、其余空转。工程手段：auxiliary load-balancing loss（Switch Transformers 引入）或 aux-loss-free 的 bias 调整（DeepSeek-V3/V2 系列）。
- **容量因子（capacity factor）**：给每个 expert 设定容量上限 `capacity = 容量因子 × tokens/expert 均值`；超容的 token 溢出（drop 或 residual 直通）。容量因子大 → 通信与显存开销大、丢 token 少；小则反之。
- **专家复制（expert replication / duplicated experts）**：热点 expert 复制多份放到不同卡上分担流量；或用 "duplicated experts" 填满 EP 组里没排满的卡（MoE Parallel Folding 的做法之一）。

## 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ **显存效率极高**：每张 GPU 只存一部分 expert | ❌ **负载不均衡**：路由可能不均匀，部分 GPU 过载 |
| ✅ **计算效率高**：被激活的 expert 满负荷运转 | ❌ **All-to-All 通信开销大**：每层两次，随 EP degree 增加 |
| ✅ **与 MoE 天生匹配**：不需要把全部 expert 复制到每卡 | ❌ **容量因子要调**：丢 token 与通信开销之间权衡 |
| ✅ **支持超大模型**：DeepSeek-V2 236B 靠 EP 训练 | ❌ **实现复杂**：需要框架级的 dispatch/combine 操作 |

## EP 在 2026 年的实践

### MoE 模型的典型规格

| 模型 | 总参数量 | 激活参数量 | 专家数 | 激活专家/Token |
|------|---------|-----------|--------|---------------|
| Mixtral 8×7B | 47B | 13B | 8 | 2 |
| DeepSeek-V2 | 236B | 21B | 160 | 6 |
| **Qwen2.5-MoE-A14B** | **14.3B** | **2.6B** | **64** | **8** |
| **Qwen2-57B-A14B** | **57B** | **14B** | **64** | **8** |
| GPT-4 MoE（传闻） | ~1.8T | ~280B | — | — |

（注意：Qwen2.5-MoE-A14B 和 Qwen2-57B-A14B 是两个不同模型，不要混用规格；两者都是 64 专家、top-8。）

### EP + TP + PP + CP + DP 的 5D 并行

**Megatron-Core 支持 TP + EP + CP + DP + PP 五维并行**——出自 "MoE Parallel Folding: Heterogeneous Parallelism Mappings for Efficient Large-Scale MoE Model Training with Megatron Core"（**arXiv:2504.14960，2025-04**）。5D 是 TP、EP、CP、DP、PP 这五个维度，**SP（序列并行）不单算一维**（它附着在 TP 组上）：

```
MoE Parallel Folding 的核心洞察：
Attention 层和 MoE 层需要不同的并行策略！
  - Attention 层：适合 TP + CP（切 hidden_dim 和序列）
  - MoE 层：适合 EP（切 expert 维度）
  - 两者用异构的并行映射 + 灵活的 token 路由连接
```

这种"分别优化"的方案在 **128×H100**（论文配置）上：Mixtral 8×22B 达到 **49.3% MFU**，Qwen2-57B-A14B 达到 **39.0% MFU**。

## 🛠 实操指南

### 📋 决策指南：你的 MoE 模型需要 EP 吗？

```
模型使用了 MoE 架构吗？
├─ 否 → 不需要 EP，用 TP+PP+DP 就够了
└─ 是 →
   ├─ 专家总参数 > 单卡显存 → 需要 EP
   ├─ 专家数 < 8 → EP 收益有限，考虑 TP 代替
   └─ 专家数 > 8 → EP 是必须的

EP degree 选择：
  EP ≤ DP 组可用卡数（EP 组从 DP 组内组织，不是额外乘的一维）
  EP 最好是 2 的幂（2, 4, 8, 16...）
  推荐 EP = 专家数 ÷ 每 GPU 存放的专家数（通常 2-8 个/GPU）
  总卡数仍 = TP × PP × DP
```

### 🔧 自己动手验：EP 的负载均衡

```python
# 检查 MoE 路由的负载均衡情况
# 在训练中记录每个 expert 被激活的次数

def check_load_balance(expert_counts, num_experts):
    """expert_counts: list of activation counts per expert"""
    max_load = max(expert_counts)
    min_load = min(expert_counts)
    avg_load = sum(expert_counts) / num_experts
    
    imbalance = max_load / avg_load
    print(f"Expert 激活分布：max/min/avg = {max_load}/{min_load}/{avg_load:.0f}")
    print(f"负载不均衡系数: {imbalance:.2f}（理想 = 1.0）")
    
    if imbalance > 1.2:
        print("⚠️ 负载不均衡明显，检查 aux loss / 容量因子设置")
    if imbalance > 1.5:
        print("❌ 严重不均衡，考虑专家复制或调整 Router")
    
    return imbalance

# 模拟 64 个 expert 的负载
import random
ideal = [100] * 64
check_load_balance(ideal, 64)
unbalanced = [200 if i < 12 else 50 for i in range(64)]
check_load_balance(unbalanced, 64)
```

### ⚠️ 常见误区

- **误区**："EP 是第五个维度，总卡数 = TP×PP×DP×SP×EP"
  - **实际**：SP 附着在 TP 组上、不占卡数；EP 的组从 DP 组内组织（EP ≤ DP×TP 视实现）。**总卡数仍然 = TP×PP×DP**，MoE 场景只是 DP 组的卡以 EP 方式存专家。把五个数相乘会算出根本不存在的集群规模。

- **误区**："MoE 模型的总参数量大，所以一定比稠密模型慢"
  - **实际**：MoE 的速度取决于**激活参数量**，不是总参数量。DeepSeek-V2（236B 总参，21B 激活）的推理速度比 70B 稠密模型更快。**MoE 的代价不在算力，而在显存和 All-to-All 通信。**

- **误区**："EP 的 All-to-All 通信太贵，应该用 TP 代替"
  - **实际**：TP 把每层都切分并在每步做 All-Reduce。对于 MoE 层，TP 需要每张 GPU 存储全部 expert 的切分版本——这抵消了 MoE 最核心的显存优势。**EP 虽然 All-to-All 通信有开销，但在专家数多时（>8），显存节省远大于通信代价。**

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 专家数 | 8-64 | 2-8 或 64-256 | > 256 |
| 激活专家/Token | 2-8 | 8-16 | > 16 |
| EP degree | ≤ DP 组卡数 | 略超 DP 组 | 与 DP 无关地乱设 |
| 负载均衡系数 | < 1.1 | 1.1-1.3 | > 1.3 |
| MoE 层 All-to-All 通信占比 | < 10% | 10-25% | > 25% |
| 容量因子 | 1.0-1.25（丢 token < 1%） | 1.25-2.0 | 溢出率 > 5% 或 CF > 2 |

### 💡 一句话记住

> **"专家并行让每个 GPU 只存一部分专家——token 通过路由、经 All-to-All dispatch/combine 去对应卡上计算。EP 的组从 DP 组里组织出来，总卡数还是 TP×PP×DP；要盯住三件事：负载不均衡、容量因子、热点专家的复制。"**

## 对后续的铺垫

到此为止，你了解了所有的并行策略：
- **DP**：数据并行，复制模型、切分数据
- **TP**：张量并行，切分层内
- **PP**：流水线并行，切分层间
- **SP/CP**：序列/上下文并行，切分激活与 attention 的序列维
- **EP**：专家并行，切分 MoE 专家（从 DP 组内组织）
