# Q: MoE 模型为什么需要专家并行（EP）？

## 为什么会有这个问题

MoE（Mixture of Experts，混合专家模型）是 2025-2026 年大模型的核心架构趋势。它的核心思想：**不激活全部参数，而是根据输入只激活一部分"专家"**。

```
MoE 层结构：
输入 → Router（路由） → Expert 1（激活） → 输出
                      → Expert 2（激活） 
                      → Expert 3（未激活）
                      → Expert 4（未激活）
                      ...
                      → Expert N（未激活）

只有部分 expert 被激活，但所有 expert 都占用显存
```

**核心矛盾**：MoE 模型的总参数量巨大（DeepSeek-V2 有 236B 总参数），但每个 token 只激活一小部分（比如激活 2/16 个 expert）。**用常规的 TP/DP，每张 GPU 都要存储所有 expert 的参数，大量的参数被闲置。**

## 解决什么问题：专家并行（Expert Parallelism，EP）

EP 的核心思想：**把不同的 expert 放在不同的 GPU 上，每个 token 的路由决定它去哪些 GPU 上计算。**

```
EP 方式（EP=4）：
GPU 0: Expert 0, 1, 2, 3
GPU 1: Expert 4, 5, 6, 7
GPU 2: Expert 8, 9, 10, 11
GPU 3: Expert 12, 13, 14, 15

输入 token 经过路由决定去 GPU 0 和 GPU 2
→ 通信（All-to-All 将 token 发送到对应 GPU）
→ 在 GPU 0 上计算 Expert 0-3
→ 在 GPU 2 上计算 Expert 8-11
→ 通信（All-to-All 将结果返回原 GPU）
```

**关键差异**：TP/DP 是**等量切分**——每张 GPU 处理的数据量相同。EP 是**按需分配**——不同 GPU 处理不同数量的 token，取决于路由的分配。

### EP 的通信模式：All-to-All

EP 的通信模式和 TP/DP/PP 完全不同：
- **TP/DP**：All-Reduce（所有 GPU 参与，等量数据交换）
- **PP**：P2P（邻居之间传激活值）
- **EP**：**All-to-All**（每个 GPU 向所有其他 GPU 发送/接收 token）

All-to-All 意味着 EP 的通信量取决于路由的分配模式——如果大多数 token 都去同一组 expert，那部分 GPU 的通信负载就会重。

---

## 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ **显存效率极高**：每张 GPU 只存一部分 expert | ❌ **负载不均衡**：路由可能不均匀，部分 GPU 过载 |
| ✅ **计算效率高**：被激活的 expert 满负荷运转 | ❌ **All-to-All 通信开销大**：随 EP degree 增加 |
| ✅ **与 MoE 天生匹配**：不需要把全部 expert 复制到每卡 | ❌ **与 TP 有交互问题**：TP 分片 + EP 路由的集成复杂 |
| ✅ **支持超大模型**：DeepSeek-V2 236B 靠 EP 训练 | ❌ **实现复杂**：需要框架级的 dispatch/combine 操作 |

## EP 在 2026 年的实践

### MoE 模型的典型配置

| 模型 | 总参数量 | 激活参数量 | 专家数 | 激活专家/Token | EP degree |
|------|---------|-----------|--------|---------------|-----------|
| Mixtral 8×7B | 47B | 13B | 8 | 2 | EP=8 |
| DeepSeek-V2 | 236B | 21B | 160 | 6 | EP=16 |
| Qwen2.5-MoE | 72B | 18B | 128 | 8 | EP=16 |
| GPT-4 MoE（传闻） | ~1.8T | ~280B | 16 | 2 | EP=8 |

### EP + TP + PP + DP 的 5D 并行

2026 年 Megatron-Core 已支持 **TP + EP + SP + CP + DP 五维并行**（"MoE Parallel Folding" 论文，2026.03）：

```
MoE Parallel Folding 的核心洞察：
Attention 层和 MoE 层需要不同的并行策略！
  - Attention 层：适合 TP + SP（切 hidden_dim 和 seq_len）
  - MoE 层：适合 EP（切 expert 维度）
  - 两者用灵活的 token 路由连接
```

这种"分别优化"的方案在 Mixtral 8×22B 上达到了 **49.3% MFU**，在 Qwen2-57B-A14B 上达到 **39.0% MFU**（1,024 GPU H100）。

## 🛠 实操指南

### 📋 决策指南：你的 MoE 模型需要 EP 吗？

```
模型使用了 MoE 架构吗？
├─ 否 → 不需要 EP，用 TP+PP+DP 就够了
└─ 是 →
   ├─ 总参数量 > 单卡显存 → 需要 EP
   ├─ 专家数 < 8 → EP 收益有限，考虑 TP 代替
   └─ 专家数 > 8 → EP 是必须的

EP degree 选择：
  EP degree ≤ 专家总数
  EP degree 最好是 2 的幂（2, 4, 8, 16...）
  推荐 EP = 专家数 ÷ 每 GPU 存放的专家数（通常 2-4 个/GPU）
```

### 🔧 自己动手验：EP 的负载均衡

```python
# 检查 MoE 路由的负载均衡情况
# 在训练中记录每个 expert 被激活的次数

def check_load_balance(expert_counts, num_experts):
    """expert_counts: list of activation counts per expert"""
    max_load = max(expert_counts)
    min_load = min(expert_counts)
    avg_load = sum(expert_counts) / num_experts
    
    imbalance = max_load / avg_load
    print(f"Expert 激活分布：max/min/avg = {max_load}/{min_load}/{avg_load:.0f}")
    print(f"负载不均衡系数: {imbalance:.2f}（理想 = 1.0）")
    
    if imbalance > 1.2:
        print("⚠️ 负载不均衡明显，考虑增加 aux_loss 系数")
    if imbalance > 1.5:
        print("❌ 严重不均衡，需要调整 Router 或增加负载均衡 loss")
    
    return imbalance

# 模拟 16 个 expert 的负载
import random
# 理想均衡
ideal = [100] * 16
check_load_balance(ideal, 16)
# 不均衡
unbalanced = [200 if i < 3 else 50 for i in range(16)]
check_load_balance(unbalanced, 16)
```

```bash
# 查看训练中 expert 负载的统计数据
grep "expert_util\|aux_loss\|load_balance" training.log | tail -10
# aux_loss 期望：< 0.01
# 如果 aux_loss > 0.05 → 路由偏向某些 expert
```

### ⚠️ 常见误区

- **误区**："EP 和 DP 可以互相替代"
  - **实际**：EP 和 DP 解决的是不同的问题。**DP 切分数据**（每张 GPU 处理不同的数据批次），**EP 切分模型**（每张 GPU 处理不同的 expert）。它们通常结合使用：DP 处理数据并行，EP 处理 expert 分布。

- **误区**："MoE 模型的总参数量大，所以一定比稠密模型慢"
  - **实际**：MoE 的速度取决于**激活参数量**，不是总参数量。DeepSeek-V2（236B 总参，21B 激活）的推理速度比 70B 稠密模型更快。**MoE 的代价不在算力，而在显存和通信。**

- **误区**："EP 的 All-to-All 通信太贵，应该用 TP 代替"
  - **实际**：TP 把每层都切分并在每步做 All-Reduce。对于 MoE 层，TP 需要每张 GPU 存储全部 expert 的切分版本——这抵消了 MoE 最核心的显存优势。**EP 虽然 All-to-All 通信有开销，但在专家数多时（>8），显存节省远大于通信代价。**

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 专家数 | 8-64 | 2-8 或 64-256 | > 256 |
| 激活专家/Token | 2-4 | 4-8 | > 8 |
| EP degree | = 专家数 × GPU 分配 | < 专家数 | > 专家数 |
| 负载均衡系数 | < 1.1 | 1.1-1.3 | > 1.3 |
| MoE 层通信占比 | < 10% | 10-25% | > 25% |
| MoE 总参/激活比 | > 5×（节省显著） | 2-5× | < 2×（不如用稠密） |

### 💡 一句话记住

> **"专家并行让每个 GPU 只存一部分专家——token 通过路由决定去哪个 GPU 上找专家计算。它是 MoE 模型能训练几百亿参数的关键，代价是需要 All-to-All 通信来转移 token。"**

- **SP**：序列并行，切分序列
