# Q: 这些并行策略哪个最好？— 2026 年选型决策树

## 为什么会有这个问题

现在你已经知道了五种并行策略——DP、TP、PP、SP、EP。每种策略都有各自的最佳场景和约束条件。**没有一种策略是"最好"的，只有"最适合你的模型的"。**

## 解决问题：一个完整的选型框架

### 第一步：确定你的模型能不能单卡装下

```
模型能不能单卡装下？
├─ 能（< 7B）→ 只需要 DP（甚至单卡就够）
└─ 不能 / 训练太慢 →
   ├─ 是单层太大还是层太多？
   │  ├─ 单层大（hidden_dim 超显存）→ 加 TP
   │  └─ 层太多 → 加 PP
   └─ 数据吞吐不够？→ 加 DP
```

### 第二步：检查是否需要特殊并行

```
序列是否超长（> 16K tokens）？
├─ 是 → 加 SP
└─ 否 → 不需要

模型是否是 MoE 架构？
├─ 是 → 加 EP
└─ 否 → 不需要
```

### 第三步：确定具体参数

```
固定约束：
  TP degree = NVLink 域内 GPU 数（通常 8）
  总 GPU 数 = TP × PP × DP × SP × EP

调整原则：
  1. TP 和 DP 是通信最重的 → 优先满足 TP 的 NVLink 约束
  2. PP 和 EP 是通信较轻的 → 跨节点的首选
  3. SP 只在长序列时才需要 → 不是必须的
    
2026 年推荐起始配置：
  < 32 GPU:  TP=8 (或 4), PP=1-4, DP=1-4, SP=1, EP=1
  32-256 GPU: TP=8, PP=4-8, DP=4-32, SP=1-4, EP=1
  > 256 GPU: TP=8, PP=8, DP=4-32, SP=1-8, EP=EP_degree
```

## 2026 年框架的并行能力

| 能力 | FSDP2 + 原生 PyTorch | DeepSpeed | Megatron-Core |
|------|-------------------|-----------|---------------|
| DP | ✅ 原生支持 | ✅ ZeRO-3 | ✅ DP + 数据并行 |
| TP | ⚠️ 需手动配置 | ⚠️ 需结合 Megatron | ✅ **原生支持** |
| PP | ❌ 没有原生 PP | ✅ PipeDream | ✅ 1F1B + Zero Bubble |
| SP | ⚠️ 通过 DCP | ✅ DeepSpeed-Ulysses | ✅ **Megatron-SP + CP** |
| EP | ❌ 不支持 | ✅ DeepSpeed-MoE | ✅ **原生 MoE + EP** |
| 组合 | FSDP2 + TP4 | ZeRO-3 + Megatron | **TP+PP+SP+CP+EP 5D** |
| 推荐场景 | **微调/中小模型** | 内存受限/长上下文 | **超大模型预训练** |

## 🛠 实操指南

### 📋 决策指南：一句话总结，你的模型怎么配

```python
def recommend_parallelism(model_size_B, num_gpus, seq_len, is_moe=False):
    """根据模型和硬件推荐并行配置"""
    tp = 8 if num_gpus >= 8 else min(num_gpus, 1)  # 优先 NVLink 域
    remaining_gpu_groups = num_gpus // tp
    
    # PP 通常 4-8
    pp = min(8, max(1, remaining_gpu_groups // 2))
    
    # 剩下的给 DP
    dp = remaining_gpu_groups // pp
    dp = max(1, dp)
    
    # SP 只在长序列时启用
    sp = max(1, seq_len // 32768) if seq_len > 16384 else 1
    # 确保总卡数匹配
    if tp * pp * dp * sp > num_gpus:
        sp = 1
    
    # EP 只用于 MoE
    ep = 1
    if is_moe:
        ep = min(16, num_gpus // (tp * pp))
    
    total = tp * pp * dp * sp * ep
    print(f"推荐配置（{model_size_B}B, {num_gpus} GPU）:")
    print(f"  TP={tp}, PP={pp}, DP={dp}, SP={sp}, EP={ep}")
    print(f"  总 GPU: {total}")
    print(f"  每卡: {model_size_B * 1e9 * 2 / (tp * ep) / 1024**3:.0f} GB 参数")
    
    if total > num_gpus:
        print("⚠️ 总 GPU 数超过可用数量，需要减少 PP 或 DP")
    
    return tp, pp, dp, sp, ep

# 示例调用
recommend_parallelism(70, 256, 4096)     # 70B, 256 GPU, 4K 序列
print("---")
recommend_parallelism(405, 1024, 128*1024)  # 405B, 1024 GPU, 128K 序列
print("---")
recommend_parallelism(236, 512, 8192, True) # DeepSeek-V2, 512 GPU
```

### ⚠️ 常见误区

- **误区**："并行策略越复杂越好，5D 并行肯定比 3D 强"
  - **实际**：每增加一个并行维度，就增加一层通信开销和调度复杂度。**如果 3D 并行（TP+PP+DP）已经能让 MFU 达到 50%+，加 SP/EP 可能反而因为通信开销降低整体效率。** 只在有明确需求时增加并行维度。

- **误区**："只要 GPU 够多，什么模型都能训练"
  - **实际**：Amdahl 定律——串行部分（通信、同步）不随 GPU 数增加而减少。当 DP degree > 128 时，All-Reduce 的通信时间可能超过计算时间。**GPU 翻倍，速度可能只提升 60-80%**（256→512 卡时）。

- **误区**："MFU 是衡量并行策略好坏的唯一标准"
  - **实际**：MFU 只衡量**算力利用率**，不衡量显存效率、通信延迟、可维护性。有时候选择 MFU 稍低但实现更简单的方案（如 FSDP2 而非 Megatron），长期维护成本更低。

### 📊 底线数字速查

| 场景 | 推荐并行方案 | 典型 GPU 数 | 预期 MFU | 实现复杂度 |
|------|------------|-----------|---------|-----------|
| 单卡微调 | 无 | 1 | 30-40% | 极低 |
| 小规模训练（< 7B） | DP（FSDP2） | 8-32 | 50-60% | 低 |
| 中等训练（7B-34B） | TP+DP | 32-128 | 45-55% | 中 |
| 大规模训练（70B-405B） | TP+PP+DP（3D） | 128-1024 | 40-55% | 高 |
| 长上下文（> 32K） | 3D + SP（4D） | 256-1024 | 35-50% | 高 |
| MoE 大模型 | 3D + SP + EP（5D） | 512-2048 | 40-50% | 极高 |

### 💡 一句话记住

> **"没有最好的并行策略，只有最适合你模型的——TP 固定 8（NVLink 域内），PP 放 4-8（跨节点最友好），DP 撑满剩下的。只有当序列超长或模型是 MoE 时，才加 SP 和 EP。复杂度本身也是成本。"**

## 对后续的铺垫

你知道了选择哪种并行策略，但怎么在实际中落地？不同的训练框架对并行策略的支持深度不同：
- **FSDP2**：PyTorch 原生，支持 DP + TP，推荐中小模型
- **DeepSpeed**：支持 ZeRO-3 + MoE + Ulysses，内存受限场景首选
- **Megatron-Core**：支持 5D 并行，超大模型预训练的工业标准
