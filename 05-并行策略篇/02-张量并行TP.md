# Q: 显存放不下整个模型怎么办？— 张量并行（TP）

## 为什么会有这个问题

数据并行要求每张 GPU 都有完整的模型副本。当模型大到**单卡连一层都放不下**时，DP 即使配上 ZeRO-3 也不够——ZeRO-3 能把参数分片到多卡存储，但它**不能把单个 GEMM 拆到多卡上并行计算**（那正是 TP 的工作）。

先算清楚"一层有多大"（以 Llama 3 405B 为例：hidden_dim=16384，126 层，128 heads，GQA 8 个 KV heads）：

```
单层 Q/K/V/O 矩阵参数：
  W_q: 16384×16384 = 2.68 亿
  W_k: 16384×1024  = 0.17 亿（GQA）
  W_v: 16384×1024  = 0.17 亿
  W_o: 16384×16384 = 2.68 亿
  合计 ≈ 5.7 亿参数 ≈ 0.57B → BF16 约 1.14 GB/层

单层完整参数（attention + SwiGLU MLP，MLP 约 8h² 量级）：
  ≈ 3.2B 参数 → BF16 约 6.4 GB/层

全部 126 层的 attention 矩阵合计：0.57B × 126 ≈ 72B 参数 ≈ 144 GB（BF16）
```

**核心矛盾**：完整训练状态是 16 B/参数。405B 模型 6.48 TB，就算用 ZeRO-3 分到 64 卡，每卡还有 100 GB + 激活——**显存放不下是一方面，更根本的是必须把单层矩阵的计算本身拆到多卡同时算**，否则单卡的算力和带宽都跟不上。

## 解决什么问题：张量并行（Tensor Parallelism，TP）

TP 的核心思想：**把一层内的矩阵切成多份，每张 GPU 算一个切片，再按数学规则合并结果。**

### Megatron-LM 的 TP 方案（最广泛使用的实现）

以 Transformer 的 MLP 层为例（Llama 3 70B 的 hidden_dim = 8192）：

```
原始计算：Y = GeLU(X × W1) × W2

TP=2 的切法（Megatron 组合）：
W1 按列切：W1 = [W1a | W1b]
  GPU 0: Z0 = GeLU(X × W1a)   ← GeLU 作用在各自的列片上，数学等价
  GPU 1: Z1 = GeLU(X × W1b)
  Z0、Z1 是同一个激活张量的不同列切片，各自保持局部，不需要通信

W2 按行切：W2 = [W2a; W2b]
  GPU 0: Y0 = Z0 × W2a        ← 部分和
  GPU 1: Y1 = Z1 × W2b        ← 部分和
  All-Reduce 一次：Y = Y0 + Y1（前向 1 次；反向再 1 次）
```

**关键设计**：
- **列并行（Column-Parallel）的输出是分片**（各卡持有自己的列），**保持局部**，不需要 All-Gather——只有当后续算子需要完整张量时才通信；
- **行并行（Row-Parallel）的输出是部分和**，需要**一次 All-Reduce 求和**（前向、反向各一次）；
- "列并行后接行并行"的精妙之处：两者之间**不需要任何通信**，每个 Transformer 块（attention、MLP）各只有一次 All-Reduce。

### 为什么 TP 对通信要求极高

每个 Transformer 块前向 1 次 All-Reduce + 反向 1 次；一层有 attention 和 MLP 两个块，**每层共 4 次 All-Reduce**。

以 70B、TP=4、B=4、S=4096、FP16 为例，重算每步通信量：

```
每次 All-Reduce 的消息 = B × S × H × 2 字节
                       = 4 × 4096 × 8192 × 2 = 268 MB

每层 4 次（前向 attention 1 + MLP 1，反向同）
→ 每层 4 × 268 MB = 1.07 GB
→ 80 层 × 1.07 GB ≈ 85.9 GB / step（消息量口径）

若按 Ring 线上流量（× 2(N−1)/N，TP=4 时 ×1.5）：≈ 129 GB / step
```

前向 2 次 + 反向 2 次 = 320 次 All-Reduce/step，而 DP 每步只有 1 次梯度 All-Reduce——**TP 的通信频率是 DP 的 300 倍以上**，这就是为什么 TP 必须限制在 NVLink 域内（TP ≤ 8，对应一个 8 卡 DGX/HGX 机箱）。一旦跨机，带宽从 900 GB/s（NVLink 4 双向）掉到每卡 40–50 GB/s（IB NDR），性能直接崩溃。

## 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ **打破单卡内存限制**：把单个 GEMM 拆到多卡并行算 | ❌ **通信极其频繁**：每层 4 次 All-Reduce |
| ✅ **数学等价**：没有近似误差 | ❌ **必须限制在 NVLink 域内**：TP 度通常 ≤ 8，跨机 TP 性能灾难 |
| ✅ **不需要修改优化器** | ❌ **TP degree 受单机卡数限制** |
| ✅ **和 DP/PP 正交组合** | ❌ **实现复杂**：需要框架级支持（Megatron-Core） |

## 实际经验

### TP degree 怎么选？

| TP degree | 适用场景 | 瓶颈 |
|----------|---------|------|
| TP=1（不切） | 小模型或推理 | 不需要 |
| TP=2 | 中等模型（7B-13B），单节点 | 通信适中 |
| TP=4 | 13B-34B 模型 | 通信较多，适合 NVLink |
| **TP=8** | **70B+ 模型，8 卡 DGX** | **最常用配置** |
| TP > 8 | 极少使用 | 跨机通信太慢，得不偿失 |

**一条经验**：TP degree 总是设为 1、2、4 或 8 —— 对应单节点内的 GPU 数。让 TP 跨节点几乎总是错误的。这是 TP 的**适用边界**：TP 度通常 ≤ 8（NVLink 域内），跨机 TP 的每层 All-Reduce 会走 IB，代价极高。

### TP 的显存账本（别只数参数）

TP 只分摊参数/梯度/优化器，**不减少每卡看到的激活中 attention 的部分**（激活还要叠 SP/重算手段）：

- 70B 完整训练状态：70×10⁹ × 16 B = **1.12 TB**
- TP=8 每卡：1.12 TB ÷ 8 = **140 GB/卡** —— **超过 80GB H100！**
- 结论：**TP=8 单独装不下 70B 的训练**。必须再叠 PP（把 1.12 TB 再除以 PP），或叠 ZeRO/激活重算。这就是 3D 并行存在的原因。

## 🛠 实操指南

### 📋 决策指南：什么时候需要 TP？

```
单卡能装下完整训练状态 + 激活？（16 B/参数账本 + 激活）
├─ 能 → 只用 DP/ZeRO 就够了
└─ 不能 →
   └─ 是单层太大还是层太多？
      ├─ 单层参数字节数 > 单卡显存 → TP 必须
      └─ 层太多但单层不大 → 用 PP（下一篇）就够了
```

**2026 年典型判断**（单层 = attention + MLP，BF16）：

| 模型 | 训练状态（16 B/参数） | 单层参数 | 需要 TP？ | 推荐 TP degree |
|------|---------------------|---------|----------|---------------|
| Llama 3 8B | 128 GB | ~0.5 GB | ❌ 状态可用 ZeRO 分 | TP=1-2 |
| Llama 3 70B | 1.12 TB | ~1.76 GB | ✅ 建议 | TP=8 |
| Llama 3 405B | 6.48 TB | ~6.4 GB | ✅ 必须 | TP=8 |
| GPT-4（传闻 1.8T） | ~29 TB | ~30 GB（推测口径） | ✅ 必须 | TP=8 |

### 🔧 自己动手验：理解 TP 的通信量

```python
# TP 每步通信量（统一假设：Llama 3 70B，L=80，H=8192，B=4，S=4096，FP16）
L, H, B, S, nbytes = 80, 8192, 4, 4096, 2

per_ar = B * S * H * nbytes            # 每次 All-Reduce 的消息 = 268 MB
per_layer = 4 * per_ar                 # 每层 4 次（前向 2 + 反向 2）
total = L * per_layer
print(f"每次 AR: {per_ar/1e6:.0f} MB；每步消息量: {total/1e9:.1f} GB")
# → 85.9 GB / step（消息量口径，GB = 10⁹ 字节）

# 线上流量还要乘 Ring 系数 2(N-1)/N：TP=4 → ×1.5 ≈ 129 GB
tp = 4
wire = total * 2 * (tp - 1) / tp
print(f"TP={tp} 线上流量: {wire/1e9:.1f} GB / step")

# 若 500ms/step：消息量口径下 TP 通信占比约 17%（还要看 NCCL 实测带宽）
```

### ⚠️ 常见误区

- **误区**："TP 就是数据并行的变种，实现起来差不多"
  - **实际**：TP 和数据并行完全不同。数据并行通信**每次迭代一次**（All-Reduce 梯度），TP 通信**每个 Transformer 层 4 次**（前向 attention/MLP 各 1 次 + 反向各 1 次）。70B 模型 80 层 = 320 次/step，**TP 的通信频率是 DP 的 300 倍以上**。这就是为什么 TP 对通信要求极其苛刻。

- **误区**："ZeRO-3 已经分片了，和 TP 差不多"
  - **实际**：ZeRO-3 按 tensor element 分片，**包括层内矩阵**——每张卡确实只存 1/N 的每一层。但 ZeRO-3 只是"分着存"，**不能把单个 GEMM 拆到多卡上并行计算**（用时还要先 All-Gather 出完整矩阵）；把单层计算拆开并行算，是 TP 的工作。二者解决的是不同问题。

- **误区**："TP=8 就能放下 70B"
  - **实际**：TP=8 每卡仍要 1.12 TB ÷ 8 = **140 GB**（完整训练状态口径），超过 80GB H100。TP 只是账本里的一个除数，还需要 PP 或 ZeRO 配合才能装下，另外还要给激活留空间。

- **误区**："TP 不改变计算结果，所以没有精度问题"
  - **实际**：理论上 TP 是数学等价的，但实际中矩阵切分后的 GEMM 计算顺序不同可能导致**浮点舍入误差的微小差异**。虽然这些差异通常不影响收敛（在统计噪声范围内），但在某些数值敏感的场景（如强化学习训练）中可能导致不一致。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| TP degree | ≤ 8（NVLink 域内） | ≤ 4 | > 8（跨节点） |
| TP 通信占比（70B、B4、S4K，~86 GB/step） | < 10% | 10-30% | > 30% |
| 单机 8 卡 All-Reduce busbw（NVLink 4） | > 400 GB/s | 200-400 GB/s | < 200 GB/s |
| 单层参数字节数 vs 单卡显存 | < 30% | 30-70% | > 70% |

### 💡 一句话记住

> **"张量并行把一层大矩阵切成多份并行计算——列切分的输出保持分片，行切分的输出做 All-Reduce，每个 Transformer 层前向反向共 4 次通信。TP 只把显存账本除以 TP 度：70B 在 TP=8 下每卡仍要 140 GB 训练状态，还必须叠 PP 或 ZeRO。TP 绑死 NVLink，度永远 ≤ 8。"**

## 对后续的铺垫

TP 解决了"单层太大"的问题。但即使每层能切开放下，**层数太多**（比如 80 层甚至 126 层）意味着每张卡还是要串行算完所有层——要么放不下，要么只有少量卡参与、其余的卡没有活干。

解决思路是：**把不同的层放到不同的 GPU 上，像流水线一样同时计算。**
