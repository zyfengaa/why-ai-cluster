# Q: 这几种并行能组合吗？— 3D 并行

## 为什么会有这个问题

你已经有了三种并行策略：
- **数据并行（DP）**：复制模型，切分数据（解决吞吐不够）
- **张量并行（TP）**：切分层内参数（解决单层/单 GEMM 太大）
- **流水线并行（PP）**：切分层间（解决层数多、单卡装不下所有层）

但问题是：**在真实的大模型训练中，这三种瓶颈往往同时存在。** 只用一种，其他瓶颈就会冒出来。

## 解决什么问题：3D 并行（TP + PP + DP）

### 核心思路

三种并行策略是**正交**的——它们解决不同维度的瓶颈，可以叠加使用：

```
总 GPU 数 = TP degree × PP degree × DP degree

例如 512 GPU：
TP=8（每个节点 8 卡做张量并行）
PP=8（节点间流水线）
DP=8（数据并行复制 8 份流水线）
→ 总 GPU = 8 × 8 × 8 = 512
```

**计数规则（重要）**：3D 并行的总卡数就是 `TP × PP × DP` 这三个数相乘。后面文章里的 **SP（序列并行）不是独立维度**——Megatron-SP 附着在 TP 组上，不增加卡数；**EP（专家并行）也不是简单再乘一个数**——它把 DP 组内的卡重新组织来放不同专家。真正的"4D/5D"里新增的独立维度是 **CP（上下文并行）** 和 **EP（专家并行）**，详见后文。

### 通信层次结构

```
             TP（每层 4 次 All-Reduce，频率最高、对时延最敏感）
              ↑ 必须放 NVLink 域内
             DP（每步 1 次梯度 All-Reduce；量大但频率低，可与反向重叠）
              ↑ 可跨机，受跨机带宽限制
             PP（P2P 传激活，量最小，对带宽最不敏感）
              ↑ 可跨机，甚至走 IB
```

TP 是通信频率之王（70B 每步 320 次 All-Reduce），必须绑在 NVLink 上；DP 每步只有一次梯度同步但单次量大（≈2S，70B BF16 梯度 140 GB）；PP 只传边界激活，最"便宜"，适合跨机。

### 层级的物理映射

```
┌─────────────── 512 GPU 集群 ───────────────┐
│                                              │
│  ┌────── 物理机架 ──────┐                    │
│  │  ┌─── 8 GPU (TP=8) ───┐  ← 同一 NVLink 域  │
│  │  │  GPU 0-7           │                   │
│  │  └────────────────────┘                   │
│  │  ┌─── 8 GPU (TP=8) ───┐  ← 下一个机箱      │
│  │  │  GPU 8-15          │                   │
│  │  └────────────────────┘                   │
│  │  ... 8 组这样的 TP 组组成 PP=8 流水线       │
│  └──────────────────────────────────────────┘
│  整个结构复制 8 份（DP=8）                       │
└──────────────────────────────────────────────┘
```

## 2026 年典型 3D 并行配置

### 不同规模集群的推荐配置（TP×PP×DP = 总 GPU）

| 总 GPU | 节点数（8×GPU） | TP | PP | DP | 适合模型 |
|--------|---------------|-----|-----|-----|---------|
| 8 | 1 | 8 | 1 | 1 | 7B-13B |
| 32 | 4 | 8 | 4 | 1 | 13B-34B |
| 64 | 8 | 8 | 4 | 2 | 34B-70B |
| 128 | 16 | 8 | 4 | 4 | 70B |
| 256 | 32 | 8 | 8 | 4 | 70B-130B |
| **512** | **64** | **8** | **8** | **8** | **130B-405B** |
| 1024 | 128 | 8 | 8 | 16 | 405B+（405B 建议 PP=16，见下） |

> 405B 的显存账本：6.48 TB 训练状态 ÷ (TP=8 × PP=8) = 约 101 GB/卡，超过 80GB——所以 405B 实际常用 **TP=8、PP=16**（Meta 训练 Llama 3 405B 就是 8×16×128 = 16,384 卡）。

### 经验的黄金比例

Megatron 论文的经验是在大集群上 TP、PP、DP 按一定比例均衡时通信/显存/吞吐的权衡较好（理想化推导约为 D ≈ T ≈ P ≈ N^(1/3)）。

**但现实有一个硬约束**：TP 受 NVLink 限制通常固定为 8（一个 8 卡节点），所以实际是在固定 TP=8 后，再按显存预算和气泡公式分配 PP 和 DP。

## 更进一步的并行：4D / 5D（怎么数维度）

### 先明确：SP 不占新维度

Megatron-SP（序列并行）附着在 TP 组上——它切的是 TP 域内激活的序列维区域，**不增加总卡数**。所以"TP+PP+DP+SP"仍然是 3D 并行的卡数 `TP×PP×DP`。详见 → [[05-序列并行SP]]。

### 4D 并行（+ 上下文并行 CP）

适用场景：超长序列训练（> 128K tokens），attention 的计算和激活需要真正按序列切分
- TP + PP + DP + **CP（Context Parallelism，Ring Attention / Ulysses）**
- CP 切的是 attention 计算本身的序列维，是独立的并行维度
- 详见 → [[05-序列并行SP]]

### 5D 并行（+ 专家并行 EP）

适用场景：MoE（稀疏混合专家）模型
- **TP + EP + CP + DP + PP**（Megatron-Core "MoE Parallel Folding"，arXiv:2504.14960，2025-04）
- EP 将不同 expert 放在不同 GPU 上，通常在 DP 组内组织，不是简单再乘一维
- 详见 → [[06-专家并行EP]]

## 🛠 实操指南

### 📋 决策指南：3D 并行怎么配？

```
找到你的总 GPU 数 N
↓
固定 TP=8（因为 NVLink 限制）
↓
剩余可分配 = N ÷ 8
↓
先按显存预算定 PP（训练状态 ÷ (TP×PP) ≤ 单卡预算），再在 PP 和 DP 之间均衡
└─ PP 取 4 或 8（超大模型 16；P 大时必须配足 microbatch，否则气泡变大）
└─ DP = 剩余 ÷ PP
```

**公式**：`DP = N ÷ (TP × PP)`

**示例（256 卡）**：
1. TP = 8 → 剩余 32 个"TP 组"
2. PP = 8 → 4 组流水线
3. DP = 4 → 4 路数据并行

### 🔧 自己动手验：评估 3D 并行效率

```python
# 3D 并行配置下的通信次数估算（70B 模型，L=80）
N = 512  # 总 GPU
TP = 8   # 张量并行度
PP = 8   # 流水线并行度
DP = N // (TP * PP)  # 数据并行度 = 8

# TP 通信（每层 4 次 All-Reduce：前向 attention/MLP 各 1 次 + 反向各 1 次）
TP_comm_per_mb = 4 * 80          # 每 microbatch 320 次（80 层 × 4）

# PP 通信（每 microbatch 每边界前向+反向各 1 次 P2P）
PP_comm_per_mb = 2 * (PP - 1)    # 每 microbatch 14 次 P2P

# DP 通信（每步 1 次梯度 All-Reduce，量大但每步只 1 次）
DP_comm_per_step = 1

print(f"TP: {TP_comm_per_mb} 次 All-Reduce / microbatch")
print(f"PP: {PP_comm_per_mb} 次 P2P / microbatch")
print(f"DP: {DP_comm_per_step} 次 All-Reduce / step（量大、频率低）")
# TP 频率占绝对主导 → 它才是必须绑 NVLink 的那个
```

```bash
# 检查当前 3D 并行配置是否合理
# 查看 Megatron-Core 训练日志中的通信占比
grep -E "comms|all-reduce|reduce-scatter" training.log | tail -5
# 每步通信时间 > 计算时间 → 配置需要调整

# 查看 NCCL 拓扑是否和 3D 配置匹配
NCCL_DEBUG=INFO mpirun ... 2>&1 | grep "rank.*nvlink"
# 同一 TP 组的所有 rank 应该在 NVLink 域内
```

### ⚠️ 常见误区

- **误区**："TP、PP、DP 三种并行度越高越好"
  - **实际**：三种并行度相互制约。TP 高 → 通信开销大；PP 高 → 气泡增加（除非 M 足够大并上 ZB-H2/ZBV）；DP 高 → 跨机梯度 All-Reduce 变慢、且总状态被复制更多份。**3D 并行是平衡的艺术**，不是单纯地"把每个值都调到最大"。

- **误区**："3D 并行可以在任意规模上线性加速"
  - **实际**：**Amdahl 定律**在 3D 并行中同样生效。通信开销占总时间的比例不会随 GPU 数增加而减少。2026 年的实测数据显示，在 512 GPU 到 1024 GPU 的扩展中，**加速比通常在 1.7-1.9× 之间**，远达不到理想的 2×。

- **误区**："并行维度越多越好，5D 一定比 3D 强"
  - **实际**：每个新维度都有代价。SP 附着在 TP 上不占卡数但增加通信；CP/EP 只有在超长序列 / MoE 场景才有正收益。**先 3D 打满，再按需加 CP（长序列）和 EP（MoE）。**

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 加速效率（512 卡，相对 8 卡基线） | > 85% | 70-85% | < 70% |
| TP 通信占比 | < 15% | 15-30% | > 30% |
| PP 气泡率（1F1B） | < 10% | 10-25% | > 25% |
| DP 通信占比 | < 5% | 5-15% | > 15% |
| 总 MFU | > 50% | 30-50% | < 30% |
| 配置是否满足 TP=8（NVLink 域内） | ✅ | ⚠️ TP 跨节点 | ❌ |

### 💡 一句话记住

> **"3D 并行就是把 TP（层内切分）、PP（层间切分）、DP（数据复制）三种方式像三明治一样叠起来，总卡数 = TP × PP × DP。TP 绑死 NVLink 域内，PP 穿针引线跨节点，DP 在外层复制。SP 挂在 TP 组上不占卡数；真正的新维度是 CP（长序列）和 EP（MoE）。"**

## 对后续的铺垫

3D 并行适用于标准 Transformer 训练。但有两个场景，3D 并行不够用：

1. **超长序列训练**（>128K token）：Attention 的激活显存和计算随序列长度**二次增长**，需要按序列维度切分（CP）
2. **MoE 模型**：每个 token 只激活部分 expert，需要不同的切分方式（EP）

这两个问题分别由序列/上下文并行（SP/CP）和专家并行（EP）解决。
