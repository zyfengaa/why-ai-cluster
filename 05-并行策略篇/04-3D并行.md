# Q: 这几种并行能组合吗？— 3D 并行

## 为什么诞生这个问题？

你已经有了三种并行策略：
- **数据并行（DP）**：复制模型，切分数据（解决吞吐不够）
- **张量并行（TP）**：切分层内参数（解决单层太大）
- **流水线并行（PP）**：切分层间（解决层太多）

但问题是：**在真实的大模型训练中，这三种瓶颈往往同时存在。** 只用一种，其他瓶颈就会冒出来。

## 解决什么问题：3D 并行（TP + PP + DP）

### 核心思路

三种并行策略是**正交**的——它们解决不同维度的瓶颈，可以叠加使用：

```
总 GPU 数 = TP degree × PP degree × DP degree

例如 512 GPU：
TP=8（每个节点 8 卡做张量并行）
PP=8（节点间流水线）
DP=8（数据并行复制 8 份流水线）
→ 总 GPU = 8 × 8 × 8 = 512
```

**注**：SP（序列并行）与 EP（专家并行）不是独立相乘的维度——SP 与 TP 同开、共用同一进程组，EP 通常复用 DP×CP 的 rank。官方口径是 `Total GPUs = TP × PP × CP × DP`，把 SP、EP 再乘一遍会把卡数算得虚高。

### 通信层次结构

```
                      DP（All-Reduce 梯度，最轻）
                         ↑
                    PP（P2P 传输激活值，中等）
                         ↑
                    TP（All-Reduce 每层，最重）
                         ↑
                   NVSwitch / NVLink（最快的通信）
```

### 层级的物理映射

```
┌─────────────── 512 GPU 集群 ───────────────┐
│                                              │
│  ┌────── 物理机架 ──────┐                    │
│  │  ┌─── 8 GPU (TP=8) ───┐  ← 同一 NVLink 域  │
│  │  │  GPU 0-7           │                   │
│  │  └────────────────────┘                   │
│  │  ┌─── 8 GPU (TP=8) ───┐  ← 下一个机箱      │
│  │  │  GPU 8-15          │                   │
│  │  └────────────────────┘                   │
│  │  ... 8 组这样的 TP 组组成 PP=8 流水线       │
│  └──────────────────────────────────────────┘
│  整个结构复制 8 份（DP=8）                       │
└──────────────────────────────────────────────┘
```

## 2026 年典型 3D 并行配置

### 不同规模集群的推荐配置

| 总 GPU | 节点数（8×GPU） | TP | PP | DP | 适合模型 |
|--------|---------------|-----|-----|-----|---------|
| 8 | 1 | 8 | 1 | 1 | 7B-13B |
| 32 | 4 | 8 | 4 | 1 | 13B-34B |
| 64 | 8 | 8 | 4 | 2 | 34B-70B |
| 128 | 16 | 8 | 4 | 4 | 70B |
| 256 | 32 | 8 | 8 | 4 | 70B-130B |
| **512** | **64** | **8** | **8** | **8** | **130B-405B** |
| 1024 | 128 | 8 | 8 | 16 | 405B+ |

### 实务中的分配方式

**不存在"D ≈ T ≈ P"这样的黄金比例**——TP 被 NVLink 域钉死在 8，剩下的卡数在 PP 和 DP 之间分配：

- **TP = 8（或 4）**：受 NVLink 域限制，跨机 TP 不划算，所以先固定。
- **PP**：按气泡率（(P-1)/(M+P-1)）与跨机带宽来定，通常 4-8。
- **DP**：吃掉剩下的卡数（`DP = N / (TP × PP)`），并受跨机 All-Reduce 带宽限制。

## 更进一步的并行：4D / 5D 并行

### 4D 并行（+ 上下文并行 CP）

业界（Megatron-Core / NeMo）所谓的"4D"通常指 **TP + PP + DP + CP**，而不是 TP + PP + DP + SP——**SP 是 TP 的伴生优化、不是独立维度**（它与 TP 同开、共用同一进程组）。

适用场景：长序列训练（> 32K tokens）
- TP + PP + DP + **CP（Context Parallelism）**
- CP 把序列维度切分到多卡，解决 Attention 分数矩阵的 O(S²) 显存爆炸
- 详见 → [[05-序列并行SP]]

### 5D 并行（+ 专家并行 EP）

适用场景：MoE（稀疏混合专家）模型
- TP + PP + DP + CP + **EP（Expert Parallelism）**
- EP 将不同 expert 放在不同 GPU 上，按需求激活
- 详见 → [[06-专家并行EP]]

## 🛠 实操指南

### 📋 决策指南：3D 并行怎么配？

```
找到你的总 GPU 数 N
↓
固定 TP=8（因为 NVLink 限制）
↓
剩余可分配 = N ÷ 8
↓
在 PP 和 DP 之间均衡分配
└─ PP 取 4 或 8（太少气泡大，太多通信慢）
└─ DP = 剩余 ÷ PP
```

**公式**：`DP = N ÷ (TP × PP)`

**示例（256 卡）**：
1. TP = 8 → 剩余 32 个"TP 组"
2. PP = 8 → 4 组流水线
3. DP = 4 → 4 路数据并行

### 🔧 自己动手验：评估 3D 并行效率

```python
# 计算 3D 并行配置下的通信量估算（比字节，不是比次数）
N = 512  # 总 GPU
TP = 8   # 张量并行度
PP = 8   # 流水线并行度
DP = N // (TP * PP)  # 数据并行度 = 8

hidden = 8192        # 70B 级模型
batch, seq = 4, 4096
bytes_ = 2           # bf16
layers = 80

# TP 通信：每层 4 次 All-Reduce（前向 2 + 反向 2），每次 h 维激活
TP_comm_bytes = layers * 4 * 2 * batch * seq * hidden * bytes_   # ≈ 160 GB/步

# PP 通信：每微批次传激活值，量级为 b×s×h×bytes
PP_comm_bytes = 16 * 2 * batch * seq * hidden * bytes_           # ≈ 8 GB/步

# DP 通信：一次梯度 All-Reduce，数据量 = 参数量 × 字节数（含环状系数 2）
DP_comm_bytes = 2 * 70e9 * bytes_                                # ≈ 260 GB/步

total = TP_comm_bytes + PP_comm_bytes + DP_comm_bytes
print(f"TP 通信量/步: {TP_comm_bytes/1024**3:.0f} GB")
print(f"PP 通信量/步: {PP_comm_bytes/1024**3:.0f} GB")
print(f"DP 通信量/步: {DP_comm_bytes/1024**3:.0f} GB")
print(f"→ TP 占总通信量的 {TP_comm_bytes/total*100:.0f}%")
# 结论：比较通信开销必须比字节、不能比"次数"。按字节看 DP 的梯度 AllReduce
# 总量并不比 TP 小（一次就是整个模型的梯度），但 TP 的代价在于频率
# （每层 4 次、共 320 次）且必须锁在 NVLink 域内串行执行，
# 而 DP 每步只有 1 次、可跨机、还能与 backward 重叠。
```

```bash
# 检查当前 3D 并行配置是否合理
# 查看 Megatron-Core 训练日志中的通信占比
grep -E "comms|all-reduce|reduce-scatter" training.log | tail -5
# 每步通信时间 > 计算时间 → 配置需要调整

# 查看 NCCL 拓扑是否和 3D 配置匹配
NCCL_DEBUG=INFO mpirun ... 2>&1 | grep "rank.*nvlink"
# 同一 TP 组的所有 rank 应该在 NVLink 域内
```

### ⚠️ 常见误区

- **误区**："TP、PP、DP 三种并行度越高越好"
  - **实际**：三种并行度相互制约。TP 高 → 通信开销大；PP 高 → 气泡增加（即使 Zero Bubble 也有残余）；DP 高 → 跨机 All-Reduce 变慢。**3D 并行是平衡的艺术**，不是单纯地"把每个值都调到最大"。

- **误区**："3D 并行可以在任意规模上线性加速"
  - **实际**：**Amdahl 定律**在 3D 并行中同样生效。通信开销占总时间的比例不会随 GPU 数增加而减少，因此在 512 GPU 扩展到 1024 GPU 时，加速比达不到理想的 2×（具体数值取决于网络带宽与模型大小，需实测）。

- **误区**："3D 并行是唯一正确的并行方式"
  - **实际**：对于长序列训练（>32K token），**4D 并行（加 SP）**是必须的。对于 MoE 模型，**5D 并行（加 EP）**是标准配置。3D 并行是基础，但不是终点。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 加速效率（512 卡，相对 8 卡基线） | > 85% | 70-85% | < 70% |
| TP 通信占比 | < 15% | 15-30% | > 30% |
| PP 气泡率 | < 5% | 5-15% | > 15% |
| DP 通信占比 | < 5% | 5-15% | > 15% |
| 总 MFU | > 50% | 30-50% | < 30% |
| 配置是否满足 TP=8（NVLink 域内） | ✅ | ⚠️ TP 跨节点 | ❌ |

### 💡 一句话记住

> **"3D 并行就是把 TP（解决层太宽）、PP（解决层太多）、DP（解决吞吐不够）三种方式像三明治一样叠起来。TP 绑死在 NVLink 域内，PP 穿针引线跨节点，DP 在外层复制加速。黄金配比：TP=8, PP≈DP≈(N/8)^(1/2)。"**

## 对后续的铺垫

3D 并行适用于标准 Transformer 训练。但有两个场景，3D 并行不够用：

1. **超长序列训练**（>32K token）：Attention 的显存消耗随序列长度**二次增长**，3D 并行无法处理（注：FlashAttention 通过在线 softmax 已把 attention 的**显存**降到 O(S)，不再存 S² 矩阵；但**计算量**仍是 O(S²)，且序列本身仍要切分到多卡才能扩展上下文长度）
2. **MoE 模型**：每个 token 只激活部分 expert，需要不同的切分方式

这两个问题分别由序列并行（SP）和专家并行（EP）解决。
