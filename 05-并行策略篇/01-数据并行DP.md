# Q: 数据并行（DP）是怎么工作的？

## 为什么会有这个问题

当单卡训练不够用时，最自然的想法就是：**"把同一个模型复制到多张 GPU 上，每张处理不同的数据，然后汇总结果。"**

这就是数据并行（Data Parallelism，DP）——最直观、最简单的多卡训练方式。

## 解决什么问题

### 核心思想

```
GPU 0: batch[0:32]  → 前向 → 反向 → 梯度 g0
GPU 1: batch[32:64] → 前向 → 反向 → 梯度 g1
GPU 2: batch[64:96] → 前向 → 反向 → 梯度 g2
...
GPU 7: batch[224:256] → 前向 → 反向 → 梯度 g7

         ↓ All-Reduce（所有 GPU 参与）

平均梯度 g_avg = (g0 + g1 + ... + g7) / 8

         ↓

每张 GPU 用 g_avg 更新自己的模型参数
```

所有 GPU 上的模型参数始终保持一致，但每张处理的**数据不同**，从而实现训练吞吐的（近似）线性扩展——注意是"近似"：通信、数据加载和收敛质量都会让扩展效率低于 100%。

### 从 DP 到 DDP 的演进

| 阶段 | 方式 | 通信开销 | 说明 |
|------|------|---------|------|
| **Naive DP**（PyTorch 早期） | 主卡收集梯度→更新→广播 | 主卡集中瓶颈 | 主卡内存和带宽成为瓶颈 |
| **DDP**（DistributedDataParallel） | Ring All-Reduce，每卡只和邻居通信 | 每卡约 2S，与卡数 N 基本无关 | 时延步数 O(N)，小消息场景受影响 |
| **ZeRO-1** | 只分片优化器状态 | ≈ DDP | 梯度仍需 All-Reduce（实际实现为 reduce-scatter + all-gather，总量相同）|
| **ZeRO-2** | 分片梯度 + 优化器状态 | ≈ DDP | 梯度 reduce-scatter 代替 all-reduce，总量不变 |
| **ZeRO-3 / FSDP** | 分片参数 + 梯度 + 优化器 | **≈ DDP 的 1.5×** | 前向、反向各多一次参数 All-Gather |

（S = 每卡梯度字节数，对稠密模型 BF16 训练 S ≈ 2 B/参数。）

**DDP（PyTorch DistributedDataParallel）** 是最基本的实现方式，通过 **Ring All-Reduce** 算法让每张 GPU 只和相邻的 GPU 交换数据，避免主卡瓶颈。

### Ring All-Reduce 原理

```
Step 1: 每张卡把梯度切成 N 份（N = GPU 数）
Step 2: reduce-scatter 阶段：N−1 步，每步每卡向邻居发送/接收一份并累加
        → 结束后每张卡持有梯度的 1/N 的完整归约结果
Step 3: all-gather 阶段：N−1 步，把各卡的归约结果在环上轮转补齐
        → 共 2(N−1) 步（没有"再广播"这一步）
每卡总通信量 = 2S(N−1)/N ≈ 2S
耗时 T ≈ 2S(N−1)/(N·B)（B = 链路带宽）
```

**关键结论**：每卡通信量约 2S，**与卡数 N 基本无关**——所以"256 卡 DDP 每卡通信量是 8 卡的 32 倍"是错的。随 N 增长的是**步数**（Ring 的 O(N) 步），它影响小消息场景的时延；对大梯度（几百 MB 起），瓶颈是带宽而不是步数。

## 优缺点

### 优点
- ✅ **实现最简单**：一行代码 `model = DDP(model)` 即可
- ✅ **不修改模型结构**：适合任何模型
- ✅ **吞吐近似线性扩展**：GPU 翻倍、batch size 翻倍时吞吐接近翻倍（受通信、数据加载与收敛约束，不会是严格的 100%）
- ✅ **ZeRO/FSDP 可解决显存瓶颈**：当模型状态放不进单卡时，用 ZeRO-3 分片

### 缺点
- ❌ **纯 DDP 要求每卡放下完整训练状态**：模型 + 梯度 + 优化器 ≈ 16 B/参数，70B 模型就要 1.12 TB/卡——纯 DDP 对 70B+ 确实失效。但 **DP + ZeRO-3/FSDP 仍然可用**：参数、梯度、优化器全部分片后，每卡显存 ≈ 总状态/N + 激活。DP 的前提不是"模型小于某个大小"，而是"分片后每卡能放下自己的那份"
- ❌ **通信量由参数量决定**：每步每卡约 2S（S=梯度大小），跨机带宽低时占比显著
- ❌ **总 batch size 太大可能影响收敛**：极端大 batch 需要 warmup 和学习率调整
- ❌ **跨机通信瓶颈**：单机内 8 卡靠 NVLink 很快，跨机受单端口带宽限制

## 2026 年的实际数字

下表按 **128 MB 消息**（nccl-tests 基准口径）计算，Ring All-Reduce 耗时 `T ≈ 2S(N−1)/(N·B)`，N=8 时 ≈ 0.224 GB ÷ B：

| 场景 | 实测 busbw 量级 | 128MB All-Reduce 时间 | 通信占比（按 200ms 步算） |
|------|---------------|----------------------|--------------------------|
| 单机 8×H200 NVLink | > 400 GB/s | **约 0.6–1 ms** | **约 0.3–0.5%** |
| 跨机 IB NDR（每卡 40–50 GB/s，受单端口 50 GB/s 限制） | 40–50 GB/s | **约 5–7 ms** | **约 3%** |
| 跨机 RoCE / 普通配置（~30 GB/s） | ~30 GB/s | **约 8–13 ms** | **约 5%** |

**两个关键点**：

1. **128 MB 不是真实训练的通信量**。真实 DP 的 S 是整个梯度：70B 模型 BF16 梯度 ≈ 140 GB，跨机 40 GB/s 时一次梯度同步就要约 7 秒——这才是 DP degree 不能无限加大的真正原因，而不是 128MB 基准慢。
2. **通信占比 = 每步通信时间 ÷ 单步计算时间**。大模型单步计算时间长，同样的通信量占比反而低——所以"DP degree 超过某个数就失效"没有统一答案，要按你的模型和单步时间算。

## 🛠 实操指南

### 📋 决策指南：你的场景用哪种 DP？

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 模型 < 7B，单卡能装下完整训练状态 | **DDP** | 最简单，零侵入 |
| 7B-13B，显存紧张 | **FSDP2 SHARD_GRAD_OP** | 省 ~8× 优化器显存 |
| 13B-70B，多节点训练 | **FSDP2 FULL_SHARD** | 参数分片，跨节点高效 |
| 70B+，需要 CPU Offload | **DeepSpeed ZeRO-3 + Offload** | CPU/NVMe 二级卸载 |
| MoE 模型 | **DeepSpeed-MoE + ZeRO** | 专家并行 + 数据并行结合 |
| 微调（LoRA） | **FSDP2 SHARD_GRAD_OP** | 轻量，显存效率高 |

# 每步每卡通信量 ≈ 2S，与卡数基本无关

### ⚠️ 常见误区

- **误区**："DDP 的通信量随卡数线性增长（O(N)），卡越多每卡通信越多"
  - **实际**：Ring All-Reduce 每卡通信量 ≈ 2S，与 N 基本无关；随 N 增长的是步数（Ring O(N) 步），只对小消息的时延有明显影响。大梯度场景的瓶颈是带宽。

- **误区**："模型超过 70B，DP 就失效了"
  - **实际**：失效的是**纯 DDP**（每卡要放 16 B/参数的完整训练状态，70B 就是 1.12 TB）。**DP + ZeRO-3/FSDP 依然是 70B+ 训练的主力方案**——分片后每卡只放 1/N 状态。DP 的前提是"分片后每卡放得下"，不是"模型小于 70B"。

- **误区**："有 FSDP2 了，不需要其他并行策略"
  - **实际**：FSDP2/ZeRO-3 解决的是显存问题，但每步的梯度/参数通信量不变（约 2S 或 1.5×2S），跨机带宽有限时通信占比可能超过 30%（取决于模型大小与单步计算时间）。此时要引入 TP/PP 降低 DP degree，把梯度同步分摊到更多卡上。

> **"数据并行是最简单的多卡方案——复制模型、切分数据、同步梯度。Ring All-Reduce 每卡只传约 2S，与卡数无关；纯 DDP 的前提是每卡放得下完整训练状态，放不下就上 ZeRO-3/FSDP 分片，还不行才轮到 TP/PP。"**

## 对后续的铺垫

纯 DDP 要求每卡放下完整的模型状态。当模型大到分片之后单卡仍然放不下、或跨机梯度同步占比过高时，就要把**模型本身**切开：先把一层内的矩阵切开（TP），再把不同的层放到不同的卡上（PP）。
