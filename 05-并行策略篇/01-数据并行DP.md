# Q: 数据并行（DP）是怎么工作的？

## 为什么诞生这个问题？

当单卡训练不够用时，最自然的想法就是：**"把同一个模型复制到多张 GPU 上，每张处理不同的数据，然后汇总结果。"**

这就是数据并行（Data Parallelism，DP）——最直观、最简单的多卡训练方式。

## 解决什么问题

### 核心思想

```
GPU 0: batch[0:32]  → 前向 → 反向 → 梯度 g0
GPU 1: batch[32:64] → 前向 → 反向 → 梯度 g1
GPU 2: batch[64:96] → 前向 → 反向 → 梯度 g2
...
GPU 7: batch[224:256] → 前向 → 反向 → 梯度 g7

         ↓ All-Reduce（所有 GPU 参与）

平均梯度 g_avg = (g0 + g1 + ... + g7) / 8

         ↓

每张 GPU 用 g_avg 更新自己的模型参数
```

所有 GPU 上的模型参数始终保持一致，但每张处理的**数据不同**，从而实现训练吞吐的线性扩展。

### 从 DP 到 DDP 的演进

| 阶段 | 方式 | 通信开销 | 缺点 |
|------|------|---------|------|
| **Naive DP**（PyTorch 早期） | 主卡收集梯度→更新→广播 | O(N) 主卡瓶颈 | 主卡内存和带宽成为瓶颈 |
| **DDP**（DistributedDataParallel） | Ring All-Reduce，每卡只和邻居通信 | O(N) 但均摊 | 相对 Naive DP 是本质改进：消除主卡瓶颈、通信均摊 |
| **ZeRO-1** | 每卡只存部分优化器状态 | 不变 | 需要梯度 All-Reduce（与 DDP 相同）|
| **ZeRO-2** | 每卡只存部分梯度 + 优化器状态 | 不变 | 梯度从 All-Reduce 改为 ReduceScatter（通信量不变，省梯度显存）|
| **ZeRO-3 / FSDP** | 每卡只存部分权重 + 梯度 + 优化器状态 | 增加参数 All-Gather | 需要参数 All-Gather，通信增加约 50% |

**DDP（PyTorch DistributedDataParallel）** 是最基本的实现方式，通过 **Ring All-Reduce** 算法让每张 GPU 只和相邻的 GPU 交换数据，避免主卡瓶颈。

### Ring All-Reduce 原理

```
Step 1: 每张卡把梯度分成 N 份（N=GPU 数）
Step 2: ReduceScatter 阶段：进行 N-1 轮，每轮每张卡向邻居发送一份、接收一份并累加
Step 3: 经过 N-1 轮后，每张卡持有其中一个分片的最终归约结果（注意：不是全部结果）
Step 4: AllGather 阶段：再进行 N-1 轮，把各卡持有的分片沿环汇聚，得到完整的归约结果

→ 共 2(N-1) 步（ReduceScatter N-1 + AllGather N-1），不是"先归约再广播"

每张卡的通信量 ≈ 2 × (N-1)/N × 数据量
DP 每步梯度 AllReduce 的数据量 = 参数量 × 精度字节数
→ DP 每步通信量 ≈ 2 × 参数量 × 字节数（N 大时 2(N-1)/N → 2）
例：70B / bf16 一步 ≈ 2 × 70e9 × 2 ≈ 280 GB
```

## 优缺点

### 优点
- ✅ **实现最简单**：一行代码 `model = DDP(model)` 即可
- ✅ **不修改模型结构**：适合任何模型
- ✅ **理论上线性扩展**：GPU 翻倍，batch size 翻倍，吞吐翻倍
- ✅ **ZeRO/FSDP 可解决显存瓶颈**：当模型放不进单卡时，用 ZeRO-3 分片

### 缺点
- ❌ **模型必须能放进单卡**：传统 DP 要求每张 GPU 有完整模型副本
- ❌ **通信开销随 GPU 数增加**：Ring AllReduce 的**每卡通信量几乎与 N 无关**，变慢的根源是步数随 N 增加（延迟累积）以及跨机后带宽退化——256 卡往往比 8 卡慢得多
- ❌ **batch size 太大可能影响收敛**：极端大 batch 需要 warmup 和学习率调整
- ❌ **跨机通信瓶颈**：单机内 8 卡靠 NVLink 很快，跨机走网络明显变慢

## 2026 年的实际数字

DP 的梯度 AllReduce 是**带宽主导**的：数据量 = 参数量 × 精度字节数（70B / bf16 ≈ 140 GB），与模型规模强相关。因此**不能用"128 MB 小消息"的延迟数字去推断大模型的通信占比**——128 MB 量级是**延迟主导**，真实梯度是**带宽主导**，两者不可混用。要测通信占比，应当用**接近真实梯度的消息大小**跑 nccl-tests，并记录测试参数与机器规格：

```bash
# 用接近真实梯度的消息大小，并记录 busbw、算法与拓扑
mpirun -np 512 --hostfile hosts \
  nccl-tests/build/all_reduce_perf -b 8G -e 140G -f 2 -g 1
# 记录：busbw（GB/s）、通道/线程数、NVLink/IB/RoCE 拓扑
```

**关键结论**：当每步梯度 All-Reduce 的时间占单步时间超过 ~15% 时（经验上对应 DP degree > 64，具体阈值取决于梯度大小与跨机带宽），通信开销开始显著影响训练效率。这时需要引入其他并行策略（TP/PP）来降低 DP degree。

## 🛠 实操指南

### 📋 决策指南：你的场景用哪种 DP？

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 模型 < 7B，单卡能装下 | **DDP** | 最简单，零侵 |
| 7B-13B，显存紧张 | **FSDP2 梯度+优化器分片**（`reshard_after_forward=False`） | 省 Nd× 优化器显存（Nd = 分片 GPU 数，Nd=8 时省 ~8×）|
| 13B-70B，多节点训练 | **FSDP2 全分片**（`reshard_after_forward=True`） | 参数分片，跨节点高效 |
| 70B+，需要 CPU Offload | **DeepSpeed ZeRO-3 + Offload** | CPU/NVMe 二级卸载 |
| MoE 模型 | **DeepSpeed-MoE + ZeRO** | 专家并行 + 数据并行结合 |
| 微调（LoRA） | **FSDP2 梯度+优化器分片** | 轻量，显存效率高 |

### 🔧 自己动手验：你的 DP 通信效率

```bash
# 1. 测单机 8 卡 All-Reduce 带宽
mpirun -np 8 nccl-tests/build/all_reduce_perf -b 128M -e 128M -f 2
# H200 期望：> 400 GB/s

# 2. 测跨机 All-Reduce 带宽
mpirun -np 16 --host node1,node2 \
  nccl-tests/build/all_reduce_perf -b 128M -e 128M -f 2
# IB NDR 期望：> 80 GB/s，RoCE 期望：> 35 GB/s

# 3. 在训练脚本中埋点测通信占比
import torch
import time

global_start = time.time()   # 记录整步起点
...
step_start = time.time()
loss.backward()              # DDP 的梯度 AllReduce 发生在 backward 的 hook 里
torch.cuda.synchronize()
backward_time = time.time() - step_start
optimizer.step()             # 对 DDP 而言，这一步只是本地参数更新，不含 all-reduce

print(f"DP 通信占比: {backward_time / (time.time() - global_start) * 100:.1f}%")
# 如果 > 15% → 考虑减少 DP degree 或引入 TP/PP
```

### ⚠️ 常见误区

- **误区**："DP 就是简单的数据切分，没有副作用"
  - **实际**：DP 的 batch size = 单卡 batch size × GPU 数。如果总 batch size 太大（比如 > 4M token），模型收敛可能变差，需要更长的 warmup 或调整学习率。**DP 不是免费的午餐。**

- **误区**："DDP 和 DP 是一样的"
  - **实际**：PyTorch 的 `DataParallel`（已废弃）是主卡收集模式，主卡是瓶颈。`DistributedDataParallel`（DDP）用 Ring All-Reduce 均摊通信负载，**性能好得多**。2026 年新代码不要用 `DataParallel`。

- **误区**："有 FSDP2 了，不需要其他并行策略"
  - **实际**：FSDP2/ZeRO-3 解决了单卡放不下模型的问题，但通信开销随 GPU 数增加。**当每步梯度 All-Reduce 的通信占比超过 30% 时（经验上对应 DP degree > 64，具体阈值取决于梯度大小与跨机带宽）**，必须引入 TP/PP 来减少 DP degree。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 单机 8 卡 All-Reduce（H200） | > 400 GB/s | 200-400 GB/s | < 200 GB/s |
| 跨机 IB NDR All-Reduce | > 80 GB/s | 40-80 GB/s | < 40 GB/s |
| DP 通信占比（小模型 < 7B） | < 5% | 5-15% | > 15% |
| DP 通信占比（大模型 > 70B） | < 10% | 10-25% | > 25% |
| ZeRO-3 相对 DDP 显存节省（随 Nd 增长，Nd = 分片 GPU 数）| ~Nd×（Nd=8 时约 8×）| 4-8× | < 4× |

### 💡 一句话记住

> **"数据并行是最简单的多卡方案——复制模型、切分数据、同步梯度。但它有个前提：你的模型得能放进单卡。放不进？那就得用 ZeRO-3 分片，或者干脆换 TP/PP。"**

## 对后续的铺垫

数据并行要求模型能放进单卡。当模型大到一张 GPU 装不下全部参数时（70B+ 模型），DP 就失效了——无论你怎么分片，每张卡总是需要完整的模型层。

那怎么办呢？**把模型的一层切开，让多张 GPU 各自算一层的一部分。**
