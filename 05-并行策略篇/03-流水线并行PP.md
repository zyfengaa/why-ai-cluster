# Q: 层数太多怎么办？— 流水线并行（PP）

## 为什么会有这个问题

TP 解决了"单层太大"，但层数还是那么多——Llama 3 70B 有 80 层，405B 有 126 层。注意在 TP 模式下，每层的计算所有 TP 卡都参与，"串行"的痛点不是"部分 GPU 闲着"，而是：**每张卡都要装下并计算全部层（哪怕已按 TP 切分），层数 × 每层大小超过了单卡预算；就算放得下，其余未参与这层的卡也只能等**。

**PP 的动机**：把不同的层放到不同的卡上，突破"所有层都要在一张（组）卡上"的容量限制；再用 microbatch 把各阶段的空闲时间填起来。

**核心矛盾**：按层切分后，流水线天然有"填充"和"排空"阶段——不是每张卡每个时刻都有活干，这就是**气泡**。

## 解决什么问题：流水线并行（Pipeline Parallelism，PP）

PP 的核心思想：**把模型按层切成多个阶段（Stage），每个阶段放在不同的 GPU 上，让 microbatch 像流水线一样流过各阶段。**

### 直观理解

```
假设你有 P=4 张 GPU，模型有 8 层，M=8 个 microbatch：

Stage 0 (GPU 0): 层 1-2
Stage 1 (GPU 1): 层 3-4
Stage 2 (GPU 2): 层 5-6
Stage 3 (GPU 3): 层 7-8

1F1B 时间线（F=前向，B=反向，数字=microbatch 编号）：
GPU 0: F0 F1 F2 F3 | B0 F4 B1 F5 ...
GPU 1:    F0 F1 F2 | B0 F3 B1 F4 ...
GPU 2:       F0 F1 | B0 F2 B1 F3 ...
GPU 3:          F0 | B0 F1 B2 ...
（前几个 slot 是"填充"：上游还没算出可传的激活）
```

**类比**：TP 是"把一道菜的配料分给多人同时切"，PP 是"把菜品的制作流程拆成多个工序，流水线操作"。

### 气泡率公式与方向

1F1B 的气泡率约为：

```
bubble = (P − 1) / (M + P − 1)    （P = 流水线阶段数，M = microbatch 数）
```

**方向要记对**：P 越大、M 越小，气泡越大。P=4、M=16 → 3/19 ≈ 15.8%；P=8、M=16 → 7/23 ≈ 30.4%；同样 P=8 但 M=32 → 7/39 ≈ 17.9%。所以工程上的口诀是 **M ≫ P**（通常 M ≥ 4×P 甚至更高），而不是"P 越小越好"。

### 调度策略的演进

| 策略 | 诞生年份 | 气泡率 | 说明 |
|------|---------|--------|------|
| **GPipe** | 2019 | (P−1)/(M+P−1) | 先全算前向，再全算反向；激活显存随 M 线性增长 |
| **1F1B（PipeDream 风格）** | 2019 | (P−1)/(M+P−1)（同公式） | 一个前向紧跟一个反向；气泡率与 GPipe 同阶，但激活显存降到 O(P) |
| **Interleaved 1F1B** | 2021 | (P−1)/(v·M+P−1) | 每阶段拆 v 段虚拟流水线，气泡率约降为 1/v（通信次数增加） |
| **Zero Bubble（ZB-H1）** | 2024 | **≈ 1F1B 的 1/3** | 把反向拆成 W-grad 和 I-grad，用 W-grad 填空闲 |
| **Zero Bubble（ZB-H2 / ZBV）** | 2024 | **≈ 0** | 更激进的调度 + 激活传递优化，接近零气泡 |

**Zero Bubble（2024）是最重要的突破**——它发现反向传播可以拆成两个独立的计算（权重梯度 W-grad 和输入梯度 I-grad），把 W-grad 安排在原本空闲的气泡时间内。注意分寸：**ZB-H1 约把 1F1B 的气泡降到 1/3；接近零需要 ZB-H2/ZBV**，不要把"H1"当成"零气泡"。

---

### 配置约束：PP 必须整除层数

PP 不是"取个 4/8/16 就能跑"，它和模型结构有硬约束：

1. **`num_layers % PP == 0`**：Megatron 默认要求每个 stage 层数相同，否则直接拒绝启动。Llama 3 70B 的 80 层，合法 PP = 1/2/4/5/8/10/16/20/40/80；Llama 3 405B 的 126 层，合法 PP = 1/2/3/6/7/9/14/18/21/42/63/126——**16 不在其中**，Meta 的训练框架实际用了不均匀切分。
2. **Interleaved 更严格**：`num_layers % (PP × v) == 0`，v 是虚拟流水线段数。例：80 层、PP=8、v=2 → 要满足 `80 % 16 == 0` ✅。
3. **首尾 stage 天然更重**：stage 0 扛 embedding，最后一个 stage 扛 LM head + loss。即使层数相同，最后一段的显存和计算也更大。Megatron 的 `--account-for-embedding-in-pipeline-split` 会把它们的参数量计入切分账本。
4. **microbatch 约束**：`M = global_batch ÷ (micro_batch × DP) ≥ PP`，工程上取 `M ≥ 4×PP`；`M` 不够时气泡会把收益吃光（见上文公式）。

**除不尽怎么办**（按优先级）：

- **选因子**：从层数的因数里重新挑 PP（80→8/16，96→8/12/16/24）；
- **把 embedding + LM head 算作 2 个"层"**：126 + 2 = 128，正好 ÷ 16；
- **接受不均匀切分**：例如 126 层、PP=16 时，14 个 stage 放 8 层、2 个放 7 层；代价是节拍由最慢 stage 决定，约 10% 损失；
- **复制 LM head** 到最后多个 stage，用显存换均衡。

> 这也是**微调场景不爱用 PP** 的原因：batch 小 → M 上不去 → 气泡无法摊薄，而微调本来就不需要那么大的显存节省。

## 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ **通信量通常最低**：只传阶段边界的激活值（P2P），远低于 TP 的每层 All-Reduce——但不是任何配置都绝对最低（见下文） | ❌ **有气泡**：(P−1)/(M+P−1)，靠 M 和 ZB 调度压制 |
| ✅ **适合跨节点**：通信带宽要求低，可以走 InfiniBand/RoCE | ❌ **负载不均衡**：首尾阶段显存/计算需求不同 |
| ✅ **和 TP 正交**：TP 处理层内，PP 处理层间 | ❌ **实现复杂度中等**：需要处理微批次的调度逻辑 |
| ✅ **把层分摊到多卡**：126 层模型 PP=16 每卡只放 8 层 | ❌ **梯度滞后**：异步版本的 PP 可能有 stale gradient |

**"PP 通信最低"的边界**：PP 只传层边界激活，每 microbatch 每边界前向+反向各一次 P2P。以 70B、B=4、S=4096、H=8192 为例，单次传 B×S×H×2B = 268 MB，M=16 时约 8.6 GB/step（P=8 时叠加双向与多边界的调度开销可达 ~15 GB）——与 TP 的每步几十 GB 相比确实小，**但如果 TP 配置很小（B、S 都小），两者可能同量级**。"PP 通信最低"是经验规律，不是定理。

## PP 在 2026 年的实际应用

### 典型配置

| 集群规模 | TP | PP | DP | 总 GPU（TP×PP×DP） |
|---------|---|----|----|--------|
| 单机 8 卡 | TP=8 | PP=1 | DP=1 | 8 |
| 4 机 32 卡 | TP=8 | PP=4 | DP=1 | 32 |
| 16 机 128 卡 | TP=8 | PP=8 | DP=2 | 128 |
| 64 机 512 卡 | TP=8 | PP=8 | DP=8 | 512 |

**关键点**：PP degree 通常取 4-8（405B 级别会到 16）。由公式 (P−1)/(M+P−1)：**P 太大、M 跟不上时气泡会明显变大**；P 太小则每卡分的层数少、省显存有限。要配套足够的 microbatch。

### Zero Bubble 的实际收益（气泡率）

| 配置 | 1F1B | ZB-H1（≈1/3） | ZB-H2/ZBV（≈0） |
|------|------|--------------|----------------|
| PP=4，M=16 | 3/19 ≈ 15.8% | ≈ 5% | ≈ 0–2% |
| PP=8，M=16 | 7/23 ≈ 30.4% | ≈ 10% | ≈ 1–3% |
| PP=8，M=32 | 7/39 ≈ 17.9% | ≈ 6% | < 1% |

## 🛠 实操指南

### 📋 决策指南：用 PP 还是 TP？

| 情况 | 推荐 | 理由 |
|------|------|------|
| 单层参数字节数 > 单卡显存 | **TP** | TP 解决层内放不下 |
| 层数多、完整训练状态除以 TP 后仍超单卡预算 | **PP** | PP 把层分摊到多卡，突破容量 |
| 两者都有 | **TP + PP 结合** | 3D 并行 |
| 跨节点集群 | **PP 优先** | PP 对跨机通信友好 |
| 单节点 8 卡 | **TP 优先** | TP 利用 NVLink |

### 🔧 自己动手验：当前 PP 配置的气泡率

```python
# 计算 PP 气泡率（1F1B 调度）
# 注意方向：P 越大、M 越小 → 气泡越大；M 要 ≫ P
def bubble_ratio(P, M):
    return (P - 1) / (M + P - 1)

print(f"PP=4, M=16 → {bubble_ratio(4, 16)*100:.1f}%")   # 15.8%
print(f"PP=8, M=16 → {bubble_ratio(8, 16)*100:.1f}%")   # 30.4%（M 不够）
print(f"PP=8, M=32 → {bubble_ratio(8, 32)*100:.1f}%")   # 17.9%
print(f"PP=16, M=32 → {bubble_ratio(16, 32)*100:.1f}%") # 31.9%（必须上 ZB/interleaved）

# Zero Bubble：ZB-H1 ≈ 上面结果的 1/3；ZB-H2/ZBV ≈ 0
# 在 Megatron-Core 中启用：
#   --num-micro-batches 32（保证 M ≥ 4×P）
#   --overlap-grad-reduce 等（ZB 相关开关按版本文档）
```

### ⚠️ 常见误区

- **误区**："PP 不省显存，只是提高利用率"
  - **实际**：PP 确实**省显存**，但账要算全。PP=4 时 70B 模型每卡参数 = 140 GB ÷ 4 = **35 GB——这只是参数**。完整账本（16 B/参数）：BF16 权重 35 GB + BF16 梯度 35 GB + FP32 master + Adam m/v 210 GB = **280 GB/卡**，仍远超 80GB H100。所以 PP 几乎总是和 TP（或 ZeRO）叠着用：TP=8、PP=4 时每卡 1.12 TB ÷ 32 = 35 GB，才装得下。

- **误区**："PP degree 越大越好，越大的 PP 越省显存"
  - **实际**：PP degree 增大有代价：① 气泡率增加——公式 (P−1)/(M+P−1) 中 P 增大、气泡变大（除非用 ZB-H2/ZBV 并保证 M 足够）；② 阶段间通信次数增加（每 microbatch 每边界传 2 次）。**PP degree 通常在 4-8（超大模型可到 16），并保证 M ≥ 4×P。**

- **误区**："Zero Bubble 完全没有开销"
  - **实际**：ZB-H1 只是约 1/3；接近零需要 ZB-H2/ZBV，其实现需要额外的调度逻辑和内存管理。它把反向计算拆成 W-grad 和 I-grad 两部分，增加了调度复杂度，并且需要**额外激活值存储**（I-grad 依赖前向激活值，这些激活值要保留更久）。在激活显存本来就很紧张的大模型训练中，这可能是个问题。

## 对后续的铺垫

TP 解决"单层太大"（层内切分），PP 解决"层数太多、单卡装不下全部层"（层间切分）。这两者可以组合——但如何组合才是最优？

更进一步，如果模型本身是**稀疏的**（比如 MoE），只有部分参数被激活，那并行策略就要完全重新思考。

但在讨论这些之前，先看看最常见的组合方式：**3D 并行（TP + PP + DP）。**
