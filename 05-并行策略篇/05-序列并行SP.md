# Q: 长序列训练为什么需要序列并行（SP）？

## 为什么诞生这个问题？

当序列长度从 4K 增加到 128K 甚至 1M 时，**Attention 层的显存消耗随序列长度二次增长**：

```
Attention 分数矩阵显存 ≈ O(batch_size × num_heads × seq_len² × precision)

# 注意：分数矩阵的维度是 B × num_heads × S × S，与 hidden_dim 无关
# （head_dim = hidden_dim / num_heads，误用 hidden_dim 会把规模夸大 head_dim=128 倍）
# 下表按 num_heads = 64 估算（如 Llama 3 70B：hidden_dim=8192，64 个 head，head_dim=128）
 
seq_len=4K:   ~2 GB（单层，容易承受）
seq_len=32K:  ~128 GB（单层，已经接近 H100 总显存）
seq_len=128K: ~2 TB（单层，远超单卡极限）
```

**核心矛盾**：标准 TP/PP 把模型参数切分到多卡，但 Attention 的**中间激活值**随序列长度二次增长，而且这些激活值需要在反向传播时保留——**当序列长度超过 32K 时，单卡存不下这些激活值。**

## 解决什么问题：序列并行（Sequence Parallelism，SP）

SP 的核心思想：**把序列维度也切分到多张 GPU 上，每张 GPU 只处理序列的一个片段。**

### 主流方案（先分清两条路线）

**关键区分**：下面三个方案不是同一类机制，动机也不同，不能混为一谈。

- **Megatron-SP（arXiv 2205.05198）切的是 LayerNorm / Dropout 的激活值**——Attention 的输入和输出仍是完整序列，只在 attention 前后的 LN/Dropout 区段沿序列切分，通信是 AllGather / ReduceScatter。它**不减少 O(S²) 的 attention 分数矩阵显存**，而且**必须与 TP 同开**（共用同一进程组，通信与 TP 合并）。
- **真正削减 O(S²) 的是上下文切分（Context Parallel，CP）**：Ulysses 和 Ring Attention 把整条序列（含 Q/K/V）切到多卡，让每卡只算一段 attention——这才是"Attention 显存二次爆炸"的解药。

| 类别 | 方案 | 组织 | 核心思路 | 适用场景 |
|------|------|------|---------|---------|
| **激活切分** | **Megatron-SP** | NVIDIA | 只在 LayerNorm + Dropout 区段沿序列切分激活，Attention 保持完整序列 | 省激活显存，**不削减 O(S²)** |
| **上下文切分（CP）** | **DeepSpeed-Ulysses** | Microsoft | 2 次 All-to-All：序列维切分 ↔ head 维切分互换 | ≥128K 序列（HF 路径下配合 ZeRO-2）|
| **上下文切分（CP）** | **Ring Attention** | 学术界 | KV 块沿环 P2P 轮转，与 attention 计算重叠 | 极端长序列（1M+）|

### 三类机制的工作原理

```
# Megatron-SP（激活切分，attention 仍是全序列）
LN/Dropout 区段：序列沿 SP 维切分，各卡只算自己那段 LN/Dropout
进入 attention 前：AllGather 恢复全序列
attention 之后：ReduceScatter 重新沿序列切分
→ 省的是 LN/Dropout 激活；配合 TP 还能省掉 TP 重复存储的激活

# DeepSpeed-Ulysses（上下文切分，2 次 All-to-All）
输入：序列沿 S 维切分，各卡持有 S/SP 个 token 的全部 heads
第 1 次 All-to-All：[S/SP, H] → [S, H/SP]，即"切序列"换成"切 head"
各卡对分到的 H/SP 个 head 计算完整序列上的 attention
第 2 次 All-to-All：[S, H/SP] → [S/SP, H]，换回序列维
→ 硬约束：head 数需能被 SP degree 整除

# Ring Attention（上下文切分，P2P 环）
KV 沿序列切成块，每卡持有 Q 的一块 + KV 的一块
每一轮：各卡用本地 Q 块算当前 KV 块，同时把 KV 块 P2P 传给环上邻居
KV 块绕环转一圈后，每卡得到自己 Q 块对全序列的 attention
→ 计算与 KV 传输重叠，可扩到 1M+ 序列
```

### 为什么 SP 和 TP 是互补的

```
标准 3D 并行把模型参数切分到多卡（TP/PP），但序列依然完整。
SP 再在序列维度上切一刀：

4D 并行：
TP（切 hidden_dim）+ PP（切 layers）+ DP（切 batch）+ SP（切 seq_len）

→ 每张 GPU 持有的显存 = 总显存 ÷ (TP × PP × SP)
  （DP 是复制模型、不切显存，不能出现在除数里；SP 与 TP 同开、共用同一进程组）
```

## 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ **解决长序列的显存爆炸（CP / Ring Attention / Ulysses）**：显存随 seq_len 线性扩展而不是二次 | ❌ **增加通信开销**：Megatron-SP 每层多一次 AllGather / ReduceScatter，CP 每层 2 次 All-to-All |
| ✅ **和 TP 天然的互补**：TP 切 hidden_dim，SP 切 seq_len，同一个 All-Reduce 可以合并 | ❌ **实现复杂度高**：需要精确控制切分边界 |
| ✅ **支持超长上下文**：CP / Ring Attention 可扩到 1M+（Megatron-SP 本身不提供长序列能力，需与 CP 配合）| ❌ **Ring Attention 实现复杂**：生产和框架集成还在早期 |
| ⚠️ **DeepSpeed-Ulysses 与 ZeRO 的兼容性**：HF 客户端路径下 Ulysses 稳定支持到 ZeRO-2（ZeRO-3 目前不支持）；Megatron-DeepSpeed 路径可组合 | ❌ **SP degree 受序列长度限制**：序列太短时切分没有意义 |

## 2026 年的实际应用

| 场景 | 序列长度 | 推荐方案 | 显存节省 |
|------|---------|---------|---------|
| 标准训练 | 4K - 8K | 不需要 SP | — |
| 中等上下文 | 32K - 64K | Context Parallel（Ulysses，SP=4 或 8） | ~4-8× |
| 长上下文 | 128K | Context Parallel（Ulysses / Ring Attention） | ~8-16× |
| 超长上下文 | 1M+ | Ring Attention + Flash Attention 3 | ~40×+ |

**2026 年趋势**：长上下文已成为标配。GPT-4 支持 128K，Claude 支持 200K，Gemini 2.5 支持 1M 以上。**SP 不再是"高级特性"，而是长上下文训练的必需品。**

## 🛠 实操指南

### 📋 决策指南：你的场景需要 SP 吗？

```
当前序列长度是多少？
├─ < 16K → 不需要 SP，3D 并行就够
├─ 16K - 64K → 建议 SP=4，Context Parallel（Ulysses）
├─ 64K - 256K → 建议 SP=8，Context Parallel（Ulysses 或 Ring Attention）
└─ > 256K → Ring Attention + Flash Attention 3
```

**显存快速判断公式**：
```python
# 单层 Attention 的分数矩阵显存占用（激活值）
seq_len = 128000
num_heads = 64        # 例如 Llama 3 70B：hidden_dim=8192，64 个 head，head_dim=128
batch_size = 1
precision = 2         # FP16 bytes

# 分数矩阵维度是 B × num_heads × S × S，与 hidden_dim 无关
attn_mem = batch_size * num_heads * seq_len * seq_len * precision
print(f"单层 Attention 激活值: {attn_mem / 1024**3:.1f} GB")
# 128K 序列 × 64 heads → 约 2 TB（单层！）
# H100 总显存只有 80 GB → 完全放不下
```

### 🔧 自己动手验：启用 SP 前后的内存对比

```python
# 启用 SP 前的显存需求：
# 单个 Transformer 层
def estimate_layer_mem(seq_len, hidden_dim, num_heads, batch_size):
    # 参数（W_q, W_k, W_v, W_o, MLP）
    param_mem = 4 * hidden_dim * hidden_dim * 2  # FP16
    # Attention 分数矩阵激活值（维度是 B × heads × S × S，与 hidden_dim 无关）
    attn_mem = batch_size * num_heads * seq_len * seq_len * 2
    # MLP 激活值
    mlp_mem = batch_size * seq_len * hidden_dim * 4 * 2
    return (param_mem + attn_mem + mlp_mem) / 1024**3

# 对比 SP=1 vs SP=8（hidden_dim=8192，num_heads=64）
no_sp = estimate_layer_mem(128000, 8192, 64, 1)
with_sp = estimate_layer_mem(128000 // 8, 8192, 64, 1)  # SP=8 切分序列
print(f"无 SP: {no_sp:.1f} GB/层")
# 无 SP: ~2 TB/层（完全放不下）

print(f"SP=8: {with_sp:.1f} GB/层")
# SP=8: ~32 GB/层（可接受）
```

### ⚠️ 常见误区

- **误区**："SP 和 TP 是一样的，切分方式不同而已"
  - **实际**：TP 切的是 **hidden_dim**（矩阵的列），SP 切的是 **seq_len**（序列的位置）。它们的通信模式也不同：TP 每层都做 All-Reduce，SP 只在 Attention 和 LayerNorm 之间插入通信。**实践中 SP 和 TP 可以共用同一个 All-Reduce 操作**（这也是 Megatron-SP 的设计精妙之处）。

- **误区**："序列越长才需要 SP，4K 序列完全不需要"
  - **实际**：即使序列不长（4K），SP 也可以和其他并行策略结合来**减少激活值显存**，从而允许更大的 batch size 或降低通信。**SP 不是只为了超长序列，它在标准训练中也是一个有用的优化维度。**

- **误区**："SP 是纯显存优化，不影响计算速度"
  - **实际**：只有**上下文切分（CP / Ring Attention / Ulysses）**减少了每张 GPU 负责的序列长度，Attention 计算量的二次复杂度（O(N²)）变为 O((N/CP)²)，**单卡计算量大幅降低**；**Megatron-SP 不改变 attention 的计算量与显存**，它省的是 LN/Dropout 的激活（以及配合 TP 省掉的重复激活）。两者都新增了通信开销。在序列长度极大时，这个权衡非常值得。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| 序列长度 | < 16K（不需要 SP） | 16K-128K（需要 SP） | > 128K（必须 SP） |
| SP 显存节省 | > 8× | 4-8× | < 4× |
| SP 通信开销增量 | < 5% | 5-15% | > 15% |
| SP degree vs seq_len 匹配 | seq_len/SP > 1K | seq_len/SP 256-1K | seq_len/SP < 256 |

### 💡 一句话记住

> **"序列并行解决的是 Attention 的'显存二次爆炸'——序列从 4K 到 128K，显存需求从 2GB 涨到 2TB。把序列切到多卡上，每卡只处理一段，让长度扩展从指数变线性。"**

## 对后续的铺垫

SP 解决了长序列训练的显存问题。还有一种并行策略针对的是**模型结构本身**的稀疏性——MoE（混合专家模型）中，每个 token 只激活一部分参数，常规的 TP/DP 无法高效处理这种"不均匀"的计算模式。
