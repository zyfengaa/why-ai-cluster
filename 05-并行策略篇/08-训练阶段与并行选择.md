# Q: 同一个模型，预训练、微调、LoRA、蒸馏、RL 的并行方案为什么不一样？

## 为什么会有这个问题

选型时最容易只问一个维度：**"这个模型多大，要几张卡？"** 但真实决策是二维的：

```
每卡显存需求 = f(模型大小, 训练阶段)
```

同一个 70B 模型：

- **预训练**：需要约 **256 张** 80GB 卡；
- **全量微调**：约 **32 张**；
- **LoRA**：**8 张**；
- **推理**：**8 张**（FP16）或 4 张（FP8）。

差 30 倍。原因不是模型变了，而是**训练状态里"谁占显存"变了**。

## 解决什么问题：先算三本账

训练状态按参数字节拆开：

| 阶段 | bf16 权重 | bf16 梯度 | FP32 master | Adam m/v | **合计** |
|------|----------|----------|------------|----------|---------|
| **预训练 / 全量微调** | 2 B | 2 B | 4 B | 8 B | **16 B/参数** |
| **LoRA** | 2 B（冻结） | 0（底座不反传） | 0 | 0 | **2 B/参数 + 适配器** |
| **蒸馏·教师** | 2 B（冻结） | 0 | 0 | 0 | **2 B/参数** |
| **推理 FP8** | 1 B | 0 | 0 | 0 | **1 B/参数** |
| **QLoRA 底座** | 0.5 B（4bit） | 0 | 0 | 0 | **0.5 B/参数** |

**这一张表就是全部差异的来源。**

> 补充：用 bf16 优化器状态、或 FP8 训练可以把 16 B 压到 12–14 B；但这不改变"预训练 = 16 B 量级、微调 = 2 B 量级"的分野。

---

## 1. 预训练：3D / 5D，追求 MFU

- 账本最大（16 B/参数），且要跑几十万步——**1% 的 MFU 值几天的机时**；
- 所以愿意用复杂方案：TP + PP + DP，MoE 再加 EP，长上下文加 CP；
- 典型：70B → `TP8 × PP4 × DP8 = 256 卡`，每卡 35 GB。

**为什么不用 FSDP/ZeRO-3？** 也能跑，但预训练规模下每一步都要 All-Gather 全参数，跨机代价高于 TP/PP 的分摊；主流做法是 **TP/PP 切计算 + ZeRO-1 分优化器状态**。

## 2. 全量微调：FSDP2 / ZeRO-3 为主

- 账本仍是 16 B/参数，但**步数只有几百到几千**；
- 决策目标从"榨 MFU"变成"**工程简单、能放下**"；
- 默认答案是 FSDP2（= ZeRO-3 等价）：逐层分片参数、梯度、优化器状态，代码侵入极低；
- 70B 全量微调 ≈ `1.12 TB ÷ 32 卡 ≈ 35 GB/卡`；
- 只有 200B 以上才考虑 PP——微调 batch 小，PP 气泡摊不薄。

## 3. LoRA：几乎只用 DP

LoRA 把账本砍到 2 B/参数，优化器状态这一项直接消失：

```
70B LoRA：140 GB 冻结权重 + 适配器（< 1 GB）+ 激活
```

| 部署方式 | 分片对象 | 通信 | 适用 |
|---|---|---|---|
| **FSDP2 / ZeRO-3** | 冻结权重按 DP 分片 | 每步 All-Gather 140 GB（可逐层 overlap） | 单机 8×80GB，最常见 |
| **HSDP** | 机内分片 + 机间复制 | All-Gather 留在 NVLink 域内 | **多机 LoRA 的正确姿势** |
| **TP**（推理式常驻） | 权重按 TP 切 | 每层激活 All-Reduce | 框架支持时更省通信 |
| 单卡 QLoRA | 4bit 量化 | 无 | 7B–13B，消费级卡 |

**关键判断**：LoRA 的通信是"**每步一遍全权重 All-Gather**"（带宽型、可重叠），不是"每层一遍激活 All-Reduce"（延迟型）。所以 LoRA 能在普通网络上跑——**多机时务必用 HSDP，别让跨机做 ZeRO-3 的 All-Gather**。

## 4. 蒸馏：两套并行拼在一起

蒸馏是"**教师推理 + 学生训练**"的复合负载：

| 部分 | 并行模型 | 账本 |
|---|---|---|
| 教师前向 | TP（机内）+ 大批量 + KV cache；超百B 加 PP | 2 B/参数 |
| 学生训练 | DP + FSDP/ZeRO；大模型加 TP/PP | 16 B/参数 |
| 中间通道 | **尽量同卡/同节点 colocate** | — |

**真正的瓶颈是 logits 带宽，不是并行度**：

```
教师 logits = B × S × V × bytes
16,384 tokens × 128,256 词表 × 4 B ≈ 8.4 GB / step
```

处理办法：top-k logits（只传 top-32/64，体积降两个数量级）、按 S 分块、或离线生成蒸馏数据（教师纯推理并行、学生纯训练并行，两者完全解耦）。

## 5. RL（GRPO / PPO）：双引擎 + 权重重分片

- **Rollout 引擎**走推理并行：TP=8 + 大批量 + KV cache；
- **训练引擎**走 FSDP/PP/TP；
- 两者之间要**权重重分片**（reshard）：训练完的权重转成推理引擎的切分格式；
- 主流框架（verl / OpenRLHF 等）默认 **colocate**：同一批 GPU 上分时复用两个引擎，避免权重跨机传输。

## 实操指南：二维决策表

| 阶段 | 每参数 | 70B 典型卡数 | 主力并行 | 关键约束 |
|---|---|---|---|---|
| 预训练（稠密） | 16 B | 256 | TP8×PP4×DP8 | MFU、PP 气泡、层数整除 |
| 预训练（MoE） | 16 B | 2,048+ | TP1×PP16×EP64×DP | All-to-All 域、负载均衡 |
| 全量微调 | 16 B | 32 | FSDP2（+TP） | 跨机 All-Gather 带宽 |
| LoRA | 2 B | 8–16 | FSDP2 / HSDP | 冻结权重的 All-Gather |
| 蒸馏·教师 | 2 B | 8–256 | TP + PP | logits 带宽、colocate |
| 蒸馏·学生 | 16 B | 按学生规模 | FSDP2 / 3D | — |
| RL·rollout | 2 B | 8–64 | TP8 + EP（MoE） | KV cache、批处理 |
| RL·训练 | 16 B | 同预训练 | FSDP / PP | 权重重分片 |
| 推理服务 | 1–2 B | 8 | TP8 + EP（MoE） | KV cache、PD 分离 |

## ⚠️ 常见误区

- **误区**："LoRA 也是微调，并行方案和全量微调一样"
  - **实际**：LoRA 的优化器状态为零，账本从 16 B 降到 2 B，**70B 从 32 卡降到 8 卡**。并行重心从"分片训练状态"变成"分片冻结权重"，HSDP 常常比 FSDP2 更优。

- **误区**："70B LoRA 单卡就能跑"
  - **实际**：140 GB 的 bf16 权重放不进 80GB 卡。单卡只能跑 **QLoRA（4bit，约 35 GB）** 或更小的模型。

- **误区**："蒸馏就是把教师和学生放一起，用同一套并行"
  - **实际**：教师是推理（2 B/参数 + KV cache），学生是训练（16 B/参数），两者的最优并行完全不同。强行统一会两头不讨好；正确做法是各自最优 + **colocate + top-k logits**。

- **误区**："微调也需要 3D 并行"
  - **实际**：微调 batch 小，`M = global ÷ (micro × DP)` 上不去，PP 气泡无法摊薄；除非模型大到单机放不下，否则 FSDP2 + TP 就够。

## 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|---|---|---|---|
| 预训练每卡状态占比 | 60-65% | 65-75% | > 80%（无激活余量） |
| LoRA 多机是否用 HSDP | 是 | — | 跨机 ZeRO-3 |
| 蒸馏 logits 是否 top-k | 是（k≤64） | 分块传输 | 全词表跨机传 |
| 教师/学生是否 colocate | 同节点 | 同机架 | 跨机 |
| RL 权重 reshard 次数/步 | 1 | 2 | > 4 |

---

## 💡 一句话记住

> **"不是模型多大决定并行，是‘谁占显存’决定并行：预训练 16 B/参数（优化器状态是大头）→ 3D/5D；LoRA 2 B/参数（只剩冻结权重）→ DP/HSDP；教师 2 B/参数（纯推理）→ TP/PP；学生 16 B/参数 → 按预训练配。先算账本，再选维度。"**
