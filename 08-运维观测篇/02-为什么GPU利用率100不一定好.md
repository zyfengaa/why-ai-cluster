# Q: 为什么 GPU 利用率 100% 不一定好？

## 为什么会有这个问题

你在 Grafana 上看到 GPU-Util 稳定在 98-100%，很高兴："我的 GPU 满负荷运转，效率真高！"

但训练吞吐却比预期低了 30%。你检查代码逻辑、数据加载、梯度累积……都没问题。

**问题出在哪？**

答案是：**GPU-Util ≠ 有效计算率。GPU 可能在"忙等"。**

## 解决什么问题

GPU-Util 这个指标有一个"坑"：**它测量的是"GPU 上是否有 kernel 在执行"，而不是"是否有有效计算"。**

### GPU-Util 的真正含义

```python
# nvidia-smi 报告的 GPU-Util 的定义是：
#   "在采样期内，至少有一个 kernel 在执行的时间比例"
#
# 注意三个细节：
#   1. 它对"什么 kernel"完全不敏感——计算 kernel 和通信 kernel 都算
#   2. 一个只占 1 个 SM 的小 kernel 在跑，GPU-Util 就是 100%
#   3. 它既不是 CUDA Core 占用率，也不是算力利用率
#
# 这意味着：
#   - GPU 在计算 → GPU-Util 上升 ✅
#   - GPU 上的 NCCL kernel 在自旋忙等对端数据 → kernel 在执行 → GPU-Util 也很高 ❌
#   - GPU 在等主机准备好数据（H2D 还没发起）→ GPU-Util 反而会下降
```

> 常见误解是"GPU 在等 H2D 传输时 GPU-Util 也会显示 100%"。实际相反：H2D 拷贝通常由**独立的 copy engine** 完成，而且"等主机数据"的阶段 GPU 上根本没有 kernel 在跑——这时 GPU-Util 往往**下降**。真正把 GPU-Util 骗高的，是 **NCCL kernel 的自旋忙等**：NCCL 通信 kernel 在等待远端数据时会持续轮询占住 SM，采样器看到的是"kernel 在执行"，于是一个纯粹在等待的 GPU 显示 100%。

### 一个典型的时间线

```
时间线 ────────────────────────────────→

GPU 活动：
  [计算][计算][计算][NCCL 自旋等待][NCCL 自旋等待][计算][计算]...
                            ↑
                这期间 GPU-Util 仍然是 100%
                但实际吞吐 ≈ 0

实际有效的利用率：
  真正算力的时间占比 ≈ 50-60%
  GPU-Util 报告的利用率 ≈ 95%+  → 严重失真
```

### 实际案例

```
一个 8 卡 H100 的训练作业：

GPU-Util（nvidia-smi 报的）：97%
有效计算率（Nsight Systems 时间线）：63%

那 34% 的差距去哪了？
  18% → NCCL All-Reduce 等待/执行（梯度同步，含慢节点等待）
  10% → PyTorch 框架开销（kernel launch、cudaStreamSynchronize）
  6%  → 数据加载等待（DataLoader 瓶颈）

结论：GPU-Util 97% ≠ 训练效率 97%
```

### 真正的训练效率指标

| 指标 | 含义 | 怎么算 | 参考值 |
|------|------|--------|--------|
| **MFU** | 算力利用率（对稠密峰值） | 实际 FLOPS ÷ 稠密峰值 FLOPS | 大模型 38-45% 已是公开水平 |
| **计算/通信比** | 计算时间 ÷ 通信时间 | Profile 分析 | > 3:1 |
| **Kernel 启动开销** | CUDA kernel 启动延迟占比 | Nsight Systems | 越低越好 |
| **Data wait 占 step 比例** | GPU 等数据的比例 | 训练循环计时（见下文） | < 10-20% |

## GPU-Util 被"骗高"的三种常见情况

### 情况 1：NCCL 通信 kernel 的自旋忙等

最常见的原因。NCCL 的通信 kernel 在等待远端 rank 的数据时，会**持续轮询占住 SM**——对采样器来说这是"kernel 在执行"，GPU-Util 于是显示 100%。

```bash
# 检测方法：对比 GPU-Util 和 SM Active
# GPU-Util 很高但 SM Active 很低 → 大量时间在"占着 SM 等通信"
# 注意：DCGM 的 SM Active 是 0-1 的比例，不是百分比！

curl -s localhost:9400/metrics | grep DCGM_FI_PROF_SM_ACTIVE
# DCGM_FI_PROF_SM_ACTIVE < 0.5 但 GPU-Util > 90% → 通信瓶颈/忙等

# 更进一步：DCGM_FI_PROF_SM_ACTIVE 衡量的是"有 warp 驻留在 SM 上"的时间比例，
# 它也不等于有效计算——NCCL 自旋 kernel 的 warp 同样驻留在 SM 上。
# 所以它的判读顺序是：SM Active 低 → 一定没在有效计算；
#                     SM Active 高 → 还要再看 MFU 才知道算得有效率吗。
```

### 情况 2：小 Kernel 启动开销

当训练的 batch size 不大，每层都调了很多小 CUDA kernel 时，**kernel launch 的开销和 GPU"浅占用"会显著拉低有效算力**——每个 kernel 都在跑（GPU-Util 高），但每个都喂不饱 SM。

```python
# 小 kernel 问题示例
for name, param in model.named_parameters():
    # 每个参数都做一次 reduce → 每次都是小消息、小 kernel
    dist.all_reduce(param.grad)

# 优化方案：合并为大的 All-Reduce
# 或者使用 FSDP/ZeRO 的 bucket 机制自动合并
```

### 情况 3：数据加载瓶颈

DataLoader 来不及把数据送到 GPU。注意：这种情况下 GPU-Util 通常**下降**（GPU 上没 kernel 可跑），而不是虚高——它是"利用率低"类问题的典型代表。

```python
# 检测方法：把"取数据"和"计算"分开计时
# 关键：在 next(loader) 前后各打一个时间点，
# 之前的时间 = 等数据（t_data），之后到下一次取数据 = 计算（t_compute）
import time

class StepTimer:
    def __init__(self, loader):
        self.loader_iter = iter(loader)
        self.t_data = 0.0    # 等数据时间
        self.t_compute = 0.0  # 计算时间

    def run_step(self, train_step_fn):
        t0 = time.perf_counter()
        batch = next(self.loader_iter)      # 取数据
        t1 = time.perf_counter()
        train_step_fn(batch)                 # 前向 + 反向 + 优化器
        t2 = time.perf_counter()
        self.t_data += t1 - t0
        self.t_compute += t2 - t1

    def report(self):
        total = self.t_data + self.t_compute
        ratio = self.t_data / total if total > 0 else 0
        print(f'data wait 占 step 时间比例: {ratio:.1%}')
        # 持续 > 10-20% → DataLoader 已经在拖训练了
```

> 别用"在 yield 前打 t0、消费者取到 batch 后再 append"的写法——那样测到的是**上一个 batch 的训练时间**，不是取数据时间。计时的分界线必须严格是 `next()` 的调用前后。

## 🛠 实操指南

### 📋 决策指南：怎么判断 GPU 利用率是否"虚假"？

```
GPU-Util > 90% → 真的高效率？
├─ 检查 SM Active（DCGM_FI_PROF_SM_ACTIVE，0-1 比例）→
│   ├─ SM Active > 0.8 → 可能真在算，继续看 MFU 确认
│   └─ SM Active < 0.5 → ❌ GPU 大部分时间没在算（典型：通信忙等）
│
├─ 检查 MFU →
│   ├─ MFU 接近同类模型公开水平（如 405B 的 38-43%）→ ✅ 合理
│   └─ MFU 远低于此 → ❌ 计算效率有重大问题
│
└─ 检查计算/通信比 →
    ├─ 计算/通信 > 3:1 → ✅ 通信不是瓶颈
    └─ 计算/通信 < 1:1 → ❌ 通信严重瓶颈
```

### 🔧 自己动手验：检查你的 GPU 是否在"假忙"

```bash
# 1. 装 Nsight Systems（最准确的视图）
nsys profile -o profile_%p -t cuda,nvtx,nccl python train.py

# 2. 快速检查：对比 GPU-Util 和 SM Active
# 终端 1：看 GPU-Util（nvidia-smi 的采样窗口约 1 秒量级，瞬时值）
watch -n 1 nvidia-smi --query-gpu=index,utilization.gpu --format=csv

# 终端 2：看 SM Active（需要 dcgm-exporter；注意是 0-1 比例）
watch -n 1 'curl -s localhost:9400/metrics | grep DCGM_FI_PROF_SM_ACTIVE'

# 3. 用上一节的 StepTimer 测 data wait 占 step 的比例
#    持续 > 10-20% → 优先解决数据加载
```

### 采样口径：别把瞬时值当长期利用率

- **nvidia-smi / NVML 的 GPU-Util**：基于约 1 秒量级的采样窗口（具体随产品与驱动不同），`nvidia-smi dmon` 默认也是每 1 秒输出一行（`-d` 可调）。**屏幕上看到的数字是"最近一秒"的答案。**
- **dcgm-exporter**：暴露的是 Prometheus 抓取时刻的最近采样值，抓取间隔由 Prometheus scrape interval 决定（常见 15-30 s）。
- 因此：看趋势要用**分钟级以上的聚合**（Prometheus 的 `avg_over_time`），把 1 秒的瞬时尖峰当成"长期利用率"或反过来把 30 秒平均当成"每个 step 的状态"，都会误判。

### ⚠️ 常见误区

- **误区**："GPU-Util 95% = GPU 95% 的时间在算东西"
  - **实际**：GPU-Util 只表示"采样期内有 kernel 在执行"，并不区分"在计算"还是"在忙等"。**真正的计算效率要看 MFU；SM Active 可以排除"假忙"，但也不等于有效计算。**

- **误区**："加大 batch size 会增大梯度同步开销，所以要小心"
  - **实际**：方向反了。**标准数据并行的 All-Reduce 通信量由参数量决定，与 batch size 无关**——每步要同步的梯度就是全部参数的梯度。加大 batch size 让每步的计算量变大、通信量不变，**计算/通信比反而提高**（例如从 1.2:1 提到 2.5:1，见 Profiling 篇的案例）。真正限制 batch size 的是显存和收敛质量，不是通信开销。

- **误区**："GPU 利用率低就要加 GPU"
  - **实际**：如果利用率低是因为通信瓶颈（计算/通信比 < 1），加更多 GPU 只会**降低**通信效率。应该先优化通信。如果低是因为 DataLoader，先加 `num_workers` / 上预取。

### 📊 底线数字速查

| 场景 | GPU-Util | SM Active（0-1） | 建议 |
|------|---------|-----------------|------|
| 正常训练 | 95-100% | 0.7-0.9 | 保持，用 MFU 复核 |
| 通信忙等 | 85-100% | 0.3-0.5 | 优化 NCCL / 计算-通信重叠 |
| 小 kernel / 浅占用 | 90-100% | 0.5-0.7 | 合并 kernel / 增大 batch |
| DataLoader 瓶颈 | 明显下降（40-80%） | 0.3-0.5 | 增加 num_workers / 预取 |
| GPU 空闲 | < 50% | < 0.2 | 检查代码/调度问题 |

### 💡 一句话记住

> **"GPU-Util 100% 只说明'有 kernel 在跑'——NCCL 的自旋忙等 kernel 算、1 个 SM 上的小 kernel 也算，但都不是有效计算。真正衡量效率的链条是：SM Active 排除假忙（注意它是 0-1 比例），MFU 确认真的算得有效率，Data wait 比例排除数据瓶颈。"**
