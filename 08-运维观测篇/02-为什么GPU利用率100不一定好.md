# Q: 为什么 GPU 利用率 100% 不一定好？

## 为什么会有这个问题

你在 Grafana 上看到 GPU 利用率稳定在 98-100%，很高兴："我的 GPU 满负荷运转，效率真高！"

但训练吞吐却比预期低了 30%。你检查代码逻辑、数据加载、梯度累积……都没问题。

**问题出在哪？"

答案是：**GPU 利用率（GPU-Util）≠ 有效计算率。GPU 可能在"忙等"。**

## 解决什么问题

GPU 利用率这个指标有一个"坑"：**它测量的是"GPU 上是否有 CUDA 活动"，而不是"是否有有效计算"。**

### GPU-Util 的真正含义

```python
# nvidia-smi 报告的 GPU-Util（NVML 官方定义）测量的是：
#   "Percent of time over the past sample period during which
#    one or more kernels was executing on the GPU."
#   即：在过去的时间段内，至少有一个 kernel（内核）在 GPU 上执行的时间比例
#
# 注意统计单位是 kernel（内核），不是"CUDA 核（core）"——
#   只要有一个 kernel 在跑，这一整段时间就计满。
#
# 这意味着：
#   - GPU 在计算 → 利用率上升 ✅
#   - GPU 在等待 NCCL 通信完成 → NCCL 的 AllReduce 会在 GPU 上跑一个自旋
#     （spin）kernel"等"对端数据，这个 kernel 一直在执行 → 利用率同样计满 ❌
#   - GPU 在等待数据从 CPU 传输 → 同样看起来像在"工作" ❌
```

### 一个典型的时间线

```
时间线 ────────────────────────────────→

GPU 活动：
  [计算][计算][计算][等待NCCL][等待NCCL][计算][计算]...
                      ↑
                这期间 GPU-Util 仍然很高
                但实际吞吐 = 0

实际有效的利用率：
  真正算力的时间占比 ≈ 50-60%
  GPU-Util 报告的利用率 ≈ 95%+  → 严重失真
```

### 实际案例

```
一个 8 卡 H100 的训练作业：

GPU-Util（nvidia-smi 报的）：97%
有效计算率（Nsight Systems）：63%

那 34% 的差距去哪了？
  18% → NCCL All-Reduce 等待（梯度同步）
  10% → PyTorch 框架开销（kernel launch、cudaStreamSynchronize）
  6%  → 数据加载等待（DataLoader 瓶颈）

结论：GPU-Util 97% ≠ 训练效率 97%
```

### 真正的训练效率指标

| 指标 | 含义 | 怎么算 | 理想值 |
|------|------|--------|--------|
| **MFU** | 理论算力利用率 | 实际 FLOPS ÷ 峰值 FLOPS | > 45% |
| **计算/通信比** | 计算时间 ÷ 通信时间 | Profile 分析 | > 3:1 |
| **Kernel 启动开销** | CUDA kernel 启动延迟占比 | Nsight Systems | < 5% |
| **DataLoader 等待** | GPU 等数据的比例 | 训练日志 async_dataloader | < 3% |

## GPU-Util 被"骗高"的三种常见情况

### 情况 1：NCCL 通信等待

最常见的原因。GPU 在做 All-Reduce 时，计算核处于"空闲但被占用"状态——NCCL 的 AllReduce 本质是在 GPU 上跑一个**自旋（spin）kernel**等待对端数据，这个 kernel 在"执行"，所以 `utilization.gpu` 会被计满，但真正做计算的 SM 很少。

```bash
# 检测方法：观察 GPU Util 和 SM Active 指标
# 如果 GPU Util 很高但 SM Active 不高 → 在等通信

# 用 DCGM 的 SM_ACTIVE 指标
curl -s localhost:9400/metrics | grep DCGM_FI_PROF_SM_ACTIVE
# SM Active < 50% 但 GPU Util > 90% → 通信瓶颈
```

**注意：`DCGM_FI_PROF_*` 属于 DCGM 的 profiling 域指标，有两个坑**：

- 它在 dcgm-exporter 的**默认 counters 列表里是被注释掉的**，需要先把该字段加进 exporter 的 counters 配置，指标才会暴露出来（见 [dcgm-exporter 默认 counters.csv](https://github.com/NVIDIA/dcgm-exporter/blob/main/etc/default-counters.csv)）。否则你 `grep` 到的永远是空结果，会误判成"没有通信瓶颈"。
- profiling 指标是**采样**的（按采样周期统计），不是逐周期计数，**量级与设备域的 `DCGM_FI_DEV_GPU_UTIL` 不可直接对比**，不能把两个数直接相减。

**要证伪"GPU 在忙"，只给 SM Active 一条证据链是不够的**，还要一起看另外两个 profiling 指标：

- **`DCGM_FI_PROF_PIPE_TENSOR_ACTIVE`**——张量管线是否真的在算。它直接对应"这一轮有没有在做矩阵运算"。SM Active 高、Tensor Pipe Active 低，说明跑的是非张量 kernel（数据搬运、norm、通信 spin 等）。
- **`DCGM_FI_PROF_DRAM_ACTIVE`**——显存带宽是否被打满。它高而 Tensor Pipe Active 低 → GPU 只是"在搬数据"（memory bound / 纯拷贝），不是在算。

SM Active + Tensor Pipe Active + DRAM Active 三条一起看，才能区分 GPU 到底是"在算""在搬"还是"在等"。

### 情况 2：小 Kernel 启动开销

当训练的 batch size 不大，每层都调了很多小 CUDA kernel 时，**kernel launch 的开销占比需要实测**——用 Nsight Systems 看 kernel 之间的空隙即可，不同模型/框架差异很大，不宜套用固定百分比。

```python
# 小 kernel 问题示例
for name, param in model.named_parameters():
    # 每个参数都做一次 reduce → 每次都是小 kernel
    dist.all_reduce(param.grad)

# 优化方案：合并为大的 All-Reduce
# 或者使用 FSDP/ZeRO 的 bucket 机制自动合并
```

### 情况 3：数据加载瓶颈

DataLoader 来不及把数据送到 GPU，GPU 在等待数据。

```python
# 检测方法
# 在训练循环中加入
loader_start = time.time()
for batch in dataloader:
    data_load_time = time.time() - loader_start
    if data_load_time > 0.1:  # 超过 100ms 意味着 DataLoader 慢了
        print(f"⚠️ DataLoader 耗时: {data_load_time:.3f}s")
    # ... 训练代码 ...
    loader_start = time.time()
```

## 🛠 实操指南

### 📋 决策指南：怎么判断 GPU 利用率是否"虚假"？

```
GPU-Util > 90% → 真的高效率？
├─ 检查 SM Active → 
│   ├─ SM Active > 80% → ✅ 真·高效率
│   └─ SM Active < 50% → ❌ GPU 在"假忙"
│
├─ 检查 MFU →
│   ├─ MFU > 45% → ✅ 算力利用率合理
│   └─ MFU < 30% → ❌ 计算效率有重大问题
│
└─ 检查计算/通信比 →
    ├─ 计算/通信 > 3:1 → ✅ 通信不是瓶颈
    └─ 计算/通信 < 1:1 → ❌ 通信严重瓶颈
```

> **阈值口径**：NVIDIA 官方的解读是——SM Active ≥ 80% 只是"有效使用 GPU"的**必要非充分条件**（necessary but not sufficient）。也就是说，80% 只是"看不出明显假忙"的门槛，达标并不代表效率高；真正的效率仍要看 MFU。不要把 80% 当成达标线。

### 🔧 自己动手验：检查你的 GPU 是否在"假忙"

```bash
# 1. 装 Nsight Systems（最准确的视图）
nsys profile -o profile_%p -t cuda,nvtx python train.py

# 2. 快速检查：对比 GPU-Util 和 SM Active
# 同时开两个终端
# 终端 1：看 GPU-Util
watch -n 1 nvidia-smi --query-gpu=index,utilization.gpu --format=csv

# 终端 2：看 SM Active（需要 DCGM）
watch -n 1 'curl -s localhost:9400/metrics | grep DCGM_FI_PROF_SM_ACTIVE'

# 3. 检查 DataLoader 是否成为瓶颈
python -c "
import time

class ProfiledDataLoader:
    def __init__(self, loader):
        self.loader = loader
        self.times = []
    
    def __iter__(self):
        for batch in self.loader:
            t0 = time.time()
            yield batch
            self.times.append(time.time() - t0)
    
    def report(self):
        avg = sum(self.times) / len(self.times)
        print(f'DataLoader avg delay: {avg*1000:.1f} ms')
        print(f'如果 > 20ms，DataLoader 可能拖慢了训练')

# 使用
loader = ProfiledDataLoader(train_loader)
for batch in loader:
    # 训练
    pass
loader.report()
"
```

### ⚠️ 常见误区

- **误区**："GPU-Util 95% = GPU 95% 的时间在算东西"
  - **实际**：GPU-Util 只表示"GPU 没闲着"，并不区分"在计算"还是"在等别人"。**真正的计算效率要看 MFU 或 SM Active。**

- **误区**："加大 batch size 就能提高 GPU 利用率"
  - **实际**：如果瓶颈在通信或数据加载，加大 batch size 只会让问题更严重——**更大的 batch → 更大的梯度同步开销 → 更长的 NCCL 等待**。

- **误区**："GPU 利用率低就要加 GPU"
  - **实际**：如果利用率低是因为通信瓶颈（计算/通信比 < 1），加更多 GPU 只会**降低**通信效率。应该先优化通信。

### 📊 底线数字速查

| 场景 | GPU-Util | SM Active | 有效计算率 | 建议 |
|------|---------|-----------|-----------|------|
| 正常训练 | 95-100% | 70-90% | ~60%+ | 保持 |
| 通信瓶颈 | 85-100% | 30-50% | ~30% | 优化 NCCL |
| 小 kernel 开销 | 90-100% | 60-70% | ~45% | 合并 kernel / 增大 batch |
| DataLoader 瓶颈 | 40-80% | 30-50% | ~30% | 增加 num_workers |
| GPU 空闲 | < 50% | < 20% | < 20% | 检查代码问题 |

### 💡 一句话记住

> **"GPU-Util 95% 可能意味着你的 GPU 在'假装工作'——它在等 NCCL 通信、等数据加载、等 kernel 启动，但不是在真正做计算。真正衡量效率的指标是 MFU 和 SM Active，不是 GPU-Util。"**
