# Q: 训练断了怎么办？

## 为什么会有这个问题

训练跑了 7 天，耗费了 512 张 H100 的 **86,016 GPU 小时**（512 × 24 × 7）——按 $150,000 折算约 **$1.74/GPU-小时**。

第 7 天晚上 3 点，集群电网波动，一台机器的电源模块烧了。训练进程全部崩溃。

**你失去的不仅是 7 天的训练进度，还有 $150,000 和两周的项目周期。**

这就是 Checkpoint（检查点）要解决的问题。

## 解决什么问题

Checkpoint 的核心功能：**在训练过程中定期保存模型的完整状态，训练崩溃后可以从最近的保存点恢复，而不是从头开始。**

### 没有 Checkpoint 的世界

```
Day 1  → Day 2  → Day 3  → ... → Day 7 → 💥崩溃
Start  10%      20%             70%    回到 0%
```

### 有 Checkpoint 的世界

```
Day 1  → Day 2  → Day 3  → ... → Day 7 → 💥崩溃 → 恢复到最近保存点
Start  10%      20%             70%    最多损失一个保存间隔
（每 30-60 分钟保存一次 → 最多丢 30-60 分钟，不是 7 天）
```

### Checkpoint 里到底存了什么

```python
# 一个完整的分布式训练 Checkpoint 需要覆盖全部"会变的状态"：
checkpoint = {
    # ── 模型与训练状态 ──
    "model": model.state_dict(),              # 模型权重
    "optimizer": optimizer.state_dict(),      # 优化器状态（Adam 的 m/v、GradScaler 的 scale）
    "scheduler": scheduler.state_dict(),      # 学习率调度器状态
    "grad_scaler": grad_scaler.state_dict(),  # FP16 混合精度的 loss scale（单独列出以示重要）
    "ema": ema.state_dict() if ema else None, # EMA 权重（如果用了）
    "step": global_step,

    # ── 并行配置（恢复时校验/重分片的关键）──
    "parallel_config": {
        "tp": tp_size, "pp": pp_size,
        "dp": dp_size, "ep": ep_size,
    },

    # ── 随机数状态（保证恢复后数据增强/dropout 轨迹一致）──
    "rng": {
        "cuda": torch.cuda.get_rng_state(),       # CUDA RNG（经常被漏掉！）
        "cpu": torch.random.get_rng_state(),      # PyTorch CPU RNG
        "python": random.getstate(),              # Python random
        "numpy": np.random.get_state(),           # numpy
    },

    # ── 数据加载位置（每个 rank 都要存自己的）──
    "dataloader": dataloader.state_dict(),    # 见下文：标准 DataLoader 没有这个！
}
```

> **数据加载器状态的正确做法**：标准 `torch.utils.data.DataLoader` **没有 `state_dict()`**。断点续训要用 `torchdata` 的 `StatefulDataLoader`（PyTorch 2.4 时代随 torchdata 0.8+ 提供，drop-in 替换），它会保存"已产出多少 batch"并快进 sampler，sampler/dataset 自己定义的 `state_dict` 也会被一并序列化——这样恢复训练不会重读或漏读数据。

### 70B 模型的一个 Checkpoint 有多大？

```python
# 训练状态 = 权重 + 梯度 + FP32 master + Adam m/v = 16 B/参数
# 仅权重 + 优化器 = 14 B/参数；仅权重 = 2 B/参数
#
# 70B 完整训练状态：70e9 × 16 B ≈ 1.12 TB
# 70B 仅权重+优化器：70e9 × 14 B ≈ 980 GB
# 70B 仅权重：      70e9 × 2 B  ≈ 140 GB
#
# 每小时存一次完整状态 → 1.12 TB/h → 约 27 TB/天
# 这还只是一个任务！这就是保留策略（见下文）重要的原因
```

### Checkpoint 的"隐形杀手"效应

Checkpoint 不但是"保险"，它本身就是一个**性能杀手**：

```
开销 = 保存耗时 ÷ checkpoint 间隔

示例：单次保存 12 s，每 10 分钟保存一次
  2 s/step → 每 300 step 一个间隔（600 s）
  开销 = 12 / 600 = 2%   ✅ 在生产常见的 1-5% 区间

反例：单次保存 6 分钟，却每 100 step（200 s）存一次
  开销 = 360 / 200 = 180%  ← 这不是备份，这是自杀
  （网上流传的"6 分钟保存 + 2s/step + 每 100 step"组合就是这种，先算账再定频率）
```

**生产常用的锚点：checkpoint 开销控制在训练时间的 1-5%**，具体按 MTBF（平均无故障时间）和恢复目标（最多肯丢多少进度）调整：故障越频繁、越丢不起，间隔就应该越短、越要投资异步/分片保存把单次耗时压下来。

## 2026 年的 Checkpoint 策略

### 1. 原子性：保存完之前，旧的不覆盖

**Checkpoint 写到一半崩溃，比不写还糟**——你丢了一个原本完好的保存点。所以每次保存必须是原子的：

```python
# 模式：先写临时目录，全部写完后再 commit
tmp_dir = f"{save_dir}/checkpoint_{step}.tmp"
final_dir = f"{save_dir}/checkpoint_{step}"

torch.distributed.checkpoint.save(
    state_dict={"model": model.state_dict(), "step": step},
    storage_writer=torch.distributed.checkpoint.FileSystemWriter(tmp_dir),
)
# DCP 在所有分片写完后会写出 .metadata 文件——它的存在即"写完了"
# （DCP 内部已是"先写分片、最后提交元数据"的两阶段模式）

# 应用层再做一个原子 rename/写标记文件，确认这个 checkpoint 可用
os.rename(tmp_dir, final_dir)          # 同文件系统下 rename 是原子的
# 或者：写一个 success 标记文件，恢复时只认带标记的 checkpoint
```

### 2. 异步 Checkpoint（推荐）——以及它的两个坑

把"复制出 state 并写盘"挪到后台，GPU 不等待：

```python
# torch.distributed.checkpoint.state_dict.get_state_dict / async_save
from torch.distributed.checkpoint.state_dict import get_state_dict
import torch.distributed.checkpoint as dcp

model_sd, optimizer_sd = get_state_dict(model, optimizer)

dcp.async_save(
    {"model": model_sd, "optimizer": optimizer_sd, "step": step},
    checkpoint_id=f"{save_dir}/checkpoint_{step}",
)
# async_save 先把数据拷到 CPU staging buffer，再由后台写盘，训练继续
```

两个必须知道的坑：

- **显存/内存代价**：staging 一份 CPU 副本意味着主机内存要吃得下完整状态（或分片后的份额）；有些实现会先在 GPU 上做拷贝——峰值显存会涨，OOM 排查时别忽略这一刻。
- **竞态**：staging 拷贝完成**之前**，训练继续修改参数/优化器状态是安全的（拷的是快照）；但如果你的实现是"延迟拷贝"，必须确认拷贝完成前数据没被覆盖——用框架提供的 async API，不要自己 `threading.Thread(torch.save(...))` 然后继续训练。

### 3. 分布式 Checkpoint（DCP）

PyTorch 的分布式 Checkpoint（`torch.distributed.checkpoint`，PyTorch 1.13 引入、2.0 Prototype、**2.1 起 Beta**）——**每个 rank 只保存自己分片的那部分参数**：

```python
import torch.distributed.checkpoint as dcp

# 保存（无需集中收集所有参数）
dcp.save(
    state_dict={"model": model.state_dict(), "optimizer": optimizer.state_dict()},
    checkpoint_id="/checkpoints/step_1000/",
)

# 恢复（原地填充：先让模型分配好，再从分片填入）
dcp.load(
    state_dict={"model": model.state_dict(), "optimizer": optimizer.state_dict()},
    checkpoint_id="/checkpoints/step_1000/",
)
```

**DCP 的优势与一个必须说清的账**：

- **每个 rank 的写入量降为 1/N**（rank 越多，单卡要写的分片越小）
- 但**聚合写入量仍然是约 1.12 TB（70B 完整状态）**——总数据量没有消失，只是被摊到了 N 个 rank 并发写
- 墙钟时间是否降 N 倍，取决于**存储系统的聚合写入带宽是否随 rank 数扩展**：并行文件系统能吃下并发 → 保存更快；单点瓶颈（一个 NFS server）→ 快不起来
- **支持 load-time resharding**：保存时的 TP/PP/DP 配置和恢复时不一样也能加载（恢复到不同拓扑的集群，见下文）

### 4. "只保存变化的部分"——为什么没有免费午餐

只保存"自上次 checkpoint 以来变化的参数"（增量 checkpoint）听起来很美，但它**不是一个现成 API**，需要系统级支持：

- 训练中**几乎所有参数每步都在变**（Adam 更新是全量的），"变化的参数"并不天然存在
- 真正可行的方向是**分片级去重/脏页跟踪**：以 shard 为粒度记录"这个分片自哪个版本以来没变过"，配合版本号与引用计数——这是 ByteCheckpoint（NSDI'25）这类系统做的事：save-time/load-time 重分片、零冗余规划、异步流水线，论文报告 checkpoint 停顿平均降低 54×
- 另一条路线是 Universal Checkpointing（ATC'25）：保存时用分布式表示、加载时转成通用格式，从而**换并行配置也能恢复**，重配置时间降低 14-257×

> 自己手写"按 `grad.norm()` 挑几个层保存"不是增量 checkpoint：它既漏了 optimizer 状态和 step，又不能保证可恢复——不要用。

### 5. 保留策略

- **保留最近 3-5 个**：防止"最后一个 checkpoint 写坏了"（配合上文的原子性）
- **定期固化长期里程碑**（如每 N 小时一个永久保留点）：长时间训练要能回退到更早的收敛状态
- **保存后验证**：至少定期做一次"能 load 回来"的演练，而不是故障时才发现 checkpoint 是废的
- 按容量算账：70B 完整状态 1.12 TB/个，留 5 个就是 5.6 TB/任务——保留策略要和存储预算一起定

### 6. 频率：统一的一组自洽例子

| 场景 | 间隔 | 单次保存 | 开销 | 最多丢失窗口 |
|------|------|---------|------|------------|
| 早期/预热（step 快、丢不起） | 每 200-300 step | — | 2-3% | ≈ 间隔（10 min 量级） |
| 正常训练 | 每 30-60 min | — | 1-5% | ≤ 间隔 |
| 稳定长跑 | 每 60 min | — | 1-3% | ≤ 间隔 |

原则：**丢失窗口 ≤ 间隔**；间隔按 MTBF 调整——如果集群 MTBF 只有几小时（参考 Llama 3：54 天 419 次中断 ≈ 每 3 小时一次），间隔必须明显小于 MTBF，否则每次故障平均都要重跑半天。

### 7. 用 MTBF 反推间隔（而不是拍脑袋）

"每 30-60 分钟"是经验值，不是最优解。把开销写成关于间隔的函数：

```
总开销率 ≈ S/I + (1/MTBF) × (I/2 + R)

S      单次保存耗时（异步时取有效耗时）
I      保存间隔
MTBF   平均无故障时间
R      重启+加载 checkpoint 的恢复耗时
I/2    平均丢失的进度（故障在间隔内均匀发生时）
```

对 I 求导并令其为 0：

```
最优间隔 I* ≈ sqrt(2 × S_eff × MTBF)
```

其中 `S_eff` 是**异步保存后的有效停顿**（GPU 实际等待的时间），不是把数据写完的墙钟时间。

**代入几个真实量级**（假设单次暂停 S_eff = 60 s）：

| 集群规模 | MTBF（按规模近似） | I* | 说明 |
|---|---|---|---|
| 512 卡 | ≈ 4 天 | ≈ 1.8 小时 | 故障少，可以少存 |
| 4,096 卡 | ≈ 12 小时 | ≈ 38 分钟 | 接近经验值 |
| 16,384 卡 | ≈ 3 小时 | ≈ 19 分钟 | 故障频繁，必须加密 |

> 表中 MTBF 按"故障率随卡数线性增长"近似，只用于说明趋势；你的真实 MTBF 要从故障工单统计，不能照抄。

**公式也解释了异步 checkpoint 的价值**：异步把 `S_eff` 从"分钟级"压到"秒级"，`I*` 随之缩短，但总开销率 `S/I` 大幅下降——**不是"存得更少"，而是"用更小的停顿换更密的保存"**。

**两个前提**：
- 间隔不能短到与单次保存时间同量级，否则会连续备份、互相拖慢；
- 恢复耗时 R 不参与 I* 的推导（它是"每次故障的固定税"），但 R 很大时应优先优化恢复路径（并行加载、内存映射、热缓存），而不是继续加密 checkpoint。

**配套做法**：两级存储（先写本地 NVMe 快照、再异步上传共享存储）、保留最近 3-5 个、每季度做一次"从 checkpoint 真恢复"的演练——没演练过的 checkpoint 只能算"可能可用"。

time_per_save_s = checkpoint_size_gb / storage_bandwidth_gbps
print(f"单次保存耗时: {time_per_save_s:.1f} s")

# 目标开销 2%：间隔 = 单次耗时 / 开销
interval_s = time_per_save_s / 0.02

# 单次 5.6 s → 间隔约 4.7 分钟即可满足 2% 开销；

### 🔧 恢复时的重分片（Resharding）

```
故障恢复 ≠ 原样重启。常见情况：

1. 坏了 1 台 8 卡机，集群从 512 卡缩到 504 卡重启
   → world size 变了，每 rank 的分片边界全变
   → DCP 的 load-time resharding：按新分片边界把旧分片拼回来

2. 从"预训练配置"恢复到"继续训练配置"（TP/PP/DP 组合改变）
   → 同样靠 resharding；Universal Checkpointing / ByteCheckpoint
     把这件事做成了通用能力（任意并行配置间转换）

3. 不支持 resharding 的老式 torch.save 单文件 checkpoint：
   → 只能起一个和原来完全相同的拓扑来读——这就是大规模训练
     一开始就选 DCP 的理由之一
```

### 🔧 弹性训练（Elastic Training）

Checkpoint 解决"状态不丢"，弹性训练解决"**成员变化后继续跑**"：

```bash
# torchrun 的弹性机制：节点数变化时自动重新 rendezvous
torchrun \
  --nnodes=2:8 \                    # 最少 2 个、最多 8 个节点，区间内可弹性
  --nproc-per-node=8 \
  --rdzv-backend=c10d \             # 动态 rendezvous（不用固定 rank 映射）
  --rdzv-endpoint=master:29400 \
  --max-restarts=5 \                # 成员变更/失败后的自动重启次数
  train.py
```

- **Rendezvous**：每次启动/成员变化时，所有存活节点重新协商"这次有哪些成员、谁是谁"（rank 重排），然后各自从最近的 checkpoint 恢复。
- **Slurm**：配合 `sbatch --requeue` + checkpoint——作业被抢占/节点故障时重新入队，重启后从 checkpoint 恢复。
- **Kubernetes**：JobSet（kubernetes-sigs/jobset）为多副本训练作业提供整体成功/失败语义，配合弹性重跑；训练框架侧用 torchrun 的 rendezvous 处理成员变化。

**弹性训练和 checkpoint 的关系**：弹性不是 checkpoint 的替代品——恰恰相反，**每次成员变更都要从 checkpoint 恢复**（新成员集合从上一个保存点重新出发），所以弹性训练对 checkpoint 的要求更高（频率、恢复速度、resharding）。

**为什么不是所有模型都能无缝弹性**：

- 全局 batch size 通常绑定 world size——成员数变了，要么改梯度累积步数补偿，要么接受有效 batch 变化影响收敛
- TP/PP 的划分一般绑定固定拓扑（TP=8 就需要 8 卡一组），成员变化只能动 DP 维度
- 优化器/数据流水线的 RNG 与数据分片都要随新 rank 映射重算
- 因此"真弹性"（任意规模变化不中断）目前只在有限范围内实用，多数生产系统的形态是：**缩容恢复 + 从 checkpoint 重启**，而不是热变更

### ⚠️ 常见误区

- **误区**："Checkpoint 频率越高越好"
  - **实际**：Checkpoint 本身就是性能开销——**开销 = 保存耗时 ÷ 间隔**。生产控制在 1-5%，更实际的做法：先定"丢得起的最长训练时间"（结合 MTBF），再倒推间隔，最后确认开销可接受。

- **误区**："DCP 让每张卡少写 N 倍，所以保存一定快 N 倍"
  - **实际**：单 rank 写入量降 N 倍，但**聚合写入量仍是完整状态的 1.12 TB（70B）**。墙钟提速取决于存储聚合带宽能否随 rank 扩展——并行文件系统可以，单点存储不行。先实测存储带宽，再定频率。

- **误区**："Checkpoint 保存完就安全了"
  - **实际**：写到一半的 checkpoint 可能是坏的（这正是需要**原子提交**的原因）。保留最近 3-5 个 + 定期验证可加载。更保险的做法：保存到临时目录，rename/写标记后才算成功。

- **误区**："标准 DataLoader 的状态会自动被保存"
  - **实际**：标准 `torch.utils.data.DataLoader` 没有 `state_dict()`。用 `torchdata` 的 `StatefulDataLoader`，并确认每个 rank 的 sampler 状态、CUDA/numpy/python RNG 都进了 checkpoint。

### 📊 底线数字速查

| 模型 | 仅权重（BF16, 2B/参数） | 权重+优化器（14B/参数） | 完整训练状态（16B/参数） |
|------|----------------------|----------------------|------------------------|
| 7B | 14 GB | 98 GB | 112 GB |
| 13B | 26 GB | 182 GB | 208 GB |
| 70B | 140 GB | 980 GB | **1.12 TB** |
| 405B | 810 GB | 5.67 TB | 6.48 TB |

| 项目 | 推荐值 |
|------|-------|
| 保存间隔 | 每 30-60 分钟（或按"丢得起的时间"倒推） |
| 开销 | 1-5%（保存耗时 ÷ 间隔） |
| 保留 | 最近 3-5 个 + 定期永久里程碑 |
| 数据状态 | StatefulDataLoader（标准 DataLoader 无 state_dict） |
| 原子性 | 临时目录 + rename/commit，恢复只认已提交的 checkpoint |
| 恢复 | 依赖 DCP load-time resharding 应对拓扑变化 |

### 💡 一句话记住

> **"Checkpoint 的三笔账：账一，存什么——权重只是零头（140GB），完整训练状态是 1.12TB，漏了 RNG/sampler/优化器状态就恢复不出原轨迹；账二，多久存——开销 = 保存耗时 ÷ 间隔，锚定 1-5%，丢失窗口 ≤ 间隔，间隔小于 MTBF；账三，存到哪——原子提交 + 保留策略 + 可 reshard 的分片格式，坏 checkpoint 比没 checkpoint 更糟。"**
