# Q: 训练断了怎么办？

## 为什么会有这个问题

训练跑了 7 天，耗费了 512 张 H100 的 **86,016 GPU 小时**（512 × 7 × 24）——折合云计算成本约 **$150,000**（约 $1.74/GPU·h，符合 H100 市价）。

第 7 天晚上 3 点，集群电网波动，一台机器的电源模块烧了。训练进程全部崩溃。

**你失去的不仅是 7 天的训练进度，还有 $150,000 和两周的项目周期。**

这就是 Checkpoint（检查点）要解决的问题。

## 解决什么问题

Checkpoint 的核心功能：**在训练过程中定期保存模型的完整状态，训练崩溃后可以从最近的保存点恢复，而不是从头开始。**

### 没有 Checkpoint 的世界

```
Day 1  → Day 2  → Day 3  → ... → Day 7 → 💥崩溃
Start  10%      20%             70%    回到 0%
```

### 有 Checkpoint 的世界

```
Day 1  → Day 2  → Day 3  → ... → Day 7 → 💥崩溃 → 恢复到 Day 6 晚
Start  10%      20%             70%    回到 65% → 损失 0.5 天
```

### Checkpoint 里到底存了什么

```python
# 一个完整的 Checkpoint 包含
checkpoint = {
    "model_state_dict": model.state_dict(),  # 模型权重
    "optimizer_state_dict": optimizer.state_dict(),  # 优化器状态（Adam 动量和方差）
    "scheduler_state_dict": scheduler.state_dict(),  # 学习率调度器状态
    "epoch": current_epoch,
    "step": global_step,
    "loss": current_loss,
    "random_state": torch.random.get_rng_state(),  # 随机数状态（保证可复现）
    "data_loader_state": dataloader.state_dict(),  # 数据加载器位置
}
```

### 70B 模型的一个 Checkpoint 有多大？

```python
# 按统一口径 16 bytes/参数估算（fp16 权重 2 + fp16 梯度 2 + fp32 master 权重 4 + Adam 动量 4 + 方差 4）：
# 70B 参数 × 2 bytes（BF16 权重）= 140 GB
# 70B 参数 × 2 bytes（BF16 梯度）= 140 GB
# 70B 参数 × 4 bytes（FP32 master 权重）= 280 GB
# 70B 参数 × 8 bytes（Adam 动量 + 方差，各 4 bytes）= 560 GB
# 总计 ≈ 16 bytes/参数 ≈ 1.12 TB（这才是一个"完整的"训练态 Checkpoint）
#
# 如果按"每 1 小时存一次"这种激进策略 → ~1.12 TB/h → ~27 TB/天
# 这还只是一个任务！（按 1% 规则，推荐间隔要长得多，见下）
```

### Checkpoint 的"隐形杀手"效应

Checkpoint 不但是"保险"，它本身就是一个**性能杀手**：

```
单次 Checkpoint 写入时间 = 1.12 TB / 写入带宽

假设写入带宽为 2 GB/s（对标 NVIDIA DGX SuperPOD 参考架构的 Medium 档）：
  1120 GB / 2 GB/s = 560 秒 ≈ 9.3 分钟

如果每小时存一次 → 每 60 分钟里有 9.3 分钟在"空转" → 约 15.6% 的 GPU 时间浪费
在 512 GPU 集群上：浪费 512 × 0.156 × 24h ≈ 1,916 GPU 小时/天
```

> 想让写入更快，还可以让 Checkpoint 路径走 **GPU Direct Storage（GDS）**——绕过 CPU 直接 SSD↔显存，详见 [[04-存储篇/04-GPU-Direct-Storage]]。

**这就是所谓的 Checkpoint 开销——训练团队在"保险"和"效率"之间不断权衡。**

## 2026 年的 Checkpoint 策略

### 1. 异步 Checkpoint（推荐）

将 Checkpoint 写入操作卸载到后台线程，不让 GPU 等待：

```python
# 异步保存（训练不暂停）
import torch
import threading

class AsyncCheckpointer:
    def __init__(self, save_dir, interval_steps=1000):
        self.save_dir = save_dir
        self.interval = interval_steps
    
    def save(self, model, optimizer, step):
        if step % self.interval != 0:
            return
        
        # 关键：先做 D2H（GPU→CPU）拷贝到 pinned 主机内存，再交给后台线程落盘。
        # 绝不能像常见写法那样 {k: v.clone() ...} 只在 GPU 上复制 state_dict——
        # 那样后台线程里的 torch.save 仍要读 GPU 显存（走 H2D 带宽），训练照样被拖慢，
        # 而且显存会短暂翻倍。工业实现（DCP async / DeepSpeed / NeMo）都走"pinned CPU 内存"这条路。
        state = {
            'model': {k: v.detach().to('cpu', non_blocking=True) for k, v in model.state_dict().items()},
            'optimizer': optimizer.state_dict(),   # 严格做法：优化器状态也应同样 D2H 后再传
            'step': step,
        }
        
        # 后台线程保存到磁盘（不阻塞训练）
        thread = threading.Thread(
            target=self._write_to_disk,
            args=(state, f'{self.save_dir}/checkpoint_{step}.pt')
        )
        thread.start()
    
    def _write_to_disk(self, state, path):
        torch.save(state, path)
```

### 2. 分布式 Checkpoint（DCP）

PyTorch 从 2.0/2.1 起就提供了分布式 Checkpoint 能力（最初叫 `torch.distributed._shard.checkpoint`，后稳定为公开 API `torch.distributed.checkpoint`）——**每张卡只保存自己分片的那部分参数**：

```python
from torch.distributed.checkpoint import save, load, FileSystemWriter, FileSystemReader
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP

# 保存（无需集中收集所有参数）
save(
    state_dict={"model": model.state_dict()},
    storage_writer=FileSystemWriter("/checkpoints/"),
    checkpoint_id="/checkpoints/step_1000",
)

# 恢复
load(
    state_dict={"model": model.state_dict()},
    storage_reader=FileSystemReader("/checkpoints/"),
    checkpoint_id="/checkpoints/step_1000",
)
```

**DCP 的优势**：
- 每卡只保存自己的分片 → 写入量从 ~1.12 TB 降到 ~1.12 TB/N
- 写入时间从 ~9.3 分钟降到 ~9.3/N 分钟
- 支持弹性 Checkpoint（节点数量发生变化时也能恢复）

### 3. 增量 Checkpoint

只保存自上次 Checkpoint 以来**发生变化**的参数：

```python
# 只保存梯度变化较大的层
for name, param in model.named_parameters():
    if param.grad is not None:
        grad_norm = param.grad.norm().item()
        if grad_norm > threshold:
            # 保存这一层
            incremental_state[name] = param.data.clone()
```

### 4. 分阶段 Checkpoint 策略

| 训练阶段 | 频率 | 保存量 | 理由 |
|---------|------|--------|------|
| 预热（前 500 step） | 每 100 step | 完整 | 这个阶段变化快，丢失代价高 |
| 正常训练 | 每 1000-5000 step | 完整 | 平衡保险和性能 |
| 收敛阶段 | 每 500 step | 完整 | 接近期望结果，不可丢失 |
| 日常恢复 | — | 最近的 3 个 | 防止"坏 Checkpoint" |

### 5. 弹性训练：让它自己重启（这才是"训练断了怎么办"的核心答案）

Checkpoint 只解决"不丢进度"，真正让训练"断了能自动接着跑"的是**弹性训练**：

- **torchrun 弹性**：`torchrun --nnodes=8-16 --nproc_per_node=8 --max-restarts=10 --rdzv-backend=c10d --rdzv-endpoint=node0:29500 train.py`。`--max-restarts` 控制自动重启次数，节点数写成区间（`8-16`）即可在节点增减时继续。
- **Slurm**：`sbatch --requeue` + 训练脚本捕获信号后保存并退出，被抢占/故障的作业会自动重新排队。
- **K8s**：Job 的 `restartPolicy: OnFailure`，或带重启能力的调度器（Volcano / JobSet），配合 Checkpoint 实现自愈。

只要"Checkpoint + 自动重启"配好，机器偶尔挂掉就不会变成"白跑"。

## 🛠 实操指南

### 📋 决策指南：你的 Checkpoint 策略应该怎么做？

```python
# Checkpoint 频率计算器
model_size_gb = 140       # 70B BF16 权重（2 B/参数）
grad_size_gb = 140        # 70B BF16 梯度（2 B/参数）
master_size_gb = 280      # 70B FP32 master 权重（4 B/参数）
optimizer_size_gb = 560   # Adam 动量 + 方差（8 B/参数）
checkpoint_size_gb = model_size_gb + grad_size_gb + master_size_gb + optimizer_size_gb  # ≈1120 GB

storage_bandwidth_GBps = 2  # 存储系统写入带宽（GB/s，对标 DGX SuperPOD Medium 档）
time_per_checkpoint_min = checkpoint_size_gb / storage_bandwidth_GBps / 60
print(f"单次 Checkpoint 耗时: {time_per_checkpoint_min:.1f} 分钟")

# 1% 规则：Checkpoint 开销不要超过训练时间的 1%
checkpoint_interval_min = time_per_checkpoint_min * 100
print(f"推荐间隔: 每 {checkpoint_interval_min:.0f} 分钟")
print(f"= 在 batch_size=4, seq_len=4096 下:")

# 显式定义步时（此前隐式的"2 秒/step"）：本配置实测约 2 s/step，
# 需按你的实际吞吐替换。2 s/step → 30 step/分钟。
steps_per_min = 30
print(f"  约 {checkpoint_interval_min * steps_per_min:.0f} step 存一次")

# 更严谨的做法：Young/Daly 最优检查点间隔（MTBF 意义下，而非"由结果反推间隔"）
#   P = sqrt(2 · μ · C)                       （μ = MTBF，C = 单次 checkpoint 耗时）
#   计入检测/恢复开销 D、R 后（Daly 修正）：
#   P = sqrt(2 · (μ + D + R) · C) + C
import math
mtbf_h = 96         # 示例：512 卡集群按 Llama 3 故障率折算的 MTBF（小时）
C_h = time_per_checkpoint_min / 60
D_plus_R_h = 0.5    # 检测 + 重启恢复的开销（小时）
young_daly_min = (math.sqrt(2 * (mtbf_h + D_plus_R_h) * C_h) + C_h) * 60
print(f"Young/Daly 最优间隔: 约 {young_daly_min:.0f} 分钟（{young_daly_min/60:.1f} 小时）")
```

```
你的集群规模？
├─ < 8 卡 →
│   └─ 简单 torch.save，每 1000-5000 step 存一次
│
├─ 8-64 卡 →
│   ├─ 使用 DCP（分布式 Checkpoint）
│   └─ 每 1-2 小时存一次
│
├─ 64-512 卡 →
│   ├─ DCP + 异步 Checkpoint
│   ├── Checkpoint 开销不应超过 5%
│   └── 保留最近 3-5 个 Checkpoint
│
└─ > 512 卡 →
    ├─ DCP + 增量 Checkpoint + 异步写入
    ├─ 分阶段调整频率（预热期更频繁）
    ├─ 多路径写入（同时写到两个存储位置）
    └─ 自动验证 Checkpoint 完整性
```

### ⚠️ 常见误区

- **误区**："Checkpoint 频率越高越好"
  - **实际**：Checkpoint 本身就是性能开销——频繁保存意味着更多的 GPU 时间被用在写入磁盘上。**推荐让 Checkpoint 开销不超过训练时间的 1-5%**。更实际的做法：找到"丢得起的最长训练时间"，然后把这个时间作为 Checkpoint 间隔。

- **误区**："分布式训练每张卡都要保存完整的 Checkpoint"
  - **实际**：FSDP/ZeRO-3 下每张卡只保存自己分片的那部分参数。**使用 DCP（分布式 Checkpoint）可以节省 N 倍的存储空间和写入时间**。不要用传统的 `torch.save(model.state_dict())` 做分布式 Checkpoint。

- **误区**："Checkpoint 保存完就安全了"
  - **实际**：**Checkpoint 在写入过程中可能损坏**（磁盘故障、网络中断）。保留最近 3-5 个 Checkpoint 并定期验证其完整性。更保险的做法：**保存后立即读取验证**。

### 📊 底线数字速查

| 模型大小 | 单次 Checkpoint | 建议间隔（1% 规则）| 存储需求（日）|
|---------|----------------|---------|--------------|
| 7B | ~110 GB | 每 1-2 h | ~1.8 TB |
| 13B | ~210 GB | 每 3 h | ~1.7 TB |
| 70B | ~1.12 TB | 每 12-18 h | ~1.8 TB |
| 405B | ~6.5 TB | 每 3-4 天 | ~1.9 TB |

> 口径说明：Checkpoint 体积按 **16 bytes/参数** 的统一口径估算；间隔由"1% 规则"反推（约 100 × 单次耗时）。在固定写入带宽下，把开销控制在 1% 意味着"日存储量"大致恒定（约 0.01 × 86400 s × 2 GB/s ≈ 1.7 TB/天），与模型大小无关。

### 💡 一句话记住

> **"Checkpoint 是训练的'保险单'——保费（写入时间）不能太高，保额（恢复进度）不能太低。2026 年的最佳实践是：分布式 Checkpoint（DCP）+ 异步写入 + 分阶段调整频率 + 保留最近 3-5 个。不要让一次断路器跳闸毁了你 7 天的训练。"**
