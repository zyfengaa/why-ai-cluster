# 第八篇：运维观测篇 — 集群跑起来之后

## 本篇章回答的问题

| Q&A | 核心链条 |
|------|---------|
| [Q1: 集群监控到底要监控什么？](01-集群监控到底要监控什么.md) | 分层指标（应用/框架/系统/基础设施）+ MFU 才是主线 |
| [Q2: 为什么 GPU 利用率 100% 不一定好？](02-为什么GPU利用率100不一定好.md) | GPU-Util 只统计"有 kernel 在执行"，通信会"假忙"；看 SM/Tensor/DRAM Active 与 MFU |
| [Q3: NCCL 调优到底在调什么？](03-NCCL调优到底在调什么.md) | 算法×协议×信道：先建 nccl-tests 基线，再确认 IB/GDR 没被 TCP 回退 |
| [Q4: 为什么说"慢节点"是大集群的头号杀手？](04-为什么说慢节点是大集群的头号杀手.md) | 同步通信取 max(t_i)，一个慢节点拖平全局；靠训练前扫 + 训练中检测 |
| [Q5: 训练断了怎么办？](05-训练断了怎么办.md) | Checkpoint（DCP + 异步）决定"丢多少"，弹性重启决定"能不能自己接着跑" |
| [Q6: Profiling 工具怎么用？](06-Profiling工具怎么用.md) | Nsight Systems 定层、Nsight Compute 定 kernel、PyTorch Profiler 验证 |

**核心因果链**：先把指标看清（监控）→ 发现利用率会骗人（GPU-Util 假忙）→ 定位到通信开销（NCCL 调优）→ 揪出拖垮全局的慢节点（Straggler）→ 断了自己能恢复（Checkpoint + 弹性重启）→ 用 Profiling 定位根因
