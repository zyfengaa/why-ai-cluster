# Q: 万卡集群的监控数据放哪、怎么查？

## 为什么会有这个问题

8 卡的时候，`nvidia-smi` + 一个 Grafana 面板就够了。到了 1,000 卡甚至 10,000 卡，同一套方案会依次崩在三件事上：

- **采集崩**：指标 series 从几千涨到百万级，Prometheus 内存和查询都扛不住；
- **存储崩**：保留 30 天要几十 TB，本地磁盘先爆；
- **归因崩**：你知道 3 号机 5 号卡在忙，但不知道它属于哪个用户、哪个作业、哪一步。

这一篇解决的是"指标从哪来、放哪、怎么查、怎么归因"。

## 解决什么问题：四层数据管道

```
采集 → 传输/存储 → 查询/面板 → 归因/告警
DCGM    Prometheus     Grafana      job/user 标签
各 exporter + remote write + 降采样   + SLO
```

### 1. 先算基数，再选存储

一个粗略但够用的估算：

```
活跃 series ≈ GPU 数 × 每卡指标数 × 标签维度放大系数

10,000 卡 × 30 个 DCGM 指标 × 1.5（job/rack/namespace 等标签）
≈ 45 万 ~ 100 万 series
```

再乘采集频率：**15 秒采集、百万 series，一天就是几十 GB 的压缩后数据**。单机 Prometheus 的默认配置（本地 TSDB、15 天保留）在万卡规模下一定会被撑爆。

> 不要用"每卡一个面板"的思路做万卡监控。面板数量不是问题，**series 基数**才是。

### 2. 存储分层：本地 + 长期 + 降采样

| 层 | 保留 | 用途 | 常见方案 |
|---|---|---|---|
| **本地** | 7-15 天 | 即时查询、告警 | Prometheus 本地 TSDB |
| **长期** | 6-12 个月 | 趋势、容量规划、复盘 | Thanos / Mimir / VictoriaMetrics |
| **降采样** | 1-3 年 | 季度/年度报表 | 5 min → 1 h 聚合 |

```yaml
# prometheus.yml：本地保留 15 天，同时远程写长期存储
remote_write:
  - url: http://mimir:9009/api/v1/push
    queue_config:
      max_samples_per_send: 10000
      max_shards: 50
```

```bash
# Prometheus 启动参数
--storage.tsdb.retention.time=15d
--storage.tsdb.retention.size=500GB
```

**降采样规则**：原始 15s 数据保留 15 天，5 分钟聚合保留 6 个月，1 小时聚合保留 2 年。查询"上周三下午的尖峰"用原始层，查询"这个季度 GPU 利用率趋势"用降采样层。

### 3. 采集分层：基础指标常开，profiling 指标按需

DCGM 的指标不是免费的，开销分两档：

| 类型 | 例子 | 开销 | 建议 |
|---|---|---|---|
| **基础设备指标** | `DCGM_FI_DEV_GPU_UTIL`、温度、功耗、显存、时钟 | 低 | 常开，15-30s |
| **profiling 指标** | `DCGM_FI_PROF_SM_ACTIVE`、`DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` | 高（需要额外采样） | 按需开启，或只在排障窗口开 |
| **事件/错误指标** | XID、ECC、NVLink CRC | 低 | 常开，立即告警 |

**不要把 `nvidia-smi` 当采集器**：它是查询工具，不是监控代理；高频调用会和训练抢驱动锁。

### 4. 标签设计：决定你能怎么查

```text
推荐：cluster / rack / node / gpu / job_id / user / namespace
禁止：container_id / pid / gpu_uuid（高基数） / timestamp
```

高基数标签是 series 爆炸的头号原因。`gpu_uuid` 看起来有用，但每张卡一个值，10,000 卡就是 10,000 倍；可以用 `node + gpu_index` 代替，需要 UUID 时再关联。

### 5. 作业归因：把 GPU 指标映射到人

DCGM 只知道 GPU，不知道"谁在用"。归因要补一层映射：

```bash
# Slurm：从进程 cgroup 反查 job id
for pid in $(nvidia-smi --query-compute-apps=pid --format=csv,noheader); do
  job=$(cat /proc/$pid/cgroup | grep -oP 'job_\K[0-9]+' | head -1)
  user=$(ps -o user= -p $pid)
  echo "pid=$pid job=$job user=$user"
done
```

```bash
# K8s：device plugin 会给 Pod 注入 NVIDIA_VISIBLE_DEVICES，
# 用它把 GPU UUID ↔ Pod ↔ Namespace 关联起来
kubectl get pod -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.metadata.namespace}{" "}{.spec.containers[*].env[?(@.name=="NVIDIA_VISIBLE_DEVICES")].value}{"\n"}{end}'
```

有归因之后，才能回答"这个月的 GPU 时间花在哪个项目上"——这是容量规划和成本分摊的前提。

### 6. 日志与 Trace：指标之外的证据

- **结构化日志**：训练日志按 JSON 输出（step、loss、lr、tokens/s、rank），便于按 job 聚合；
- **OpenTelemetry**：把"数据加载 → 前向 → 反向 → 通信 → checkpoint"做成 span，定位是哪个阶段慢；
- **NCCL Flight Recorder / Inspector**：通信层的持续记录，出问题时 dump 最近的 collective 历史；
- **不要把所有日志都塞进 Prometheus**：日志走 Loki/ES，指标走 TSDB，trace 走 Jaeger/Tempo，各管一段。

### 7. 推理集群的指标（与训练不同）

训练看 MFU 和 step time，推理看 **TTFT / TPOT / 吞吐 / 队列**：

| 指标 | 含义 | 典型 SLO（示例） |
|---|---|---|
| TTFT | 首 token 延迟 | P99 < 2 s |
| TPOT | 每输出 token 延迟 | P99 < 50 ms |
| 队列深度 | 等待调度的请求数 | 持续为 0 或可解释 |
| KV cache 命中率 | prefix cache 命中比例 | 越高越好，按场景定 |
| GPU KV 使用率 | KV cache 占显存比例 | < 80% 留余量 |

vLLM 等引擎会直接暴露这些指标（如 `vllm:time_to_first_token_seconds`、`vllm:gpu_cache_usage_perc`，名称以你的版本为准）。推理集群的完整设计见 [09-06-推理集群](../09-前沿与实践篇/06-推理集群.md)。

## 🛠 实操指南

### 📋 决策指南：你的监控栈怎么搭？

```
集群规模？
├─ < 64 卡 → Prometheus 单机 + Grafana，15 天保留
│
├─ 64-512 卡 → Prometheus 本地 + 远程写到 Mimir/Thanos
│              + 基础指标 30s，profiling 指标按需
│
├─ 512-5,000 卡 → 分片采集（每机房一个 Prometheus）
│                  + 长期存储 + 降采样 + 作业归因
│
└─ > 5,000 卡 → 专用可观测平台（Mimir/VictoriaMetrics 集群）
                 + 分级告警 + 推理/训练分开采
                 + 数据质量巡检（缺失 series、标签漂移）
```

### 🔧 自己动手验：基线与基数

```bash
# 1. 查 series 基数（最该先做的体检）
curl -s localhost:9090/api/v1/query --data-urlencode 'query=count({__name__=~".+"})' | jq
# > 200 万 → 该上远程存储/降采样了

# 2. 查哪个指标 series 最多
curl -s localhost:9090/api/v1/query --data-urlencode 'query=topk(10, count by (__name__)({__name__=~".+"}))' | jq

# 3. 查每个 scrape 的样本量
curl -s localhost:9090/api/v1/query --data-urlencode 'query=sum(scrape_samples_scraped)' | jq

# 4. 检查是否有高基数标签（返回结果里出现 uuid/pid 就要警惕）
curl -s localhost:9090/api/v1/query --data-urlencode 'query=count by (gpu_uuid)(DCGM_FI_DEV_GPU_UTIL)' | jq
```

### ⚠️ 常见误区

- **误区**："指标越多越好"
  - **实际**：指标的成本是**存储 × 基数 × 采集频率**。万卡规模下，多 10 个 profiling 指标可能多出几十万 series。先定义"要回答的问题"，再决定采什么。

- **误区**："Prometheus 能存一年"
  - **实际**：单机 Prometheus 适合短保留（7-15 天）。长期存储要靠 Thanos/Mimir/VictoriaMetrics，且必须做降采样，否则查询会慢到不可用。

- **误区**："DCGM profiling 指标是免费的"
  - **实际**：`DCGM_FI_PROF_*` 需要额外采样，开销明显高于基础设备指标。长期全量采集会挤占训练资源，建议按需开启或只在排障窗口开。

- **误区**："有监控面板就能定位问题"
  - **实际**：面板告诉你"哪里异常"，`nsys` / `ncu` / 日志 / trace 才告诉你"为什么异常"。监控是入口，不是终点。

- **误区**："训练和推理可以用同一套指标"
  - **实际**：训练看 MFU、step time、通信占比；推理看 TTFT、TPOT、队列、KV 命中率。指标体系不同，面板和告警阈值都要分开。

## 📊 底线数字速查

| 项目 | 推荐值 | 说明 |
|---|---|---|
| 基础指标采集间隔 | 15-30 s | 再密对诊断帮助有限，成本线性上涨 |
| 本地保留 | 7-15 天 | 覆盖最近一次故障复盘 |
| 长期保留 | 6-12 个月 | 容量规划与季度报表 |
| 降采样 | 5 min / 1 h 两级 | 长期查询只走降采样 |
| series 规模警戒线 | 单 Prometheus > 200 万 | 超过就该分片或上远程存储 |
| 告警数量 | 每人每天 < 5 条 | 超过说明阈值/分组有问题 |
| 归因覆盖率 | > 95% 的 GPU 时间可归到 job | 否则成本分摊不可信 |

---

## 💡 一句话记住

> **"万卡监控的瓶颈不是面板，是 series 基数和保留策略：基础指标常开、profiling 指标按需、本地只留 7-15 天、长期靠远程存储 + 降采样；再用 job/user 标签把 GPU 指标归因到人。训练看 MFU，推理看 TTFT/TPOT，两套指标别混。"**
