# Q: 集群监控到底要监控什么？

## 为什么会有这个问题

一个 AI 集群跑起来了。你在 Grafana 上搭了 20 个面板，实时刷新 CPU 使用率、内存占用、网络流量……看起来很酷。

但问题来了：**CPU 使用率 50% 意味着什么？网络流量 10 Gbps 是好是坏？GPU 利用率 100% 是不是真的高效？**

AI 集群监控的坑是：**指标太多，但真正能指导行动的太少**。本章帮你理清：到底哪些指标值得看，哪些只是"看起来有用"。

## 解决什么问题

AI 集群监控要回答的核心问题只有三个：

```
1. 训练跑得快不快？  →  性能指标
2. 集群健康不健康？  →  健康检查
3. 出问题了找谁？    →  根因定位
```

### 监控的分层结构

```
┌─────────────────────────────────────────┐
│              应用层指标                    │
│  MFU、吞吐（tokens/s）、Loss 曲线        │
├─────────────────────────────────────────┤
│              框架层指标                    │
│  NCCL 通信时间、计算时间、梯度同步延迟    │
├─────────────────────────────────────────┤
│              系统层指标                    │
│  GPU kernel 执行时间占比、显存、          │
│  NVLink 带宽、PCIe、XID/ECC 错误         │
├─────────────────────────────────────────┤
│              基础设施层指标                │
│  网络吞吐、延迟、丢包、存储 IOPS          │
└─────────────────────────────────────────┘
```

### 关键指标速查

| 层级 | 关键指标 | 怎么看 | 报警阈值 |
|------|---------|--------|---------|
| **GPU 计算** | GPU-Util（kernel 执行时间占比） | `nvidia-smi` | < 80%（连续 5 min）——注意它**不是算力利用率** |
| **GPU 内存** | 显存占用 | `nvidia-smi` | > 95%（OOM 风险） |
| **GPU 互联** | NVLink 链路状态与错误 | `nvidia-smi nvlink -s`（状态）、`-e`（错误计数） | 链路速率低于标称、CRC 错误持续增长 |
| **GPU 温度** | 核心温度 | `nvidia-smi` | > 85°C（降频风险）|
| **GPU 降频** | throttle reasons | `nvidia-smi -q -d PERFORMANCE` | 满载时出现 HW/SW slowdown 且非功耗/温度正常代价 |
| **网络** | IB/RoCE 吞吐与端口错误 | `ibstat`, `ibqueryerrors` | 低于基准 20%、端口错误计数非零 |
| **存储** | Checkpoint 写入带宽 | `iostat` / 并行文件系统自带指标 | 低于设计值（DCGM 不采集存储指标）|
| **训练** | MFU（Model FLOPS Utilization）| Profiling | < 40%（亮黄牌）|

### 最重要的指标：MFU

AI 集群监控里没有比 **MFU（Model FLOPS Utilization）** 更重要的指标了。它不是"GPU 利用率"——而是 **"GPU 的理论算力被实际用上了百分之几"**。

```python
# MFU 的计算
def calc_mfu(observed_tflops, gpu_peak_tflops, n_gpus):
    return observed_tflops / (gpu_peak_tflops * n_gpus)

# 示例：64 卡 H100 的 MFU
peak = 989  # H100 BF16 稠密峰值 TFLOPS（稀疏是 1,979，别混用）
observed = 32000  # 64 卡实际 TFLOPS
mfu = calc_mfu(observed, peak, 64)
print(f"MFU = {mfu:.1%}")  # ~50%
```

**MFU 参考值**：

| 模型 | 并行配置 | MFU 范围 | 评价 |
|------|---------|---------|------|
| Llama 7B | 8×H100, FSDP2 | 35-45% | 入门水平（经验值） |
| Llama 70B | 64×H100, FSDP2+TP | 40-50% | 及格（经验值） |
| Llama 405B | 16,384×H100, Megatron 4D | **38-43%** | Meta 公开值（Llama 3 论文） |

> 注意：405B 的 38-43% 是 Meta 公开报告的数字，不要拿小模型的经验值去"要求"超大模型。

## 监控工具栈

| 工具 | 层级 | 优点 | 缺点 |
|------|------|------|------|
| **DCGM（NVIDIA）** | GPU 系统 | 官方指标集，低开销 | 只覆盖 GPU，不覆盖存储/网络 |
| **Prometheus + Grafana** | 全栈 | 标准方案，生态丰富 | 需要搭建 |
| **nvidia-smi** | GPU 硬件 | 默认安装，随手查 | 不能长期存储 |
| **NVML（NVIDIA Management Library）** | GPU 底层 | Python 可编程 | 较底层 |
| **DCGM Exporter** | Prometheus | GPU 指标自动暴露 | 需部署 DaemonSet |
| **NCCL Inspector** | 通信层 | 每个 collective 的带宽/耗时 | NCCL 2.23+ 才有 profiler 插件接口 |

### DCGM 的推荐采集指标

```bash
# 安装并启动 dcgm-exporter
docker run -d --gpus all --rm \
  --name dcgm-exporter \
  -p 9400:9400 \
  nvidia/dcgm-exporter:latest

# Prometheus 可抓取的 GPU 指标
# curl localhost:9400/metrics | head -20

# 关键指标（均为 DCGM 真实字段名）：
# - DCGM_FI_DEV_GPU_UTIL       → GPU-Util：kernel 执行时间占比（不是算力利用率）
# - DCGM_FI_PROF_SM_ACTIVE     → SM Active：0-1 比例，warp 驻留情况
# - DCGM_FI_DEV_FB_FREE        → 剩余显存（容量看 FB_USED/FB_FREE，不是 MEM_COPY_UTIL）
# - DCGM_FI_DEV_NVLINK_BANDWIDTH_TOTAL → NVLink 总带宽计数
# - DCGM_FI_DEV_POWER_USAGE    → GPU 实时功耗
# - DCGM_FI_DEV_SM_CLOCK       → SM 时钟频率（降频检测）
# - DCGM_FI_DEV_MEM_CLOCK      → 显存时钟频率
# - DCGM_FI_DEV_XID_ERRORS     → 最近一次 XID 错误码
# - DCGM_FI_DEV_ECC_DBE_VOL_TOTAL → 易失性双位（uncorrectable）ECC 错误总数
# - DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_TOTAL → NVLink CRC flit 错误总数
# - DCGM_FI_DEV_POWER_VIOLATION → 功耗违例（power violation）事件计数
```

> **存储不在 DCGM 的职责范围内。** Checkpoint 写入带宽、并行文件系统吞吐要用 `iostat`、`nfsiostat` 或文件系统自带工具（GPFS `mmfsmon`、Lustre `lctl get_param`、WEKA/对象存储的监控端点）采集。

## 🛠 实操指南

### 📋 决策指南：你的监控方案应该怎么做？

```
你的集群规模？
├─ < 8 卡（个人/小团队）→
│   └─ nvidia-smi + 简单的训练日志就够了
│       watch -n 2 nvidia-smi
│
├─ 8-64 卡（小集群）→
│   └─ DCGM Exporter + Prometheus + Grafana
│       核心面板：GPU-Util/SM Active、显存、温度、NVLink
│
├─ 64-512 卡（中等集群）→
│   ├─ 系统层：DCGM + Prometheus
│   ├─ 框架层：训练日志 / WandB
│   └─ 训练层：MFU 面板 + Loss 曲线
│
└─ > 512 卡（大规模）→
    ├─ 全栈监控 + 报警
    ├─ 慢节点检测系统（Guard / SMon / Falcon / NCCL Inspector）
    └─ 拓扑健康状况自动巡检
```

> 注意区分两类同名带"Straggler"的东西：**Guard、SMon、Falcon 是慢节点检测/管理系统**；**StragglAR 是一种 AllReduce 算法**（利用 straggler 到达同步点的延迟先做 ReduceScatter），它是通信算法，不是检测系统。

### 🔧 自己动手验：搭建最小监控系统

```bash
# 1. 最快的 GPU 监控方式
watch -n 2 nvidia-smi --query-gpu=index,utilization.gpu,memory.used,temperature.gpu,power.draw,clocks.sm --format=csv

# 2. 搭建 DCGM + Prometheus（Docker Compose）
cat <<EOF > docker-compose.yml
version: '3'
services:
  dcgm-exporter:
    image: nvidia/dcgm-exporter:latest
    runtime: nvidia
    ports:
      - "9400:9400"
  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
EOF

# 3. 检查 GPU 是否在"认真工作"（不仅仅是驱动在跑）
python -c "
import subprocess

result = subprocess.run(
    ['nvidia-smi', '--query-gpu=index,utilization.gpu,utilization.memory',
     '--format=csv,noheader,nounits'],
    capture_output=True, text=True
)
for line in result.stdout.strip().split('\n'):
    idx, gpu_util, mem_util = line.split(', ')
    gpu_util = int(gpu_util)
    mem_util = int(mem_util)
    status = '⚠️' if gpu_util < 10 and mem_util > 50 else '✅'
    print(f'GPU {idx}: compute={gpu_util}%, mem={mem_util}% {status}')
"

# 4. 检查 NVLink 链路是否健康
nvidia-smi nvlink -s
# -s 显示每条链路的速率与状态；正常负载下应为标称速率（如 H100 每链路 50 GB/s）
# 出现 "Inactive"/"Sleep" 的链路 = 没在工作的链路

nvidia-smi nvlink -e
# -e 显示每条链路的错误计数（CRC/flit 错误）
# 错误计数持续增长 → 线缆/光模块/交换端口问题
```

### GPU 健康：XID、ECC/Row Remapping、NVLink CRC、IB 端口错误

除了温度功耗这类"环境指标"，大规模集群必须监控这四类**错误类**指标：

**1. XID 错误码（驱动层错误）**

```bash
# DCGM 指标：DCGM_FI_DEV_XID_ERRORS = 最近一次 XID 错误码，0 表示正常
# 主机日志：dmesg | grep -i xid
# 完整 XID 码表见 NVIDIA 官方文档（Xid Errors 章节），常见：
#   Xid 48/63/64/65 → ECC 双位错误
#   Xid 74          → NVLink 错误
#   Xid 79          → GPU 从总线上掉落（基本要重启/换卡）
```

**2. ECC 错误与 Row Remapping**

```bash
# DCGM 指标：DCGM_FI_DEV_ECC_DBE_VOL_TOTAL（易失性双位错误，累计值）
# 单比特可纠正错误偶尔出现不必恐慌；双位（uncorrectable）错误出现即高危

# A100/H100 支持显存 row remapping（坏行重映射）：
nvidia-smi -q -d ROW_REMAPPER
# remapped 行数增长且未提交（pending failure）→ 计划性下线重映射
```

**3. NVLink CRC 错误**

```bash
# DCGM 指标：DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_TOTAL
# 命令行：nvidia-smi nvlink -e
# 少量可纠正 CRC 错误可能偶发；持续增长说明链路质量劣化，
# NCCL 会自动降速重传 → 整机通信带宽悄悄下降（典型的"慢节点"来源之一）
```

**4. IB 端口错误**

```bash
ibstat                          # 端口速率/状态：确认是 NDR 400G 而不是降速
ibqueryerrors                   # 扫描整个子网的端口错误计数器
# 注意：错误计数器是累计值，关注"是否在增长"，而不是绝对值
```

### Prometheus 告警规则示例

```yaml
groups:
- name: gpu-health
  rules:
  - alert: GpuXidError
    expr: DCGM_FI_DEV_XID_ERRORS != 0
    for: 1m
    labels:
      severity: critical
    annotations:
      summary: "GPU {{ $labels.gpu }} 出现 XID 错误码 {{ $labels.value }}"

  - alert: GpuUncorrectableEcc
    expr: increase(DCGM_FI_DEV_ECC_DBE_VOL_TOTAL[10m]) > 0
    for: 0m
    labels:
      severity: critical
    annotations:
      summary: "GPU {{ $labels.gpu }} 出现双位（uncorrectable）ECC 错误"

  - alert: NvlinkCrcErrorsGrowing
    expr: increase(DCGM_FI_DEV_NVLINK_CRC_FLIT_ERROR_TOTAL[15m]) > 100
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "GPU {{ $labels.gpu }} NVLink CRC 错误持续增长"

  - alert: GpuPowerViolation
    expr: increase(DCGM_FI_DEV_POWER_VIOLATION[15m]) > 0
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "GPU {{ $labels.gpu }} 持续功耗违例（检查散热/功耗墙）"
```

### ⚠️ 常见误区

- **误区**："GPU 利用率 100% 就是好的"
  - **实际**：GPU-Util 只表示"采样期内有 kernel 在执行"，不代表"在做有效计算"。NCCL 通信等待（自旋忙等）、显存带宽瓶颈、小 kernel 启动开销都会让 GPU-Util 看起来很高但实际 MFU 很低。**监控 GPU-Util 的同时，一定要看 MFU 和 SM Active。**

- **误区**："功耗超过 TDP 的 105% 就是硬件老化"
  - **实际**：短时 boost 到 TDP 附近甚至瞬时略超是**正常行为**——GPU 的 boost 机制本来就是贴着功耗墙跑的。要担心的不是"功耗数值高"，而是**持续**的功耗违例 + 伴随降频。正确做法：看 `nvidia-smi -q -d PERFORMANCE` 的 Clocks Event Reasons（throttle reasons）和 `DCGM_FI_DEV_POWER_VIOLATION` 的增长趋势，结合遥测与配置（功耗墙设置、散热状态）判断，而不是给功耗绝对值设一条 105% 的报警线。

- **误区**："SM 时钟等于基准值说明健康"
  - **实际**：方向反了。**负载下的健康状态是 SM 时钟接近最大加速时钟（max boost）**；基准时钟只是最低保证。判断降频的依据是：满载时 SM 时钟明显低于 max boost，且 throttle reasons 显示被功耗/温度/HW slowdown 压住。空闲时时钟低（甚至降到 idle 频率）反而是省电的正常表现。

- **误区**："指标越多越好"
  - **实际**：指标过多会导致"告警疲劳"——真正严重的问题被噪音淹没。**建议只关注 10-15 个核心指标**，其他的按需查看。

### 📊 底线数字速查

**GPU 健康检查速查表**：

| 指标 | 健康 | 警告 | 危险 |
|------|------|------|------|
| GPU 温度 | < 70°C | 70-85°C | > 85°C |
| GPU 功耗 | 短时 ≈ TDP（boost 正常） | 持续贴功耗墙 + 轻度降频 | 持续功耗违例 + 明显降频 |
| SM 时钟（满载） | 接近 max boost | 低于 max boost 且 throttle 非零 | 大幅低于 max boost |
| NVLink 链路 | 全链路标称速率 | 个别链路 Inactive | 链路 Down + CRC 错误增长 |
| GPU 内存 ECC | 0 双位错误 | 偶发可纠正错误 | 双位错误 / remapped 行耗尽 |
| XID 错误 | 0 | 可纠正类（查码表） | 74/79 等硬件类 |
| PCIe 链路 | 达到本 GPU 型号的标称代数（A100=Gen4 x16，H100/B200=Gen5 x16） | — | 低于本型号标称一代以上 |

> PCIe 一栏**没有全局的"Gen4=警告"**：A100 的正常满速就是 Gen4 x16，把它判成警告会误报。判据是"低于本型号标称"——H100 掉到 Gen4、A100 掉到 Gen3 才是问题。

**训练性能速查**：

| 模型 | GPU 数 | 优秀 MFU | 及格 MFU | 需要优化 |
|------|-------|---------|---------|---------|
| < 7B | 8 | > 45% | 30-45% | < 30% |
| 7-70B | 64 | > 45% | 30-45% | < 30% |
| 405B 级 | 16,384 | **38-43%**（公开值） | 30-38% | < 30% |

### 💡 一句话记住

> **"AI 集群监控的核心不是'看指标'，而是'回答三个问题'：训练跑得快不快（MFU）、集群健康不健康（XID/ECC/NVLink/温度）、出问题了找谁（根因定位）。GPU-Util 是 kernel 执行时间占比不是算力利用率；功耗高和时钟低都不是病，持续违例 + throttle 才是。"**

## 对后续的铺垫

监控告诉你"GPU-Util 100%"。但这就够了吗？

**一个真实案例**：某团队的 GPU-Util 持续 100%，但训练吞吐始终上不去。后来发现大半个 step 的时间，GPU 上的 NCCL kernel 在"自旋忙等"——kernel 在执行（所以 GPU-Util 是 100%），但不是在做有效计算。

所以：**GPU-Util 100% 不等于训练效率高。**
