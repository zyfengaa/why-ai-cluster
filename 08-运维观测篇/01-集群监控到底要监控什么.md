# Q: 集群监控到底要监控什么？

## 为什么会有这个问题

一个 AI 集群跑起来了。你在 Grafana 上搭了 20 个面板，实时刷新 CPU 使用率、内存占用、网络流量……看起来很酷。

但问题来了：**CPU 使用率 50% 意味着什么？网络流量 10 Gbps 是好是坏？GPU 利用率 100% 是不是真的高效？**

AI 集群监控的坑是：**指标太多，但真正能指导行动的太少**。本章帮你理清：到底哪些指标值得看，哪些只是"看起来有用"。

## 解决什么问题

AI 集群监控要回答的核心问题只有三个：

```
1. 训练跑得快不快？  →  性能指标
2. 集群健康不健康？  →  健康检查
3. 出问题了找谁？    →  根因定位
```

### 监控的分层结构

```
┌─────────────────────────────────────────┐
│              应用层指标                    │
│  MFU、吞吐（tokens/s）、Loss 曲线        │
├─────────────────────────────────────────┤
│              框架层指标                    │
│  NCCL 通信时间、计算时间、梯度同步延迟    │
├─────────────────────────────────────────┤
│              系统层指标                    │
│  GPU 利用率、显存、NVLink 带宽、PCIe      │
├─────────────────────────────────────────┤
│              基础设施层指标                │
│  网络吞吐、延迟、丢包、存储 IOPS          │
└─────────────────────────────────────────┘
```

### 关键指标速查

| 层级 | 关键指标 | 怎么看 | 报警阈值 |
|------|---------|--------|---------|
| **GPU 计算** | GPU Util（计算利用率） | `nvidia-smi` | < 80%（连续 5 min） |
| **GPU 内存** | 显存使用率 | `nvidia-smi` | > 95%（OOM 风险） |
| **GPU 互联** | NVLink 带宽 | `nvidia-smi nvlink -s` | 链路 < 100% 链接 |
| **GPU 温度** | 核心温度 | `nvidia-smi` | > 85°C（降频风险）|
| **GPU 功耗** | 功率使用率 | `nvidia-smi` | > TDP 105%（可能硬件老化）|
| **网络** | IB/RoCE 吞吐 | `ibstat`, `perf query` | 低于基准 20% |
| **存储** | Checkpoint 写入速度 | `iostat`, `dcgm` | < 1 GB/s（400 GPU 集群）|
| **训练** | MFU（Model FLOPS Utilization）| Profiling | < 40%（亮黄牌）|

### 最重要的指标：MFU

AI 集群监控里没有比 **MFU（Model FLOPS Utilization）** 更重要的指标了。它不是"GPU 利用率"——而是 **"GPU 的理论算力被实际用上了百分之几"**。

```python
# MFU 的计算
def calc_mfu(observed_tflops, gpu_peak_tflops, n_gpus):
    return observed_tflops / (gpu_peak_tflops * n_gpus)

# 示例：64 卡 H100 的 MFU
peak = 989  # H100 FP16 Tensor Core TFLOPS
observed = 32000  # 64 卡实际 TFLOPS
mfu = calc_mfu(observed, peak, 64)
print(f"MFU = {mfu:.1%}")  # ~50%，还不错
```

**2026 年的 MFU 参考值**：

| 模型 | 并行配置 | MFU 范围 | 评价 |
|------|---------|---------|------|
| Llama 7B | 8×H100, FSDP2 | 35-45% | 入门水平 |
| Llama 70B | 64×H100, FSDP2+TP | 40-50% | 及格 |
| Llama 405B | 512×H100, Megatron 4D | 45-55% | 优秀 |
| 1T+ MoE | 1024×B200, Megatron 5D | 40-48% | 良好 |

## 监控工具栈

| 工具 | 层级 | 优点 | 缺点 |
|------|------|------|------|
| **DCGM（NVIDIA）** | GPU 系统 | 官方指标集，低开销 | 需要配置 |
| **Prometheus + Grafana** | 全栈 | 标准方案，生态丰富 | 需要搭建 |
| **nvidia-smi** | GPU 硬件 | 默认安装，随手查 | 不能长期存储 |
| **NeMo Monitoring** | 框架 | 自动采集 MFU | 只能 NeMo 使用 |
| **NVIDIA Management Library（NVML）** | GPU 底层 | Python 可编程 | 较底层 |
| **DCGM Exporter** | Prometheus | GPU 指标自动暴露 | 需部署 DaemonSet |

### DCGM 的推荐采集指标

```bash
# 安装并启动 DCGM
docker run -d --gpus all --rm \
  --name dcgm-exporter \
  -p 9400:9400 \
  nvidia/dcgm-exporter:latest

# Prometheus 可抓取的 GPU 指标
# curl localhost:9400/metrics | head -20

# 关键指标：
# - DCGM_FI_DEV_GPU_UTIL → GPU 计算利用率
# - DCGM_FI_DEV_FB_FREE → 剩余显存
# - DCGM_FI_DEV_NVLINK_BANDWIDTH_TOTAL → NVLink 总带宽
# - DCGM_FI_DEV_POWER_USAGE → GPU 功耗
# - DCGM_FI_DEV_SM_CLOCK → SM 时钟频率（降频检测）
# - DCGM_FI_DEV_MEM_CLOCK → 显存时钟频率
```

## 🛠 实操指南

### 📋 决策指南：你的监控方案应该怎么做？

```
你的集群规模？
├─ < 8 卡（个人/小团队）→
│   └─ nvidia-smi + 简单的训练日志就够了
│       watch -n 2 nvidia-smi
│
├─ 8-64 卡（小集群）→
│   └─ DCGM Exporter + Prometheus + Grafana
│       核心面板：GPU 利用率、显存、温度、NVLink
│
├─ 64-512 卡（中等集群）→
│   ├─ 系统层：DCGM + Prometheus
│   ├─ 框架层：NeMo Monitoring / WandB
│   └─ 训练层：MFU 面板 + Loss 曲线
│
└─ > 512 卡（大规模）→
    ├─ 全栈监控 + 报警
    ├─ 自动异常检测（eBPF + 机器学习）
    ├─ Straggler 检测系统（Guard / StragglAR）
    └─ 拓扑健康状况自动巡检
```

### 🔧 自己动手验：搭建最小监控系统

```bash
# 1. 最快的 GPU 监控方式
watch -n 2 nvidia-smi --query-gpu=index,utilization.gpu,memory.used,temperature.gpu,power.draw --format=csv

# 2. 搭建 DCGM + Prometheus（Docker Compose）
cat <<EOF > docker-compose.yml
version: '3'
services:
  dcgm-exporter:
    image: nvidia/dcgm-exporter:latest
    runtime: nvidia
    ports:
      - "9400:9400"
  prometheus:
    image: prom/prometheus:latest
    ports:
      - "9090:9090"
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
  grafana:
    image: grafana/grafana:latest
    ports:
      - "3000:3000"
EOF

# 3. 检查 GPU 是否在"认真工作"（不仅仅是驱动在跑）
python -c "
import subprocess
import json

result = subprocess.run(
    ['nvidia-smi', '--query-gpu=index,utilization.gpu,utilization.memory',
     '--format=csv,noheader,nounits'],
    capture_output=True, text=True
)
for line in result.stdout.strip().split('\n'):
    idx, gpu_util, mem_util = line.split(', ')
    gpu_util = int(gpu_util)
    mem_util = int(mem_util)
    status = '⚠️' if gpu_util < 10 and mem_util > 50 else '✅'
    print(f'GPU {idx}: compute={gpu_util}%, mem={mem_util}% {status}')
"

# 4. 检查 NVLink 链路是否健康
nvidia-smi nvlink -s
# 输出应显示所有链路都是 "Active"
# 如果有 "Disabled" 或 "Failed" → 硬件问题
```

### ⚠️ 常见误区

- **误区**："GPU 利用率 100% 就是好的"
  - **实际**：GPU 利用率只表示"有 CUDA 核在运行"，不代表"在做有效计算"。NCCL 通信等待、显存带宽瓶颈、小 kernel 启动开销都会让 GPU 利用率看起来很高但实际 MFU 很低。**监控 GPU 利用率的同时，一定要看 MFU。**

- **误区**："指标越多越好"
  - **实际**：指标过多会导致"告警疲劳"——真正严重的问题被噪音淹没。**建议只关注 10-15 个核心指标**，其他的按需查看。

- **误区**："免费的监控工具就够了"
  - **实际**：免费工具能告诉你"现在出问题了"，但**专业工具（Nsight Systems、DCGM）能告诉你"为什么出问题"**。区别就像"油表报警"和"引擎诊断报告"。

### 📊 底线数字速查

**GPU 健康检查速查表**：

| 指标 | 健康 | 警告 | 危险 |
|------|------|------|------|
| GPU 温度 | < 70°C | 70-85°C | > 85°C |
| GPU 功耗 | < TDP | TDP-105% TDP | > 105% TDP |
| SM 时钟 | = 基准值 | < 基准 5% | < 基准 10% |
| NVLink 链路 | 全部 Active | 1-2 条 Down | > 2 条 Down |
| GPU 内存 ECC | 0 errors | 1-5 correctable | > 5 or uncorrectable |
| PCIe 链路 | Gen5 x16 | Gen4 | Gen3 或更差 |

**训练性能速查**：

| 模型 | GPU 数 | 优秀 MFU | 及格 MFU | 需要优化 |
|------|-------|---------|---------|---------|
| < 7B | 8 | > 45% | 30-45% | < 30% |
| 7-70B | 64 | > 50% | 40-50% | < 40% |
| > 70B | 512+ | > 50% | 40-50% | < 40% |

### 💡 一句话记住

> **"AI 集群监控的核心不是'看指标'，而是'回答三个问题'：训练跑得快不快（MFU）、集群健康不健康（NVLink/温度/显存）和出问题了找谁（根因定位）。不要把 80% 的精力花在 CPU 利用率这种噪音指标上。"**

## 对后续的铺垫

监控告诉你"GPU 利用率 100%"。但这就够了吗？

**一个真实案例**：某团队的 GPU 利用率持续 100%，但训练吞吐始终上不去。后来发现 50% 的时间花在了 NCCL 通信等待上——GPU 核在"忙等"，不是在做真正的计算。

所以：**GPU 利用率 100% 不等于训练效率高。**
