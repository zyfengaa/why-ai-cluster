# Q: 拓扑感知调度为什么重要？

## 为什么会有这个问题

你提交一个 8 卡训练任务。调度器给了你 8 张 GPU——但它们分别位于：

```
机器 A：GPU 0, 1, 2, 3（NVLink 互联）
机器 B：GPU 4, 5, 6, 7（NVLink 互联）
A ↔ B：PCIe 连接
```

问题：NCCL 在这 8 张卡上做 All-Reduce 时，4+4 的拓扑意味着每次同步都需要跨 PCIe 做一次通信。速度从 NVLink 的 900 GB/s 降到 PCIe 的 64 GB/s——**慢了 14 倍**。

如果调度器知道 NVLink 拓扑，把 8 张卡全部放在同一台 8-GPU 机器上（通过 NVSwitch 互联）——问题就解决了。

## 解决什么问题

拓扑感知调度（Topology-Aware Scheduling）解决的核心问题：**分配 GPU 时，不仅看"数量够不够"，还要看"这堆 GPU 的物理拓扑是否最优"**。

### GPU 拓扑层级

```
最差 ←────────────────────────────────────→ 最好
不同机架     不同机器     同一机器    同一机器
不同交换机   不同 PCIe   不同 NVSwitch   同一 NVSwitch
                             同一 NVSwitch 域
                                 ↓
                         NCCL 通信速度最快
```

| 拓扑层级 | 典型带宽 | 延迟 | 适合场景 |
|---------|---------|------|---------|
| **NVSwitch（同域）** | 900 GB/s（H100） | ~1 μs | 最优，TP/All-Reduce |
| **NVSwitch（跨域）** | 450 GB/s | ~2 μs | 可接受，DP 通信 |
| **NVLink（直连）** | 600 GB/s（4 卡） | ~2 μs | 小规模 TP |
| **PCIe 同机** | 64 GB/s（Gen5） | ~10 μs | 差，尽量避免 |
| **网络跨机** | 50-400 GB/s（IB） | ~5-50 μs | 数据并行可接受 |

### 不感知拓扑的后果

```bash
# 一个 AI 公司的真实案例（2025）：
# 64 卡训练任务，分配到 4 台 8-GPU 机器 + 2 台 16-GPU 机器
# ─────────────────────────────────────────
# 期望吞吐：450 TFLOPS
# 实际吞吐：180 TFLOPS（下降 60%）
# 原因：6 台机器的拓扑不匹配
#   · 4 台机器用了不同代的 NVSwitch
#   · 2 台机器在另一个 InfiniBand leaf 交换机下
#   · NCCL 选择了 Ring 算法 → All-Reduce 跨 leaf 交换机
# 修复后（拓扑感知调度）→ 420 TFLOPS
```

### 拓扑感知的典型实现

**Slurm 的拓扑感知**：
```bash
# topology.conf
SwitchName=spine001 Switches=leaf[01-04]
SwitchName=leaf001 Nodes=node[001-008]
SwitchName=leaf002 Nodes=node[009-016]

# 分配策略：尽量把任务分配到同一 leaf 交换机下
# --switches=leaf001: 表示优先从 leaf001 分配节点

sbatch --nodes=4 --switches=leaf001@60 train.sh
# 60 = 如果在 60 秒内 leaf001 凑不齐 4 个节点，可以放宽约束
```

**Kubernetes 的拓扑感知**：
```yaml
# 通过 Node Affinity + Topology Labels
apiVersion: v1
kind: Pod
metadata:
  name: training-pod
  annotations:
    nvidia.com/gpu-request-topology: "nvlink"
spec:
  affinity:
    nodeAffinity:
      requiredDuringScheduling:
        nodeSelectorTerms:
        - matchExpressions:
          - key: nvidia.com/gpu.nvlink.domain
            operator: In
            values:
            - "0"  # 指定需要同一 NVLink 域
  schedulerName: kai-scheduler
```

**NVIDIA GPU Operator + Topology Manager**：
```
Kubernetes Topology Manager:
  1. 收集节点上的 GPU 拓扑信息
  2. 在调度 Pod 时，确保 GPU 分配对齐 NUMA 节点
  3. 避免跨 NUMA 的 GPU 通信（性能损失 ~20%）
```

## 拓扑感知的三种粒度

### 1. GPU 级（NVLink 域）

最重要的拓扑维度：**把同一 NVSwitch 域内的 GPU 分给同一个任务**。

```bash
# 查看 GPU 拓扑
nvidia-smi topo -m

# 输出示例：
#         GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
# GPU0    X    NV1   NV1   NV2   SYS   SYS   SYS   SYS
# GPU1   NV1    X    NV2   NV1   SYS   SYS   SYS   SYS
# GPU2   NV1   NV2    X    NV1   SYS   SYS   SYS   SYS
# GPU3   NV2   NV1   NV1    X    SYS   SYS   SYS   SYS
# GPU4   SYS   SYS   SYS   SYS    X    NV1   NV1   NV2
# GPU5   SYS   SYS   SYS   SYS   NV1    X    NV2   NV1
# GPU6   SYS   SYS   SYS   SYS   NV1   NV2    X    NV1
# GPU7   SYS   SYS   SYS   SYS   NV2   NV1   NV1    X
#
# NV1/NV2 = NVLink 连接（高速）
# SYS = PCIe 连接（低速）→ 跨 CPU socket 了

# 结论：GPU0-3 是一个 NVLink 域，GPU4-7 是另一个
# 8 卡任务如果拿到 GPU0-7 → 性能打折
```

### 2. 节点级（InfiniBand leaf 交换机）

```bash
# 检查哪些节点在同一 IB leaf 下
# 方法 1：查看 Slurm topology.conf
SwitchName=leaf01 Nodes=node[001-032]

# 方法 2：IB 拓扑
ibnetdiscover | grep -E "Switch|CA" | head -20
```

### 3. 机架级（供电/散热边界）

```bash
# 有些数据中心的机架有供电上限
# 如果 4 台 GPU 服务器放在同一个机架 → 可能触发断路器
# 拓扑感知调度需要知道：
#   · 哪些机器共用一个 PDU（电源分配单元）
#   · 每个机架的供电容量
```

## 🛠 实操指南

### 📋 决策指南：你的调度需要多强的拓扑感知？

```
你的训练任务特点？
├─ 单机 8 卡（单节点内）→
│   └─ 只需保证 GPU 在同一 NVLink 域内
│
├─ 多机 8-64 卡（2-8 节点）→
│   ├─ 需要 GPU 级拓扑（NVLink 域）
│   └─ 需要节点级拓扑（同一 IB leaf 下）
│
├─ 多机 64-512 卡 →
│   ├─ GPU 级：同一机器内保证 NVLink
│   ├─ 节点级：尽量同一 leaf 交换机
│   └─ 机架级：避免单一 PDU 过载
│
└─ > 512 卡 →
    └─ 拓扑感知 + 网络拓扑联合优化
        ├─ NCCL Ring 算法：需要环状拓扑
        └─ NCCL Tree 算法：需要分层拓扑
```

### 🔧 自己动手验：检查你的 GPU 拓扑

```bash
# 1. 查看 GPU 间的拓扑关系
nvidia-smi topo -m
# NV1/NV2 = 好（NVLink）
# PIX/PXB = 可接受
# SYS = 差（跨 CPU socket）

# 2. 检查 NVSwitch 健康状态
nvidia-smi nvswitch -s
# 确认所有 NVSwitch Link 都是 "Active"

# 3. 检查 NCCL 选择的通信拓扑
NCCL_DEBUG_SUBSYS=GRAPH NCCL_DEBUG=INFO python -c "
import torch, torch.distributed as dist
dist.init_process_group('nccl')
print('NCCL initialized')
" 2>&1 | grep -E "Ring|Tree|Topo|pattern"
# 输出会显示 NCCL 选择的通信算法和拓扑

# 4. 拓扑感知调度测试：比较不同拓扑分配的吞吐
python -c "
import torch, time

def bench_topo(devices):
    \"\"\"测试特定 GPU 组合的 All-Reduce 性能\"\"\"
    tensors = []
    for d in devices:
        t = torch.randn(1024, 1024, device=f'cuda:{d}')
        tensors.append(t)
    
    t0 = time.time()
    for _ in range(100):
        for t in tensors:
            dist.all_reduce(t)
    torch.cuda.synchronize()
    return 100 / (time.time() - t0)

# 比较同一 NVSwitch 域 vs 跨域性能
print(f'同域吞吐: {bench_topo([0,1,2,3]):.1f} it/s')
print(f'跨域吞吐: {bench_topo([0,4]):.1f} it/s')
print(f'速度比: 跨域是同域的 {bench_topo([0,4])/bench_topo([0,1,2,3]):.2f} 倍')
"
```

### ⚠️ 常见误区

- **误区**："所有 GPU 之间的带宽是一样的"
  - **实际**：NVLink 带宽是 PCIe 的 **14 倍**，是跨机网络的 **2-10 倍**。不关注拓扑就等于主动放弃 50-90% 的性能。**物理即是命运。**

- **误区**："Kubernetes 默认支持拓扑感知"
  - **实际**：K8s 的 Topology Manager 只管理 **NUMA 对齐**（CPU 和 GPU 的关系），不管理 **GPU 之间的 NVLink 拓扑**。NVLink 拓扑需要 NVIDIA GPU Operator + 自定义调度器（KAI Scheduler）来实现。

- **误区**："拓扑感知只对大模型训练重要"
  - **实际**：**任何多 GPU 通信密集型的任务都需要拓扑感知**。包括：模型并行训练、大规模 batch inference、科学计算（MD、CFD 等）。

### 📊 底线数字速查

| 拓扑分配 | All-Reduce 吞吐（8×H100） | 相比最优的损失 |
|---------|------------------------|--------------|
| 同一 NVSwitch 域（最优）| ~460 GB/s | 0% |
| 同一机器跨 NVSwitch | ~400 GB/s | ~13% |
| 跨机器 PCIe | ~64 GB/s | ~86% |
| 跨机器 IB（2 层交换）| ~50-350 GB/s | 20-90% |
| 跨机器 TCP（无 RDMA）| ~5 GB/s | ~99% |

**经验法则**：
- TP 张量并行 → 必须同一 NVSwitch 域
- FSDP/ZeRO-3 数据并行 → 同一机器即可（NVLink 不是必须）
- PP 流水线并行 → 可以跨机器，但需保证网络带宽充足

### 💡 一句话记住

> **"拓扑感知调度就是'让距离最近的 GPU 一起工作'。NVLink 域内通信 900 GB/s，跨 PCIe 通信 64 GB/s——差了 14 倍。不认识拓扑的调度器，就是在亲手把训练性能砍掉一个数量级。"**
