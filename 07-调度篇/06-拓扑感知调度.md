# Q: 拓扑感知调度为什么重要？

## 为什么会有这个问题

你提交一个 8 卡训练任务。调度器给了你 8 张 GPU——但它们分别位于：

```
机器 A：GPU 0, 1, 2, 3（NVSwitch 全互联，NVLink 4）
机器 B：GPU 4, 5, 6, 7（NVSwitch 全互联，NVLink 4）
A ↔ B：走 InfiniBand/RoCE 网络（不是 PCIe——跨机没有 PCIe 这回事）
```

问题：NCCL 在这 8 张卡上做 All-Reduce 时，机内 4 张卡走 NVLink（H100 上 900 GB/s 双向聚合带宽），但跨机的每一步都要走 IB 网卡（NDR 单端口 400 Gb/s = 50 GB/s 单向）。**机内 NVLink 和跨机网络的带宽差了一个数量级**，All-Reduce 的关键路径被跨机链路卡死。

如果调度器知道拓扑，把 8 张卡全部放在同一台 8-GPU 机器上（通过 NVSwitch 互联）——问题就解决了。

**先统一口径**（全书约定）：PCIe、NVLink、IB 带宽默认说**双向**，单向值必须标注。

- PCIe 5.0 x16：**64 GB/s 单向，128 GB/s 双向**（PCIe 4.0 是 32 / 64 GB/s）
- NVLink 4（H100）：**900 GB/s 双向**

所以"NVLink 是 PCIe 的几倍"这个问题，答案取决于口径：900（双向）÷ 128（双向）≈ **7×**。如果你看到"14×"的说法，那是拿 NVLink 双向除以 PCIe 5.0 单向混算出来的——**同一对比较必须用同一口径**。

## 解决什么问题

拓扑感知调度（Topology-Aware Scheduling）解决的核心问题：**分配 GPU 时，不仅看"数量够不够"，还要看"这堆 GPU 的物理拓扑是否最优"**。

### GPU 拓扑层级

```
最差 ←─────────────────────────────────────────────→ 最好
跨机（IB/RoCE）    同机跨 CPU      同机同 NVSwitch 域    同机同 NVSwitch 域
跨 leaf/spine      socket（PCIe）   但跨 NVSwitch 层级    且 NUMA 对齐
                        ↓
              NCCL 通信速度最快
```

| 拓扑层级 | 典型带宽 | 延迟量级 | 适合场景 |
|---------|---------|---------|---------|
| **同机 NVSwitch 域（H100）** | 900 GB/s 双向（NVLink 4） | 微秒级 | 最优，TP/All-Reduce |
| **同机 PCIe（跨 NUMA）** | 64 GB/s 单向 / 128 GB/s 双向（Gen5 x16） | ~10 μs | 差，尽量避免 |
| **跨机 IB NDR** | 每卡 ~50 GB/s 单向（400G 端口） | ~2-5 μs（同 leaf） | 数据并行可接受 |
| **跨机 IB 跨多层交换** | 同上，但拥塞/对分带宽受限 | 更高 | 需要拓扑感知缓解 |
| **跨机 TCP（无 RDMA）** | 个位数至十几 GB/s | 数十 μs 以上 | 不可接受 |

> 注意：**PCIe 是机内总线，不存在"跨机器的 PCIe 拓扑"**。跨机通信只有 IB/RoCE/以太网。任何把"跨机"和"PCIe"写进同一行的说法，都是概念错误。

### 不感知拓扑的机制性后果

不感知拓扑的调度器可能把一个 64 卡任务分散到：不同代的机器、不同 NVSwitch 域、不同 IB leaf 交换机上。后果是：

- NCCL 检测到不均匀拓扑后，要么选了次优的 Ring/Tree 形状，要么把慢链路放进关键路径——**整个作业的步时被最慢的那条链路决定**（`T_step = max_i(T_i)`，一卡慢全组慢）
- 同一作业的机器分散在多个 leaf → All-Reduce 跨 spine 的流量大增，还拖累其他作业

这类问题在 8 卡到 64 卡规模最常见，也最容易被误诊成"网络带宽不够"——其实是分配位置不对。

### 拓扑感知的典型实现

**Slurm 的拓扑感知**：

```bash
# topology.conf：描述树状网络拓扑（机内+机间层级由插件/配置生成）
SwitchName=leaf01 Nodes=node[001-032]
SwitchName=leaf02 Nodes=node[033-064]
SwitchName=spine01 Switches=leaf01,leaf02

# --switches 的语法是"交换机数量[@最长等待时间]"，不是交换机名！
# --switches=2@60 表示：这个作业的节点最多跨 2 台交换机；
# 如果 60 分钟内凑不齐，就放宽约束允许跨更多交换机（max-time 单位是分钟）。
sbatch --nodes=8 --switches=2@60 train.sh

# 不带 @60 则无限期等待"2 台交换机以内"的分配
sbatch --nodes=8 --switches=1 train.sh
```

前提是管理员用 `topology.conf`（或拓扑插件）描述了树状拓扑，Slurm 才知道"哪些节点在同一个 leaf 下"。新版本（25.05+）还有支持 block/topology aware GPU 分配的 `topology/block` 等插件，可以对接 NVIDIA topograph 生成的 NVLink 域信息。

**Kubernetes 的拓扑感知**：

```yaml
# 方式一：用节点标签做 Pod 亲和（示例——标签来自 NVIDIA GPU Operator 的
# GPU Feature Discovery，其中 nvidia.com/gpu.clique=<ClusterUUID>.<CliqueID>
# 标识节点所在的 NVLink 分区/域；非 MNNVL 硬件不会生成该标签）
apiVersion: v1
kind: Pod
metadata:
  name: training-pod
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:   # 注意字段全名
      - labelSelector:
          matchExpressions:
          - key: job-name
            operator: In
            values: ["training-job"]
        topologyKey: nvidia.com/gpu.clique   # 同一作业的 Pod 落在同一个 NVLink 域内
  schedulerName: kai-scheduler
```

> **别用不存在的字段/资源名**：`requiredDuringScheduling` 不是合法的 affinity 字段（必须写成 `requiredDuringSchedulingIgnoredDuringExecution`，或者用 `nodeAffinity`/`podAffinity` 的对应结构）；`nvidia.com/gpu-request-topology`、`nvidia.com/gpu.nvlink.domain` 不是 Kubernetes 或 NVIDIA 官方的标准资源/注解名，写了不生效。生产中真正可核验的路径有三条：
> 1. **GPU Feature Discovery 节点标签**（如 `nvidia.com/gpu.clique`，MNNVL 场景）+ Pod/node 亲和
> 2. **DRA**（Kubernetes 1.34 起 GA 的 `resource.k8s.io/v1`）：NVIDIA DRA 驱动的 **ComputeDomain** 原生表达"一组 GPU 要在同一个 NVLink 域里"
> 3. **NVIDIA Topograph**：把 NVLink/IB 拓扑导入 Slurm（topology/block）或 K8s 调度层

**Kubernetes Topology Manager 的边界**：它只负责**单节点内**的 NUMA 对齐（CPU、内存、PCIe 设备分到同一个 NUMA 域），不负责跨节点的 GPU/NVLink/IB 拓扑。跨节点的部分要靠上面的标签亲和、DRA 或专用调度器（KAI、Volcano 的拓扑插件、Kueue 的 Topology-Aware Scheduling）。

### 补充：rail-optimized 与 All-Reduce 的实际收益

现代 GPU 集群按"rail"设计网络：每台服务器的 GPU0 都接到 leaf 交换机 1，GPU1 接到 leaf 交换机 2……（rail-optimized 拓扑）。于是：

- **一个 DP rank 组（比如第 i 号卡组）如果全部落在 rail i 上，它们的跨机通信只需经过一个 leaf，不碰 spine**
- 调度器如果不看 rail，把同一个 rank 组打散到不同 rail，All-Reduce/All-to-All 的流量就要跨 spine，拥塞和对分带宽限制立刻显现

对 All-Reduce 的实际收益可以这样理解：

- Ring All-Reduce 的每步通信都走相邻 rank 之间的链路，**rank 摆放位置直接决定这些链路是 NVLink、同 leaf IB 还是跨 spine IB**
- 机内 NVLink（900 GB/s 双向）比跨机 IB（每卡 ~50 GB/s 单向）快一个数量级 → 能把 8 卡放进同一台机器就绝不拆两台
- 跨机部分，同 leaf 内比跨 spine 的有效带宽高、抖动小 → rail 对齐能把大集群的有效 busbw 明显拉高（幅度取决于收敛比和负载，需实测）
- 反过来，拓扑不对齐的代价是乘法式的：`T_step = max_i(T_i)`，一条慢链路拖住整个作业

## 拓扑感知的三种粒度

### 1. GPU 级（NVLink 域）

最重要的拓扑维度：**把同一 NVSwitch 域内的 GPU 分给同一个任务**。

```bash
# 查看 GPU 间的拓扑关系
nvidia-smi topo -m

# 先看两种典型输出，别拿错模板去对照自己的机器：

# A. DGX/HGX 8×SXM（NVSwitch 全互联，H100/H200/B200 的常见形态）
#         GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
# GPU0     X   NV18  NV18  NV18  NV18  NV18  NV18  NV18
# GPU1   NV18    X   NV18  NV18  NV18  NV18  NV18  NV18
# GPU2   NV18  NV18    X   NV18  NV18  NV18  NV18  NV18
# ...（8 卡两两 NV18，全部经 NVSwitch 互联）
# 判读：没有 SYS 分组 → 8 卡在同一 NVLink 域，TP=8 可用。

# B. 双路 CPU + 每路 4 卡走 NVLink bridge（非 NVSwitch 平台）
#         GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
# GPU0     X   NV1   NV1   NV2   SYS   SYS   SYS   SYS
# GPU1   NV1    X   NV2   NV1   SYS   SYS   SYS   SYS
# GPU2   NV1   NV2    X   NV1   SYS   SYS   SYS   SYS
# GPU3   NV2   NV1   NV1    X   SYS   SYS   SYS   SYS
# GPU4   SYS   SYS   SYS   SYS    X   NV1   NV1   NV2
# GPU5   SYS   SYS   SYS   SYS   NV1    X   NV2   NV1
# GPU6   SYS   SYS   SYS   SYS   NV1   NV2    X   NV1
# GPU7   SYS   SYS   SYS   SYS   NV2   NV1   NV1    X
#
# NV1/NV2 = NVLink bridge 连接；SYS = 走 PCIe，跨 CPU socket

# 判读规则：
#   看到 SYS 分组 → 这是两个 4 卡域，不是 8 卡全互联。
#   8 卡任务跨域 → 要么换一台 8 卡 SXM 机器，要么把任务缩到 4 卡；
#   强行跑 TP=8，跨域那部分 All-Reduce 会走 PCIe，性能明显下降。
```

### 2. 节点级（IB leaf 交换机 / rail）

```bash
# 检查哪些节点在同一 IB leaf 下
# 方法 1：查看 Slurm topology.conf
SwitchName=leaf01 Nodes=node[001-032]

# 方法 2：IB 拓扑
ibnetdiscover | grep -E "Switch|CA" | head -20
```

### 3. 机架级（供电/散热边界）

```bash
# 有些数据中心的机架有供电上限
# 如果 4 台 GPU 服务器放在同一个机架 → 可能触发断路器
# 拓扑感知调度需要知道：
#   · 哪些机器共用一个 PDU（电源分配单元）
#   · 每个机架的供电容量
```

## 🛠 实操指南

### 📋 决策指南：你的调度需要多强的拓扑感知？

```
你的训练任务特点？
├─ 单机 8 卡（单节点内）→
│   └─ 只需保证 GPU 在同一 NVLink 域内
│
├─ 多机 8-64 卡（2-8 节点）→
│   ├─ 需要 GPU 级拓扑（NVLink 域）
│   └─ 需要节点级拓扑（同一 IB leaf / 同一 rail 下）
│
├─ 多机 64-512 卡 →
│   ├─ GPU 级：同一机器内保证 NVLink
│   ├─ 节点级：rail 对齐（同一 DP rank 组落到同一 rail）
│   └─ 机架级：避免单一 PDU 过载
│
└─ > 512 卡 →
    └─ 拓扑感知 + 网络拓扑联合优化
        ├─ NCCL Ring 算法：需要环状拓扑
        └─ NCCL Tree 算法：需要分层拓扑
```

### 🔧 自己动手验：检查你的 GPU 拓扑

```bash
# 1. 查看 GPU 间的拓扑关系
nvidia-smi topo -m
# NV1/NV2 = 好（NVLink）
# PIX/PXB = 可接受
# SYS = 差（跨 CPU socket）

# 2. 查看 GPU NVLink 链路状态与错误计数
# （注意：没有 "nvidia-smi nvswitch" 这个子命令；NVSwitch 侧信息在 nvidia-smi -q 里）
nvidia-smi nvlink -s        # 列出每条 NVLink 链路状态（应为 Active）
nvidia-smi nvlink -e        # 查看每条链路的错误计数器
nvidia-smi -q | grep -A 20 NVSWITCH   # NVSwitch 相关信息（部分平台）

# 3. 检查 NCCL 选择的通信拓扑
NCCL_DEBUG_SUBSYS=GRAPH NCCL_DEBUG=INFO python -c "
import torch, torch.distributed as dist
dist.init_process_group('nccl')
print('NCCL initialized')
" 2>&1 | grep -E "Ring|Tree|Topo|pattern"
# 输出会显示 NCCL 选择的通信算法和拓扑

# 4. 拓扑感知调度测试：比较不同拓扑分配的吞吐
python -c "
import torch, time

def bench_topo(devices):
    \"\"\"测试特定 GPU 组合的 All-Reduce 性能\"\"\"
    tensors = []
    for d in devices:
        t = torch.randn(1024, 1024, device=f'cuda:{d}')
        tensors.append(t)
    
    t0 = time.time()
    for _ in range(100):
        for t in tensors:
            dist.all_reduce(t)
    torch.cuda.synchronize()
    return 100 / (time.time() - t0)

# 比较同一 NVSwitch 域 vs 跨域性能
print(f'同域吞吐: {bench_topo([0,1,2,3]):.1f} it/s')
print(f'跨域吞吐: {bench_topo([0,4]):.1f} it/s')
print(f'速度比: 跨域是同域的 {bench_topo([0,4])/bench_topo([0,1,2,3]):.2f} 倍')
"
```

### ⚠️ 常见误区

- **误区**："所有 GPU 之间的带宽是一样的"
  - **实际**：NVLink 4（900 GB/s 双向）约是 PCIe 5.0 x16（128 GB/s 双向）的 **7 倍**（单向口径同理：900÷64≈14，但那样必须两边都标单向——混用两个口径得出"14×"是最常见的算术错误）。跨机网络又比机内 PCIe 慢。不关注拓扑就等于主动放弃数倍的性能。**物理即是命运。**

- **误区**："调度器可以按'跨机器 PCIe 拓扑'做亲和"
  - **实际**：PCIe 是**机内总线**，两台服务器之间没有 PCIe。跨机拓扑只有 IB/RoCE/以太网的交换机层级（leaf/spine、rail）。正确的心智模型是：**机内 PCIe/NVLink 拓扑 + 机间 rail/leaf 拓扑**，两层分别配置。

- **误区**："Kubernetes 默认支持拓扑感知"
  - **实际**：K8s 的 Topology Manager 只管理**单节点内的 NUMA 对齐**，不管理**跨节点的 NVLink/IB 拓扑**。跨节点拓扑需要 GPU Feature Discovery 标签 + 亲和、DRA（ComputeDomain）或专用调度器来实现。

- **误区**："拓扑感知只对大模型训练重要"
  - **实际**：**任何多 GPU 通信密集型的任务都需要拓扑感知**。包括：模型并行训练、大规模 batch inference、科学计算（MD、CFD 等）。

### 📊 底线数字速查

> 下表是数量级参考（8×H100 单机最优拓扑为基准的 All-Reduce busbw），具体值取决于卡型、NCCL 版本、网络收敛比——请以实测为准。

| 拓扑分配 | All-Reduce busbw（量级） | 相比最优的损失（量级） |
|---------|------------------------|---------------------|
| 同机 NVSwitch 域（最优）| 数百 GB/s | 0%（基准） |
| 同机但跨 NUMA/PCIe | 显著低于 NVLink | 数成 |
| 跨机 IB（同 leaf，rail 对齐）| 每卡 ~40-50 GB/s | 大幅低于机内 |
| 跨机 IB（跨 spine/多层）| 更低且抖动更大 | 取决于收敛比 |
| 跨机 TCP（无 RDMA）| 个位数至十几 GB/s | 接近两个数量级 |

**经验法则**：
- TP 张量并行 → 必须同一 NVSwitch 域（同机）
- FSDP/ZeRO-3 数据并行 → 同一机器最优；跨机可行，但需保证 IB 带宽与 rail 对齐
- PP 流水线并行 → 可以跨机器，但需保证网络带宽充足

### 💡 一句话记住

> **"拓扑感知调度就是'让距离最近的 GPU 一起工作'。NVLink 域内 900 GB/s 双向，PCIe 5.0 x16 双向 128 GB/s——同口径下差 7 倍；跨机再走 IB，又慢一个数量级。不认识拓扑的调度器，就是在亲手把训练性能砍掉一个数量级。"**
