# Q: 拓扑感知调度为什么重要？

## 为什么会有这个问题

你提交一个 8 卡训练任务。调度器给了你 8 张 GPU——但它们分别位于：

```
机器 A：GPU 0, 1, 2, 3（NVLink 域内互联）
机器 B：GPU 4, 5, 6, 7（NVLink 域内互联）
A ↔ B：InfiniBand 网络（注意：PCIe 不跨机器，跨机只能走网络）
```

问题：NCCL 在这 8 张卡上做 All-Reduce 时，4+4 的拓扑意味着每次同步都要跨机走一次网络。速度从卡内 NVLink 的 900 GB/s 掉到跨机 IB 的几十到几百 GB/s——**慢了一个数量级**。

如果调度器知道 NVLink 拓扑，把 8 张卡全部放在同一台 8-GPU 机器上（通过 NVSwitch 互联）——问题就解决了。

## 解决什么问题

拓扑感知调度（Topology-Aware Scheduling）解决的核心问题：**分配 GPU 时，不仅看"数量够不够"，还要看"这堆 GPU 的物理拓扑是否最优"**。

### GPU 拓扑层级

```
最差 ←────────────────────────────────────→ 最好
不同机架     不同机器     同一机器    同一机器
不同交换机   不同 PCIe   不同 NVSwitch   同一 NVSwitch
                             同一 NVSwitch 域
                                 ↓
                         NCCL 通信速度最快
```

| 拓扑层级 | 典型带宽 | 延迟 | 适合场景 |
|---------|---------|------|---------|
| **NVSwitch（同域）** | 900 GB/s（H100） | ~1 μs | 最优，TP/All-Reduce |
| **NVSwitch（跨域）** | 450 GB/s | ~2 μs | 可接受，DP 通信 |
| **NVLink（直连）** | 600 GB/s（4 卡） | ~2 μs | 小规模 TP |
| **PCIe 同机** | 64 GB/s（Gen5） | ~10 μs | 差，尽量避免 |
| **网络跨机** | 50-400 GB/s（IB） | ~5-50 μs | 数据并行可接受 |

### 不感知拓扑的后果

```bash
# 一个示意性案例（非真实测量值，仅用于说明拓扑错配的后果）：
# 64 卡训练任务，分配到 4 台 8-GPU 机器 + 2 台 16-GPU 机器
# ─────────────────────────────────────────
# 期望吞吐：450 TFLOPS（示意值）
# 实际吞吐：180 TFLOPS（下降 60%）
# 原因：6 台机器的拓扑不匹配
#   · 4 台机器用了不同代的 NVSwitch
#   · 2 台机器在另一个 InfiniBand leaf 交换机下
#   · NCCL 选择了 Ring 算法 → All-Reduce 跨 leaf 交换机
# 修复后（拓扑感知调度）→ 420 TFLOPS
```

### 拓扑感知的典型实现

**Slurm 的拓扑感知**：
```bash
# topology.conf
SwitchName=spine001 Switches=leaf[01-04]
SwitchName=leaf001 Nodes=node[001-008]
SwitchName=leaf002 Nodes=node[009-016]

# 分配策略：尽量把任务分配到同一 leaf 交换机下
# --switches 的参数是"交换机数量"，不是交换机名字，语法为 --switches=<count>[@<max-time>]

sbatch --nodes=4 --switches=1@60 train.sh
# 1 = 最多占用 1 台 leaf 交换机；60 = 最多等 60 秒，凑不齐就放宽约束
```

**Kubernetes 的拓扑感知**：
```yaml
# 通过 topologyKey + GFD 写入的拓扑标签表达 NVLink 域约束
apiVersion: v1
kind: Pod
metadata:
  name: training-pod
spec:
  affinity:
    podAffinity:
      # 正确字段名是 requiredDuringSchedulingIgnoredDuringExecution
      requiredDuringSchedulingIgnoredDuringExecution:
      - topologyKey: nvidia.com/gpu.clique   # GFD 写入的 NVLink 域标签
        labelSelector:
          matchLabels:
            app: trainer
  schedulerName: kai-scheduler
```

> 注意：`nvidia.com/gpu-request-topology` 这类注解、以及 `nvidia.com/gpu.nvlink.domain` 这样的标签**都不存在**——GPU 拓扑信息由 **GPU Feature Discovery（GFD）** 采集后写成节点标签（`nvidia.com/gpu.product`、多节点 NVLink 场景下的 `nvidia.com/gpu.clique`），调度侧再用 **topologyKey** 或 **DRA ComputeDomain** 表达约束。

**NVIDIA GPU Operator + Topology Manager**：
```
Kubernetes Topology Manager:
  1. 收集节点上的 GPU 拓扑信息
  2. 在调度 Pod 时，确保 GPU 分配对齐 NUMA 节点
  3. 避免跨 NUMA 的 GPU 通信（性能损失 ~20%）
```

## 拓扑感知的三种粒度

### 1. GPU 级（NVLink 域）

最重要的拓扑维度：**把同一 NVSwitch 域内的 GPU 分给同一个任务**。

```bash
# 查看 GPU 拓扑
nvidia-smi topo -m

# 输出示例 A：4+4 双 NVLink 桥（两块各 4 卡的桥接板）——会出现 SYS
#         GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
# GPU0    X    NV2   NV1   NV1   SYS   SYS   SYS   SYS
# GPU1   NV2    X    NV2   NV1   SYS   SYS   SYS   SYS
# GPU2   NV1   NV2    X    NV2   SYS   SYS   SYS   SYS
# GPU3   NV1   NV1   NV2    X    SYS   SYS   SYS   SYS
# GPU4   SYS   SYS   SYS   SYS    X    NV2   NV1   NV1
# GPU5   SYS   SYS   SYS   SYS   NV2    X    NV2   NV1
# GPU6   SYS   SYS   SYS   SYS   NV1   NV2    X    NV2
# GPU7   SYS   SYS   SYS   SYS   NV1   NV1   NV2    X
#
# 输出示例 B：8 卡 NVSwitch 全互联——8 张卡之间两两都是 NV1/NV2，不会出现 SYS
#         GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
# GPU0    X    NV2   NV2   NV2   NV2   NV2   NV2   NV2
# GPU1   NV2    X    NV2   NV2   NV2   NV2   NV2   NV2
# GPU2   NV2   NV2    X    NV2   NV2   NV2   NV2   NV2
# GPU3   NV2   NV2   NV2    X    NV2   NV2   NV2   NV2
# GPU4   NV2   NV2   NV2   NV2    X    NV2   NV2   NV2
# GPU5   NV2   NV2   NV2   NV2   NV2    X    NV2   NV2
# GPU6   NV2   NV2   NV2   NV2   NV2   NV2    X    NV2
# GPU7   NV2   NV2   NV2   NV2   NV2   NV2   NV2    X

# 图例说明：
# NV1/NV2 = NVLink 连接（高速）
# SYS = 经由 PCIe 以及 NUMA 节点之间的 SMP 互连（QPI/UPI）——不等于"纯 PCIe 连接"

# 结论：
#  · 示例 A（4+4 桥）：GPU0-3、GPU4-7 是两个 NVLink 域；8 卡任务若拿到 GPU0-7，
#    跨域那部分通信要走 SYS → 性能打折
#  · 示例 B（8 卡 NVSwitch）：8 卡同处一个 NVLink 域，不存在"分成两个域"的问题，
#    "8 卡任务性能打折"这件事在这个模型上不成立
```

### 2. 节点级（InfiniBand leaf 交换机）

```bash
# 检查哪些节点在同一 IB leaf 下
# 方法 1：查看 Slurm topology.conf
SwitchName=leaf01 Nodes=node[001-032]

# 方法 2：IB 拓扑
ibnetdiscover | grep -E "Switch|CA" | head -20
```

### 3. 机架级（供电/散热边界）

```bash
# 有些数据中心的机架有供电上限
# 如果 4 台 GPU 服务器放在同一个机架 → 可能触发断路器
# 拓扑感知调度需要知道：
#   · 哪些机器共用一个 PDU（电源分配单元）
#   · 每个机架的供电容量
```

### 4. 多节点 NVLink 域（GB200 NVL72 与 ComputeDomain）

前面讲的都还是 H100 时代"单机 8 卡 NVSwitch 域"。而 **GB200 NVL72 把 72 张 GPU 跨 18 个 compute tray、通过 NVLink 交换机全互联**——一个 NVLink 域**横跨多个节点**。这时"拓扑感知"的含义变了：调度器要让一个作业拿到**同一个多节点 NVLink 域（MNNVL）**里的资源。

要把它暴露给 K8s 作业，需要两样东西：

1. **IMEX（Internode Memory Exchange）**：NVIDIA 的节点间内存交换服务，让不同节点上的 GPU 能经 NVLink 直接访问彼此的显存。NVIDIA Fabric Manager 初始化完成后，GFD 的 IMEX labeler 会给节点打上 `nvidia.com/gpu.clique` 标签，标识它属于哪个 NVLink 域。
2. **K8s 的 `ComputeDomain` CRD**：由 **NVIDIA DRA driver** 提供，把一组节点组织成"用 NVLink fabric 跑多节点作业"的逻辑域。作业申请一个 ComputeDomain，就拿到了这个 MNNVL 域内的 GPU 与 IMEX 通道。

```yaml
# 1) 创建多节点 NVLink 域
apiVersion: resource.nvidia.com/v1beta1
kind: ComputeDomain
metadata:
  name: my-compute-domain
spec:
  numNodes: 0            # 推荐置 0：由控制器按需决定节点数
  channel:
    resourceClaimTemplate:
      name: imex-channel-0
---
# 2) 作业申请该域中的 IMEX channel
apiVersion: v1
kind: Pod
metadata:
  name: my-workload
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: nvidia.com/gpu.clique    # GFD 写入的 NVLink 域标签
            operator: Exists
  resourceClaims:
  - name: imex-channel-0
    resourceClaimTemplateName: imex-channel-0
  containers:
  - name: app
    image: ubuntu:22.04
    resources:
      claims:
      - name: imex-channel-0
```

两个配套工具也值得知道：

- **topograph**（NVIDIA Run:ai）：自动发现 NVLink fabric / accelerator domain 拓扑，供调度器使用，免去手工维护拓扑表。
- **Kueue 的 Topology Aware Scheduling（TAS）**：支持 `required`/`preferred` 拓扑约束与 PodSet slices，能按 zone/block/rack/node 的层级拓扑放置 Pod，把"尽量靠近"变成可声明的调度意图。

## 🛠 实操指南

### 📋 决策指南：你的调度需要多强的拓扑感知？

```
你的训练任务特点？
├─ 单机 8 卡（单节点内）→
│   └─ 只需保证 GPU 在同一 NVLink 域内
│
├─ 多机 8-64 卡（2-8 节点）→
│   ├─ 需要 GPU 级拓扑（NVLink 域）
│   └─ 需要节点级拓扑（同一 IB leaf 下）
│
├─ 多机 64-512 卡 →
│   ├─ GPU 级：同一机器内保证 NVLink
│   ├─ 节点级：尽量同一 leaf 交换机
│   └─ 机架级：避免单一 PDU 过载
│
└─ > 512 卡 →
    └─ 拓扑感知 + 网络拓扑联合优化
        ├─ NCCL Ring 算法：需要环状拓扑
        └─ NCCL Tree 算法：需要分层拓扑
```

### 🔧 自己动手验：检查你的 GPU 拓扑

```bash
# 1. 查看 GPU 间的拓扑关系
nvidia-smi topo -m
# NV1/NV2 = 好（NVLink）
# PIX/PXB = 可接受（同一 PCIe 交换机/桥下）
# SYS = 经 PCIe + NUMA 间 SMP 互连（QPI/UPI），跨域通信，尽量避免

# 2. 检查 NVLink / NVSwitch 链路状态
nvidia-smi nvlink -s
# 查看每条 NVLink 的状态与速率；nvidia-smi nvlink -e 可看错误计数
# 也可用 DCGM 做整机诊断：dcgmi diag -r 3
# （注意：nvidia-smi 没有 nvswitch 子命令）

# 3. 检查 NCCL 选择的通信拓扑
# 注意：init_process_group 需要 rendezvous 信息，单文件直接调用会抛异常。
# 这里用 torchrun 拉起 8 个进程（torchrun 会自动注入 MASTER_ADDR/MASTER_PORT/RANK/WORLD_SIZE）
cat > init_test.py <<'PY'
import torch.distributed as dist
dist.init_process_group(backend='nccl')   # torchrun 已注入 rendezvous 环境
if dist.get_rank() == 0:
    print('NCCL initialized, world_size =', dist.get_world_size())
PY

NCCL_DEBUG_SUBSYS=GRAPH NCCL_DEBUG=INFO torchrun --nproc_per_node=8 init_test.py 2>&1 \
  | grep -E "Ring|Tree|Topo|pattern"
# 输出会显示 NCCL 选择的通信算法和拓扑

# 4. 拓扑感知调度测试：比较不同 GPU 组合的 All-Reduce 吞吐
# 关键点：dist.all_reduce 只能作用于"已建立的进程组"，跨域比较必须先 dist.new_group，
# 且 new_group 需被所有 rank 集体调用。下面是可运行的完整脚本（用 torchrun 拉起 8 进程）：
cat > bench_topo.py <<'PY'
import time
import torch
import torch.distributed as dist

def bench_topo(devices):
    """在给定 GPU 组合上建一个子进程组，测 All-Reduce 吞吐"""
    group = dist.new_group(ranks=devices)   # 必须被所有 rank 集体调用
    if dist.get_rank() not in devices:
        return None                         # 不属于此组的 rank 直接返回
    t = torch.randn(1024, 1024, device=f'cuda:{dist.get_rank()}')

    for _ in range(10):                     # 预热
        dist.all_reduce(t, group=group)
    torch.cuda.synchronize()
    t0 = time.time()
    for _ in range(100):
        dist.all_reduce(t, group=group)
    torch.cuda.synchronize()
    return 100 / (time.time() - t0)         # it/s

def main():
    dist.init_process_group(backend='nccl')   # torchrun 注入 rendezvous 环境
    rank = dist.get_rank()
    torch.cuda.set_device(rank)

    same = bench_topo([0, 1, 2, 3])   # 同一 NVLink 域内的 4 卡
    cross = bench_topo([0, 4])        # 跨域的两张卡

    if rank == 0 and same and cross:
        print(f'同域 4 卡吞吐: {same:.1f} it/s')
        print(f'跨域 2 卡吞吐: {cross:.1f} it/s')
        print(f'速度比: 跨域是同域的 {cross / same:.2f} 倍')

    dist.destroy_process_group()

if __name__ == '__main__':
    main()
PY

torchrun --nproc_per_node=8 bench_topo.py
```

### ⚠️ 常见误区

- **误区**："所有 GPU 之间的带宽是一样的"
  - **实际**：NVLink 带宽是 PCIe 的 **14 倍**，是跨机网络的 **2-10 倍**。不关注拓扑就等于主动放弃 50-90% 的性能。**物理即是命运。**

- **误区**："Kubernetes 默认支持拓扑感知"
  - **实际**：K8s 的 Topology Manager 只管理 **NUMA 对齐**（CPU 和 GPU 的关系），不管理 **GPU 之间的 NVLink 拓扑**。NVLink 拓扑需要 NVIDIA GPU Operator + 自定义调度器（KAI Scheduler）来实现。

- **误区**："拓扑感知只对大模型训练重要"
  - **实际**：**任何多 GPU 通信密集型的任务都需要拓扑感知**。包括：模型并行训练、大规模 batch inference、科学计算（MD、CFD 等）。

### 📊 底线数字速查

| 拓扑分配 | All-Reduce 吞吐（8×H100） | 相比最优的损失 |
|---------|------------------------|--------------|
| 同一 NVSwitch 域（最优）| ~460 GB/s | 0% |
| 同一机器跨 NVSwitch（4+4 桥）| ~400 GB/s | ~13% |
| 跨机 InfiniBand（RDMA）| ~50-350 GB/s | 20-90% |
| 跨机 TCP（无 RDMA）| ~5 GB/s | ~99% |

**经验法则**：
- TP 张量并行 → 必须同一 NVSwitch 域
- FSDP/ZeRO-3 数据并行 → 同一机器即可（NVLink 不是必须）
- PP 流水线并行 → 可以跨机器，但需保证网络带宽充足

### 💡 一句话记住

> **"拓扑感知调度就是'让距离最近的 GPU 一起工作'。NVLink 域内通信 900 GB/s，跨 PCIe 通信 64 GB/s——差了 14 倍。不认识拓扑的调度器，就是在亲手把训练性能砍掉一个数量级。"**
