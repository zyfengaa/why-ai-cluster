# Q: 为什么需要资源调度器？

## 为什么会有这个问题

你有一个 1024 张 GPU 的集群。10 个团队的 50 个训练任务同时涌进来——有的要 64 卡跑 3 天，有的要 8 卡跑 2 小时，有的要 512 卡但只用 30 分钟。

**如果手工分配**：排期冲突、资源碎片、有人抢卡、有人空等。

**如果放任自流**：两个任务同时抢同一张 GPU → OOM → 双双崩溃。

资源调度器就是为了解决这个问题而生的。

## 解决什么问题

资源调度器（Resource Scheduler / Job Scheduler）的核心功能：

1. **资源抽象**：把几千张 GPU 抽象成一个统一的资源池
2. **排队与优先级**：任务多时按策略排队（FIFO、公平分享、优先级抢占）
3. **资源隔离**：保证任务之间互不干扰（内存、GPU、网络）
4. **拓扑感知**：知道哪 8 张 GPU 在同一个 NVSwitch 域内，分配时尽量凑在一起

### 没有调度器的混乱世界

```
用户 A 提交 64 卡训练任务 → 在集群上找到 64 张空闲 GPU...  
  但在找的过程中，用户 B 占了 8 张 → A 只能等  
  用户 A 等到 64 张都空闲了，启动训练 →  
  跑了 6 小时后，用户 C 提交了一个 8 卡任务，资源调度策略不好，
  用户 A 的 64 卡中有 8 张被 C 的优先级抢占 →  
  用户 A 的 NCCL All-Reduce 超时 → 训练崩溃
	  
  用户 A：😡
```

### 有调度器的有序世界

```
用户 A 提交 64 卡任务 → 调度器查看排队策略 →
  A 排在队列第 2 位，前一个任务还需 2 小时 →
调度器预留 64 张拓扑对齐的 GPU →
2 小时后，A 的任务启动，全部 64 卡在同一 NVSwitch 域内 →
用户 C 提交 8 卡任务 → 调度器安排到另一个资源池 →
A 和 C 互不干扰 → 双方都满意
```

### 调度器的核心指标（经验参考值）

衡量一个调度器好不好，绕不开这几个指标。**注意：下面的区间是经验值，不同集群的实测结果差异很大**——它取决于任务大小分布、排队策略、拓扑约束和团队用法，不要当成任何集群的"标准答案"。

| 指标 | 含义 | 经验参考区间 |
|------|------|-------------|
| **资源利用率** | GPU 实际使用 / 总 GPU 数 | 多数生产集群在 60%–85% |
| **排队等待时间** | 任务提交到开始执行的时间 | 从分钟到小时级，取决于队列长度与任务规模 |
| **碎片率** | 无法被任何排队任务利用的 GPU 比例 | 良好配置下可控制在个位数百分比 |
| **调度延迟** | 调度器做出分配决策的时间 | 通常在毫秒到秒级 |
| **拓扑对齐率** | 任务拿到拓扑最优资源的比例 | 越大任务越难保证，需要专门的拓扑感知策略 |

这些数字的正确用法是：**拿它们当仪表盘，而不是当及格线**。你的集群利用率是 70% 还是 85%，更多取决于负载形态，而不是调度器本身。

## 主流的调度器选型

| 调度器 | 出身 | 定位 | 适用场景 |
|--------|------|------|---------|
| **Slurm** | HPC 领域（2002） | 批处理作业调度 | 大规模预训练、批处理任务 |
| **Kubernetes** | 云计算领域（2014） | 服务编排 | 推理服务、微服务、MLOps |
| **Slurm + K8s 混合** | 2024 起逐步成熟（Slinky/SUNK） | 统一调度 | 训练 + 推理共存 |

2026 年的最大变化是：**两边不再是非此即彼的关系**。

### Slurm 的核心设计

```
用户视角：
  sbatch job.slurm    # 提交作业
  squeue              # 查看排队
  scancel <jobid>     # 取消作业
  
调度器视角：
  fairshare 策略 → 多用户公平分配
  整块资源分配 → 作业申请的节点到位后才启动
  topology.conf → 感知网络/GPU 拓扑
  partition → 分区隔离（训练池、推理池、开发池）
```

### Kubernetes 的核心设计

```
用户视角：
  kubectl apply -f pod.yaml    # 提交任务
  kubectl get pods              # 查看状态
  kubectl delete pod <name>     # 删除任务

调度器视角：
  scheduler 调度 Pod
  device plugin / DRA 管理 GPU
  topology manager 保证 NUMA 对齐
  custom scheduler（Volcano/KAI）扩展批处理能力
```

## 🛠 实操指南

### 📋 决策指南：你需要什么样的调度器？

```
你的集群规模？
├─ < 32 GPU → 基本不需要调度器，手工分配或简单脚本即可
│
├─ 32-256 GPU →
│   ├─ 只有训练任务 → Slurm（简单可靠）
│   └─ 训练 + 推理混合 → Kubernetes（统一管理）
│
├─ 256-1024 GPU →
│   ├─ 你的团队更熟悉 HPC → Slurm
│   └─ 你的团队更熟悉 DevOps → Kubernetes + KAI Scheduler
│
└─ > 1024 GPU → 
    ├─ 纯大规模预训练 → Slurm（万卡级生产验证）
    └─ 混合负载 → Slurm on Kubernetes（Slinky / CoreWeave SUNK）
```

### 🔧 自己动手验：判断你的集群是否需要调度器

```bash
# 1. 查看当前集群有多少任务在手动管理
squeue 2>/dev/null || kubectl get pods 2>/dev/null
echo "如果输出为空，你可能已经在手动分配..."

# 2. 检查 GPU 利用率波动
nvidia-smi pmon -d 5 -s u -c 12
# 如果利用率频繁在 0% 和 100% 之间跳动 → 调度策略有问题

# 3. 检查是否有"碎片"GPU
nvidia-smi pmon -d 10 -c 6 | awk '{print $2}' | sort | uniq -c
# 观察到只有部分卡被占用，部分空闲 → 调度器分配不佳
```

```python
# 简单调度器 vs 不用调度器的 GPU 利用率对比模拟
import random

def simulate_no_scheduler(n_gpus=64, n_tasks=20):
    """模拟没有调度器的情况——任务随意抢占"""
    gpu_usage = {i: 0 for i in range(n_gpus)}
    tasks = []
    
    for _ in range(n_tasks):
        gpu_needed = random.choice([1, 2, 4, 8])
        duration = random.randint(1, 100)
        
        # 随机找 GPU（没有调度器的做法）
        available = [g for g in range(n_gpus) if gpu_usage[g] == 0]
        if len(available) >= gpu_needed:
            for g in available[:gpu_needed]:
                gpu_usage[g] = duration
            tasks.append(("running", gpu_needed, duration))
        else:
            tasks.append(("queued", gpu_needed, duration))
    
    used_gpus = sum(1 for v in gpu_usage.values() if v > 0)
    return used_gpus / n_gpus

def simulate_with_scheduler(n_gpus=64, n_tasks=20):
    """模拟有调度器的情况——分批排队分配"""
    gpu_usage = {i: 0 for i in range(n_gpus)}
    queue = []
    
    for _ in range(n_tasks):
        gpu_needed = random.choice([1, 2, 4, 8])
        duration = random.randint(1, 100)
        queue.append((gpu_needed, duration))
    
    # 调度器：按需求排序，大任务优先
    queue.sort(reverse=True)
    
    for gpu_needed, duration in queue:
        available = [g for g in range(n_gpus) if gpu_usage[g] == 0]
        if len(available) >= gpu_needed:
            for g in available[:gpu_needed]:
                gpu_usage[g] = duration
        # 装不下就跳过（等待下次调度周期）
    
    used_gpus = sum(1 for v in gpu_usage.values() if v > 0)
    return used_gpus / n_gpus

print(f"无调度器利用率: {simulate_no_scheduler():.0%}")
print(f"有调度器利用率: {simulate_with_scheduler():.0%}")
```

### ⚠️ 常见误区

- **误区**："有调度器就能 100% 利用 GPU"
  - **实际**：调度器解决的是"调度问题"，不是"利用率问题"。利用率还取决于任务大小、排队策略、拓扑约束。调度器做得再好，碎片通常也不会降到零。

- **误区**："Kubernetes 可以完全替代 Slurm 做训练调度"
  - **实际**：Kubernetes 天然适合**服务**（微服务、推理），但对**批处理作业**（训练）的支持需要额外组件（Volcano、KAI Scheduler、Kueue）。2026 年的共识是：**训练用 Slurm 或 K8s + 批调度扩展，推理用 K8s，两者混合是趋势**。

- **误区**："调度器越智能越好"
  - **实际**：过于复杂的调度策略本身会引入延迟。Google 的 Borg 论文（Verma et al., EuroSys 2015）描述的形态是：**调度决策本身在秒级完成**（大规模 cell 中调度器吞吐可达每分钟上万任务），但一个任务从提交到真正运行起来还包含镜像拉取、环境初始化等步骤，通常是**分钟级**。也就是说：调度要快，但任务的端到端启动时间并不等于调度延迟——把它误当成"10 秒"这种单一精确数字，就误解了论文的口径。

### 💡 一句话记住

> **"资源调度器就是 AI 集群的'交通警察'——它不让任何人抢道，不让任何卡闲置，不让大任务等太久。2026 年，Slurm 统治训练调度，Kubernetes 统治推理调度，而它们的混合（Slurm on K8s）正在缝合两边的世界。"**
