# 第七篇：调度篇 — 谁来分配几千张卡？

## 本篇章回答的问题

| Q&A | 核心链条 |
|------|---------|
| Q1: 为什么需要资源调度器？ | 手工分配不可能——排期冲突、资源碎片、互相抢占（[01-为什么需要资源调度器](01-为什么需要资源调度器.md)） |
| Q2: Slurm 为什么是 HPC 的传统选择？ | 多节点原子分配 + 批处理队列，万卡超算 20 年验证（[02-Slurm为什么是HPC传统选择](02-Slurm为什么是HPC传统选择.md)） |
| Q3: Kubernetes 为什么在 AI 场景崛起？ | 弹性、自愈、统一平台——AI 从"提交作业"变成"端到端流水线"（[03-Kubernetes为什么在AI场景崛起](03-Kubernetes为什么在AI场景崛起.md)） |
| Q4: NVIDIA 收购 SchedMD 意味着什么？ | Slurm 保持开源与厂商中立；"Slurm on K8s"（Slinky/SUNK）成为新选项（[04-NVIDIA收购SchedMD意味着什么](04-NVIDIA收购SchedMD意味着什么.md)） |
| Q5: Gang Scheduling 是什么？ | All-or-Nothing：要么全班到齐，要么一个不上（[05-Gang Scheduling](05-Gang%20Scheduling.md)） |
| Q6: 拓扑感知调度为什么重要？ | 感知 NVLink 域与交换机层级，把通信最密集的卡放在物理最近处（[06-拓扑感知调度](06-拓扑感知调度.md)） |

**核心因果链**：集群变大，手工分配失效（Q1）→ 批处理归 Slurm（Q2）、服务与端到端归 K8s（Q3）→ 两者从对立走向融合（Q4）→ 但融合也解决不了"所有 GPU 必须同时到位"（Q5）→ 到位了，还得把它们放在拓扑最优的位置上（Q6）
