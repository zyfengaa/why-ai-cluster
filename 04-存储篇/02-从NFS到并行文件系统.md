# Q: NFS 为什么不行？并行文件系统解决了什么？

## 为什么会有这个问题

很多企业搭建 AI 集群时，第一个想到的存储方案就是 NFS——因为它最简单、最熟悉。"不就是个网络共享文件夹吗？"

但 NFS 的架构在 AI 训练场景下有几个躲不开的坑——不过先说清楚它到底坑在哪：**NFS 并不是处处不行**，文本预训练的原始读带宽其实很小（见下文复算），NFS 真正的死穴是单点聚合带宽、小文件元数据和 checkpoint 写入。

## NFS 的根本问题

```
┌──────────────────────────────────────────────────┐
│                  NFS 服务器                         │
│  ┌─────────────────────────────────────────────┐  │
│  │        单块磁盘或单一 RAID 阵列               │  │
│  └─────────────────────────────────────────────┘  │
│                       ↑                           │
│                单点带宽瓶颈                          │
│             （通常 1-10 GbE = 125 MB/s - 1.25 GB/s）│
└────────────────────┬──────────────────────────────┘
                     │
     ┌───────────────┼───────────────┐
     │               │               │
┌────▼────┐   ┌─────▼────┐   ┌─────▼────┐
│ GPU 机 A│   │ GPU 机 B │   │ GPU 机 C │
└─────────┘   └──────────┘   └──────────┘

问题：1 台 NFS 要喂饱 N 台 GPU 服务器，共享单点带宽
```

NFS 的三个致命缺陷：
1. **单点瓶颈**：所有流量经过一台 NFS 服务器，**聚合带宽上限固定，不随客户端数量增长**——8 台机器一起读，总吞吐还是那 1-2 GB/s
2. **无并行机制**：多客户端同时读写同一文件时锁竞争严重
3. **元数据慢**：`ls` 一个有 10 万个文件的目录可能需要几十秒

## 并行文件系统怎么解决

并行文件系统的核心思想：**把数据分布到多台存储服务器上，让所有 GPU 可以并行读写**。

```
                   并行文件系统（以 Lustre 为例）
┌───────────────────────────────────────────────────┐
│   元数据服务器（MDS）     │    元数据只占一小部分流量      │
│   ───────────────────────┘                         │
│                                                     │
│   对象存储服务器 1（OSS1）──── OST1（硬盘组）           │
│   对象存储服务器 2（OSS2）──── OST2（硬盘组） ← 数据分布  │
│   对象存储服务器 3（OSS3）──── OST3（硬盘组）   到这 128  │
│   ...                             个 OST              │
│                                                     │
│   高速网络互连（IB/RoCE，40-100 Gb/s）                │
└────────────────────┬────────────────────────────────┘
                     │
     ┌───────────────┼───────────────┐
     │               │               │
┌────▼────┐   ┌─────▼────┐   ┌─────▼────┐
│ GPU 机 A│   │ GPU 机 B │   │ GPU 机 C │
└─────────┘   └──────────┘   └──────────┘
```

关键改进：

| NFS 问题 | 并行文件系统方案 |
|---------|----------------|
| 单点带宽 | **N 台存储服务器** = N 倍聚合带宽，128 个 OST 可达数百 GB/s 聚合 |
| 单点故障 | 多台 OSS，一台挂了数据仍在其他节点可读 |
| 元数据慢 | **独立的元数据服务器**（MDS），或分布式元数据（WEKA） |
| 文件锁冲突 | 分布式锁管理，支持并行写入同一文件的不同部分 |

### NFS 家族的现代化与补充角色

NFS 不是只能躺在原地被批判，它也在演化，另外两类存储也有自己的位置：

- **pNFS（NFSv4.1+，RFC 5661）**：允许客户端绕过元数据服务器，直接并行访问多台存储设备，元数据与数据路径分离。这修复了"数据面单点"的问题，但命名空间与锁服务仍在单一服务器上，海量小文件的元数据瓶颈依旧。
- **对象存储（S3 类）**：适合当**数据湖/冷数据层**——数据集原始副本、历史 checkpoint 的归档。直接从 S3 喂训练吃不消，但配合缓存层是标配架构。
- **Burst Buffer**：在计算节点与主存储之间加一层高速缓冲（如跑在 GPU 节点本地盘上的 BeeOND），吸收 checkpoint 写入和临时数据峰值，让主存储不用直面 IO 洪峰。

## 🛠 实操指南

### 📋 决策指南：你的存储要升级吗？

**先测再决定。回答这三个问题：**

```
Q1：你的数据集多大？有多少文件？

  企业 NFS 通常能处理 < 10 万文件
  AI 训练数据集通常包含数百万到数亿个文件（未打包）
  → 如果 `ls -l /data | wc -l` 超过 10 万，且 ls 耗时 > 30 秒 → NFS 元数据瓶颈

Q2：你的训练任务每步需要读多少数据？（复算一遍）

  以 32 GPU 训练 70B、每卡 batch 4、序列长 4096、每 token 输入 ID 2 字节为例：
  4 × 4096 × 2 B × 32 GPU = 1,048,576 B ≈ 1 MB/步 —— 是 1 MB，不是 1 GB！
  每步 0.5 秒 → 只需约 2 MB/s 聚合读吞吐。
  → 对纯文本预训练，这个量任何存储（包括最烂的 NFS）都毫无压力。
    文本训练的存储压力来自海量分片文件的元数据与 checkpoint 写入，
    而不是原始读带宽。
  → 多模态（图像/视频）每步几百 MB-GB 级，读带宽才成为硬约束。

Q3：你的 Checkpoint 写需要多快？（口径：完整训练状态）

  Checkpoint 完整状态 = 16 B/参数（权重 2 + 梯度 2 + FP32 master 4 + Adam m/v 8）
  70B → 1.12 TB（仅权重 140 GB，仅权重+优化器 980 GB，见 FACTS 口径表）
  NFS 写速度 ~1 GB/s → 1.12 TB ≈ 19 分钟 GPU 空闲
  → 每 45 分钟保存一次 = 每天约 10 小时 GPU 白等
```

**决策树：**

```
NFS 可以继续用？
├─ 只有 1-2 台 GPU 服务器，数据集 < 1TB，checkpoint 少 → ✅ 暂时可以
├─ 4-8 台 GPU，checkpoint 用本地 NVMe 中转 → ⚠️ 考虑 BeeOND（临时缓冲）
└─ > 8 台 GPU，70B+ 模型训练 → ❌ 必须换并行文件系统
  
并行文件系统选哪个？
├─ 有 HPC 运维团队 → Lustre（免费，运维成本高）
├─ 预算充足，追求极致 → WEKA（省心，配合 GDS 性能最高）
├─ 32 节点以下 → BeeGFS（轻量，易部署）
└─ 临时/实验任务 → BeeOND（跑在 GPU 节点本地盘，零额外成本）
```

### 🔧 自己动手验：你的 NFS 到底有多慢？

```bash
# 1. 测 NFS 单机读吞吐（单客户端口径）
time dd if=/shared/dataset/shard-00001.bin of=/dev/null bs=1M count=10000
# 期望：> 1 GB/s。如果 < 500 MB/s → NFS 严重瓶颈

# 2. 测 NFS 元数据性能
time ls -l /shared/dataset/ | wc -l
# 10 万文件期望 < 5 秒。如果 > 30 秒 → 元数据瓶颈

# 3. 测多客户端并发读：区分"单客户端"和"聚合"两种口径
# 在 4 个节点上同时读取
for node in node1 node2 node3 node4; do
  ssh $node "time dd if=/shared/data/shard-\$(hostname).bin of=/dev/null bs=1M count=5000" &
done
wait
# 看聚合总吞吐：
#   ≈ 单节点 × 节点数   → 存储可扩展，聚合口径正常
#   ≈ 单节点吞吐        → 所有流量挤在单点上（NFS 单点瓶颈确认！）

# 4. 训练中实测数据加载停顿率
torch.cuda.synchronize()
t0 = time.time()
batch = next(train_loader)
torch.cuda.synchronize()
load_time = time.time() - t0
# load_time 占 step 的比例 > 10% → 数据加载是瓶颈（完整测法见 06 篇）
```

### ⚠️ 常见误区

- **误区**："我买了全闪存 NAS，SSD 那么快，NFS 肯定不会慢"
  - **实际**：**瓶颈在 NFS 协议的单点架构，不是磁盘本身**。一块 NVMe SSD 可以跑到 7 GB/s（单盘顺序读），但经过 NFS 服务器转发后，多客户端共享的聚合带宽上限通常只有 1-2 GB/s（取决于网卡和协议开销）。你花大价钱买的 SSD 在 NFS 下只能发挥一小部分性能。
- **误区**："数据集只有几百 GB，NFS 足够用了"
  - **实际**：几百 GB 是数据集大小，但训练过程中**每 30-45 分钟要写一次完整训练状态 Checkpoint（70B = 1.12 TB）**。NFS 约 1 GB/s 的写入速度意味着每次 Checkpoint GPU 要闲置约 19 分钟，一天 32 次就是约 10 小时。**存储系统不仅要喂数据集，还要接 Checkpoint 的写入。**
- **误区**："并行文件系统太复杂了，小团队搞不定"
  - **实际**：WEKA 和 BeeGFS 的部署已经非常简化。WEKA 可以用容器化方式部署，BeeGFS 在 8-16 节点规模下几小时内能搭好。Lustre 确实复杂（需要独立 MDS/OSS 配置、条带化设置），但**你也未必需要 Lustre**。32 节点以下 BeeGFS/BeeOND 是很好的选择，**不需要 HPC 运维经验**。

### 📊 底线数字速查

| 指标 | NFS（10GbE） | NFS（25GbE + NVMe） | Lustre（32 OST） | WEKA（32 节点） |
|------|------------|-------------------|-----------------|----------------|
| **单客户端**读吞吐 | ~1 GB/s | ~2.5 GB/s | ~3-5 GB/s | ~5-10 GB/s |
| **聚合**读吞吐（8 节点同时读） | ~1 GB/s（单点，不随节点扩展） | ~2.5 GB/s（单点） | **~208 GB/s** | **~272 GB/s** |
| 元数据 10 万文件 ls | > 30 秒 | > 30 秒 | ~3 秒（独立 MDS） | **< 1 秒（分布）** |
| Checkpoint 写入（1.12 TB 完整状态，聚合） | ~19 分钟 | ~7.5 分钟 | ~29 秒 | ~25 秒 |
| GPU 利用率损失（设计不佳时） | 10-30% | 5-15% | 1-3% | < 2% |
| 部署难度 | 极低 | 低 | **高（需 HPC 经验）** | 中（容器化） |
| 月成本（128 GPU 集群，量级估算） | ~$0（已有） | ~$0-200 | ~$5,000（主要是运维人力） | ~$5,000-6,000（许可为主） |

把第二行读明白：Lustre/WEKA 的 **单客户端 3-10 GB/s** 和 **聚合 208-272 GB/s** 不矛盾——前者是"一台机器一条连接能跑多少"，后者是"8 台机器一起跑能堆到多少"。NFS 的悲剧是这两个数字永远相等：单客户端 1 GB/s，100 台机器一起读还是 1 GB/s，因为数据面只有一个单点。**并行文件系统的本质改进是让聚合带宽随存储服务器数量线性扩展。**

成本口径说明：Lustre 的 ~$5,000/月是 128 GPU（16 台）自建集群的**运维人力**量级估算；WEKA 是商业许可的量级估算。不同配置、不同年份、不同报价方式不可直接比较，请按自己的报价复算。

### 💡 一句话记住

> **"NFS 的问题不是'慢'，是'不扩展'：单客户端 1 GB/s，一百台机器加起来还是 1 GB/s。并行文件系统把聚合带宽变成 N 台存储服务器的函数——这才是选型的分水岭。"**
