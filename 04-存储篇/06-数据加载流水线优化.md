# Q: 数据加载流水线怎么优化？

## 为什么会有这个问题

前面几篇解决了"用什么存储"和"怎么写 checkpoint"，但训练时最高频的 I/O 是另一件事：**每个 step 把一批样本从磁盘读到 GPU 显存**。这条流水线上任何一跳卡住——磁盘慢、解码慢、CPU 不够、没有重叠——GPU 都会空转等数据。

数据等待最麻烦的地方是**看不见**：nvidia-smi 的 GPU-Util 只看采样期内有没有 kernel 在执行，dataloader 偶尔迟到一个 batch、GPU 快速算完然后干等，GPU-Util 照样可能显示高值，而 MFU 已经掉下去了。所以优化数据流水线的第一步是**先测出来 GPU 到底在等谁**，第二步才是逐跳提速。

## 解决什么问题

### 一条 batch 的旅程

```
磁盘（并行 FS / 对象存储 / 本地 NVMe）
  → 页缓存 → worker 进程：读取 + 解码 + 增强/augmentation
  → collate 成 batch → pin memory（锁页）
  → H2D 拷贝（PCIe）→ GPU 计算
```

每一段的瓶颈不同：磁盘段看存储带宽与文件布局，解码段看 CPU，H2D 段看 PCIe 与内存分配。下面逐个拆。

### DataLoader 的三个旋钮

PyTorch `DataLoader` 影响最大的三个参数：

| 参数 | 作用 | 常见坑 |
|------|------|--------|
| `num_workers` | 子进程并行做读取/解码/collate。解码和 tokenize 是 CPU 密集活，主进程单线程根本喂不饱 GPU | 不是越多越好：每 worker 一份 dataset 内存拷贝，太多会内存爆、上下文切换开销上升 |
| `prefetch_factor` | 每个 worker 提前准备多少个 batch。让"读数据"和"算模型"错峰重叠 | 设 1 相当于不预取，GPU 常等；设太大浪费内存 |
| `pin_memory=True` | 用锁页内存做 host→device 拷贝，配合 `non_blocking=True` 让 H2D 与计算重叠 | 内存开销约翻倍，小数据集随手开会 OOM |

另一个必开项：`persistent_workers=True`。默认设置下每个 epoch 都销毁重建 worker，几百 GB 数据集的 epoch 开头总有一段"worker 冷启动"的停顿。

### CPU 才是常被忽略的瓶颈

图像类任务里，JPEG/PNG 解码、resize、增强都是纯 CPU 计算；文本任务里 tokenize 也一样。常见症状是：iostat 显示磁盘远没跑满，但 GPU 还是在等数据——**瓶颈在 CPU 解码，不在存储**。对策按优先级：

1. **离线化**：tokenize、格式转换在数据集构建期做完，训练时只读结果（分片文件）；
2. **加 worker**：`num_workers` 从 4–8 起步，按实测调整；
3. **换解码库**：NVIDIA [DALI](https://docs.nvidia.com/deeplearning/dali/user-guide/docs/index.html) 把解码/增强搬到 GPU 或批量流水线化。

### 小文件 vs 分片格式

数百万个几 KB 的小文件是所有文件系统的噩梦：元数据操作（open/stat/ls） dominate，吞吐上不去。训练前先打包：

- **WebDataset（tar 分片）**：样本按序打进几十至几百 MB 的 tar 分片，顺序大块读——这是所有存储最擅长的负载；
- **Parquet / Mosaic Streaming 等列式/流式格式**：表格与多模态数据的等效方案。

一个 70B 文本预训练每步的纯 token ID 读取量其实很小（`batch × seq × 数字节`，例如 4 × 4096 × 4 B ≈ 64 KB/卡量级），**文本预训练的数据读取压力主要来自海量分片文件的元数据与解压，而不是原始带宽**；多模态（图像/视频）每步几百 MB 起步，带宽才成为硬约束。

### 本地 NVMe 缓存与数据局部性

- **节点内局部性**：第一次 epoch 从对象存储/并行 FS 把分片拉到节点本地 NVMe，之后直接本地读。本地 NVMe 单盘顺序读 5–7 GB/s（单客户端口径），远端存储的元数据开销直接归零。
- **跨节点局部性**：不同 rank 读不同分片，避免所有节点同时读同一批文件造成存储热点；调度器做拓扑感知调度（数据在哪，任务调度到哪）。

### 断点续训：StatefulDataLoader

标准 `torch.utils.data.DataLoader` **没有 `state_dict()`**——checkpoint 恢复后 sampler 会从头开始，前半个 epoch 的数据被重复训练。PyTorch 2.4+ 的 `torchdata.stateful_dataloader.StatefulDataLoader` 是 drop-in 替代，提供 `state_dict()/load_state_dict()`，把 sampler、迭代位置、worker 状态一起保存，与 05 篇的 checkpoint 配套使用。

### Overlap：让取数和计算重叠

理想流水线里，GPU 算 batch i 时，CPU 正在准备 batch i+1、H2D 在拷 batch i。实现要点：

- `num_workers` ≥ 2 + 足够的 `prefetch_factor`，让"取数"天然跑在"计算"前面；
- H2D 用 `tensor.to("cuda", non_blocking=True)` + `pin_memory`，与计算重叠；
- 指标用 **data wait time 占 step 的比例** 来验收（见下）。

## 🛠 实操指南

### 📋 决策指南：我的流水线哪一跳是瓶颈？

```
Q1：data wait 占比 > 10%？（测法见下）→ 有瓶颈，继续
Q2：iostat/存储监控显示读带宽接近上限？
    是 → 存储带宽/文件布局问题 → 打包分片、加缓存、换存储
    否 → 继续
Q3：CPU 利用率接近 100%，尤其某个进程单核打满？
    是 → 解码/tokenize 瓶颈 → 加 worker、离线化、DALI
    否 → 继续
Q4：每个 epoch 开头有明显慢速段？
    是 → worker 重建/页缓存冷启动 → persistent_workers、预热
```

### 🔧 自己动手验：测取数时间，别测反

关键点：用显式 `next(loader)` 计时，把 **CPU 等待 batch + H2D 拷贝** 记为取数时间，把 **H2D 完成后的计算** 记为计算时间，两边都用 `torch.cuda.synchronize()` 切开：

```python
import time, torch
from torch.utils.data import DataLoader

loader = DataLoader(
    dataset,
    batch_size=64,
    num_workers=8,            # 解码/tokenize 交给子进程
    prefetch_factor=4,        # 每 worker 预取 4 个 batch
    pin_memory=True,          # 锁页内存，H2D 可 non_blocking
    persistent_workers=True,  # 跨 epoch 复用 worker
)

it = iter(loader)
fetch_times, compute_times = [], []
WARMUP = 20   # 跳过前 N 步：worker 冷启动/页缓存未热时会虚高
STEPS  = 200

for step in range(STEPS):
    torch.cuda.synchronize()
    t0 = time.perf_counter()

    batch = next(it)                                        # CPU 侧等待数据就绪
    x = batch["pixel_values"].to("cuda", non_blocking=True) # H2D
    y = batch["labels"].to("cuda", non_blocking=True)
    torch.cuda.synchronize()                                # 等 H2D 真正完成

    t1 = time.perf_counter()
    fetch = t1 - t0                                         # 取数时间

    loss = model(x, y)                                      # 正常训练步
    torch.cuda.synchronize()                                # 等计算真正完成
    t2 = time.perf_counter()
    compute = t2 - t1                                       # 计算时间

    if step >= WARMUP:
        fetch_times.append(fetch)
        compute_times.append(compute)

f, c = sum(fetch_times), sum(compute_times)
print(f"data wait 占比 = {f/(f+c)*100:.1f}%")   # > 10% 即需优化
print(f"平均取数 {f/len(fetch_times)*1000:.1f} ms / 计算 {c/len(compute_times)*1000:.1f} ms")
```

**不要测反**：如果只在外面套一个总计时器，取数与计算会混在一起；如果忘了在计算后 `synchronize()`，异步执行的 kernel 会让"计算时间"虚假地接近零、取数时间被夸大。判断标准始终是 `data wait 占比 = Σ取数 / (Σ取数 + Σ计算)`。

### ⚠️ 常见误区

- **误区**："num_workers 越大越好"
  - **实际**：每个 worker 都复制一份数据集对象，worker 数超过 CPU 核数后收益归零、内存和调度开销上升。从 4–8 起步，用 data wait 占比实测校准。
- **误区**："GPU 利用率 100%，数据加载肯定没问题"
  - **实际**：GPU-Util 只表示"有 kernel 在跑"。数据晚到 → GPU 快速算完干等 → 采样期内仍有 kernel 执行。请用 MFU 和 data wait 占比判断。
- **误区**："存储监控显示磁盘很闲，所以不是 I/O 问题"
  - **实际**：磁盘闲 + GPU 等，多半是 CPU 解码/tokenize 瓶颈，或小文件元数据开销。先分层定位，再对症下药。
- **误区**："断点续训只要恢复模型和优化器"
  - **实际**：数据位置也得恢复，否则重复或跳过半个 epoch 的数据。用 StatefulDataLoader，并把它的 `state_dict()` 和模型 checkpoint 用同一个 step 对齐保存。

### 📊 底线数字速查

| 指标 | 优秀 | 及格 | 报警 |
|------|------|------|------|
| data wait 占 step 比例 | < 2% | 2–10% | > 10% |
| 单客户端本地 NVMe 顺序读 | > 5 GB/s | 2–5 GB/s | < 2 GB/s |
| 预处理产物格式 | tar 分片/parquet，单分片 100 MB+ | 中等分片 | 数百万小文件直读 |
| worker CPU 余量 | CPU 占用 < 80% | 80–95% | 单核 100% |
| 断点续训的数据状态 | StatefulDataLoader 与 step 对齐 | 手工记录 epoch/step | 不恢复数据状态 |

### 💡 一句话记住

> **"数据流水线的目标是让取数时间在 step 里'消失'——GPU 算 batch i 时，CPU 已经备好了 batch i+1。先用 next(loader) 前后计时把等待测出来，再按'磁盘→解码→H2D'逐跳修：小文件打包、解码离线化、本地 NVMe 缓存、pin_memory + non_blocking。"**
