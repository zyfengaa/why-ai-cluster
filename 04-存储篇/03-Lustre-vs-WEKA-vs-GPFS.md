# Q: Lustre vs WEKA vs GPFS 怎么选？

## 为什么会有这个问题

并行文件系统不止一种。Lustre、WEKA、GPFS、BeeGFS……每个有各自的设计哲学和适用场景。选错了，不仅成本高，还可能成为集群的性能陷阱。

## 核心对比

| 特性 | **Lustre** | **GPFS / Spectrum Scale** | **WEKA** | **BeeGFS** |
|------|-----------|--------------------------|---------|-----------|
| 架构 | 内核模块，元数据/数据分离（DNE 可多 MDT） | 内核模块，NSD 架构，企业级 | **软件定义**，NVMe 原生，用户态 | 用户态，轻量 |
| 元数据 | 单 MDT 起步，**DNE 横向扩展到多 MDT** | 分布式 + 管理节点 failover | **全分布式** | 分布式 |
| 最大聚合吞吐 | 100s GB/s - 1 TB/s 量级 | 100s GB/s 量级 | **1+ TB/s 量级** | 500+ GB/s 量级 |
| **GPU Direct Storage** | 较新版本支持（需确认版本/配置） | 有支持，需确认版本 | ✅ **原生支持** | ✅ 7.3+ 支持（需确认客户端/内核/驱动组合） |
| 小文件性能 | 弱（需打包为 TAR） | 良好 | **优秀**（千万级文件秒级 list，厂商口径） | 良好 |
| 安装难度 | ❌ 困难 | ❌ 困难 | ✅ 简单 | 中等 |
| 许可证 | 开源 (GPL) | 商业（通常最贵） | 商业（中等） | 开源（商业支持另计） |
| 典型场景 | HPC/科研，传统超算 | 企业/HPC，金融，混合负载 | **AI/HPC 前沿** | HPC/科研 |

注意：聚合吞吐一栏都是**量级**——同一系统配 32 个 OST 和配 128 个 OST 差好几倍，厂商口径数字不作精确承诺。

## 深度看 Lustre

**最广泛使用的 HPC 并行文件系统**（TOP500 超算的多数席位，公开口径）。

### 部署要点

```
核心组件：
  MGS（管理服务器）+ MDS/MDT（元数据）+ OSS/OST（存储）

元数据扩展：
  单 MDT 起步即可服务中等规模集群；规模上来后用 DNE
  （Distributed Namespace）扩到多 MDT，元数据随之横向扩展。
  下文的"4 个 MDT"就是 DNE 配置——元数据服务不是天生单点。

关键调优命令：
  # Checkpoint 目录 — 全条带化，最大化聚合写带宽
  lfs setstripe -c -1 -S 4M /checkpoints
  
  # 数据集目录 — 少量条带，减少元数据开销
  lfs setstripe -c 4 -S 1M /datasets
```

### Lustre 的适用边界

| ✅ 适合 | ❌ 不太适合 |
|--------|-----------|
| 有专业 HPC 运维团队 | 没有 HPC 经验的小团队 |
| 大量顺序大文件（100 MB+） | 海量小文件（如大量 JSON） |
| 预算有限（Lustre 软件免费） | 需要 GDS 且不想折腾版本兼容 |
| 128+ 节点集群 | 8-16 节点小规模（杀鸡用牛刀） |

**128 节点规模**需要 128 个 OST（对象存储目标）+ 4 个 MDT（DNE 多元数据目标），可达约 480 GB/s **聚合**写吞吐。

**网络要求**：Lustre 的 LNet 支持 socklnd，**标准 TCP 以太网上也能跑**——"必须 IB/RoCE"是误传。但生产环境追求大吞吐时普遍用 IB/RoCE：TCP 模式的吞吐与延迟明显吃亏（具体损失取决于 MTU、条带数与负载，不是固定百分比）。

## 深度看 GPFS / IBM Storage Scale

**IBM 的企业级并行文件系统**（Spectrum Scale 是旧名，现名 IBM Storage Scale），从 HPC 起家但在企业混合负载中扎根最深。选型对比里它经常被一笔带过，这里补齐同一维度的信息：

1. **NSD（Network Shared Disk）架构**：磁盘/目标盘通过 NSD server 暴露给整个集群，客户端可以直连磁盘（SAN 场景）或经 NSD server 中转（NFS/对象场景）。数据访问路径支持多路，天然多节点并发。

2. **分布式元数据 + 管理节点 failover**：元数据按文件系统散布在多个节点（Filesystem Manager / Token Manager 角色分布在管理节点上，故障时自动 failover）。没有 Lustre 那样的"单 MDT 起步"心智负担，但管理节点的选举与 failover 是运维要理解的核心机制。

3. **ILM / 策略引擎**：`mmapplypolicy` 按策略自动把冷数据迁移到磁带/对象存储、做分层与生命周期管理。企业"热训练数据 + 冷归档"混存的场景里，这是 GPFS 相对 Lustre/WEKA 的招牌能力（WEKA 用内置 S3 分层解决类似问题）。

4. **许可成本**：纯商业许可，按容量/节点计价，通常高于 WEKA 且远高于免费的 Lustre——换来的是 IBM 支持体系和企业功能（加密、多集群、ILM）。**规模小、预算紧的团队一般不会选它；金融/大型企业已有 IBM 存储生态的，续用它最顺。**

## 深度看 WEKA

**近年 AI 场景增长最快的并行文件系统之一**。它专为 AI 训练设计，而不是从 HPC 改造来的。

### 架构核心优势

1. **DPDK 内核绕过**：传统 I/O 路径 = 用户态 → 内核态 → NVMe 驱动。WEKA 直接从**用户态访问 NVMe**，降低延迟。

2. **元数据全分布式**：不需要独立的 MDS 节点，海量小文件/目录遍历不经过集中元数据点。

3. **GPU Direct Storage (GDS) 原生支持**：顺序大块 I/O 在 GDS 路径下约 2.5× 提升（统一口径见 04 篇：单 GPU 顺序读 8 → 20 GB/s，本地 NVMe、1 MB 顺序块），CPU 占用显著下降（厂商口径：降低 4-6×）。

4. **内置 S3 自动分层**：热数据留在 NVMe，冷 checkpoint 自动迁移到对象存储。

### 经济性分析（示意 benchmark，口径同 01 篇）

32 GPU H200 集群：
- WEKA 额外存储成本：约 $2/小时（按报价估算）
- GPU 有效利用率：72% → 99%，提升 27 个百分点（相对提升 37.5%）
- 32 卡 × 0.27 ≈ 每小时多产出 8.6 个有效 GPU 小时；按 $5/GPU·小时 计价 ≈ $43/小时
- **盈亏平衡：约 3 分钟（按上述假设；报价与利用率不同请自行复算）**

**如果你在意 GPU 利用率，WEKA 几乎肯定值这个钱。**

## 实际场景 Benchmark（示意，口径：多节点聚合）

### Checkpoint 写（70B 模型，完整训练状态 1.12 TB，32 GPU H200 集群）

| 存储 | 聚合写吞吐 | 写 1.12 TB | 每 45 分钟间隔的停顿占比 |
|------|-----------|-----------|------------------------|
| NFS | 1.1 GB/s | ~17 分钟 | ~38% |
| BeeOND（临时缓冲） | 28 GB/s | ~40 秒 | 1.5% |
| Lustre（32 OST, RoCE） | 38 GB/s | ~29 秒 | 1.1% |
| **WEKA（32 GPU）** | **44 GB/s** | **~25 秒** | 0.9% |

### 数据加载（聚合读）

| 存储 | 聚合读吞吐 | Dataloader 停顿 |
|------|-----------|----------------|
| NFS | 0.9 GB/s | 31% |
| BeeOND | 18 GB/s | 2% |
| Lustre | 26 GB/s | 1.1% |
| **WEKA** | **34 GB/s** | 0.7% |

## 容量规划：1,024 卡集群要买多少存储

选型之前先把容量算出来。分三笔账：

### 1. 热数据集（训练中反复读）

| 数据类型 | 原始规模 | 说明 |
|---|---|---|
| 文本语料 | 10–100 TB | tokenize 后可能膨胀 1–2× |
| 多模态（图像/视频） | 数百 TB – PB 级 | 必须对象存储 + 本地缓存，不能全放并行 FS |
| 指令/对齐数据 | 数十–数百 GB | 小文件多，元数据压力大 |

### 2. Checkpoint 容量

```
70B 完整训练状态 = 1.12 TB/个
保留 5 个 = 5.6 TB/任务
同时跑 10 个 70B 任务 → 56 TB
再乘 1.5 的安全系数 → 约 84 TB
```

### 3. 带宽与本地缓存

| 口径 | 需求 |
|---|---|
| Checkpoint 写（70B，30 秒写完） | 约 32.7 GB/s 聚合 |
| 数据预处理峰值 | 30+ GB/s 聚合 |
| 本地 NVMe 缓存 | 每节点 2–4 TB（装当前 epoch 的热分片） |

### 一个可代入的算例

```
集群：1,024 卡（128 台 8 卡服务器）
负载：10 个 70B 训练任务
热数据 50 TB + checkpoint 84 TB + 余量 50%
→ 并行文件系统可用容量 ≈ 200 TB
→ 聚合带宽 ≈ 30–50 GB/s（写峰值为主）
→ 每节点本地 NVMe 2–4 TB
```

**结论**：容量按"热数据 + checkpoint × 保留数 + 1.5 余量"算；带宽按"checkpoint 写峰值"和"预处理峰值"取大者。只算容量不算带宽，会买到大而慢的存储；只算带宽不算容量，会在第三个 checkpoint 就爆盘。

## 选型决策树

```
你的团队有 HPC 运维经验吗？
├─ 没有 →
│  集群规模 > 32 节点？
│  ├─ 是 → WEKA（买省心）
│  └─ 否 → BeeGFS 或 WEKA
└─ 有 →
   预算充足？
   ├─ 是 → WEKA（性能天花板最高）
   └─ 否 → Lustre（免费但运维成本高）
   已有 IBM 存储生态/需要 ILM 归档？
   └─ → GPFS / Storage Scale（企业支持与分层能力）
```

## 🛠 实操指南

### 📋 决策指南：你的存储到底该花多少钱？

精确回本时间取决于报价和实际利用率提升，不要照抄别人的表。用这个方法算：

```
回本时间 ≈ 存储月成本 ÷ (GPU 利用率提升百分点 × 卡数 × GPU 单价 × 24 × 30)

示例（假设 H200 $5/GPU·小时，利用率 +10 个百分点，128 卡）：
  省下 GPU 时间价值 ≈ 0.10 × 128 × $5 × 720h ≈ $46,000/月
  存储月成本（Lustre 自建或 WEKA，量级 $5,000-6,000/月）
  → 回本 ≈ 3-4 天

不同假设下回本时间从数小时到数周不等，但只要利用率提升
是真实的（用 data wait 占比实测验证），存储成本通常在
数天到数周量级内被覆盖。
```

各方案月成本的**量级**（估，随报价波动）：

| 集群规模 | 存储方案 | 月成本量级 | 说明 |
|---------|---------|-----------|------|
| 32 GPU（4 台） | BeeOND（临时） | ~$0 | 跑在 GPU 节点本地盘 |
| 32 GPU（4 台） | WEKA（商业许可） | 数千美元 | 许可 + 支持 |
| 128 GPU（16 台） | Lustre（自建） | ~$5,000 | 主要是 HPC 运维人力 |
| 128 GPU（16 台） | WEKA | ~$5,000-6,000 | 许可为主 |
| 1,024 GPU（128 台） | Lustre 或 WEKA | 数万美元 | 硬件 + 许可/人力 |

### 🔧 自己动手验：你的存储够快吗？

```bash
# 1. 检查 Dataloader 停顿率
# 在你的训练日志里搜索类似：
#   "DataLoader time: XX ms"
#   或看 Nsight Systems 里的 CPU-GPU 同步等待
# 如果 data wait 占比 > 5% → 存储是瓶颈

# 2. 简单测一下存储读吞吐（单节点，单客户端口径）
dd if=/path/to/dataset/file of=/dev/null bs=1M count=10000
# 单节点期望：> 5 GB/s

# 3. 测试多节点并行读（聚合口径）
# 每个节点同时读取不同的文件，看聚合吞吐
# 128 节点、单客户端 5 GB/s 的系统，期望聚合读吞吐 > 640 GB/s
```

### ⚠️ 常见误区

- **误区**："存储就是硬盘，随便买个 NFS 就好"
  - **实际**：NFS 在 AI 训练中是"省小钱花大钱"的典型。单点聚合带宽不随客户端扩展，checkpoint 与数据读取两头吃亏。换并行文件系统的动机是**聚合扩展性**，不是"SSD 更快"。
- **误区**："WEKA 太贵了，用免费的 Lustre 省预算"
  - **实际**：Lustre 软件免费但运维成本高：懂 Lustre 的工程师、MDS/条带化调优、定期健康检查。**小规模部署下 Lustre 的总拥有成本可能高于 WEKA。**
- **误区**："Checkpoint 就几百 GB，几秒钟就能写完"
  - **实际**：70B 完整训练状态 = 16 B/参数 = **1.12 TB/次**（不是 420 GB）。NFS 1.1 GB/s 下每次约 17 分钟，每 45 分钟一次就是每天约 9 小时 GPU 纯闲置。

### 📊 底线数字速查

| 存储系统 | 适合规模 | 聚合写吞吐（量级） | 部署复杂度 | 成本量级 |
|---------|---------|--------------------|-----------|----------------|
| NFS | < 16 GPU | 1-2 GB/s（单点） | 极低 | $0（已有基础设施） |
| BeeOND | 8-64 GPU | 28 GB/s（临时缓冲） | 低 | $0（用 GPU 节点本地盘） |
| Lustre | 64-1,024+ GPU | 数十-数百 GB/s（随 OST 数扩展） | ❌ 困难 | 软件免费，运维人力为主 |
| WEKA | 32-1,024+ GPU | 数十 GB/s - TB/s 级（随节点扩展） | ✅ 简单 | 商业许可 |
| GPFS / Storage Scale | 企业级 | 100+ GB/s 量级 | ❌ 困难 | 商业许可，通常最贵 |

### 💡 一句话记住

> **"Lustre 用运维换许可费，WEKA 用许可费换省心，GPFS 用最贵的许可换企业级功能和 ILM。三者聚合吞吐都能到数百 GB/s——真正的分水岭是：你的团队养不养得起这套存储的复杂度。"**
